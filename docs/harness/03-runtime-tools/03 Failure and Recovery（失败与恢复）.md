# Failure and Recovery（失败与恢复）

> 当前成熟度层级：`L3 可指导实现的治理规格层`
> 编码门槛：`可直接指导重试策略、租约恢复、未知提交核对、Outbox 重放和投影重建`

## 1. 目标

失败恢复的目标不是“不让用户看到错误”，而是保证：

1. 原始输入不丢失。
2. 已确认状态不被失败任务覆盖。
3. 不确定的提交结果不被盲目重放。
4. 后台失败不长期阻塞 Chat。
5. 每次恢复都有可追溯依据和次数上限。

## 2. 错误分类

| 分类 | 典型情况 | 默认处理 |
| --- | --- | --- |
| 暂时错误 | 网络抖动、模型限流、只读工具暂时不可用 | 在预算内重试 |
| 输入错误 | Schema 不合法、引用缺失、参数不完整 | 不重试，保留缺口 |
| 权限拒绝 | 工具或操作未授权 | 不重试，不提升权限 |
| 尚未准备好 | 信息不足、确认范围不清 | 不写入，回到后续 Chat |
| 已过期 | 消息、状态或包版本变化 | 停止，不重跑旧结果 |
| 治理拒绝 | 提案不能升级相应信息地位 | 保留记录，不提交 |
| 提交结果未知 | 超时或进程中断，无法确认是否提交 | 按幂等键查询 |
| 投影失败 | 状态已提交，画布或 Toast 更新失败 | 重放事件或重建投影 |

错误分类必须使用稳定错误码，不能依赖异常文案做控制流。

## 3. Chat 失败

1. User 消息必须在模型调用前持久化。
2. Assistant 生成失败时，Chat 回合进入 `failed`，User 消息仍然可见。
3. 重试同一 Chat 回合时复用回合 ID 或明确记录父回合，避免产生两条竞争回复。
4. 未完成的 Assistant 流式片段不作为完整回复，也不触发正常收敛判断。
5. Chat 中读取工具失败时，可以在主回复中说明缺口；不得伪造工具结果。
6. Chat 失败不占用收敛租约，也不阻塞用户继续输入。

## 4. 判断失败

- 规则预筛能够明确 `skip` 时，不调用小模型。
- 小模型判断失败时，默认记录为失败并保留待判断水位，不得为了继续推进而默认 `trigger`。
- 同一消息范围可以在暂时错误后重新判断，但必须有重试上限。
- 新消息扩展范围后，旧判断请求可以标为被新范围替代，不逐个补跑。

## 5. 收敛回合失败

### 5.1 提交前失败

模型、只读工具或结构输出校验出现暂时错误时，可以在同一收敛回合内增加尝试次数并重试。

重试前必须满足：

- 尚未进入提交成功状态。
- 基础消息和状态版本仍有效。
- 工具调用可以安全重试。
- 未超过回合重试预算。

预算耗尽后回合进入 `failed`。旧结果不自动创建新回合；如果存在待重新判断水位，由最新判断决定后续是否再收敛。

### 5.2 已过期

发现消息、状态或包版本变化时：

- 回合进入 `stale`。
- 提案不得提交。
- 保留使用范围、基础版本和过期原因。
- 不自动修改提案适配新状态。
- 不自动重跑旧回合。

当前回合结束后，可以消费待重新判断水位；这是对最新消息的判断，不是旧回合重试。

### 5.3 尚未准备好或治理拒绝

`not_ready` 与 `rejected_by_governance` 是正常业务结果，不是基础设施故障。

- 不进行技术重试。
- 不发送第二条 Assistant 消息打断 Chat。
- 将缺口或拒绝原因保留给后续 Chat 工作面和 Trace。
- 不提升内容信息地位。

## 6. 提交失败与未知结果

提交器按 `operation_id` 保证幂等。

### 6.1 明确失败

事务明确回滚时，提交记录进入 `failed`，状态版本和包版本都不推进。可以在版本仍匹配且错误可重试时，用同一 `operation_id` 重试。

### 6.2 版本过期

期望版本不匹配时，提交记录进入 `stale`。不得用新版本号继续提交原提案。

### 6.3 结果未知

出现超时、进程中断或响应丢失时：

1. 将提交尝试标记为 `unknown`。
2. 按 `operation_id` 查询提交记录或目标版本。
3. 已存在成功结果时返回原结果，状态视为 `duplicate` 或已应用。
4. 明确不存在且版本仍匹配时，才允许重新执行。
5. 无法确认时保持待核对，不盲目重放。

## 7. Outbox 与投影恢复

状态事务内只登记 Outbox 事件，事务提交后再发布。

- 发布失败不回滚已提交事实。
- Outbox 消费使用事件 ID 去重，可以重复投递。
- 画布、Todo、搜索索引和 Toast 分别维护消费位置。
- 投影缺失或损坏时，从当前结构化包、状态账本和未消费事件重建。
- Toast 可以放弃补发，但画布和关键缺口投影必须最终一致。

## 8. 进程中断与租约恢复

恢复器定期检查过期租约：

1. 读取运行记录、提交尝试和 `operation_id`。
2. 如果已经提交成功，补齐回合终态并继续发布 Outbox。
3. 如果尚未提交且基础版本仍有效，可以在重试预算内恢复同一回合。
4. 如果基础版本变化，标记为 `stale`。
5. 如果是否提交无法判断，进入提交结果核对，不直接重跑。
6. 释放失效租约后，消费同包待重新判断水位。

恢复使用原运行 ID 并增加尝试次数，不伪装成从未失败的新回合。

## 9. 工具失败恢复

- 幂等读取：暂时错误可重试。
- 确定性转换：输入和工具版本不变时可重试。
- 内部写入：只允许使用原幂等键恢复。
- 外部副作用：默认不自动重试；先查询实际结果。
- 权限拒绝：不重试，不静默改用其他高权限工具。
- 来源失效：标记证据缺口，不用模型补全。

## 10. 用户可见原则

- 正常后台收敛失败默认不发送第二条 Chat 消息。
- 如果失败不影响 Chat 和已确认事实，只记录 Trace，必要时使用低打扰提示。
- 如果用户明确要求生成包或交接物但失败，应在主 Chat 中说明未完成及原因。
- 如果提交结果未知、外部副作用未知或已确认版本可能受影响，必须显式提示。
- 不使用“已完成”掩盖降级、过期或部分失败。

## 11. 设计禁令

- 不允许用无限重试掩盖持续错误。
- 不允许过期回合自动适配新状态后继续写入。
- 不允许在提交结果未知时更换幂等键重试。
- 不允许投影失败反向污染事实状态。
- 不允许因为后台失败而拒绝新的 User 消息。
- 不允许把业务上的 `not_ready` 记录成系统故障。

## 12. L3 验收场景

至少验证：

1. Assistant 生成失败后 User 原文仍然存在，并可安全重试。
2. 小模型判断失败不会默认启动收敛。
3. 暂时错误只在预算内重试。
4. 新消息到达后旧收敛回合停止为 `stale`。
5. 提交响应丢失后可通过 `operation_id` 找到原结果。
6. 进程在提交前、提交中和提交后中断时都不会产生重复版本。
7. Outbox 重复投递不会重复应用画布变化。
8. 画布投影损坏后可以从事实状态重建。
9. 后台收敛失败期间仍能接收新 User 消息。
10. `not_ready` 不触发技术重试，也不产生第二条 Assistant 消息。
