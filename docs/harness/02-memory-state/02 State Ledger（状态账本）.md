# State Ledger（状态账本）

> 当前成熟度层级：`L2 对象与流程定义层`
> 编码门槛：`未达到 L3，不应直接作为稳定实现规格；需继续补齐状态枚举、事件字段与验证规则`

状态账本记录 EvoCanvas 1.0 中对象状态如何变化、为什么变化、变化后还有什么未决。

它不是完整审计系统，但必须让系统和用户能解释：

- 当前对象为什么是这个状态。
- 谁或什么让它进入这个状态。
- 是否仍有未决、冲突或风险。
- 这个状态是否能被下游继续引用。

## 1. 这一层回答什么问题

状态账本回答：

- 卡片、约束、待决策和交接物有哪些状态。
- 状态变化何时发生、由谁触发、基于什么来源。
- 哪些状态可以作为稳定前提，哪些只能作为草稿或提醒。
- 当状态变化后，Active Todos、里程碑提示和交接物如何同步。

## 2. 最小记录范围

每一次重要状态变化，状态账本至少记录：

1. 对象 ID。
2. 对象类型。
3. 原状态。
4. 新状态。
5. 触发来源。
6. 关键原因。
7. 仍存未决。
8. 是否影响交接物或 Active Todos。

这里的触发来源可以是：

- 用户确认
- AI 建议被接受
- 系统自动整理
- 来源更新
- 冲突解决
- 底层约束或决策变化

## 3. 通用状态基线

按 PRD，所有卡片共享五个顶层状态：

- 草稿中
- 待确认
- 已确认
- 已归档
- 异常

这些状态只表达通用治理地位，具体业务对象还需要类型化状态。

## 4. 类型化状态基线

### 4.1 问题卡

问题卡至少区分：

- 初步理解
- 待收敛
- 已收敛

### 4.2 待澄清卡

待澄清卡至少区分：

- 待提出
- 待确认
- 已澄清
- 已阻塞
- 已关闭

已澄清或已关闭后，不应继续作为 Active Todos 的活跃缺口展示。

### 4.3 约束卡

约束卡至少区分：

- 草稿中
- 待确认
- 已生效
- 已替代
- 已归档

草稿约束不得默认视为生效约束。

### 4.4 待决策 / 方案承接卡

待决策 / 方案承接卡至少区分：

- 待判断
- 待确认
- 已决定
- 已归档

未完成决策必须持续可见，不得被系统自动关闭。

### 4.5 交接物承接卡

交接物承接卡至少区分：

- 草稿中
- 待确认
- 已确认
- 已过时

未确认的交接物不得被标记为可直接外发。若底层约束或决策变化，应提示“已过时”。

## 5. 确认记录

任何进入“已确认”或“已生效”的内容，必须有确认记录。

确认记录至少包含：

1. 新状态。
2. 确认来源。
3. 确认方式。
4. 确认时间。
5. 关联来源或对象。
6. 确认时仍存未决。

这能避免“确认”把未决问题洗平。

## 6. 仍存未决的处理

状态账本记下“仍存未决”之后，默认按影响范围处理。

### 6.1 继续阻塞

若未决影响以下任一事项，应继续作为阻塞条件：

- 事实成立
- 下游推进
- 范围边界
- 结构化交接物可用性

### 6.2 作为活跃缺口

若未决正在影响当前主题推进，应投影到 Active Todos。

投影来源只能是源卡状态，Todo 不得悬空存在。

### 6.3 作为非阻塞提醒

若未决已知但暂不阻断当前推进，可以保留为非阻塞提醒。

非阻塞提醒主要挂在对应对象上，状态账本保留摘要。

## 7. 状态同步规则

### 7.1 与 Active Todos

Active Todos 是当前活跃缺口投影，不是任务列表。

当源卡状态变化时：

- 待澄清卡已澄清或已关闭后，对应 Todo 应消失或失效。
- 待决策卡已决定后，对应 Todo 应消失或转为后续提醒。
- 待确认约束已生效后，对应 Todo 应消失。

### 7.2 与里程碑提示

里程碑提示只表达推进位置感知，不是严格项目计划。

可作为里程碑更新依据的状态包括：

- 当前主题完成关键澄清与约束沉淀。
- 必要决策已完成。
- 结构化交接物达到可继续推进状态。

单个普通文本编辑不应单独推动里程碑变化。

### 7.3 与交接物

交接物依赖的约束或决策发生变化后，应触发交接物状态重判。

若变化影响交接物主要内容，交接物应进入 `已过时` 或待刷新状态。

## 8. 状态账本不负责什么

状态账本不负责：

- 重新生成对象正文。
- 替代验证器判断结构是否合格。
- 替代治理层宣布高影响动作放行。
- 直接把系统挂件投影写成事实。

它只记录状态变化和最小可解释原因。
