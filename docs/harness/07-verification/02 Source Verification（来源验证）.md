# Source Verification（来源验证）

> 当前成熟度层级：`L3 可指导实现的治理规格层`

## 1. 这一层回答什么问题

来源验证回答：当前判断有没有足够依据，能不能被追溯。

它检查的不是措辞是否顺，而是这次对象创建、状态变化或交接收束，是否真的站在可回溯的输入、确认或历史对象之上。

## 2. 通用来源检查

来源验证至少检查：

- 是否存在来源引用。
- 是否能回到原始输入、导入材料、用户消息、用户确认或历史对象。
- 当前来源是否足以支撑当前状态，而不只是支撑“可以先提一下”。
- 是否存在未处理冲突。
- 是否记录了确认方式、确认人或用户裁决痕迹。
- 是否把来源缺失真实暴露出来。

来源不足不一定意味着对象要删除，但一定会影响它能进入什么状态、能被谁继续依赖。

## 3. 按对象类型检查

### 3.1 证据卡

证据卡必须能说明它来自哪份原始材料以及材料中的具体位置，并保留原始摘录、结构化摘要和与当前主题的关联。摘要不得覆盖或伪装成原文。

### 3.2 问题卡

问题卡应能回指触发它的问题背景、冲突信息或模糊表述。没有来源支撑的问题，不应伪装成当前稳定问题结构。

### 3.3 待澄清卡

待澄清卡必须能说明：它究竟是由哪条缺口、哪组冲突、哪个模糊指代或哪个待确认事项引出的。

### 3.4 约束卡

约束卡创建、实质修改或替代前，至少要能说明：

- 来源证据是什么，或
- 用户是如何确认的，或
- 它来自哪个已成立的上游对象。

如果存在冲突约束，不能把它们同时当成已生效依据使用。

### 3.5 待决策 / 方案承接卡

待决策卡必须能回指相关待澄清、冲突信息、约束分歧或用户明确需要拍板的事项。建议方案不能只是无来源偏好。

### 3.6 交接物承接卡

交接物必须能回指：

- 已确认约束
- 已完成决策
- 仍未解决的问题
- 关键背景输入
- 相关来源引用

如果底层约束或决策变化，且交接物未更新，应触发已过时判断。

## 4. 冲突来源检查

当两条证据、两条约束，或证据与当前判断之间存在冲突时，来源验证必须要求：

- 冲突对用户可见。
- 冲突可以回溯到具体来源。
- 冲突解决前，不得把对应内容写成已生效约束或已确认交接内容。
- 当冲突需要产品负责人拍板时，应升级为待决策，而不是静默合并。

## 5. 来源强度与状态边界

同一份来源，在不同状态下的要求不同。

例如：

- 能支持“提出一个待澄清问题”的来源，不一定足够支持“写成已生效约束”。
- 能支持“生成交接物草稿”的来源，不一定足够支持“确认交接物可继续外发”。
- 模糊偏好或单句判断可以支持待决策或其他未决内容，但不足以创建约束卡、完成决策或确认交接物。

所以来源验证不仅看“有没有来源”，也看“这份来源够不够支撑当前状态”。

## 6. 可见结果的来源检查

来源验证不只作用于对象本体，也作用于用户可见解释：

- 显影提示说“已沉淀 2 条约束”，应能回到对应约束对象和实际提交版本。
- Active Todos 说“还缺关键确认”，应能说明缺的是哪类确认。
- 交接物说“已过时”，应能回指触发过时的约束、决策或冲突变化。
- 若系统本轮没有写入正式对象，而是选择追问、停住或等待确认，也应能说明依据是什么。

## 7. 来源验证失败后的去向

- 缺少来源：标记来源缺失，并要求补来源。
- 来源冲突：显性化冲突，并转入待澄清或待决策。
- 来源不足以支撑当前状态：降级为草稿、待确认或仅保留为问题线索。
- 交接物来源链断裂：不得确认交接物。
