# Context（上下文）

> 当前成熟度层级：`L2 对象与流程定义层`

## 1. 这一层回答什么问题

上下文定义模型当前应该看到什么信息。

在 EvoCanvas 中，这里的“看到”不是泛指任何可读取数据，而是指本轮推理真正应进入模型工作面的内容。

## 2. 上下文的两个来源

模型工作面由两类独立信息共同构成：

1. 从当前活跃工作上下文的结构化工作包确定性装配出的 Structured Package Input。
2. 由完整活动窗口、历史压缩产物和按需复水的精确旧记录共同构成的 `user / assistant / tool` 消息历史。

Structured Package Input 是从完整工作包确定性投影出的短结构化工作面，常态约 200 字，目标不超过 1K Token。它只承载当前目标、最关键的稳定结论与未决、包 / 状态版本和必要来源引用，不嵌入完整对象正文、证据摘录集合或复水后的原始材料正文。

原始消息保留对话中仍有价值的原文、工具结果和表达语气。Source Resolver 按引用读取的精确原文也必须先保存为原始 `tool` 记录，再由后续收敛决定是否形成新证据或来源关系。结构化包与原始记录不能互相替代，也不能把其中一类伪装成另一类。

当前用户输入始终作为独立的 Raw User Message 传入，不属于工作包，也不应被运行时改写。

## 3. 结构化包不是画布

画布只是结构化状态的显影层，不是上下文或事实来源。卡片位置、栏目、选中态和画布快照不得作为独立事实再注入模型。

结构化工作包与结构化交接物不采用两套 Schema，也不复制两份对象正文。它们来自同一个 `package_id` 的不可变版本链：

- `current_version` 服务于当前 Chat 和收敛回合，可以是草稿或待确认版本，未确认内容不能被当作稳定依据。
- `latest_confirmed_version` 指向最近仍可作为正式交接依据的确认版本，可供人或下游 AI 继续推进。
- 版本确认、过时和风险标注由状态账本叠加为有效治理状态，不回写不可变版本正文。

包的模块、内容分层和正式状态门槛沿用 [Handoff Governance（交接物治理）](../05-safety-governance/06%20Handoff%20Governance%EF%BC%88%E4%BA%A4%E6%8E%A5%E7%89%A9%E6%B2%BB%E7%90%86%EF%BC%89.md)，上下文层不另造一套包结构。日常 Chat 读取当前版本，但不能因为读取了草稿版本就把未确认内容当作已成立事实。

## 4. 当前主题工作面

每个结构化包以一个活跃工作上下文为范围，而不是整个工作区，也不是单张卡片（活跃工作上下文与主题的 1:1 关系见 [Memory §2.1](../02-memory-state/01%20Memory%EF%BC%88%E8%AE%B0%E5%BF%86%EF%BC%89.md)）。它沿用治理层定义的模块，并在模型工作面中至少提供：

1. 当前目标与输入背景。
2. 已确认约束与已完成决策。
3. 未解决问题、待确认决策和影响使用的冲突。
4. 推荐后续动作、当前里程碑与关键来源引用。
5. 当前包生命周期、交接有效性、适用范围或主题边界。
6. 当前包版本及其对应的结构化状态版本。

以上内容在 Structured Package Input 中使用短值、对象 ID 和引用表达，不展开完整对象列表或正文。对象较多时只指出当前最关键项，其余通过包与对象引用按需读取；不能为了覆盖所有对象把短工作面扩成完整包副本。

包内继续区分已确认内容、明确标记的未确认或候选内容、未决问题或待拍板事项。“已确认约束”“待澄清项”“候选对象”等不是额外上下文槽位，而是按现有对象治理规则组织的状态化内容；上下文层不新造一套事实状态模型。

## 5. 范围与历史

系统默认根据对话和已有结构化状态维护活跃工作上下文。用户的引用、关注或选中卡片可以帮助系统定位相关范围，但只是装配偏置，不是新的事实输入。

当用户明确引用较早的讨论时，系统应检索相关原始 `user / assistant / tool` 消息，而不是只相信工作包中的后续状态。若系统无法可靠判断用户是否切换了工作上下文，应在 Chat 中澄清。

Conversation History 不按固定轮数裁剪。第一次压缩前，系统按 `message_seq` 携带当前 Raw User Message 之前的全部既有原始消息；发生压缩后，则携带最近一份 History Compaction Artifact、从被压缩窗口尾部保留的最多 20K Token 完整近期对话链、压缩检查点之后的全部连续原始消息，以及用户明确回指时按需复水的压缩前精确消息。近期链必须同时包含 User、对应 Assistant 和中间完整 Tool 链，不能只留问题；未进入近期链的旧内容由压缩产物承接。补入任一工具调用或工具结果时，必须同时保留可解释该结果的调用与返回链。当前 Raw User Message 不在 History 中重复。

历史压缩只改变后续模型可见的 History 表示，不删除或改写原始消息。History Compaction Artifact 不是业务事实或确认记录，不能升级信息地位、抹去冲突或改写 Structured Package Input。若“刚才那个”“之前第二个方案”等回指无法唯一定位，系统应在 Chat 中澄清，不能让模型或向量检索器自行猜选历史。

五个逻辑输入面保持职责分离但不分配独立 Token 池；它们与 Tool / Schema、当前模型输出共同占用一个共享上下文窗口。共享总量触发线、Codex 式结构化压缩结果与跨供应商计数规则见 [Context Budget and Compaction（上下文预算与压缩）](./06%20Context%20Budget%20and%20Compaction%EF%BC%88%E4%B8%8A%E4%B8%8B%E6%96%87%E9%A2%84%E7%AE%97%E4%B8%8E%E5%8E%8B%E7%BC%A9%EF%BC%89.md)。

默认不应注入：

1. 跨越全部压缩窗口的原始消息全文，或没有明确回指依据的散点历史检索结果。
2. 与当前工作上下文无关的对象和旧消息。
3. 全部原始材料全文。
4. 已过时交接物全文。
5. 个人挂件、画布快照或其他仅供界面展示的数据。

## 6. 版本与上下文预算

结构化工作包只在成功的收敛与状态更新后形成不可变版本；正常 Chat 不会每轮都生成或改写一个包。活跃工作上下文通过 `current_version` 读取当前工作版本；正式交接或下游复用默认通过 `latest_confirmed_version` 选择最近仍可用的确认版本。

同一结构化状态版本在相同装配规则下，应得到相同的工作包。Chat 与收敛回合读取同一份包，不各自生成不同的业务摘要。

这个“同一份”不只表示引用同一包版本，还表示 Chat、后置判断和关联收敛回合使用完全相同的 Structured Package Input ID 与内容哈希。任务差异只发生在指令、Schema 和原始消息范围，不发生在结构化包输入。

当请求达到上下文软阈值时，运行时先压缩模型可见的 Conversation History，但保留全部原始消息。Structured Package Input 正常情况下已经足够短，不应成为主要裁剪对象；若超过 2K Token，视为装配或包边界异常并停止调用。完整结构化状态不被压缩或改写，装配过程也不得为了缩短上下文而重新解释或生成新的事实结论。

## 7. 上下文目标

上下文目标不是尽量全，而是足够正确。它要让模型：

1. 理解用户当前想推进什么。
2. 看见哪些内容已经稳定、哪些仍待收敛，以及它们各自的依据。
3. 必要时回到原始消息或来源核对，而不是把摘要当作唯一真相。
4. 在信息不足时追问或显式保留缺口，而不是硬生成结论。
