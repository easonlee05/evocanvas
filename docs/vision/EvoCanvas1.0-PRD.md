## 2. 产品背景

现实中的产品思考工作，并不是从“打开文档开始写 PRD”开始的。

更常见的真实工作流是：

1. 从 leader、老板、售前、运营、研发、设计、客户、数据报表、会议、聊天、文档、截图、竞品和临时想法中接收零散输入。
2. 在多轮对齐中不断补充信息，试图弄清楚“这件事到底要解决什么问题”。
3. 在不同人提供的信息、约束、偏好和现实限制之间来回切换。
4. 一边盯细节，一边尽量不丢掉整体目标。
5. 最终把模糊问题转化为规则、方案、结论、原型和交付物。

这套过程最典型地发生在产品经理身上，但并不只属于产品经理。创业者在梳理方向、设计师在抽象体验原则、业务负责人在收敛需求与边界时，也会经历相同的认知摩擦：脑中先有一种说不清的感觉，再慢慢逼近可以推进的结构。

这类工作天然有几个痛点：

1. 输入来源太碎，且很多是跨媒介、跨角色、跨时间出现的。
2. 会议纪要只能覆盖部分输入，不能替产品经理完成整体认知收敛。
3. 文档适合沉淀结果，不适合承载持续演化中的思考过程。
4. 自由白板虽然有空间感，但很容易变成无结构的逻辑堆积。
5. 聊天式 AI 虽然能回答问题，但无法稳定维护一张持续演化的工作面。

因此，EvoCanvas 1.0 的目标不是优化“写出来”，而是优化：

`想明白`

更准确地说，是帮助用户把脑子里的模糊想法、多源输入、反馈碎片、跨团队对齐过程，外化为一个持续演化、可回看、可推进的工作画布。对 EvoCanvas 来说，很多工作的起点甚至不是一个完整想法，而只是一种还没成形的感觉（vibe）；系统要先接住这种感觉，在对话中帮助它成形，再把已经相对稳定的结构显影到画布上。

## 3. 产品目标

### 3.1 一句话定位

EvoCanvas 1.0 是一个以 `Vibe Shaping` 为核心的对话驱动收敛工作台，首要服务产品经理，也服务其他产品思考密集型用户，用来把用户脑中尚未成形的感觉与多源输入，塑造成结构化问题、约束、决策与交接物。

### 3.1.1 Vibe Shaping 定义

本文档将 `Vibe Shaping` 定义为：

`由 agent 引导，把用户尚未成形的感觉、直觉和零散表达，逐步塑造成可讨论、可追溯、可收敛的结构化思考。`

它强调的不是“用户先想清楚再来使用”，而是允许用户从模糊开始，并通过对话、结构化对象和画布显影，把思考一步步推进到可判断、可交接的状态。

### 3.1.2 1.0 体验旅程与核心闭环

EvoCanvas 1.0 的外层体验旅程是：

`感觉接入 -> 对话塑形 -> 结构收敛 -> 画布显影 -> 结构化交接`

其中：

1. `感觉接入`：允许用户从一句话、一段聊天、一张图、几个关键词或一段语音开始，不要求先写出稳定需求。
2. `对话塑形`：agent 先理解、命名、拆解和追问，让模糊感觉逐步变成可讨论对象。
3. `结构收敛`：把已经初步成形的内容转为可治理的结构化候选对象，并持续暴露不确定性、冲突和待决策事项。
4. `画布显影`：当结构稳定到可以承载时，再在画布上显影卡片、栏目、关系、冲突、依赖和缺口。
5. `结构化交接`：把当前稳定结构打包为可供人阅读、或供下游 AI 执行与实现的产品上下文。

原有 1.0 最小闭环不废弃，而是作为 `结构收敛` 的内部展开：

`输入编译 -> 待澄清问题 -> 约束 / 待决策 -> 结构化交接物`

这意味着 `输入编译` 不是整个产品体验的最早起点，而是当用户的感觉和材料进入系统后，被治理为结构化对象的第一步。

### 3.2 核心用户问题

EvoCanvas 1.0 需要解决的不是“写 PRD 太累”，而是：

1. 起点往往只是一个模糊感觉，难以直接说清。
2. 输入来源太散，缺少统一收束入口。
3. 一旦盯住某个细节，就容易丢掉整体目标。
4. 很难持续追踪哪些问题还没澄清。
5. 规则、术语、字段口径容易在推进中散掉。
6. 结论会变化，但变化过程缺乏结构化记录。
7. 会议、聊天、文档和截图之间缺少统一的工作界面。

### 3.3 业务目标

1. 支持用户从一句感觉、一段聊天、一份纪要或一组碎片材料开始，并在对话中逐步塑形成可讨论对象。
2. 支持 AI 自动从输入中提炼证据、问题、待澄清项和候选约束；候选先留在对话中，来源事实完成完整性检查、其他语义经用户固定后，再由统一提交能力写入结构化工作包并显影到画布。
3. 支持产品经理及相邻角色围绕问题、规则、方案、结论和推进动作持续收敛工作内容。
4. 支持展示轻量里程碑提示，帮助识别当前推进位置。
5. 支持通过右侧 AI 助手持续推进画布演化，而不是仅生成静态文本。
6. 支持从画布收束出后续可交付给人或下游 AI 执行的结构化交接物，并可进一步派生为面向 AI 的 PRD。

### 3.4 成功标准

1. 用户在输入任一核心感觉或材料后，可以先得到 agent 对当前 vibe 的理解、命名和关键追问。
2. 用户可以快速看见哪些地方还没讲清楚、哪些信息彼此冲突、哪些事项必须人拍板，而不必自己从长文里翻找。
3. 用户可以在内容被固定后，在画布上同时看到输入、问题、约束、决策和交接准备状态；尚未固定的候选继续留在对话中，不以正式卡片显影。
4. 一次关键讨论后，用户可以回看“这次到底推进了什么、消除了哪些不确定性、留下了哪些未决问题”，而不是只看到聊天记录。
5. 画布中的结构最终能够收束为结构化交接物或面向 AI 的 PRD，使下游 AI 工具可以基于已收敛结论进入实现、评审或任务拆解，而不是继续参与需求收敛。

### 3.5 1.0 首版验证命题

EvoCanvas 1.0 首版要验证的不是“能不能搭一套完整 PM 工作台”，而是以下更硬的命题：

1. 用户尚未成形的 vibe 是否可以被 agent 接住、命名、追问，并逐步塑形成可讨论对象。
2. 多源混杂输入是否可以被系统稳定收束为一组可推进的 `待澄清问题`、`约束` 和 `待决策项`。
3. AI 是否可以像一个合格的产品同事一样，优先暴露不确定性，而不是过早替用户脑补结论。
4. 画布是否可以在结构相对稳定后再显影，而不是过早把所有原始混沌摊成白板对象。
5. 经过一轮收敛后的结果，是否能够生成一份可交接的结构化产品上下文，并进一步派生为面向 AI 的 PRD，供后续实现、评审或任务拆解使用。
6. 首版必须优先验证“需求失真是否降低”，而不是优先追求“对象类型是否齐全”或“界面模块是否完整”。

## 4. 核心规则与约束

1. EvoCanvas 1.0 的第一入口是 `感觉接入`，不是 `新建 PRD`，也不是要求用户先提供稳定需求。
2. EvoCanvas 1.0 的外层体验旅程是“感觉接入 -> 对话塑形 -> 结构收敛 -> 画布显影 -> 结构化交接”。
3. EvoCanvas 1.0 首版的核心验证闭环仍是 `结构收敛`，其内部展开为“输入编译 -> 待澄清问题 -> 约束 / 待决策 -> 结构化交接物”，不以搭建完整 PM 操作系统为目标。
4. 画布是稳定结构的显影层，不是原始混沌输入的第一承载层。
5. 主画布是连续画布，不采用硬边框切割大区域。
6. 主画布宽度表达逻辑结构，不表达时间顺序。
7. 时间维度通过底部轻量里程碑条承载，用于提示当前推进位置，不通过横向无限扩张画布承载。
8. 工作台可见内容分为 `卡片`、`系统挂件` 和 `个人挂件预留` 三层；前五类卡片投影正式业务对象，交接物承接卡投影结构化包版本，挂件是辅助视图或个人工具。
9. 系统挂件用于投影当前状态、推进位置或操作辅助，不得取代源卡片成为独立事实源。
10. 个人挂件用于个人思考与操作便利，可自由移动、折叠和 pin，但默认不进入结构化交接物，且 1.0 不与卡片层打通。
11. 系统可以自动形成草稿和候选结构，但任何信息地位升级都不得绕过用户确认。
12. Active Todos 不是任务管理系统，而是当前活跃缺口投影视图。
13. Todo 不是独立事实源，所有 Todo 必须回指原始卡片。
14. 首版不要求完整结论体系，任何稳定判断优先以“约束”或“待决策结果”形式落地。
15. 当输入之间存在冲突、上下文不足或指代不清时，系统必须优先显性化冲突与缺口，而不是静默合并。
16. 任何被标记为 `已生效` 或 `已确认` 的信息，都必须有明确来源、确认方式或可追溯的用户裁决。
17. 首版不做多人实时协作。
18. 首版不做自由白板模式。

## 5. 用户角色

| 用户角色 | 角色说明 | 核心诉求 |
| --- | --- | --- |
| 产品经理 | 首要核心用户，负责接收需求、整理上下文、推进收敛 | 接住输入、理清问题、追踪缺口、沉淀规则、形成结论 |
| 创业者 / 设计师 / 业务负责人 | 相邻核心用户，通常同样需要从模糊直觉出发，逐步收敛方向、边界与判断 | 把感觉塑形成方向，把碎片收成结构，把结构推进成判断 |
| AI 助手 | 系统内协作对象，负责提炼、归纳、追问和显影 | 把自然语言和输入材料编译为结构化画布变化 |

### 5.1 首版使用边界

1. 首版只面向单人工作台。
2. 首版不涉及多个 AI 在同一画布内实时协作编辑。
3. 首版默认工作流按产品经理场景设计，但不把产品经理限定为唯一用户；其他需要把模糊感觉收敛成结构化判断的单人用户，也可以沿用同一闭环工作。
4. Codex、Claude Code、Antigravity 等下游 AI 工具不作为 1.0 内部协作体参与收敛流程；它们只在后续版本中作为已收敛输出的消费方。

### 5.2 后续下游 AI 工具边界

后续版本可以支持将结构化交接物派生为面向 AI 的 PRD，交给 Codex、Claude Code、Antigravity 等下游 AI 工具使用。

该交互的边界是：

1. EvoCanvas 负责完成 idea 的感觉接入、对话塑形、结构收敛和交接物生成。
2. 下游 AI 工具消费已收敛结果，用于实现、评审、任务拆解或生成后续交付物。
3. 下游 AI 工具不默认参与 EvoCanvas 内部的澄清、约束沉淀和待决策收束。

## 6. 产品范围

### 6.0 范围分层说明

本节将 EvoCanvas 拆分为：

1. `1.0 首版必须范围`：用于验证产品核心命题的最小闭环。
2. `后续版本规划范围`：方向明确，但不纳入 1.0 交付承诺。

如果某项能力不能直接提升“多源输入收敛为可交接上下文”的验证效率，则默认不进入 1.0。

### 6.1 1.0 首版必须范围

| 一级模块 | 二级模块 | 功能范围 |
| --- | --- | --- |
| 感觉接入 | 低压力启动 | 接收一句感觉、一段模糊描述、一组关键词、语音转写、截图说明或其他未成形输入 |
| 对话塑形 | 理解与命名 | 由 agent 先理解 vibe 指向，帮助用户命名、拆解、追问，不急于生成方案 |
| 输入编译 | 输入接入 | 导入会议纪要、聊天摘录、用户反馈、数据说明、截图说明、竞品摘录、文档片段、临时想法 |
| 输入编译 | 输入编译 | 识别输入类型、提取事实、识别冲突、推断问题和缺口、生成初步结构化候选对象 |
| 主画布 | 主要栏目 | 探索发现、焦点问题、待澄清项、规则约束、方案与决策、落地交接 |
| 主画布 | 阶段映射 | 前端当前采用 discovery / define / handoff 的轻量阶段映射，不展开为完整项目阶段系统 |
| 主画布 | 卡片体系 | 证据卡、问题卡、待澄清卡、约束卡、待决策 / 方案承接卡、交接物承接卡 |
| 主画布 | 卡片关系 | 来源于、澄清了、支持、阻塞、冲突于、产出为 |
| 主画布 | 画布显影 | 只将已经固定并提交的稳定对象显影为卡片、栏目、轻量关系和活跃缺口；未固定候选留在对话中 |
| 主画布 | 卡片手动修订 | 卡片标题 / 摘要原地编辑、模块内排序、合法跨栏目迁移与轻确认 |
| AI 助手 | 对话塑形与显影 | 同一个 Pi 识别意图、理解 vibe、生成追问和结构化建议；用户固定含义与范围后，Pi 通过受治理工具更新结构化工作包，画布负责显影 |
| AI 助手 | 追问与确认 | 对模糊输入追问，在正常 Chat 中确认产品判断和作用范围，对冲突信息要求裁决 |
| 工作台挂件 | 系统挂件 | 项目时间轴与活跃缺口两类系统挂件，用于表达推进位置与当前活跃缺口投影视图，不作为独立事实源 |
| 工作台挂件 | 个人挂件预留 | 便签、停车区、时钟、专注计时器等个人挂件形态允许预留，但不纳入 1.0 首版必须验收项，且默认不进入结构化交接物 |
| 输出 | 结构化交接物 / 面向 AI 的 PRD | 从当前画布收束出可供人理解、可供下游 AI 执行的产品上下文 |

### 6.2 后续版本规划范围

后续版本不按“补功能清单”推进，而按产品能力升级路径推进。每一版都应回答一个更大的产品命题，避免在 1.0 未验证完成前过早堆叠复杂能力。

#### 2.0 路线：从“需求收敛工作台”升级到“方案收束工作台”

2.0 的目标不是简单把 1.0 中暂缓的对象补回来，而是在 `1.0 已经证明输入能够稳定收敛` 的前提下，继续回答：

`在问题、约束和待决策明确之后，系统能否帮助 PM 把当前主题继续收束成可执行方案。`

2.0 重点能力：

1. 引入方案层对象：方案卡、结论卡、推进项。
2. 让 `规划` 与 `推进` 两条阶段带从轻量承接升级为可深度使用。
3. 支持围绕多个候选方案进行比较、取舍和收束。
4. 支持从交接物继续生成结构化方案包，而不只是停留在上下文交接层。
5. 支持对“当前为什么这样做”形成更明确的决策链路记录。

2.0 不变原则：

1. 仍然坚持“先暴露不确定性，再形成方案”，不允许方案层压过问题澄清层。
2. 仍然不以多人协作为核心，不把复杂协作流提前引入。

#### 3.0 路线：从“单人 PM 工作台”升级到“多角色协作面”

3.0 的目标是让 EvoCanvas 不再只是 PM 的个人工作面，而是成为多角色围绕同一份问题、约束、方案和决策进行协作的产品协作面。

3.0 重点能力：

1. 多人实时协作与评论线程。
2. 角色化协作视图：PM、设计、研发、业务、评审参与方看到的重点不同。
3. 明确的决策和确认流：谁能确认约束，谁能确认方案，谁提供反馈。
4. 更强的评审闭环：围绕待决策 / 方案承接卡、结论卡、方案卡保留完整协作记录。
5. 更丰富的里程碑对比与进度变更追溯能力。

3.0 不变原则：

1. 协作建立在已结构化对象之上，而不是让多人同时编辑混乱输入。
2. 不为“所有人都能改”牺牲对象清晰度与事实边界。

#### 4.0 路线：从“产品协作面”升级到“交付编排面”

4.0 的目标是把 EvoCanvas 从“想明白、协同收束”继续推进到“让后续交付更可编排、更可追踪”。

4.0 重点能力：

1. 更复杂的关系网络与全局依赖分析。
2. 更完整的文档、规格、原型联动能力。
3. 更强的外部系统接入：项目管理平台、知识库、IM、需求系统等。
4. 更完整的推进状态面、交付链路和后续动作编排能力。
5. 从交接物、方案包继续派生出更正式的规格包、任务包、评审包。

4.0 不变原则：

1. 外部打通服务于“减少失真和提高交付闭环”，而不是为接入而接入。
2. 交付编排建立在前几版已经稳定的对象模型和协作协议之上。

#### 后续路线总原则

1. `1.0` 先证明“尚未成形的感觉与多源输入能被稳定收敛为可交接上下文”。
2. `2.0` 再证明“上下文能继续收束为可执行方案”。
3. `3.0` 再证明“多角色能围绕这些结构化对象协作”。
4. `4.0` 最后证明“协作结果能继续被编排到交付落地链路”。

### 6.3 首版不包含范围

1. 多人实时协作。
2. 完整项目管理甘特图。
3. 自由白板模式。
4. 复杂权限体系。
5. 高保真原型自动生成。
6. 完整文档编辑器。
7. 老板驾驶舱。
8. 复杂外部系统打通能力。
9. 完整方案卡、结论卡、推进项体系的深度运营。
10. 全局复杂关系图谱与自动化依赖推理。

## 7. 核心业务流程

## 7.1 外层体验旅程

EvoCanvas 1.0 的完整体验旅程不是从“创建文档”开始，而是从用户把尚未成形的感觉交给 agent 开始：

`感觉接入 -> 对话塑形 -> 结构收敛 -> 画布显影 -> 结构化交接`

这条旅程中的 `结构收敛` 是 1.0 的核心验证闭环，内部展开为：

`输入编译 -> 待澄清问题 -> 约束 / 待决策 -> 结构化交接物`

## 7.2 感觉接入流程

1. 用户进入 EvoCanvas 工作台。
2. 用户可以输入一句感觉、一段临时想法、一组关键词、一段聊天摘录、语音转写、截图说明或已有材料。
3. 系统不要求用户先选择模板、先定义项目名称或先写出完整需求。
4. AI 首先识别当前输入更像是 vague vibe、事实材料、问题表达、方案想法、约束线索还是待决策线索。
5. 若输入过于模糊，AI 应先用低压力方式复述理解和提出追问，而不是直接生成画布对象。

## 7.3 对话塑形流程

1. AI 先读懂用户表达可能指向的方向，并给出可被用户纠正的理解摘要。
2. AI 帮用户为模糊感觉命名，将隐约判断变成可讨论对象。
3. AI 将用户表达拆解为可能的问题、证据、假设、约束线索和候选方向。
4. 当存在关键缺口、上下文不足或多种解释时，AI 主动追问。
5. 对话塑形阶段不急于把所有内容显影到画布，而是先让语义稳定到可以被治理。

## 7.4 结构收敛流程

1. 系统将对话塑形后的内容和用户导入材料进入输入编译。
2. AI 从输入中提取事实、问题、冲突和缺口，形成结构化候选对象。
3. AI 优先判断当前输入是否应新增待澄清项、约束候选或待决策候选，而不是直接产出结论。
4. 当输入之间存在冲突、缺失关键前提或存在多种解释时，AI 必须先显性化冲突并追问，不得直接合并。
5. 草稿和候选只保留在 Primary Pi Session；来源事实可在完整性检查通过后收录，问题、待澄清、约束、方案与决定只有在用户固定其含义和范围后才写入结构化工作包。用户可以固定“该问题仍未解决”，但不得把未确认候选作为正式对象显影。
6. 结构收敛的结果进入画布显影条件判断。

## 7.5 画布显影流程

1. 只有已经固定并成功提交到结构化工作包 Revision 的对象，系统才将其显影到画布；尚未固定的结构化候选留在对话中。
2. 画布显影内容包括卡片、栏目归属、轻量关系、冲突提示、依赖提示和活跃缺口投影。
3. 系统在画布中显式标出已经固定为工作状态的冲突、信息不足点和待决策事项；仍在形成中的候选不生成正式卡片。
4. Active Todos 根据已显影卡片状态投影当前活跃缺口。
5. 用户开始在画布和右侧 AI 助手中进行进一步收敛。
6. 用户可以结合底部轻量里程碑条理解当前大致推进位置。

## 7.6 约束沉淀流程

1. 用户围绕术语、字段、状态、权限、边界和口径形成约束。
2. AI 将约束整理为约束卡，并保留对应来源和确认方式。
3. 与约束相关的待澄清卡被关闭、阻塞或转入待决策状态。
4. 已确认约束成为后续结构化交接物的组成部分。

## 7.7 待决策收束流程

1. 当某项信息不是“尚未澄清”，而是“必须由 PM 拍板”时，Pi 先在 Session 中形成待决策候选；用户固定该事项的主题和范围后，系统才提交并显影待决策 / 方案承接卡。
2. 该卡必须明确决策主题、备选解释或建议方案、影响范围和所需确认人。
3. 用户确认后，该卡进入已决定状态，其结果更新相关待澄清卡或约束卡。
4. 每一个关键节点的沉淀都可反映到轻量里程碑提示中。

## 7.8 结构化交接物流程

1. 当结构化包已具备可读边界时，系统可以生成或刷新交接草稿；关键未决尚未解决时必须显式保留，不能伪装成已完成交接。
2. 结构化交接物必须明确：当前目标、输入背景、已确认约束、仍未解决的问题、待确认决策和推荐后续动作。
3. 用户在 Chat 中确认交接内容和范围后，该版本才可进入已确认状态，并提供给其他同事或下游 AI；不再要求用户额外确认“是否生成交接卡”。
4. 若后续推进暴露新冲突或新缺口，应允许从交接物回流到待澄清或待决策状态。

## 8. 功能需求与原型设计要求

## 8.1 输入编译台

### 8.1.1 功能说明

输入编译台是 EvoCanvas 1.0 的结构收敛入口能力，用于把不同来源、不同形态、不同成熟度的输入编译为可治理的结构化候选对象。

输入编译台的目标不是简单上传文件，而是：

1. 识别输入类型。
2. 提取可用事实。
3. 推断问题与缺口。
4. 生成初步结构化候选对象。
5. 来源事实通过完整性检查、其他对象由用户固定含义与范围并提交后，再将稳定对象显影到现有画布，而不是覆盖现有理解。

### 8.1.2 支持的输入类型

首版至少支持以下输入：

1. 会议纪要
2. 聊天摘录
3. 用户反馈列表
4. 数据结论说明
5. 竞品摘录
6. 截图与配套说明
7. 历史文档片段
8. 一段临时想法或方向描述
9. 一句尚未成形的感觉或直觉判断

### 8.1.3 页面字段与组件要求

| 页面区域 | 字段名称 | 组件要求 | 说明 |
| --- | --- | --- | --- |
| 输入区 | 输入类型 | Select / 自动识别标签 | 支持手动指定或由系统自动识别 |
| 输入区 | 输入正文 | Textarea / 富文本承接区 | 支持长文本粘贴 |
| 输入区 | 附件说明 | Textarea | 用于补充截图、文件等的说明文字 |
| 输入区 | 导入按钮 | Button | 点击后进入编译流程 |
| 输入区 | 编译方式 | Segmented Control | 追加到当前画布 / 新建工作画布 |
| 状态区 | 编译状态 | Badge / 文本 | 待处理、处理中、已完成、失败 |

### 8.1.4 关键交互

1. 用户输入内容后，可直接点击导入。
2. 系统应允许用户选择“并入当前工作面”或“作为新工作面开始”。
3. 导入完成后，系统应先给出本轮理解摘要和待澄清问题。
4. 若输入内容过于模糊，AI 应先追问，不直接显影为高影响结论。
5. 只有来源事实通过完整性检查，或其他结构化含义和范围已经由用户固定并提交后，系统才进入画布显影。

### 8.1.5 状态与异常展示

1. 输入为空时，不允许提交。
2. 输入过长时，应给出长度提示或分段处理提示。
3. 识别失败时，应提示用户补充输入类型或背景说明。
4. 编译失败时，应保留原输入内容并支持重试。

### 8.1.6 验收标准

1. 用户可成功导入至少 9 类首版支持输入。
2. 系统可在合理时间内完成编译，并生成初步结构化候选对象。
3. 输入被并入现有工作面时，不会覆盖已有卡片结构。
4. 对尚未成形的感觉输入，系统应先完成理解、命名或追问；除完整来源事实外，只有用户固定含义和范围后才可提交并显影。

## 8.2 主画布

### 8.2.1 功能说明

主画布是 EvoCanvas 1.0 的结构显影工作面，用于承载已经相对稳定的输入编译结果、当前问题结构、待澄清缺口、约束沉淀、待决策事项、轻量方案承接、结构化交接物、面向 AI 的 PRD 线索以及它们之间的轻量关系。

主画布承担的不是文档展示功能，而是产品经理的核心工作功能：

1. 看见当前有哪些已显影输入正在影响这件事。
2. 看见当前对问题的理解到了哪一步。
3. 看见哪些地方还没有收敛。
4. 看见哪些约束已经形成。
5. 看见哪些事项仍待决策。
6. 看见当前是否已经具备对外交接、实现或派生面向 AI 的 PRD 的条件。

工作台中的可见内容分为三层：

1. `卡片`：前五类卡片投影正式业务对象；交接物承接卡投影结构化包版本。它们共同参与栏目组织和结构化交接显影。
2. `系统挂件`：由系统投影出的辅助视图，如活跃缺口和项目时间轴，用于帮助用户看清当前状态与推进位置。
3. `个人挂件预留`：便签、停车区、时钟、专注计时器等个人辅助工具，用于承接个人工作习惯，不纳入 1.0 首版必须验收项。

三层对象的协作规则如下：

1. 卡片必须有明确栏目归属；业务卡片回指正式业务对象，交接物承接卡回指具体包版本。
2. 系统挂件可以漂移、折叠和 pin，但任何内容都必须回指卡片或里程碑语义，不能单独成为事实源。
3. 个人挂件默认不进入结构化交接物，也不应被 AI 直接视为已确认事实。
4. 个人挂件在 1.0 中停留在个人辅助层，不进入正式对象链路。

### 8.2.2 页面布局要求

主画布采用“连续画布 + 栏目簇”的布局，不采用大块线框切割页面。

页面结构要求如下：

1. 主画布位于工作台中央区域，占据页面主体宽度和高度。
2. 主画布默认展示当前最新状态下的所有活跃栏目与卡片。
3. 画布以栏目标题提示当前内容的主要结构，而不是强调复杂阶段切换。
4. 各栏目承载同类卡片，并通过关系与状态形成整体工作面。
5. 画布本体支持纵向滚动浏览，不应依赖横向无限扩张作为首版主要交互。
6. 当内容超出当前视口时，应优先通过纵向扩展承载，而不是迫使用户频繁横向拖拽。
7. 画布与右侧 AI 助手、右上 Active Todos、底部轻量里程碑条保持联动，但在视觉上应保持主工作面的独立性。
8. 底部工具栏应提供挂件统一入口，用于打开挂件面板并添加组件；入口层不承担挂件运行态管理。

### 8.2.3 当前栏目与阶段映射

主画布在当前前端主要按六个栏目组织内容，同时在底层维持轻量阶段映射。

前端当前主栏目为：

- 探索发现
- 焦点问题
- 待澄清项
- 规则约束
- 方案与决策
- 落地交接

其中，底层阶段映射当前采用：

- discovery
- define
- handoff

这些栏目表达主流程方向，但不意味着流程严格单向。系统必须允许回流、替代和重新打开。

各栏目当前承担的职责如下：

1. 探索发现：承接证据、来源、附件线索与原始输入投影。
2. 焦点问题：表达当前主题、问题定义与阶段性理解。
3. 待澄清项：显性化信息不足、术语冲突、边界未定与待补问事项。
4. 规则约束：只沉淀已经获得语义与作用范围确认的边界、口径、规则与限制；未确认的约束提议留在 Chat，不进入栏目和画布。
5. 方案与决策：承接需要拍板的事项，以及轻量方案比较或建议。
6. 落地交接：承接结构化交接内容、面向 AI 的 PRD 线索及后续执行所需的最小上下文。

### 8.2.4 栏目定义与展示规则

栏目簇是当前前端中的语义聚类容器，不是死板分栏。

展示规则如下：

1. 每个栏目必须有清晰标题。
2. 栏目内部卡片应自动聚类，默认采用自上而下堆叠或小范围网格排列。
3. 栏目之间应通过留白形成视觉分组，而不是通过粗线框切割。
4. 栏目在当前状态下无内容时，应支持隐藏或轻量空状态展示，不应强制占满空间。
5. 同一张卡片应有一个主归属栏目，但允许被其他栏目引用。
6. 当前固定栏目集合应与前端一致：探索发现、焦点问题、待澄清项、规则约束、方案与决策、落地交接。

### 8.2.5 卡片排布与聚类规则

主画布中的卡片排布需要同时满足可读性和结构稳定性。

排布规则如下：

1. 卡片默认按栏目自动聚集。
2. 同类型卡片在同一栏目内应保持统一样式和近似尺寸节奏。
3. 新生成卡片默认插入所属栏目的可见区域，不应随机散落在画布空白区。
4. 用户拖动卡片时，应优先吸附到最近的合法栏目。
5. 首版不允许卡片脱离栏目长时间悬浮在无归属区域。
6. 当一个栏目中卡片数量较多时，应优先纵向展开，而不是自动拆成多个远距离分区。
7. 被 pin 的卡片应优先保持在用户当前可见区域或该栏目顶部。

### 8.2.6 关系线展示规则

关系线是辅助信息，不应压过卡片本身成为主视觉对象。

展示规则如下：

1. 默认只展示轻量关系提示，不展示全图复杂连线网络。
2. 用户选中卡片时，仅高亮该卡片的直接相关关系。
3. 未选中卡片的关系线应弱化展示或隐藏。
4. 关系线应避免穿越大量无关卡片，减少视觉污染。
5. 首版关系线主要用于帮助用户理解“来源于、澄清了、支持、阻塞、替代、产出为”等关键关系。

### 8.2.7 轻量里程碑提示对主画布的影响

当前前端中的底部时间组件为轻量里程碑条，主要用于提供推进位置感知，而不是切换一套严格的历史快照视图。

当前 1.0 的时间提示规则如下：

1. 里程碑条默认展示一个示意性的推进位置。
2. 它用于辅助用户理解“当前大致处于什么推进阶段”，不要求切换严格的历史版本视图。
3. Active Todos 与主画布仍以当前最新状态为准。
4. 时间提示不应改变真实底层数据。
5. 后续若演进为真实里程碑系统，再补充历史快照与状态切换语义。

### 8.2.8 关键交互

1. 用户可在栏目内浏览已显影卡片。
2. 用户可点击任一卡片查看其完整内容或进入对应编辑态。
3. 用户可拖动卡片到其他合法栏目。
4. 用户选中卡片时，仅高亮直接相关关系。
5. 用户可从 Todo 面板点击回到主画布中的源卡。
6. 用户可从低打扰变化提示或画布高亮定位到对应卡片。

### 8.2.9 空状态与异常展示

1. 当某个栏目为空时，应展示轻量空状态，而不是占满大面积说明文案。
2. 当当前状态下没有某类卡片时，不应强行展示占位噪音。
3. 当主画布首次初始化失败时，应保留输入编译结果和错误提示。
4. 当某张卡片的关系解析失败时，应优先保底展示卡片本体，不应导致整块栏目消失。
5. 当画布内容过少时，不应通过大面积留白掩盖信息不足，而应继续补齐结构说明、字段说明和栏目定义。

### 8.2.10 验收标准

1. 用户可以一眼识别当前主要栏目。
2. 同类卡片在视觉上保持一致，并按栏目自然聚类。
3. 画布不会因为关系线过多而失去可读性。
4. 轻量里程碑条不会干扰主画布理解。
5. 用户能够通过主画布快速定位当前问题、当前缺口和当前可对外交接的结构。

## 8.3 卡片体系

### 8.3.1 功能说明

EvoCanvas 1.0 的主对象不是文档章节，而是产品经理在真实工作中持续操作的中间对象和结构化包版本。

卡片与挂件必须显式区分：

1. 证据、问题、待澄清、约束和待决策 / 方案承接卡投影正式业务对象，参与关系和类型化状态流转。
2. 交接物承接卡投影同一主题的结构化包版本及其交接模块，不另存一份独立正文或状态。
3. 系统挂件是系统生成的辅助视图，不取代卡片或包版本本身。
4. 个人挂件是工作台层工具，不默认进入正式对象层。

为避免首版过度设计，卡片体系分为：

#### 1.0 首版核心卡片

- 证据卡
- 问题卡
- 待澄清卡
- 约束卡
- 待决策 / 方案承接卡
- 交接物承接卡

#### 后续版本扩展卡片

- 方案卡
- 结论卡
- 推进项

### 8.3.2 通用卡片设计原则

卡片体系必须同时满足以下目标：

1. 支持用户在高密度信息场景下快速扫描。
2. 支持 Pi 形成稳定结构提案，并在用户固定后通过统一提交能力更新内容。
3. 支持产品经理逐步把模糊认知收束成结构化对象。
4. 支持通过少量字段和状态表达当前推进位置。
5. 支持详情面板承载更完整内容，而不是把所有内容都挤在卡面上。

### 8.3.3 通用卡面字段

所有卡片在产品上统一展示这些基础信息：

- 标题
- 一句话摘要
- 当前状态
- 标签
- 更新时间
- 来源
- 关联项数量

通用展示规则如下：

1. 标题默认单行展示，超出部分省略。
2. 一句话摘要默认展示 2 行，超出部分折叠。
3. 状态必须以明确标签或标记展示，不允许只写进正文。
4. 来源以短标签或来源计数方式展示，不在卡面堆叠长来源文本。
5. 卡面默认不展示长段落正文。

### 8.3.4 卡片详情面板要求

用户点开任一卡片后，应能查看：

1. 完整标题
2. 完整摘要
3. 当前状态
4. 来源引用
5. 关联卡片
6. 历史变更摘要
7. 可执行操作

详情面板是卡片的完整信息承载层。卡面只承载“扫一眼就能判断”的信息，不承担长文阅读功能。

### 8.3.5 证据卡

#### 8.3.5.1 功能说明

证据卡用于承接会议纪要、聊天、截图、访谈、反馈、竞品资料和文档片段等输入来源。

它是事实输入的结构化投影，不代表正式结论。

#### 8.3.5.2 卡面字段与组件要求

| 字段名称 | 组件要求 | 说明 |
| --- | --- | --- |
| 标题 | 文本 | 证据来源标题或 AI 提炼标题 |
| 摘要 | 多行文本 | 证据的核心内容提炼 |
| 来源类型 | Tag | 会议纪要 / 聊天 / 截图 / 反馈 / 竞品 / 文档 |
| 来源状态 | Tag | 可追溯 / 不完整 / 不可用 |
| 核验状态 | Tag | 未验证 / 已验证 / 已反驳；不得由 AI 自报置信度代替 |
| 引用数量 | Text / Badge | 当前被多少卡片引用 |

#### 8.3.5.3 详情面板字段

1. 原始摘录
2. 来源对象
3. 输入时间
4. AI 提炼说明
5. 被引用关系

#### 8.3.5.4 关键交互

1. 用户可查看原始内容与提炼摘要。
2. 用户可手动修订证据摘要。
3. 用户可把证据卡绑定到问题卡、约束卡或待决策 / 方案承接卡。

#### 8.3.5.5 状态与异常展示

1. 证据原文缺失时，仍需保留摘要和来源标记。
2. 原文解析失败时，应展示“原始内容不可完整解析”提示。

#### 8.3.5.6 验收标准

1. 系统可正确展示证据来源类型。
2. 用户可查看原始证据与提炼摘要。
3. 证据卡可被其他卡片引用。

### 8.3.6 问题卡

#### 8.3.6.1 功能说明

问题卡用于表达当前对问题的理解，包括业务问题、用户对象、痛点和目标方向。

#### 8.3.6.2 卡面字段与组件要求

| 字段名称 | 组件要求 | 说明 |
| --- | --- | --- |
| 标题 | 文本 | 当前问题名称 |
| 摘要 | 多行文本 | 当前对问题的简述 |
| 成熟度 | Tag | 初步理解 / 待收敛 / 已收敛 |
| 关联待澄清数 | Badge | 与该问题相关的缺口数量 |
| 更新时间 | Text | 最近更新时间 |

#### 8.3.6.3 详情面板字段

1. 问题背景
2. 目标用户
3. 核心痛点
4. 当前业务目标
5. 关联证据
6. 关联待澄清
7. 关联规则和方案

#### 8.3.6.4 关键交互

1. 用户可编辑问题定义。
2. 用户可将证据卡归并到问题卡下。
3. 用户可从问题卡生成待澄清卡、约束卡或待决策 / 方案承接卡。

#### 8.3.6.5 状态与异常展示

1. 当问题定义过于模糊时，应提示用户继续收敛。
2. 当问题卡失去来源证据支撑时，应提示“缺少来源支撑”。

#### 8.3.6.6 验收标准

1. 用户可从问题卡理解当前问题核心。
2. 问题卡可关联证据、待澄清、规则和方案。

### 8.3.7 待澄清卡

#### 8.3.7.1 功能说明

待澄清卡用于暴露术语冲突、规则未定、边界不清、风险未决和必须补问的信息。

它是 Active Todos 的主来源，也是 EvoCanvas 1.0 首版最重要的显性对象。

#### 8.3.7.2 卡面字段与组件要求

| 字段名称 | 组件要求 | 说明 |
| --- | --- | --- |
| 标题 | 文本 | 待澄清问题名称 |
| 摘要 | 多行文本 | 为什么需要澄清 |
| 优先级 | Badge | 高 / 中 / 低 |
| 阻塞范围 | Tag | 约束 / 决策 / 交接 |
| 当前状态 | Tag | 待提出 / 待确认 / 已澄清 / 已阻塞 / 已关闭 |

#### 8.3.7.3 详情面板字段

1. 具体待确认问题
2. 建议追问对象
3. 阻塞说明
4. 关联问题
5. 被哪些约束或决策澄清

#### 8.3.7.4 关键交互

1. 用户可手动确认是否将其纳入当前活跃缺口。
2. 用户可在聊天中直接回答该问题。
3. 用户确认后可关闭、阻塞或转化为约束 / 待决策项。

#### 8.3.7.5 状态与异常展示

1. 已澄清问题不得继续展示为活跃缺口。
2. 被关闭的问题应保留历史，不应直接删除。
3. 当系统无法判断“该继续追问还是该进入待决策”时，应优先保持待澄清状态，而不是过早升级。

#### 8.3.7.6 验收标准

1. 待澄清卡能够清晰表达当前缺口。
2. 待澄清卡可被 Todo 面板正确投影。
3. 用户可将其关闭、阻塞或澄清。

### 8.3.8 冲突信息显性化要求

EvoCanvas 1.0 首版必须把冲突信息当作一等对象处理，即使首版不单独设计“冲突卡”，也必须满足以下规则：

1. 当两条证据、两条约束、或证据与当前判断之间发生明显冲突时，系统必须在相关卡片上显式标记“存在冲突”。
2. 冲突状态必须能够被用户看见、点击和追溯来源，不能仅作为 AI 内部推理状态存在。
3. 冲突被解决前，不得将对应信息默认为已生效约束或稳定交接内容。
4. 当冲突需要 PM 明确拍板时，Pi 应先提出待决策候选；用户固定其主题和范围后才生成正式待决策 / 方案承接卡，不得静默合并或提前显影。

### 8.3.9 约束卡

#### 8.3.9.1 功能说明

约束卡用于沉淀术语、字段、状态、约束、权限、流程、数据口径等定义。它是 1.0 首版的核心对象，因为首版要验证的重点不是方案是否完整，而是边界是否被钉住。

#### 8.3.9.2 卡面字段与组件要求

| 字段名称 | 组件要求 | 说明 |
| --- | --- | --- |
| 标题 | 文本 | 约束标题 |
| 摘要 | 多行文本 | 当前约束的一句话说明 |
| 约束类型 | Tag | 术语 / 字段 / 状态 / 权限 / 计费 / 流程 / 边界 |
| 当前状态 | Tag | 已生效 / 已替代 / 已归档；未确认提议只留在 Session |
| 冲突标记 | Icon / Badge | 提示当前约束是否存在未决冲突 |
| 影响关系投影 | Graph / Link | 自动投影受其约束的下游对象关系，不要求手动输入 |

#### 8.3.9.3 详情面板字段

1. 完整约束描述
2. 适用范围
3. 例外说明
4. 关联字段或数据口径
5. 来源证据
6. 确认人或确认方式
7. 是否存在冲突约束

#### 8.3.9.4 关键交互

1. 用户可修改约束文本。
2. 用户可确认约束生效。
3. 用户可将旧约束替代为新约束。
4. 用户可将互相冲突的约束标记为待决策输入。

#### 8.3.9.5 状态与异常展示

1. 未确认的约束提议只留在 Session，不生成约束卡；进入画布的约束从“已生效”开始。
2. 已替代约束应保留历史，并显式展示“已替代”状态。
3. 发生冲突的约束不得同时参与“已生效”判断，必须显式标记冲突状态或进入待决策。

#### 8.3.9.6 验收标准

1. 用户可区分草稿约束与生效约束。
2. 约束卡可作为结构化交接物的支持依据。

### 8.3.10 待决策 / 方案承接卡

#### 8.3.10.1 功能说明

待决策 / 方案承接卡用于表达“不是信息不足，而是必须由 PM 明确拍板，或需要以轻量方案承接比较”的事项。

#### 8.3.10.2 卡面字段与组件要求

| 字段名称 | 组件要求 | 说明 |
| --- | --- | --- |
| 标题 | 文本 | 当前决策主题 |
| 摘要 | 多行文本 | 为什么需要拍板 |
| 决策类型 | Tag | 口径 / 方向 / 边界 / 优先级 / 例外 |
| 当前状态 | Tag | 待判断 / 待确认 / 已决定 / 已归档 |
| 推荐倾向 | Text | AI 的方案建议或分析方向倾向 |
| 影响关系投影 | Graph / Link | 自动投影受决策影响的下游对象关系，不要求手动输入 |

#### 8.3.10.3 详情面板字段

1. 具体决策问题
2. 当前可选解释或方案
3. 决策影响范围
4. 关联待澄清或冲突信息
5. 决策结果引用

#### 8.3.10.4 关键交互

1. 用户可明确选择决策结果。
2. 用户可拒绝当前建议并保持待决策状态。
3. 用户确认后，相关约束和待澄清卡同步更新。

#### 8.3.10.5 状态与异常展示

1. 未完成决策的待决策 / 方案承接卡必须持续可见，不得被系统自动关闭。
2. 已决定结果需保留“如何决定”的可追溯记录。

#### 8.3.10.6 验收标准

1. 用户能区分“还没问清楚”和“必须拍板 / 需要比较承接”这两类对象。
2. 待决策 / 方案承接卡可正确回指相关待澄清、约束或冲突信息。

### 8.3.11 交接物承接卡

#### 8.3.11.1 功能说明

交接物承接卡用于承接当前主题的结构化产品上下文，是 EvoCanvas 1.0 对外继续推进的最小交接单元。

它是对应结构化工作包 Revision 的画布入口。卡面摘要、覆盖数量、未决数量和状态都从该 Revision 确定性投影，不形成可独立漂移的第六份业务对象正文。

#### 8.3.11.2 卡面字段与组件要求

| 字段名称 | 组件要求 | 说明 |
| --- | --- | --- |
| 标题 | 文本 | 当前交接主题 |
| 摘要 | 多行文本 | 当前已收敛出的可执行上下文摘要 |
| 当前状态 | Tag | 草稿中 / 待确认 / 已确认 / 已过时 |
| 自动覆盖层级 | Text / Badge | 自动统计已覆盖的问题与约束数量，无需手动填写 |
| 未决数 | Badge | 当前仍未解决的缺口数量 |

#### 8.3.11.3 详情面板字段

1. 当前目标
2. 背景输入摘要
3. 已确认约束列表
4. 已完成决策列表
5. 仍未解决的问题
6. 待确认决策
7. 推荐后续动作
8. 来源里程碑与关联卡片

#### 8.3.11.4 关键交互

1. Pi 或用户可以在稳定 Revision 基础上请求生成或刷新交接草稿，不依赖后台收敛命中。
2. 用户可确认交接物进入可使用状态。
3. 用户可从交接物回跳到原始约束、待澄清和待决策对象。

#### 8.3.11.5 状态与异常展示

1. 未确认的交接物不得被标记为可直接外发。
2. 若交接物依赖的约束或决策发生变化，应显式提示“交接物已过时”。

#### 8.3.11.6 验收标准

1. 交接物承接卡能汇总当前主题的核心背景、约束、决策和未决问题。
2. 交接物承接卡可作为新会话或新 AI 的继续输入使用。

### 8.3.12 后续版本扩展卡片

以下对象已确认有价值，但不纳入 1.0 首版必须实现：

- 方案卡
- 结论卡
- 推进项

后续版本可在 1.0 核心闭环验证通过后，再引入这些对象的完整生命周期。

### 8.3.13 卡片通用操作要求

用户应支持：

1. 编辑标题和摘要
2. 调整状态
3. pin / unpin
4. 合并重复卡片
5. 手动新增卡片
6. 移动卡片到其他栏目
7. 绑定证据或外部链接
8. 触发交接物生成或更新
9. 标记冲突或待裁决状态

这里的 `pin / unpin` 指卡片在当前可见区域或所在栏目顶部的优先保留，不等同于挂件在工作台上的悬浮钉住机制。

### 8.3.14 状态与异常展示

1. 当卡片缺少必要来源时，应给出来源缺失提示。
2. 当卡片正文过长时，卡面必须截断，详情面板完整展示。
3. 当同一输入被重复编译为多张卡片时，应支持合并。
4. 当卡片状态与其所在模块明显不匹配时，应允许系统建议迁移。
5. 当卡片存在冲突但未解决时，应显式提示，不得继续按“已生效”使用。

### 8.3.15 验收标准

1. 系统可正确展示 1.0 首版核心卡片。
2. 用户可在详情面板中查看完整内容。
3. 用户可完成核心轻量编辑操作。
4. 不同类型卡片在信息表达上有清晰区分。
5. 卡片可承接“Pi 提议、用户固定后提交”和“用户直接编辑提交”两种稳定来源；未确认候选不是卡片。


## 8.4 卡片手动修订与迁移

### 8.4.1 功能说明

EvoCanvas 1.0 的卡片不是静态展示物，而是产品经理接管已提交稳定结构、手动修正认知结构的最小操作对象。

首版需要支持一套克制但可用的卡片手动修订能力，使用户能够：

1. 直接修正已提交卡片的标题与摘要。
2. 在同一栏目内快速调整卡片顺序。
3. 在符合语义的前提下，把卡片从一个阶段或模块迁移到另一个合法归属。
4. 通过手动修订，把“尚未稳定的 AI 判断”收束为更可靠的结构化对象。

该模块的目标不是把 EvoCanvas 做成自由白板，也不是在 1.0 首版就建立完整协作审批流，而是验证：

`产品经理是否能快速接管并修正 AI 编译结果。`

### 8.4.2 设计原则

卡片手动修订模块必须遵循以下原则：

1. 优先保持浏览态清晰，不让编辑控件长期占满画布。
2. 编辑能力服务于结构化修订，而不是鼓励长文写作。
3. 拖拽代表对象归属变化或状态迁移，不代表自由摆放。
4. 同模块排序应足够顺滑，跨阶段迁移应足够谨慎。
5. 所有迁移都必须服从对象语义，不允许把画布退化为无边界白板。

### 8.4.3 首版范围

1. 支持卡片标题原地编辑。
2. 支持卡片摘要原地编辑。
3. 支持栏目内卡片排序。
4. 支持合法的跨栏目迁移。
5. 支持在跨阶段迁移时给出轻确认提示。

首版明确不包含：

1. 自由像素级摆放卡片。
2. 同一张卡片的多人同时编辑。
3. 拖拽后自动改写右侧 AI 对话历史。
4. 拖拽后自动改写结构化交接物正文。
5. 卡片级复杂审批流、评论流和权限流。

### 8.4.4 原地编辑规则

首版采用轻量原地编辑，不引入完整表单式详情编辑器作为主入口。

规则如下：

1. 用户可直接点击标题进入单行编辑态。
2. 标题编辑在失焦时自动保存。
3. 用户可直接点击摘要进入多行编辑态。
4. 摘要编辑通过 `Cmd/Ctrl + Enter` 保存，通过 `Esc` 取消。
5. 单击卡片默认仍优先执行“选中卡片”，应通过双击或明确点击可编辑区域进入编辑态。
6. 进入编辑态后，该卡片临时不可拖拽，避免文本选择与拖拽冲突。
7. 首版原地编辑只覆盖标题与摘要，不要求在卡面直接编辑标签、负责人、状态、关系和来源。

### 8.4.5 排序与拖拽规则

卡片移动在产品语义上分为两类：

1. 同栏目内排序
2. 跨栏目迁移

排序与拖拽规则如下：

1. 同栏目内排序时，用户拖动卡片后松手即生效。
2. 同栏目内排序只改变显示顺序，不改变卡片类型与阶段语义。
3. 跨栏目迁移时，目标容器必须是系统定义的合法落点。
4. 拖拽过程中，合法落点应高亮提示，非法区域应弱化或拒绝响应。
5. 卡片不得长时间停留在无归属的画布空白区。
6. 关系线在卡片落位后自动重算，不要求用户手工调整。

### 8.4.6 合法迁移路径

首版允许的跨阶段迁移不是任意移动，而是有限的状态升级路径。

系统至少应支持以下典型迁移：

1. 证据卡 -> 问题卡
2. 待澄清卡 -> 约束卡
3. 待澄清卡 -> 待决策 / 方案承接卡
4. 问题卡 -> 交接物承接卡引用输入
5. 已形成稳定结果的卡片 -> 推进阶段中的后续动作承接位

同时必须满足以下约束：

1. 不允许将任意卡片自由拖入无关栏目。
2. 不允许通过一次拖拽静默改变卡片的核心语义而不给出说明。
3. 当目标模块与当前状态明显冲突时，系统应拒绝落下并保持原位。

### 8.4.7 轻确认规则

为了兼顾效率与语义准确性，首版对不同移动动作采用不同确认策略：

1. 同栏目内排序不需要额外确认。
2. 跨阶段迁移在松手后必须给出轻确认提示。
3. 轻确认文案必须明确说明这次迁移将带来的语义变化，而不是只弹出泛化的“是否确认”。

示例：

- 这张卡将从“待澄清”转为“已确认约束”
- 这张卡将从“待澄清”转为“待决策事项”

用户取消后，卡片应恢复原位置与原状态。

### 8.4.8 状态与异常展示

1. 正在编辑的卡片不得进入拖拽态。
2. 正在拖拽的卡片不得同时进入编辑态。
3. 非法落点不应先落下再报错，而应直接拒绝。
4. 跨栏目确认被取消后，卡片应回到原栏目与原排序位置。
5. 当卡片信息不完整，不影响编辑入口显示，但应保留必要的缺失提示。

### 8.4.9 验收标准

1. 用户可直接在画布上修改标题与摘要，而不必先打开详情面板。
2. 同栏目内卡片排序可稳定生效，且不会改变卡片语义。
3. 合法跨阶段迁移可被正确识别，并在确认后更新归属。
4. 非法迁移路径会被拒绝，不会破坏画布结构。
5. 编辑与拖拽不会互相抢占，用户可清楚感知当前处于哪种操作模式。


## 8.5 卡片关系

### 8.5.1 功能说明

第一版只支持少量高价值关系，避免画布变得难以理解。

产品层统一采用中文关系词：

- 来源于
- 澄清了
- 支持
- 阻塞
- 冲突于
- 产出为

### 8.5.2 关系展示要求

1. 关系线默认轻展示。
2. 选中卡片时才重点显示其直接关系。
3. 不显示复杂全图蜘蛛网关系。

### 8.5.3 验收标准

1. 用户能清楚理解关系含义。
2. 关系不会压过卡片本身成为视觉主体。

## 8.6 右侧 AI 助手

### 8.6.1 功能说明

右侧 AI 助手不是普通聊天框，而是：

`通过自然对话推动产品判断收敛的工作入口`

它就是当前 Workspace 的 Primary Pi Session 工作面。用户始终与同一个 Pi 对话；Pi 在正常 Tool Loop 中按需读取 Skill、结构化工作包、历史和来源，形成候选并承接用户确认。用户固定具体含义与范围后，同一个 Pi 调用受治理的语义提交工具创建新 Revision；Canvas 只显影已提交状态。不存在独立收敛部件、收敛提示或产品侧阶段调度器。

右侧 AI 助手的核心价值不是“能聊天”，而是：

1. 吸收输入。
2. 提炼结构。
3. 暴露缺口。
4. 发起追问。
5. 生成建议并承接用户确认。
6. 让已提交的结构化变化在画布中显影。

### 8.6.2 页面布局要求

右侧 AI 助手采用常驻侧栏布局，固定在主画布右侧。

布局要求如下：

1. 右侧侧栏应始终可见，不作为临时弹窗存在。
2. 顶部展示 AI 助手标题、当前工作上下文提示和关闭/折叠入口。
3. 中部展示正常消息流，承载用户输入、AI 回复、追问、建议和确认产品判断的自然对话。
4. 底部展示输入区、附件入口和快捷操作入口。
5. AI 助手宽度应固定在可阅读、可操作的范围内，不随消息长度频繁抖动。

### 8.6.3 页面字段与组件要求

| 页面区域 | 字段名称 | 组件要求 | 说明 |
| --- | --- | --- | --- |
| 顶部区 | 助手标题 | Text | 展示当前助手身份 |
| 顶部区 | 当前上下文提示 | Text / Badge | 展示当前正在处理的主题或当前里程碑进度信息 |
| 消息流 | 用户消息 | Bubble | 展示用户输入 |
| 消息流 | AI 回复 | Bubble | 展示 AI 的解释、追问、建议 |
| 输入区 | 输入框 | Textarea | 支持多行自然语言输入 |
| 输入区 | 附件入口 | Icon Button | 支持导入补充材料 |
| 输入区 | 发送按钮 | Button | 提交当前输入 |
| 快捷区 | 建议动作 | Chips / Button Group | 提供总结、检查一致性、生成问题等快捷动作 |

### 8.6.4 核心能力

AI 助手首版应具备以下能力：

1. 承接多源输入。
2. 识别用户当前意图。
3. 定位应该影响的卡片或模块。
4. 生成可被用户纠正的结构化理解和更新建议。
5. 在正常 Chat 中把高影响产品判断、作用范围和仍存未决聊清楚。
6. 为同一个 Pi 的后续读取、用户确认和受治理提交提供可追溯的原始对话依据。
7. 对模糊输入主动追问。
8. 支持用户从消息跳回对应画布对象。
9. 对冲突信息进行显性说明，并在需要用户拍板时形成待决策候选。

### 8.6.5 输入模式

右侧 AI 助手首版至少支持以下输入模式：

1. 直接对话输入
2. 粘贴长文本
3. 粘贴聊天摘录
4. 粘贴会议纪要片段
5. 上传截图并补充说明
6. 引用当前画布中的卡片继续讨论

输入模式要求如下：

1. 用户可以在不离开当前工作面的情况下持续补充输入。
2. 用户在讨论某张卡片时，应支持把该卡片作为当前对话上下文。
3. 输入过长时，应提示系统正在分段理解，而不是直接静默失败。

### 8.6.6 七类基础动作

第一版只允许系统基于 AI 提案驱动以下七类基础动作：

1. 新增卡片
2. 更新卡片
3. 改变状态
4. 建立关系
5. 标记冲突
6. 关闭问题
7. 标记进度/更新里程碑

这些动作必须可被审计、可追踪、可定位到具体对象。

### 8.6.7 对话显影流程

每轮对话与结构化显影按以下流程协作：

1. 用户原始输入作为 User Entry 保存到 Workspace 的 Primary Pi Session。
2. `transformContext` 在 Pi 每次模型调用前临时注入最新稳定 Revision 的工作快照。
3. 同一个 Pi 在正常 Tool Loop 中识别意图、追问、比较、按需读取 Skill、对象、历史或来源，并形成候选理解。
4. 没有稳定变化时，Pi 直接完成正常回复，结构化工作包和 Canvas 保持不变。
5. 存在可稳定内容时，Pi 在 Chat 中展示具体含义、作用范围、依据、影响和仍存未决。
6. 用户确认后，同一个 Pi 调用受治理的 `workspace.commit` 语义提交能力；来源事实完整性收录可以按治理规则自动完成，但不自动推导其他对象。
7. 提交器完成身份、基础 Revision、Schema、来源、确认、状态转换、依赖和幂等检查，原子创建完整新 Revision。
8. Canvas、Active Todos、里程碑和必要 Toast 只显影已提交 Revision。

候选讨论可以持续多轮，但不会触发第二个 Agent、后台收敛任务或额外 Assistant 回复。用户直接编辑使用同一语义提交能力，不先转成 Chat，也不自动唤起 Pi；Pi 下一轮读取最新 Revision。

其中“识别意图”不仅适用于聊天回复，也适用于长文本导入后的后续追问。

系统应能判断输入更像：

1. 事实来源
2. 当前问题
3. 待澄清点
4. 约束补充
5. 待决策事项
6. 交接物收束

### 8.6.8 信任与稳定化边界

系统区分“在 Session 中形成候选”和“进入稳定 Revision”。

#### 可自动形成但只保留在 Session

- 问题候选
- 待澄清候选
- 约束候选
- 待决策 / 方案承接候选
- 交接内容草稿
- 候选关系和冲突解释

这些内容不会获得正式对象 ID，也不生成 Canvas 卡片。

#### 可自动收录的稳定来源事实

用户主动导入或工具实际读取的来源，在来源身份、定位和完整性检查通过后，可以记录为证据事实。该收录只证明来源陈述可追溯，不代表外部真实性已经验证，也不自动产生约束或决定。

#### 必须由用户固定后才能进入 Revision

- 问题和待澄清项的具体含义与范围
- 约束
- 正式比较的方案与待决策项
- 已决定结果
- 交接内容与可用范围
- 其他由 Pi 推断的稳定业务语义

用户可以固定“这个问题仍未解决”；这表示未决状态本身已经成为稳定工作事实，不表示问题已经得到答案。

### 8.6.9 Chat 确认依据规则

高影响信息地位升级必须来自正常 Chat 中清晰、带范围的产品判断确认，不使用独立确认请求卡或确认提案队列。

一条有效确认链至少应能回答：

1. AI 提出的具体判断或建议是什么。
2. 用户确认、否定或修正了什么。
3. 确认适用于哪些对象、字段或范围。
4. 哪些相关问题仍未一起解决。
5. 对应的 Assistant 与 User 原始消息在哪里。

如果 Chat 已经包含完整提议和明确确认，同一个 Pi 可以直接引用该依据调用语义提交工具，不得要求用户重复确认“是否生成卡片”。“可以考虑”“大概这样”等试探表达只能支持 Session 中的候选，不得被解释为已确认。

### 8.6.10 追问规则

当输入不清晰时，AI 应优先追问，而不是强行落图。

至少以下情况需要优先追问：

1. 指代不清
2. 前后冲突
3. 约束存在多种解释
4. 决策表达不完整
5. 输入更像情绪判断而非业务判断

追问应尽量具体，并指向当前缺少的信息，而不是泛泛地要求“补充更多背景”。

### 8.6.10A 协作协议

为了让 AI 更像“产品同事”而不是“会整理卡片的聊天框”，首版必须遵守以下协作协议：

1. 优先级顺序固定为：`先暴露不确定性 -> 再沉淀约束 -> 再形成待决策 -> 最后生成交接物`。
2. 当用户的一句话同时可以被理解为“约束”或“结论”时，默认先在 Chat 中保留为约束提议并继续确认语义与作用范围；确认前不创建约束卡，确认后直接形成已生效约束。
3. 当来源信息之间冲突时，AI 不得私下选择其一，必须显性标记冲突并要求用户裁决或补充背景。
4. 任何进入“已生效”或“已确认”状态的内容，都必须能追溯到具体来源、确认方式或用户裁决记录。
5. 交接草稿必须显式保留当前仍未解决的关键缺口，不能伪装成“已经完整收敛”。

### 8.6.11 变化显影与低打扰提示

结构化状态实际提交后，画布卡片是变化的主要表达。系统可以按需显示低打扰 Toast，例如：

- 工作面已更新
- 新增 2 个待澄清项
- 1 条约束已生效

显影提示遵守以下规则：

1. 只有发生事实提交时才可出现，不在每轮 Chat 后固定展示。
2. 提示必须能回指实际变化对象，但不需要逐项复述完整差异。
3. 正式卡片只投影已经固定的稳定对象；“待澄清”“待决策”等状态表示用户已经确认这些事项仍属未决，不表示普通候选可以持久化。约束只有确认后才进入画布。
4. Toast 不承担用户确认；完整差异、原因和版本关系进入 Pi Trace 与结构化工作包 Revision 审计。
5. Canvas 投影不得为了输出变化摘要而追加第二条 Assistant 消息。

### 8.6.12 关键交互

1. 用户可通过自然语言推动理解和结构化状态更新。
2. 用户可引用当前卡片继续讨论。
3. 用户可在正常消息中确认、否定或修正高影响产品判断。
4. 用户可从画布对象或变化提示定位到相关状态与来源。
5. 用户可通过快捷动作触发总结、检查一致性、生成问题等操作。

### 8.6.13 状态与异常展示

1. 当主 Chat 正在生成回复时，应展示处理中状态，但不阻塞用户继续输入。
2. 当 AI 无法理解用户输入时，应明确提示并给出继续操作建议。
3. 当稳定提交失败、基础 Revision 过时或 Canvas 投影失败时，不得伪造画布变化；当前已提交状态保持不变。
4. 确认不足时保持候选或未决，由后续正常 Chat 继续引导，不展示后台等待确认任务。
5. 当某次消息只产生讨论或追问时，不强制输出“当前未对画布做变更”。

### 8.6.14 验收标准

1. 系统只可自动收录来源完整的证据事实；其他草稿和候选必须在用户固定含义与范围后才能写入并显影。
2. 任何信息地位升级都能回指正常 Chat 中明确且带范围的确认依据。
3. AI 在模糊输入时会优先追问，而不是强行落图。
4. 已提交变化通过画布和低打扰提示显影，不依赖固定变化回执。
5. AI 助手在整个工作流中是持续性的工作入口，而不是一次性导入工具。
6. AI 在不同轮次中会优先遵守“先暴露不确定性，再推进已确认结构”的协作规则。

## 8.7 系统挂件：活跃缺口（Active Todos）

### 8.7.1 功能说明

`Active Todos` 是一个系统挂件，不是任务管理列表，也不是独立事实源。

它表达的是：

`当前还没有收敛、并且正在影响产品经理继续推进的认知缺口面板`

它的目标不是替代任务系统，而是帮助产品经理快速识别：

1. 当前最值得优先处理的问题是什么。
2. 哪些缺口正在阻塞方案继续收束。
3. 哪些动作已经清楚，但还没有被推进完成。

### 8.7.2 页面布局要求

Active Todos 采用右上角常驻悬浮挂件布局。

布局要求如下：

1. 挂件默认常驻可见，但支持折叠、pin / unpin 与画布内漂移。
2. 钉住状态下固定在工作台右上角；取消钉住后可作为漂移挂件自由移动。
3. 面板标题区展示当前 Todo 总数。
4. 面板主体区按条目列表展示当前活跃 Todo。
5. 条目数过多时，应支持滚动查看。
6. 面板不承担复杂编辑功能，重点在于快速浏览、定位和处理。

### 8.7.3 来源

第一版只从以下对象投影生成：

- 待澄清卡
- 待决策 / 方案承接卡

只有满足以下条件之一的对象才进入 Active Todos：

1. 阻塞后续推进
2. 需要 PM 明确拍板
3. 需要找别人确认
4. 已形成明确动作但还未完成

### 8.7.4 Todo 类型

产品上分为三类：

- 待澄清
- 待决策
- 待定义

类型含义如下：

#### 待澄清

表示当前还有问题没有讲清楚，需要继续问清。

#### 待定义

表示方向已经大致明确，但规则、字段、口径或范围还未落定。

#### 待决策

表示信息已收敛到需要 PM 拍板，但当前尚未做出最终判断。

### 8.7.5 页面字段与组件要求

| 字段名称 | 组件要求 | 说明 |
| --- | --- | --- |
| 标题 | 文本 | Todo 一句话标题 |
| 类型 | Badge | 待澄清 / 待定义 / 待决策 |
| 优先级 | Badge | 高 / 中 / 低 |
| 来源栏目 | 文本 | 来自哪个栏目 |
| 阻塞状态 | Icon + 文本 | 是否阻塞其他卡片推进 |
| 源卡引用 | Jump Link / Icon | 点击后跳回源卡 |

### 8.7.6 优先级规则

首版优先级分为：

- 高
- 中
- 低

优先级计算应至少参考以下因素：

1. 是否阻塞后续推进
2. 是否影响当前已确认约束或交接物
3. 是否影响当前主题能否对外继续推进
4. 是否被用户手动标记为重要

### 8.7.7 关键交互

1. 点击 Todo 后可定位到源卡。
2. 用户可在聊天中直接处理该 Todo。
3. Todo 完成后，应同步更新源卡状态。
4. 用户可快速识别当前哪些 Todo 属于“必须先处理”的内容。

### 8.7.8 状态与异常展示

1. 当没有活跃 Todo 时，应展示轻量空状态，例如“当前没有活跃缺口”。
2. 当源卡被删除、归档或状态异常时，Todo 应同步失效，不得悬空保留。
3. 当 Todo 与当前里程碑节点不一致时，应以当前里程碑进度投影视图为准。
4. 当同一缺口被重复投影时，应支持合并而不是重复展示。
5. 挂件的折叠、拖动和 pin 状态只影响展示方式，不应改变底层 Todo 投影结果。

### 8.7.9 验收标准

1. Todo 面板只展示活跃缺口。
2. 每条 Todo 均可定位回源卡。
3. Todo 不是独立事实源。
4. Todo 类型和优先级可帮助用户快速判断先处理什么。

## 8.8 系统挂件：项目时间轴

### 8.8.1 功能说明

当前前端中的项目时间轴是一个系统挂件，用于展示当前主题在推进感知上的大致位置。

它承载的是辅助性的推进提示，帮助产品经理理解“当前大致推进到哪里了”，而不是复杂的历史进度版本回放或甘特图式任务管理。

在术语上，项目时间轴延续“轻量里程碑条”的语义，但在工作台表达上统一归入系统挂件体系。

### 8.8.2 页面布局要求

项目时间轴默认以工作台左下角常驻挂件呈现；取消钉住后，可在画布中作为漂移挂件自由摆放。

布局要求如下：

1. 挂件在视觉上应清晰独立，以轻量横条和节点提示组成。
2. 挂件支持折叠、pin / unpin 与画布内漂移，不应与主画布拖拽产生冲突。
3. 组件上可展示示意性的阶段标签与节点（如：阶段定义、内测发布、MVP 上线）。
4. 可使用垂直指示线和提示标签标识“当前进度点”。
5. 它应强调“辅助定位”，不应被用户误解为完整项目排期视图。

### 8.8.3 里程碑定位

它用于查看：

1. 当前主题大致推进到了哪一个阶段。
2. 当前工作区距离下一个交付节点还差哪些关键缺口。

该组件不用于：

1. 复杂的历史认知版本回溯与回放。
2. 细粒度到人的开发工时排期与甘特图。
3. 替代外部专业的项目管理系统。

### 8.8.4 里程碑定义

当前前端中的里程碑条以演示性节点为主，用于表达工作区推进感，而不是精确项目计划：

1. 可包含阶段节点名称（如“内测发布”“MVP 上线”）。
2. 可辅助提醒当前阶段应重点收敛什么。
3. 可带有示意性时间段标注，但不要求严谨排期语义。

### 8.8.5 里程碑更新

当前 1.0 中，里程碑条以展示当前位置为主，不要求形成严格自动推进机制。

若后续保留该能力，可参考以下更新来源：

1. 当前主题完成关键澄清与约束沉淀。
2. 用户手动标记当前推进位置。
3. 结构化交接物达到可继续推进状态。

### 8.8.6 核心交互

1. 用户可查看当前里程碑节点与当前位置提示。
2. 用户可折叠、pin / unpin 或拖动该挂件，以适配当前工作习惯。
3. 前端可通过高亮节点或当前位置表达当前推进位置。
4. 首版不要求历史日志折叠、精确时间回放或完整项目计划编辑能力。
5. 用户可通过组件本体头部完成 pin、折叠、关闭和拖动等运行态操作。

### 8.8.7 验收标准

1. 项目时间轴视觉表现轻量、规整，不干扰主画布操作。
2. 用户可快速了解当前大致推进阶段及所面临的缺口。
3. 该组件不会被误解为完整项目管理视图。

### 8.8.8 个人挂件预留

除系统挂件外，EvoCanvas 1.0 为个人挂件保留正式产品定义，但不纳入首版必须验收项。

当前预留的个人挂件方向包括：

1. 便签
2. 停车区（Parking Lot）
3. 时钟
4. 专注计时器

个人挂件统一遵循以下规则：

1. 可自由移动、折叠、关闭和 pin。
2. 默认不参与卡片关系计算，也不自动写入结构化交接物。
3. 1.0 不要求个人挂件内容进入正式推进链路。
4. 个人挂件表达的是工作习惯和临时辅助，不表达稳定产品结论。
5. 个人挂件的添加入口统一放在底部工具栏，但添加后的运行态控制仍由组件本体负责。

### 8.8.9 挂件面板

#### 8.8.9.1 功能说明

挂件面板是底部工具栏触发的轻量添加面板。

它的职责只有一个：

`把挂件添加到当前画布`

它不是组件管理后台，也不是挂件运行态控制面板。

#### 8.8.9.2 页面结构要求

1. 挂件面板由底部工具栏中的挂件入口按钮触发。
2. 面板以轻量浮层形式出现在底部工具栏上方。
3. 面板不要求搜索框、Tab 分类或筛选器。
4. 面板主体直接展示当前可添加挂件列表。

#### 8.8.9.3 列表项字段与组件要求

每个挂件项至少展示：

| 字段名称 | 组件要求 | 说明 |
| --- | --- | --- |
| 图标 | Icon | 挂件识别图标 |
| 名称 | Text | 挂件名称 |
| 一句话说明 | Secondary Text | 说明该挂件解决什么问题 |
| 添加按钮 | Primary / Secondary Button | 将挂件加入当前画布 |

当前 1.0 面板中可出现的挂件项包括：

1. 项目时间轴
2. 活跃缺口
3. 便签
4. 停车区
5. 时钟
6. 专注计时器

#### 8.8.9.4 添加后的默认行为

1. 用户点击添加后，对应挂件应立即出现在当前画布中。
2. 系统挂件优先落到其默认锚点位置。
3. 个人挂件优先落到当前视口附近的非主焦点区域，避免遮挡核心卡片。
4. 新添加挂件可有轻量出现反馈，但不应打断当前工作流。

#### 8.8.9.5 不包含范围

挂件面板在 1.0 中不包含以下能力：

1. 搜索
2. Tab 分类
3. 状态标签，例如“已显示”“已钉住”“已隐藏”
4. pin / unpin
5. 折叠 / 关闭
6. 一键整理布局

这些能力若需要存在，应放在组件本体上，而不是放在挂件面板里。

#### 8.8.9.6 验收标准

1. 用户可通过底部工具栏进入挂件面板。
2. 用户可从面板中直接添加挂件。
3. 用户不会把挂件面板误解为运行态管理面板。

## 9. 数据结构与计算口径

### 9.1 卡片基础结构

每张卡片至少包含以下基础字段：

| 字段名称 | 说明 |
| --- | --- |
| 卡片 ID | 全局唯一标识 |
| 卡片类型 | evidence / problem / clarification / constraint / decision-or-option / handoff |
| 标题 | 当前卡片标题 |
| 摘要 | 卡片的一句话或短文本摘要 |
| 状态 | 当前状态 |

| 来源引用 | 指向输入来源或来源卡片 |

### 9.2 卡片类型字段口径

不同卡片在基础字段之外应具备类型化扩展字段。

#### 证据卡扩展字段

2. 原始摘录
3. 输入时间
4. 引用数量
5. 冲突标记
6. 来源完整性状态（可追溯 / 不完整 / 不可用）

1. 目标用户
2. 核心痛点
3. 当前业务目标
4. 关联待澄清数

#### 待澄清卡扩展字段

1. 优先级
2. 阻塞范围
3. 建议追问对象
4. 澄清结果引用

#### 约束卡扩展字段

1. 约束类型

4. 确认方式
5. 冲突标记（显性化警告）

#### 待决策 / 方案承接卡扩展字段

1. 决策类型或方案类型

3. 关联依赖关系（系统投影生成）

1. 当前目标

5. 推荐后续动作

### 9.3 关系结构口径

首版支持的关系类型包括：

1. 来源于
2. 澄清了
3. 支持
4. 阻塞
5. 冲突于
6. 产出为

每条关系至少记录：

1. 关系 ID
2. 起点卡片 ID
3. 终点卡片 ID
4. 关系类型
5. 创建时间
6. 是否当前有效

### 9.4 挂件基础口径

工作台挂件不是统一业务事实模型，但至少应具备以下展示与状态字段：

1. 挂件 ID
2. 挂件类型（系统挂件 / 个人挂件）
3. 挂件子类型（如活跃缺口、项目时间轴、便签）
4. 当前展示状态（钉住 / 漂移 / 折叠 / 关闭）
5. 默认锚点位置
6. 漂移坐标
7. 关联源对象引用
8. 最近更新时间

当前 1.0 首版必须落地的系统挂件包括：

1. 活跃缺口（Active Todos）
2. 项目时间轴

### 9.5 活跃缺口系统挂件计算口径

Active Todos 不是独立事实源，而是由当前活跃卡片投影生成。

只有满足以下条件之一的对象才进入 Active Todos：

1. 阻塞后续推进
2. 需要 PM 明确拍板
3. 需要找别人确认
4. 已形成明确动作但还未完成

投影来源仅限：

1. 待澄清卡
2. 待决策 / 方案承接卡

### 9.6 Todo 优先级计算口径

Todo 优先级至少参考以下因素：

1. 是否阻塞后续推进
2. 是否影响当前已确认约束或交接物
3. 是否影响当前主题能否对外继续推进
4. 是否被用户手动标记为重要

首版优先级只分为：

- 高
- 中
- 低

### 9.7 项目时间轴数据口径

每个里程碑提示节点至少可关联：

1. 当前节点对应的推进目标
2. 当前阶段关注的核心卡片集合
3. 阻塞当前推进的活跃缺口列表
4. 当前已沉淀的规则与决策

### 9.8 项目时间轴更新口径

当前前端中的项目时间轴以当前位置提示为主，不要求严格的数据驱动推进。

若后续保留更新能力，可参考以下触发来源：

1. 当前主题建立了关键卡片结构
2. 阻塞性问题被关闭或澄清
3. 用户手动标记当前位置
4. 形成可继续推进的结构化交接物

以下情况不应单独推动里程碑提示变化：

1. 卡片的常规文字微调
2. 常规画布拖拽与排布整理
3. 纯视觉样式变更

### 9.9 结构化变更集口径

同一个 Pi 不直接输出整张画布，而应基于当前结构化工作包和用户确认调用最小语义操作。画布只消费已经提交的 Revision。

首版允许的变更集类型包括：

1. 新增卡片
2. 更新卡片字段
3. 修改卡片状态
4. 新增关系
5. 标记冲突
6. 关闭问题
7. 标记当前进度/更新里程碑

模型可以在 Session 中提出语义变化，但只有来源事实的完整性收录或已经取得用户确认的稳定变化可以进入变更集；对象 ID、消息引用、基础 Revision 和提交幂等键必须由系统确定性装配或验证。

### 9.10 结构化交接物口径

结构化交接物是 EvoCanvas 1.0 首版最重要的对外交付对象。它可以进一步派生为面向 AI 的 PRD，但不等价于传统完整 PRD，也不等价于完整 machine spec。

结构化交接物与日常工作包使用同一个 `package_id`、同一套 Schema 和同一条不可变版本链。交接物只是达到治理条件的包版本及其交接视图，不复制一份独立文档正文。

每份交接物至少必须包含：

1. 当前主题与目标
2. 背景输入摘要
3. 已确认约束
4. 已完成决策
5. 仍未解决的问题
6. 待确认决策
7. 推荐后续动作
8. 关联当前里程碑和关键来源引用

结构化交接物必须满足：

1. 可被人类快速理解并进入后续执行
2. 可被下游 AI 工具作为实现、评审或任务拆解输入使用
3. 若底层约束或决策变化，应可被识别为已过时

每条变更至少应包含：

1. 变更类型
2. 目标对象
3. 变更内容摘要
4. 是否需确认
5. 变更结果状态

## 10. 状态、权限与异常规则

### 10.1 状态权威与通用治理分组

每类独立业务对象只维护一套可写的类型化状态。系统不得同时维护一套可独立修改的“通用顶层状态”，避免同一对象出现两套互相冲突的事实状态。

为了支持上下文筛选、治理门禁、交接装配和界面分组，系统可以根据“对象类型 + 类型化状态”确定性派生以下通用治理分组：

- 来源依据
- 形成中
- 未解决
- 稳定可用
- 历史保留

通用治理分组只用于统一理解和展示，不直接写入，也不能绕过类型化状态的流转规则。具体映射规则必须版本化、可重算；映射变化不得修改历史对象状态。

对象的结构或来源是否通过验证，另以独立验证结果表达：

- 未验证
- 通过
- 警告
- 不通过

验证结果不替代对象状态。例如，一项待决策可以处于“待确认”且结构验证“通过”，也可以处于“待判断”且验证结果为“警告”。约束提议即使结构验证通过，在获得有效确认前也只留在 Chat，不创建约束对象。

### 10.2 唯一权威的类型化状态

#### 证据卡

- 已收录
- 已引用
- 已归档

#### 问题卡

- 初步理解
- 待收敛
- 已收敛
- 已归档

#### 待澄清卡

- 待提出
- 待确认
- 已澄清
- 已阻塞
- 已关闭

#### 约束卡

- 已生效
- 已替代
- 已归档

#### 待决策 / 方案承接卡

- 待判断
- 待确认
- 已决定
- 已归档

#### 交接物承接卡

- 草稿中
- 待确认
- 已确认
- 已过时

交接物承接卡是结构化包版本的画布投影，不作为卡片自身可独立写入的第二套业务状态。底层交接治理可进一步区分 `suspended / invalidated / superseded`；Canvas 均显示为“已过时”并保留具体原因。

### 10.3 状态流转规则

#### 待澄清卡

可接受的主要流转包括：

1. 待提出 -> 待确认
2. 待确认 -> 已澄清
3. 待确认 -> 已阻塞
4. 待确认 -> 已关闭

#### 约束卡

可接受的主要流转包括：

1. Chat 中已获得语义与作用范围确认 -> 创建为已生效
2. 已生效 -> 已替代
3. 已生效 / 已替代 -> 已归档

未确认的约束提议不进入结构化工作包 Revision 或画布，因此不存在可持久化的约束“草稿中”或“待确认”状态。

#### 待决策 / 方案承接卡

可接受的主要流转包括：

1. 待判断 -> 待确认
2. 待确认 -> 已决定
3. 已决定 -> 已归档

#### 交接物承接卡对应的包版本

可接受的主要流转包括：

1. 草稿中 -> 待确认
2. 待确认 -> 已确认
3. 已确认 -> 已过时

以上路径表达逻辑上的信息地位演化。若正常 Chat 已经包含完整提议和明确确认，同一次原子提交可以记录对象创建与对应地位，不要求为了经过“待确认”而额外生成一个中间 Revision；完整变化与确认依据保存在不可变 Revision 审计中。

独立业务对象的状态写入都以本节的类型化状态为准；交接物承接卡只读取包版本治理状态。通用治理分组由系统在读取时派生，验证结果独立更新，二者都不得形成第二套业务状态机。

### 10.4 权限规则

1. 首版默认单人工作台，不区分多人编辑权限。
2. 当前用户拥有所有画布内操作权限。
3. AI 不直接修改 Canvas 投影；同一个 Pi 在用户确认后通过受治理的语义提交工具更新结构化工作包，Canvas 负责投影。
4. 草稿和候选可以在 Primary Pi Session 中自动形成；除来源事实完整性收录外，只有经过用户固定的语义才可写入稳定 Revision 并显影。

### 10.5 结构化动作权限与确认依据

同一个 Pi 与用户直接编辑共用受治理的语义提交能力。提交器只接受类型化操作，不接受整包自由覆写。

在来源、身份、版本和完整性检查通过后，可以自动提交的内容仅包括：

1. 用户主动导入或工具实际读取的证据事实；
2. 从 current Revision 可确定性计算的索引、复核标记和投影元数据。

以下内容由 Pi 推断时，必须先在正常 Chat 中获得对具体含义和范围的用户确认：

1. 问题和待澄清项；
2. 约束；
3. 正式方案、待决策项和决定；
4. 对对象或关系的语义更新、解决、撤回或替代；
5. 交接内容、范围和风险接受。

确认记录至少绑定确认主体、Assistant 提议与 User 回复 Entry、基础 Revision、对象或关系范围、内容哈希和仍存未决。确认已经明确时，同一个 Pi 可直接引用该依据提交，不创建确认队列，也不要求用户再次批准“是否生成卡片”。

正式外发、外部写入或其他不可逆副作用继续使用独立动作门禁，不因结构化包已经确认而自动放行。

### 10.6 异常规则

1. 输入编译失败时，原输入必须保留。
2. 信息地位升级缺少确认依据时，只能保留在 Session；若用户已固定“这是一个未决问题”，可作为未决对象提交并显影，但普通候选不得显影。
3. 里程碑进度更新失败时，不应影响当前画布状态。
4. 卡片关系解析失败时，应保底展示卡片本体。
5. AI 无法理解输入时，应优先追问；只能保留可确定的来源和缺口，不得推进信息地位。
6. Todo 投影异常时，应回退到源卡视角，而不是保留失效 Todo。

## 11. 验收标准汇总

### 11.1 输入与显影

1. 用户导入任一受支持输入后，系统可以在合理时间内完成来源完整性检查，并以通过检查的证据事实初始化或更新画布。
2. 问题、待澄清、约束和待决策候选先在 Primary Pi Session 中展示；用户固定其含义和范围后，才提交为正式卡片并显影。
3. 初始化或后续分析发现冲突、缺失时，Pi 必须在对话中显性说明；只有用户固定为正式冲突或未决对象后才进入画布，不得静默忽略或提前显影。
4. 用户可在右侧对话中继续补充信息；只有形成新的有效提交时画布才更新，普通讨论不改变画布。

### 11.2 输入类型覆盖

系统首版至少支持以下输入被编译进同一工作面：

1. 会议纪要
2. 自然语言想法
3. 聊天摘录
4. 用户反馈列表
5. 数据结论说明
6. 文档片段

### 11.3 画布结构

1. 画布采用连续结构，不出现被硬边框切碎的主区域。
2. 当前主要栏目可被清晰识别。
3. 同类卡片在视觉和布局上保持聚类一致性。

### 11.4 活跃缺口挂件

1. Todo 面板只展示当前活跃缺口。
2. 每条 Todo 均可定位回源卡。
3. Todo 处理完成后，源卡状态同步更新。

### 11.5 结构化交接物

1. 当当前主题已经形成可读边界时，系统可生成交接草稿；关键待澄清和必要决策尚未完成时，必须明确列入未决或待确认决策。
2. 交接物必须包含目标、背景、已确认约束、已完成决策、未决问题、待确认决策和推荐后续动作。
3. 只有用户确认该版本的内容、范围与未决边界后，它才可作为正式交接依据。
4. 当前前端默认将其作为只读派生结果展示。
5. 交接物可派生为面向 AI 的 PRD，供不同 AI 工具作为实现、评审或任务拆解输入使用。

### 11.6 项目时间轴

1. 用户可查看项目时间轴提供的推进位置提示。
2. 前端可通过高亮节点或当前位置提示表达当前推进位置。
3. 该组件不会替代主画布结构，也不承担完整项目管理职责。

### 11.7 AI 协作

1. 系统可在 Primary Pi Session 中自动处理草稿、候选和低风险结构化整理；除完整来源事实和确定性派生元数据外，不得据此自动提交或显影。
2. 高影响信息地位升级必须能回指正常 Chat 中明确且带范围的确认依据。
3. AI 在输入不清晰时优先追问，而不是强行落图。
4. AI 在存在冲突时优先显性化冲突，而不是私下合并。
5. Chat 已经完成确认时，系统不会再次要求用户确认是否生成卡片或结构化包。
6. AI 在首版流程中优先产出待澄清、约束和待决策，而不是过早产出最终结论。

### 11.8 核心命题验证

1. 对同一主题，根据同一份结构化交接物或面向 AI 的 PRD 进入后续实现、评审或任务拆解时，核心约束和已完成决策应保持稳定，不因表达顺序变化而大幅漂移。
2. 与“直接把聊天记录交给下游 AI”相比，使用 EvoCanvas 输出的结构化交接物或面向 AI 的 PRD 时，需求漏点和歧义应显著减少。

## 12. 非功能性需求

1. 主画布应保持视觉克制，避免白板式视觉混乱。
2. 卡片密度要支持产品经理长时间浏览，不应被长文挤满。
3. 关键操作需要可回退，尤其是结论替代和问题关闭。
4. 轻量里程碑提示展示应快速、稳定，不造成明显页面阻塞。
5. AI 更新应尽量采用增量变更，避免整图重绘。

## 13. 术语表

| 术语 | 定义 |
| --- | --- |
| 感觉接入 | 用户以一句感觉、模糊描述、关键词或其他未成形输入启动工作的入口能力 |
| 对话塑形 | agent 在对话中理解、命名、拆解和追问，让模糊感觉逐步变成可讨论对象 |
| 结构收敛 | 把初步成形的内容治理为待澄清问题、约束、待决策和结构化交接物的核心闭环 |
| 画布显影 | 当结构稳定到可承载时，将结构化对象显影为卡片、栏目、关系和缺口投影 |
| 输入编译台 | 结构收敛阶段中，把不同来源输入编译为结构化候选对象的能力 |
| 栏目簇 | 主画布上的语义分组层，当前以前端六栏目结构为准 |
| 卡片 | 进入正式对象层、参与关系和结构化交接物的业务对象 |
| 系统挂件 | 由系统投影出的辅助视图，例如活跃缺口与项目时间轴 |
| 个人挂件 | 服务个人思考和操作便利的工作台工具，默认不进入正式对象层 |
| 证据卡 | 事实输入的结构化投影 |
| 待澄清卡 | 当前尚未收敛、需要追问或确认的问题卡 |
| Active Todos | 系统挂件之一，当前还没有收敛、并且正在影响推进的缺口投影视图 |
| 项目时间轴 | 系统挂件之一，用于表达当前主题推进位置的时间轴挂件 |
| 轻量里程碑条 | 项目时间轴在里程碑语义上的旧称，当前统一归入系统挂件体系 |
