# ETCLOVG 模型总览（ETCLOVG Framework）

> 当前成熟度层级：`L1 参考框架层`
> 使用方式：`作为 harness 分层的外部参照，不直接替代 EvoCanvas 各层设计规格`

## 1. 文档目的

本文档只做一件事：

- 按权威知识源整理 `ETCLOVG` 模型本身的框架定义

本文档不做这些事：

- 不把论文框架直接等同于 EvoCanvas 当前实现
- 不替 EvoCanvas 先下具体对象、状态机或接口结论
- 不把某一层提前扩写成实现规格

因此，这是一份“外部模型总览”，不是“项目内层级定稿”。

本轮可直接核对的权威来源是：

- `From Failed Trajectories to Reliable LLM Agents: Diagnosing and Repairing Harness Flaws`，arXiv，2026-06-04

但在当前这轮整理中：

- 我们直接核读并引用的是前一篇论文中给出的 `ETCLOVG` 框架定义
- 对综述论文，目前只确认其被引用存在

- `基于可直接核对论文整理的 ETCLOVG 总览`

而不是：

- `基于全部原始论文链完整比对后的终版学术综述`

## 3. ETCLOVG 是什么

`ETCLOVG` 是一个用于分析和设计 agent harness 的七层控制框架。

这里的 harness，不是单指提示词（prompt），也不是单指某个运行时（runtime）。

它更接近：

- 包裹在模型外的一整套控制系统
- 用来约束 agent 如何接入环境、使用工具、保存上下文、推进生命周期、留下痕迹、接受验证并服从治理

因此，`ETCLOVG` 关注的不是“模型会不会答”，而是：

- 一个 agent 产品如何被构造成可运行、可控制、可验证、可审计的系统

## 4. 七层框架

`ETCLOVG` 七层分别是：

1. `E`：执行环境（Execution Environment）
2. `T`：工具接口（Tool Interfaces）
3. `C`：上下文与记忆（Context and Memory）
4. `L`：生命周期与编排（Lifecycle and Orchestration）
5. `O`：可观测性（Observability）
6. `V`：验证（Verification）
7. `G`：治理（Governance）

从低到高看，这七层大致回答：

- agent 跑在什么受控环境里
- 它如何接世界、接工具、接输入
- 它在每一轮能看到什么、记住什么
- 它如何推进、暂停、回流、协同、终止
- 它如何被记录、解释、回放
- 它如何被检查是否乱做、漏做、跳步做
- 它最终受什么规则约束，什么动作才允许生效

这七层不是七个平铺模块，而更像七个不同控制视角：

- `E/T/C` 更偏底座供给
- `L` 更偏运行主链
- `O/V` 更偏诊断与校验
- `G` 更偏最高阶约束与放行

因此，`ETCLOVG` 不是在回答“系统有哪些文件夹”，而是在回答“一个 agent 系统要被控制住，需要哪几种不同类型的控制能力”。

## 5. 各层原始职责摘要

### 5.1 E：执行环境（Execution Environment）

这一层关注 agent 运行所在的受控承载环境。

按论文语境，它至少关心：

- 运行时承载
- 沙箱与隔离
- 并发执行边界
- 故障恢复
- 基础环境安全性

这一层解决的是“系统跑在哪里、怎么安全地跑”。

### 5.2 T：工具接口（Tool Interfaces）

这一层关注 agent 如何接触外部能力。

按论文语境，它至少关心：

- 工具调用接口
- 外部系统接入
- 输入输出协议
- 工具结果的结构化回传

这一层解决的是“agent 如何把外部能力纳入可控链路”。

### 5.3 C：上下文与记忆（Context and Memory）

这一层关注模型在任务过程中看到什么、保留什么。

按论文语境，它至少关心：

- 上下文构造
- 短期状态保留
- 长期记忆策略
- 历史复水与压缩

这一层解决的是“模型如何在有限上下文里维持连续工作能力”。

### 5.4 L：生命周期与编排（Lifecycle and Orchestration）

这一层关注 agent 的运行时推进骨架。

按论文语境，它至少关心：

- 执行流控制
- 思考-行动-观察循环
- 重试机制
- 任务状态管理
- 多智能体协同
- 终止条件

这一层解决的是“agent 这轮任务怎么往前跑、何时停、何时回、何时结束”。

### 5.5 O：可观测性（Observability）

这一层关注系统如何留下足够痕迹，便于理解与诊断。

按论文语境，它至少关心：

- 运行日志
- 轨迹记录
- 回放与诊断线索
- 关键动作留痕

这一层解决的是“出了问题后，能不能知道问题发生在哪里、为什么发生”。

### 5.6 V：验证（Verification）

这一层关注系统如何证明自己的行为可靠。

按论文语境，它至少关心：

- 输出检查
- 过程检查
- 结构正确性
- 任务完成度判断
- 失败检测

这一层解决的是“系统如何确认这一步真的过关，而不是看起来像过关”。

### 5.7 G：治理（Governance）

这一层关注最高阶规则约束。

按论文语境，它至少关心：

- 策略约束
- 审批与权限
- 风险控制
- 升级与中断规则
- 最终生效边界

这一层解决的是“什么能做、什么不能做、什么必须被拦下或确认”。

## 6. 层间关系怎么理解

如果只记七层名词，很容易把它们写成七张并列卡片。

更接近论文框架精神的理解方式是：

- `E` 提供运行承载前提
- `T` 提供与外部世界交互的受控入口
- `C` 决定模型看到的任务工作面
- `L` 决定任务如何沿主链推进
- `O` 负责把运行过程留下可解释痕迹
- `V` 负责检查过程与结果是否过关
- `G` 负责决定哪些行为被允许、哪些结果可生效

可以把它理解成一条受控 agent 主链：

`环境承载 -> 能力接入 -> 上下文组织 -> 生命周期推进 -> 运行留痕 -> 结果验证 -> 治理放行`

但这条链不是严格串行流水线，因为：

- `O` 会贯穿所有层
- `V` 既能检查过程，也能检查结果
- `G` 既能事前限制，也能事中拦截，还能事后裁决

所以更准确地说：

- `ETCLOVG` 是分层控制框架，不是单向步骤图

## 7. 为什么 L / V / G 最容易混

在 agent 设计里，最常见的走偏不是忘了有 `E` 或 `T`，而是把 `L`、`V`、`G` 写糊。

原因在于，这三层都和“要不要继续下一步”有关，但它们回答的问题不同：

- `L` 关心的是“流程现在该往哪走”
- `V` 关心的是“这一步是否真的成立”
- `G` 关心的是“即便成立，是否允许生效或越权推进”

可以用一句更硬的区分来记：

- `L` 定义推进骨架
- `V` 定义过关标准
- `G` 定义放行权

常见混淆包括：

- 把验证失败写成状态推进规则，导致 `L` 层越来越像规则引擎
- 把治理拦截写成普通检查点，导致 `G` 层失去独立裁决位
- 把流程回流条件和事实生效条件混写，导致“能不能走”和“能不能算数”不再区分

这也是后续收 `L` 层时要反复回来看这个文档的原因。

## 8. 这个模型主要解决什么问题

`ETCLOVG` 的价值不在于把 agent 拆成七个漂亮名词，而在于提醒我们：

- agent 失败不只会出在模型推理
- 很多失败其实来自 harness 某一层的缺陷
- 同一个表面问题，根因可能分布在不同层

它特别适合处理以下三类问题：

### 8.1 失效归因

当系统表现出“答偏了、跳步了、乱调用、乱生效、无法回放”时，可以先问：

- 是环境没兜住
- 是工具接错了
- 是上下文喂错了
- 是生命周期主链设计错了
- 是日志不够
- 是验证缺位
- 还是治理边界缺失

也就是说，它先帮助团队把“问题现象”和“控制层根因”拆开。

### 8.2 设计拆层

当一个新能力要被引入时，`ETCLOVG` 可以帮助判断：

- 这是运行承载问题，还是工具接入问题
- 这是主链推进问题，还是放行边界问题
- 这是要补日志，还是要补验证器

这样可以减少“所有问题都往 L 层塞”或“所有问题都叫治理”的条件膨胀。

### 8.3 治理校准

当某一层越写越重、越写越像别层时，`ETCLOVG` 可以用来做反校准：

- 当前规则到底是在定义能力，还是在定义流程
- 当前规则到底是在定义检查，还是在定义裁决
- 当前规则到底是在定义承载，还是在定义观察

## 9. 常见失效模式与可能归层

下面这些不是论文逐条枚举的故障字典，而是依据框架职责做的归因整理，用来帮助后续讨论不跑偏。

### 9.1 看起来像“模型太笨”，其实可能不是模型问题

例如：

- 该看的历史没喂进去
- 工具结果回传格式混乱
- 主链允许在依据不足时提前推进
- 高风险动作没有验证或治理门

这些表面都像“模型判断差”，但真实根因可能分别落在：

- `C`
- `T`
- `L`
- `V / G`

### 9.2 看起来像“流程设计问题”，其实可能是验证缺位

例如：

- 系统一路推进到后面才发现前面结论不成立
- 交接物已经生成，但关键冲突没有被挡住
- 已经进入下一阶段，却没有任何“本阶段是否过关”的独立判断

这类问题未必说明 `L` 层流程天然错，更可能是：

- `V` 层没有建立足够明确的过关检查

### 9.3 看起来像“检查已经做了”，其实可能是治理缺位

例如：

- 系统知道内容有风险，但仍自动把它写成生效事实
- 用户未确认时，系统已替用户完成高影响选择
- 多智能体协同时，某个角色越权改写了最终结论

这类问题说明的不是“检查太少”，而是：

- `G` 层没有形成独立放行边界

## 10. 为什么它不是实现顺序

虽然 `ETCLOVG` 从 `E` 到 `G` 有一个自然的阅读顺序，但它并不自动等于工程落地顺序。

原因是：

- 有些层属于底座承载
- 有些层属于风险控制
- 有些层属于运行主链

真实设计时，团队往往会优先定义：

- 哪些结果算有效
- 哪些动作必须被拦
- 哪些状态转换才允许发生

也就是常常先抓：

- `G`
- `V`
- `L`

然后再继续细化：

- `C / T / O / E`

所以：

- `ETCLOVG` 更像分析坐标系
- 不应被误读成固定施工工序

## 11. 用这套框架看文档时，应该问什么

如果后续要用这份总览去校准 EvoCanvas 各层文档，可以对任何一条新规则连续问四个问题：

1. 它在控制什么，是环境、输入、上下文、流程、观察、验证，还是治理
2. 它是在定义“如何推进”，还是在定义“如何过关”，还是在定义“是否放行”
3. 它如果写进当前层，会不会把当前层写成别层
4. 它是框架边界，还是已经进入项目本地化实现口径

这四问的意义是：

- 先判断归层
- 再判断抽象层级
- 最后再决定要不要写进当前文档

## 12. 这个模型不等于什么

为了避免后续讨论走偏，也要明确它不等于以下东西：

- 不等于单个提示词模板
- 不等于某个 agent 框架的源码目录
- 不等于某一层单独扩张后的万能解释
- 不等于直接可编码的实现规格

它首先是：

- 一个用于分析、拆层、校准边界的框架

而不是：

- 一份把每层对象字段、状态枚举、迁移表都写完的实现蓝图

## 13. 对 EvoCanvas 的使用方式

在 EvoCanvas 里，`ETCLOVG` 更适合被当成：

- harness 设计的总分层参照
- 各层职责边界的校准器
- 后续检查“某条规则到底属于哪一层”的对照尺

不适合被当成：

- 直接替代 EvoCanvas 1.0 的产品设计
- 不经转译就硬套到每个对象与流程判断上

因此，后续各层文档更稳的工作方式是：

1. 先尊重 `ETCLOVG` 的原始分层
2. 再结合 EvoCanvas 1.0 的产品闭环做本地化转译
3. 最后在各层文档里收成 L3 / L4 规格

尤其在当前阶段，它更适合扮演两种角色：

- 文档边界校准器
- 分层争议裁判尺

而不适合直接扮演：

- 单层详细规格书
- 项目主状态机定义文档

## 14. 当前最重要的使用提醒

如果后续某层越写越像另一层，不应立刻靠直觉裁剪，而应先回到这个总览检查：

- 这条规则在 `ETCLOVG` 里本来属于哪一层
- 它是在定义能力边界，还是在定义运行主链
- 它是在定义可否生效，还是在定义如何推进
- 它是在定义观察与验证，还是在定义执行与承载

这也是本文档存在的主要意义：

- 先守住模型框架，再继续收 EvoCanvas 自己的内容
