# Governance（治理）

> 方法成熟度：`L3 可指导实现的治理规格层`
> 目标实现归属：`用户裁决 + workspace.commit 确定性门禁`
> 当前实现状态：`原生治理已接入，确认与提交边界待验证`
> 实现说明：当前 Pi 负责理解与提案，用户负责产品裁决，提交工具负责可机器验证的生效条件。

## 1. 控制目标

规定信息何时可以从来源或候选升级为稳定对象，稳定对象何时可以成为交接，以及谁有权作出每种决定。

## 2. 信息地位推进

```text
原始来源记录
-> Pi 解释或候选（仅 Session）
-> 用户确认含义与范围
-> 稳定对象（Revision）
-> 用户确认交接范围与风险
-> 已确认交接
```

来源完整性收录可以自动完成，但来源陈述不等于外部真实性已经验证。

## 3. 治理主体

- **Pi**：可提出、解释、质疑和推荐；不能自我确认产品含义。
- **用户**：对有权限范围内的产品判断和风险接受拥有最终裁决权。
- **提交器**：只执行确定性校验；不能把“模型高置信”当作用户确认。
- **Renderer / 下游**：只消费允许的稳定状态，无权回写事实。

## 4. 确认合同

确认至少绑定确认者、时间、基础 Revision、对象/关系范围、内容哈希、确认种类和已接受风险。内容或范围变化后需要新确认；历史确认保留用于审计。

## 5. 回退与纠正

错误稳定内容通过新 Revision 更正、撤回或替代，不修改历史。用户改变决定不需要否认过去确认，只需创建新决定及替代关系；依赖项进入复核，交接按影响暂停或失效。

## 6. 失败与恢复

- 无法确定用户在确认什么：不稳定化。
- 用户无权确认目标范围：拒绝并显示权限边界。
- 提交后发现错误：创建纠正 Revision，不能覆写历史。
- 治理规则版本不可用：关闭受影响写入，普通对话可继续。
- 多条规则冲突：采用更严格的生效边界并记录冲突，等待规则修复。

## 7. 验收场景

1. Pi 高置信建议仍不能绕过用户确认。
2. 确认一个对象不自动确认其所有依赖或交接。
3. 用户改变决定后，新旧决定和替代链均可追溯。
4. 来源事实被验证为错误后，依赖对象和交接按规则进入复核或失效。
5. Renderer 无法通过写 Canvas 数据改变确认状态。
