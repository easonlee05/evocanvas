# Memory and State（记忆与状态）

> 当前成熟度层级：`L3 可指导实现的治理规格层`
> 编码门槛：`可作为 1.0 结构化包身份、不可变版本、检索索引、状态账本和交接状态的实现输入`

## 1. 分组目的

本组定义 EvoCanvas 如何长期保存产品工作状态、定位相关历史，并解释当前状态为什么成立。

- [Memory（记忆）](./01%20Memory%EF%BC%88%E8%AE%B0%E5%BF%86%EF%BC%89.md) 负责记录保存、包身份、版本索引、检索与复水。
- [State Ledger（状态账本）](./02%20State%20Ledger%EF%BC%88%E7%8A%B6%E6%80%81%E8%B4%A6%E6%9C%AC%EF%BC%89.md) 负责追加式记录对象、关系、确认和包指针变化。
- [Stable State and Handoff（稳定状态与交接）](./03%20Stable%20State%20and%20Handoff%EF%BC%88%E7%A8%B3%E5%AE%9A%E7%8A%B6%E6%80%81%E4%B8%8E%E4%BA%A4%E6%8E%A5%EF%BC%89.md) 负责同一包版本何时可作为正式交接依据，以及何时过时。

记忆不是另一套事实模型，状态也不是页面显示。画布、卡片位置、Active Todos、里程碑和 Toast 都只是结构化状态的投影。

## 2. 三类权威记录

EvoCanvas 1.0 长期保存三类基础记录：

| 记录 | 权威范围 | 不负责什么 |
| --- | --- | --- |
| 原始记录 | `user / assistant / tool` 原文、来源材料、工具结果和确认原文 | 直接宣布结构化结论已经成立 |
| 结构化包版本 | 当前主题下受治理的对象、关系、已知、未知、已决和未决 | 改写原始记录或复制完整账本 |
| 状态账本 | 记录对象、包版本和指针为什么变化 | 保存对象完整正文 |

结构化包是模型当前工作的主要事实工作面；原始记录用于精确核对；状态账本用于解释变化。三者通过 ID 和版本关联，不互相复制正文。

## 3. 单一结构化包

一个活跃主题边界对应稳定的 `package_id`。结构化工作包与结构化交接物使用同一 Schema：

- 工作中时，包版本可以包含草稿、候选、未决和已确认对象。
- 需要交接时，包内的交接模块通过对象引用组织当前目标、已确认约束、已完成决策、未解决问题、待确认决策和推荐后续动作。
- 交接确认不会复制一份新正文，只改变该不可变版本的有效治理状态与版本指针。

包内对象正文只保存一份。交接模块、画布和 Active Todos 都通过对象引用或确定性投影使用它们。

## 4. 包版本与状态版本

每次成功的结构化事实提交同时形成：

1. 新的结构化状态版本 `state_version`。
2. 新的不可变 `package_version`，指向对应状态版本。
3. 同一事务内的状态账本事件。
4. `current_version` 指针推进。
5. 必要时 `latest_confirmed_version` 指针变化。

`state_version` 表示对象图和关系的权威修订；`package_version` 表示可被 Chat、收敛和交接消费的不可变包快照。1.0 中二者同提交产生，但消费者不得假设编号相等。

如果正文和对象图没有变化，只是确认已有版本、标记过时或追加风险，则不创建内容相同的新版本；系统只追加治理账本事件，并按需移动 `latest_confirmed_version`。

## 5. 状态权威

对象只维护一套权威的类型化业务状态，例如约束的 `已生效 / 已替代 / 已归档`。约束提议在 Chat 中确认前不进入结构化包，因此不存在可持久化的约束草稿态或待确认态。

系统再从对象类型和业务状态确定性映射出通用治理地位：

```text
来源 / 工作中 / 未决 / 稳定 / 历史
```

通用治理地位用于上下文筛选、门禁、交接和界面分组，但不是第二个可独立写入的业务状态。验证结果另用 `validation_state` 表达，不混入对象生命周期。

## 6. 分层检索

Memory 采用从轻到重的访问顺序：

```text
活跃范围摘要
-> 结构化包索引
-> 相关不可变包版本
-> 原始 user / assistant / tool 与来源材料
```

摘要和索引只负责定位，不获得事实地位。需要核对精确措辞、确认范围、冲突证据或工具输出时，必须继续复水原始记录。

跨包检索结果默认只是带来源候选。旧包中的确认状态不自动迁移到当前包，被当前上下文采纳后才由收敛回合形成新版本。

## 7. 核心不变量

1. 普通 Chat 只追加原始消息，不创建包版本。
2. 同一活跃主题不因每轮对话反复创建新 `package_id`。
3. 包版本正文不可变；回退通过基于旧版本创建新版本完成。
4. 索引、摘要、画布和 Todo 都不能成为事实源。
5. 对象业务状态只有一套权威写入面；通用治理地位必须可重算。
6. 已确认版本可以与更新的当前草稿版本并存。
7. 原始记录、包版本和账本在 1.0 中不自动删除；归档只改变默认检索范围。
8. 任何状态升级、替代和过时都必须能回指来源、确认或治理原因。
