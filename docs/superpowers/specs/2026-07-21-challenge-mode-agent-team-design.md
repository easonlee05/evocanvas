# EvoCanvas 挑战模式 Agent Team 产品设计

> 状态：已确认设计，待规格审阅
> 最后更新：2026-07-21
> 产品位置：EvoCanvas 2.0 候选能力
> 范围：挑战模式的产品价值、实时体验、内部对抗机制、结果回流与验收边界
> 非范围：实现计划、接口字段定稿、1.0 主闭环改造、多人协作与外部审批流

## 1. 设计摘要

EvoCanvas 的默认体验仍然是一个安静、透明、共创式的主 Agent，帮助用户把尚未成形的感觉逐步塑造成可讨论、可判断、可交接的结构。

在此基础上，增加一个由用户主动触发的 **挑战模式**：用户可以在任何思考阶段，让当前判断经受一次有组织的反驳。系统在后台无感组建一个临时对抗型 Agent Team，通过独立判断、交叉质询和立场更新暴露盲点，最终仍由主 Agent 输出一份聚焦的争议摘要并回到正常对话。

核心原则是：

> 前台始终只有一个伙伴，后台才存在一个会反驳用户的团队。

挑战模式增加的是思考深度，不增加前台声音、角色管理、卡片类型或确认流程。

## 2. 产品定位

### 2.1 要解决的问题

独立开发者、小团队和产品思考者经常缺少真实组织中的对抗性反馈：

- 没有技术负责人挑战可行性；
- 没有设计视角挑战用户行为假设；
- 没有商业视角追问收益、成本和激励持续性；
- 没有证据审计者指出推断、来源和事实之间的断裂；
- 没有人负责提出当前团队最不愿意面对的反例。

普通主对话可以给出多角度分析，但难以稳定形成“一个观点被另一个观点听见、反驳、回应并修正”的对抗过程。挑战模式用临时 Agent Team 补足这种组织能力。

### 2.2 产品承诺

挑战模式的产品承诺是：

> 在用户投入真实执行之前，让当前判断先经受一次有组织的反驳。

它不承诺替用户做最终决策，也不把 AI 评审伪装成用户研究、技术验证、合规结论或真实专家意见。

### 2.3 版本位置

挑战模式属于 2.0“方案收束工作台”的候选能力，不进入 1.0 必须闭环。

原因是它主要帮助用户检查问题框架、比较方案、暴露关键假设和形成更可靠的决策链路；它不应在 1.0 尚未证明“模糊输入能够稳定收敛”之前扩张成新的主流程。

它也不等于 3.0 的多角色协作。3.0 面向真实参与方围绕结构化对象协作；挑战模式中的角色只是一次运行内的隐形认知职责，不形成用户、权限或协作对象。

## 3. 已确认体验原则

1. **默认单一声音**：普通对话仍由主 Agent 承担，挑战团队不进入前台长期人格。
2. **用户随时触发**：不设置内容成熟度硬门槛，也不要求用户先完成方案。
3. **全程无感组队**：用户不选择角色、轮数、模型或协作拓扑。
4. **内部固定使用 Agent Team**：挑战价值来自成员互相听见、质询、回应和修正，不退化成平行 Subagent 报告。
5. **动态职责而非固定职业角色**：系统根据当前主题自适应生成最有冲突价值的立场。
6. **一次触发、一次挑战**：每次运行围绕触发时的当前焦点完成，输出后 Team 自动解散并回到普通对话。
7. **结果按争议组织**：前台不展示 Agent 对话实录，而展示被挑战的假设、关键分歧、证据缺口和下一步。
8. **不强求共识**：允许结果包含无法调和的分歧和证据不足。
9. **不新增事实源**：挑战结果是 Chat 中的候选判断，不形成第七类卡片或第二套状态机。
10. **不越过确认边界**：团队可以暴露问题，但不能自动修改已确认约束、已完成决策或已确认交接物。

## 4. 用户体验

### 4.1 触发方式

用户可以通过以下方式触发：

- 点击“挑战模式”；
- 在正常对话中表达“挑战一下这个想法”“找找这里的问题”“让反方进场”等明确意图。

系统也可以在方案已经明显成形或准备交接时低打扰地建议一次挑战，但不得自动进入挑战模式。

### 4.2 不设置成熟度门槛

用户在任何阶段都可以触发。系统根据当前内容成熟度自适应改变挑战任务：

| 当前状态 | 内部挑战重点 | 结果承诺 |
| --- | --- | --- |
| 只有模糊感觉 | 探查隐含假设、反例、可能方向和关键问题 | 多视角探索，不给正式评审结论 |
| 问题基本形成 | 检查问题定义、目标用户、证据和边界 | 指出问题框架是否稳固 |
| 存在候选方案 | 挑战可行性、用户行为、价值、成本和风险 | 形成方案压力测试结果 |
| 准备交接 | 检查遗漏、冲突、误导下游和返工风险 | 形成交接红队复核结果 |

越早期，挑战越开放、温和；越接近执行和交接，挑战越严格、具体。

### 4.3 自动锁定范围

系统自动锁定当前对话焦点、关联对象、必要来源和适用版本，不要求用户配置挑战对象。

当同时存在多个主题时，默认选择最近正在推进的主题，并在结果开头用一句话透明说明本次挑战范围。系统不为此增加前置配置或角色选择步骤。

### 4.4 运行状态

触发后，前台只显示低干扰状态：

```text
正在挑战当前判断…
```

不展示：

- 团队成员列表；
- Agent 角色选择；
- 共享任务列表；
- 任务认领和消息邮箱；
- 内部辩论记录；
- 投票或“谁赢了”。

用户感知到的仍然是同一个 EvoCanvas 伙伴，只是当前进入了更强的挑战状态。

### 4.5 一次性运行

一次触发只针对当前焦点完成一轮有界挑战。主 Agent 返回结果后，团队立即解散，后续对话自动恢复普通共创人格。

挑战模式不持续污染后续每轮对话。用户在方案发生实质变化后，可以再次主动触发。

## 5. Agent Team 内部结构

### 5.1 临时团队

每次挑战创建独立的 `Challenge Session`。团队只存在于本次运行周期内，共享冻结后的挑战简报、主张登记、证据引用和分歧记录。

团队拥有内部通信能力，但不拥有 Canvas、结构化包或状态账本的写入权。

### 5.2 最小职责

| 职责 | 作用 |
| --- | --- |
| `Challenge Lead` | 冻结范围、组织质询、控制预算、识别重复观点并保留分歧；不代表某种业务立场 |
| `Steelman` | 用最强、最完整的版本还原并捍卫当前判断，防止反方攻击稻草人 |
| `Challenger` | 从系统动态选择的冲突视角寻找反例、失败路径、隐含假设和二阶影响 |
| `Evidence Auditor` | 在需要时检查来源、事实、推断、外部约束和证据缺口 |

每轮至少需要一个支持职责和一个挑战职责。`Challenger` 数量根据主题复杂度动态确定，默认只保留真正带来增量冲突的少量成员。

这些职责不等于固定的 PM、设计、技术三人组。系统可以根据主题临时生成用户行为挑战、商业反方、技术边界、数据可信性、风险合规或其他更相关视角。

### 5.3 组队原则

1. 系统只选择能够形成不同失败假设的职责，不为了人数凑角色。
2. 多个成员若只能换词重复同一观点，应合并或移除。
3. 角色名称不得替代证据和推理责任。
4. 外部事实型挑战必须能指出来源或明确标为待验证假设。
5. Team 的组成、模型和数量属于内部执行细节，不进入用户配置面。

## 6. 对抗协议

### 6.1 冻结挑战简报

运行开始时形成只读挑战简报，至少包含：

- 本次挑战目标和范围；
- 当前问题、候选方案或交接版本；
- 已确认约束与已完成决策；
- 仍未解决的问题和待决策；
- 相关来源和证据引用；
- 明确区分的事实、推断、候选和未知；
- 触发时的上下文或包版本。

团队只能挑战简报中的当前判断，不能把其他主题偷偷引入本轮范围。

### 6.2 第一轮：独立判断

成员在看到其他成员意见前独立形成：

- 当前最关键的假设；
- 最强支持或反对理由；
- 可验证的反例和失败路径；
- 使用的证据与证据缺口；
- 如果当前判断错误，会造成什么后果；
- 什么新证据能够改变自己的立场。

先独立判断用于降低从众和早期共识偏差。

### 6.3 第二轮：交叉质询

第二轮不允许继续发表平行独白。每个成员必须选择其他成员的一条关键主张进行回应：

```text
我质疑的主张是什么
它依赖什么隐藏假设
现有证据为什么足够或不足
什么条件能够推翻我的质疑
这会如何改变当前方案或问题框架
```

被质疑者必须直接回应，不能只重复原有观点。

### 6.4 立场更新

质询结束后，每个成员必须明确选择：

- 保持原判断，并补充依据；
- 部分修正；
- 撤回原判断；
- 承认当前证据不足。

Lead 记录哪些判断经受住挑战、哪些被推翻、哪些仍然存在真实分歧。

### 6.5 不以投票替代判断

团队不得通过多数票决定真伪。Lead 不负责制造一致意见，而负责：

- 合并重复反对意见；
- 区分致命问题、重要风险、条件性风险和低价值噪声；
- 保留有依据的少数意见；
- 暴露仍缺少的证据；
- 说明各分歧对当前判断的实际影响。

## 7. 前台结果

### 7.1 统一由主 Agent 表达

团队结束后，主 Agent 读取结构化挑战结果并用统一人格表达，不复制内部发言记录，也不模拟多个角色轮流发言。

### 7.2 争议摘要结构

前台结果至少包含：

1. **本次挑战范围**：本轮实际挑战了什么。
2. **总体判断**：基本成立、有条件成立、关键假设不稳、证据不足或存在无法调和的分歧。
3. **经受住的判断**：哪些部分经过反驳后仍然成立。
4. **被击穿的假设**：哪些前提已经无法继续默认使用。
5. **关键分歧**：不同判断为何仍无法合并。
6. **证据缺口**：还缺什么信息才能继续判断。
7. **实际影响**：如果不处理，会影响哪个用户、方案、约束、决策或交接边界。
8. **优先下一步**：当前最值得先处理的一个问题。

结果按争议和影响组织，而不是按 Agent 或职业角色分段。

### 7.3 结论语义

挑战结论不使用简单“通过 / 驳回”替代真实判断。允许以下语义：

- 基本成立；
- 有条件成立；
- 关键假设不稳；
- 当前证据不足；
- 存在无法调和的分歧。

主 Agent 可以给出条件式推荐，但必须同时保留其依据、边界和仍未解决的问题。

## 8. 回到收敛主线

### 8.1 不新增卡片类型

挑战结果是当前 Chat 中的一次深度思考结果，不成为新的业务对象、永久卡片或独立事实源。

挑战模式不新增“评审卡”“反方卡”或“Agent Team 卡”，也不建立第二套任务、确认或状态流。

### 8.2 沿用现有对象体系

挑战结果通过正常 Chat 和既有收敛机制回流：

| 挑战发现 | 回流方式 |
| --- | --- |
| 新暴露的真实问题 | 可以形成问题卡 |
| 会影响后续推进的缺口 | 可以形成待澄清卡 |
| 新出现的方案冲突或取舍 | 可以形成待决策 / 方案承接候选 |
| 已确认内容受到新证据挑战 | 显性保留冲突，回到主对话处理，不静默覆盖 |
| 纯观察、弱反例或低价值噪声 | 留在 Chat 或 Trace，不强制显影 |

挑战结束后，主 Agent 只选择最值得继续处理的一个问题自然推进。用户直接用自然语言回应，不增加结果处置面板。

### 8.3 权限边界

Agent Team 可以：

- 暴露问题、冲突、反例和未知；
- 提出补充来源或验证建议；
- 建议新增待澄清或待决策候选；
- 指出已有判断可能需要重新讨论。

Agent Team 不可以：

- 自动新增、实质修改或替代已生效约束；
- 自动把待决策改为已决定；
- 自动关闭关键待澄清；
- 自动推翻用户已经完成的决策；
- 自动确认交接物或允许下游依赖；
- 触发外部不可逆动作。

任何信息地位升级仍然必须回到正常 Chat，由用户形成清晰、带范围、可追溯的裁决。

## 9. 并发与上下文变化

### 9.1 快照边界

Challenge Session 基于触发时的上下文快照运行。快照包含挑战对象、相关来源和版本引用，使结果能够说明自己基于什么产生。

用户在挑战期间仍可浏览画布和继续普通对话。新输入不会直接注入已经开始的辩论，以免成员基于不同版本展开质询。

### 9.2 过时处理

如果新输入实质改变本轮目标、候选方案、关键约束或证据基础：

1. 当前结果不得按原范围直接返回；
2. 系统最多基于最新状态自动重整一次；
3. 如果上下文继续发生实质变化，则正常结束本轮并回到普通对话；
4. 不让过时的挑战结果进入后续结构化回流。

低影响补充不要求重启，可以作为结果输出时的补充边界说明。

## 10. 失败与降级

### 10.1 团队过度附和

如果成员没有形成有效分歧，Lead 必须检查：

- 是否因为过早共享意见产生从众；
- 是否只是使用不同职业名称重复同一观点；
- 是否遗漏反例、边界条件、失败路径或二阶影响；
- 当前判断是否确实经受住了挑战。

允许最终结论是“没有发现足以推翻当前判断的问题”，但必须说明检查过的假设和边界，不能用一片赞同代替挑战过程。

### 10.2 为了对抗而制造问题

所有强反对意见必须标注为以下一种：

- 有来源支持；
- 基于合理推断；
- 假设性风险；
- 需要外部验证。

团队不得为了制造戏剧冲突而伪造事实、夸大概率或把低影响偏好包装成致命问题。

### 10.3 重复和噪声

Lead 应合并论点相同的反对意见，并按对当前判断的影响排序。前台结果不以“意见数量”表达风险强度。

### 10.4 Agent 失败或超时

如果剩余成员仍覆盖支持、挑战和证据三个必要责任，本轮可以降级完成，并在 Trace 中记录缺失部分。

如果必要责任不完整，主 Agent 不输出伪造的完整评审结论，只说明本轮未完成足够有效的挑战并回到普通对话。

内部技术失败不得被表达为“当前方案没有问题”。

### 10.5 用户停止

用户可以通过“停止挑战”或明确切换主题终止本轮。Team 立即结束，不产生结构化回流。

## 11. 可观测性与 Trace

前台保持无感，但系统需要保留足够的内部 Trace，用于回答：

- 本轮挑战了哪个快照和范围；
- 为什么选择这些对抗职责；
- 哪些成员完成或失败；
- 每条关键主张依据什么来源；
- 哪些观点在质询后保持、修正或撤回；
- 哪些分歧被保留；
- 为什么生成当前总体判断；
- 结果是否因上下文变化而重整或丢弃。

Trace 服务调试、回放和产品评估，不成为第二套业务事实源，也不默认向用户展示内部 Agent 对话全文。

## 12. 成功标准与评估

### 12.1 核心成功标准

1. 挑战模式发现普通对话未发现的高影响问题。
2. 用户认可这些问题确实值得处理，而不是为了反对而反对。
3. 用户因此修改、收紧、补证或放弃某个判断。
4. 经挑战后的方案减少后续返工、误解和交接回流。
5. 用户仍感到自己面对的是一个统一伙伴，而不是多个 AI 围攻。
6. 结果聚焦于少量关键争议，并明确最值得先处理的问题。
7. 用户愿意在下一个重要判断上再次主动触发。

### 12.2 反指标

- 用户觉得自己被多个 AI 围攻；
- 结果只是更长，没有新增高影响问题；
- 多个角色换词重复相同观点；
- 团队为了表演对抗制造伪冲突；
- 用户看完仍不知道先处理什么；
- 挑战意见被误写成已确认事实；
- 延迟和成本明显增加，但返工和失真没有下降。

### 12.3 不使用的虚假指标

以下指标不能单独证明挑战模式有价值：

- Agent 数量；
- 内部消息数；
- 辩论轮数；
- 输出字数；
- 反对意见数量；
- 最终是否形成一致意见。

## 13. 验收场景

### 13.1 模糊感觉阶段

用户只说“我想做一个让开会没那么累的东西”并触发挑战模式。

系统应探查隐藏目标、使用场景、反例和可能误解，输出探索性争议摘要；不得假装存在一个可正式评审的完整方案。

### 13.2 问题框架阶段

用户已经形成目标用户和问题描述，但证据有限。

团队应挑战问题是否真实、目标用户是否过宽、现有证据能否支持判断，并明确哪些只是待验证假设。

### 13.3 方案阶段

用户已经提出一个具体方案。

团队应存在 Steelman 与至少一个真正相反的挑战职责，完成交叉质询和立场更新；前台按争议而非角色组织结果。

### 13.4 交接前阶段

结构化交接物即将确认或外发。

团队应检查遗漏、冲突、下游误读风险和证据断裂，但不能自动确认、否定或修改交接物状态。

### 13.5 没有发现致命问题

当前判断确实经受住挑战。

系统可以输出“基本成立”，但必须说明经受住了哪些关键反例和边界检查，不得只展示多个成员一致赞同。

### 13.6 上下文中途改变

用户在团队运行期间修改核心方案。

旧结果不得直接返回或进入结构化回流；系统应基于最新状态重整一次，或正常结束本轮。

### 13.7 团队运行不完整

关键挑战职责失败或超时。

系统不得把不完整运行包装成正式结论；只有在支持、挑战和证据责任仍然完整时才允许降级输出。

### 13.8 信息地位边界

团队指出一个已确认约束可能不成立。

系统应显性保留冲突并把问题带回正常 Chat，不得自动撤销、替换或降级该约束。

## 14. 非目标

本设计不包括：

- 默认每轮对话都运行 Agent Team；
- 用户配置 Agent、模型、角色、轮数或通信拓扑；
- 展示完整 AI 辩论直播；
- 建立固定 PM / 设计 / 技术虚拟组织；
- 让挑战结果直接写入稳定事实；
- 新增评审卡、团队卡或长期挑战任务池；
- 替代真实用户研究、技术验证、数据分析、法律或合规意见；
- 提前实现 3.0 的多人权限和团队协作流；
- 在本文档中确定具体 API、数据库表、模型供应商或并发参数。

## 15. 与现有产品边界的关系

挑战模式必须继续服从主 PRD 和 Harness：

- [EvoCanvas1.0-PRD.md](../../vision/EvoCanvas1.0-PRD.md) 仍是产品真相源；本设计只描述 2.0 候选能力，不改变 1.0 承诺。
- 挑战结果进入正常 Chat 后，仍按既有六类卡片和结构化交接物规则显影。
- 卡片、挑战摘要和 Trace 都不是平行事实源。
- 任何信息地位升级继续经过用户确认、来源验证、治理与统一提交路径。
- Agent Team 只负责暴露问题，不拥有稳定状态写入权。

## 16. 后续衔接

本规格经用户审阅确认后，下一步才进入实现计划。实现计划需要进一步映射：

- 现有 AgentSession、SubagentService 与团队通信能力的复用边界；
- Challenge Session、挑战简报、主张登记和分歧记录的最小契约；
- 主 Chat 触发、运行状态和结果返回的接口；
- 上下文快照、过时检测、停止与降级策略；
- 结构化输出、Trace 和评估样本；
- 单元、集成、端到端与产品评估用例。

这些内容属于后续实施计划，不在本产品设计阶段提前定死。
