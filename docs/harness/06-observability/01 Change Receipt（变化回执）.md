# Change Receipt（变化回执）

> 当前成熟度层级：`L2 对象与流程定义层`

## 1. 这一层回答什么问题

变化回执回答：每一轮 AI 更新画布后，用户应该看到什么摘要，才能快速理解“这轮推进了什么”。

它是右侧 AI 助手中变化摘要的 harness 规格，不是工程日志。

它对应的不是一般聊天总结，而是 PRD 里的 `变化摘要（Inline Summary Card）`。

## 2. 最小内容

每份变化回执至少包含：

1. 本轮理解：系统认为用户这轮想推进什么。
2. 新增对象：新增了哪些证据卡、问题卡、待澄清卡、约束候选或交接草稿。
3. 更新对象：哪些卡片被修改、补充、移动或关联。
4. 关闭或解决：哪些待澄清被关闭、澄清或阻塞。
5. 挂起确认：哪些高影响动作等待用户确认。
6. 仍存未决：哪些问题、冲突或待确认决策仍未解决。
7. 下一步建议：最值得用户处理的一到三件事。

如果本轮没有改动画布，也要明确说明：

- 当前只是追问，没有落图。
- 当前因为冲突、来源不足或高影响确认未完成而暂停。

## 3. 用户可点击性

变化回执不应只是文本摘要。

它应能跳转到：

- 对应卡片。
- 对应确认请求。
- 对应 Active Todos 项。
- 对应交接物承接卡。

如果无法跳转，至少应保留对象标识，避免用户看见摘要却找不到变化发生在哪里。

## 4. 语气规则

变化回执应清楚区分：

- 已经自动应用的低风险更新。
- 只是生成的候选或草稿。
- 正在等待确认的高影响动作。
- 因风险或缺口被暂缓的动作。

不要使用“已经完成”“已经确定”这类词描述未确认内容。

同样地，也不要把“还没问清楚”和“已经进入待决策”写成一种语气。变化回执需要帮助用户区分：

- 这是信息缺口。
- 这是冲突显性化。
- 这是约束沉淀。
- 这是待拍板事项。
- 这是交接物收束。

## 5. 示例结构

```md
本轮我把你的输入整理成了 2 张待澄清卡和 1 条约束候选。

已应用：
- 新增待澄清：计费口径是否按 seat 还是 workspace。
- 标记冲突：用户数口径在两段输入中不一致。

等待确认：
- 是否将“首版不支持多人权限”标记为已生效约束。

仍未解决：
- 下游 AI PRD 是否属于 1.0 必须交付。
```

示例只是表达格式，实际内容必须回指真实对象。
