# Convergence Operations（收敛操作）

> 当前成熟度层级：`L3 可指导实现的治理规格层`
> 编码门槛：`可作为 1.0 结构化提案、操作类型、复杂输入策略和提交前验证的实现输入`

## 1. 职责边界

收敛操作定义：一次收敛回合可以对当前结构化包提出哪些变化，以及这些变化如何保留来源、未知、冲突和确认范围。

它不定义新的产品阶段，也不新增“复杂回合引擎”。`Vibe Shaping`、需求澄清和交付物产出使用同一套操作，只是当前提案目标和输入成熟度不同。

## 2. “足够收敛”的含义

足够收敛不等于所有问题都已经解决，而是当前增量已经清楚到可以被放入正确的信息地位：

- 已知内容能够回指来源。
- 未知内容能够表达为待澄清或未决。
- 冲突双方都被保留，未被静默合并。
- 候选内容与已确认内容不会混写。
- 用户确认的作用范围可以被验证。

只要满足这些条件，收敛回合就可以提交候选或未决版本；不必等待整个主题完成。

## 3. 操作类型

结构化提案可以组合以下操作：

| 操作类别 | 典型动作 | 默认确认要求 |
| --- | --- | --- |
| 来源收录 | 收录来源、证据片段或工具结果引用 | 不需要 |
| 缺口显性化 | 新增实际问题、Chat 后仍影响推进的待澄清、风险或缺失来源提示 | 不需要 |
| 冲突保留 | 标记冲突、建立冲突关系、保留双方解释 | 不需要 |
| 候选整理 | 新增或更新待决策候选、达到可评审条件的交接草稿 | 不需要 |
| 结构维护 | 合并重复候选、拆分混合对象、建立弱关系 | 按语义影响判断 |
| 信息地位变化 | 新增、实质修改或替代约束，完成决策，关闭关键未决，确认交接版本 | 需要有效确认依据 |
| 替代与过时 | 替代旧约束、重开决策、标记交接版本过时 | 按影响与来源判断 |

“不需要确认”不等于不需要验证。所有操作仍必须通过结构、来源、策略、版本和权限检查。

## 4. 提案操作最小结构

每个提案操作至少包含：

| 字段 | 含义 |
| --- | --- |
| `operation_type` | 操作类型 |
| `target_object_id` | 目标对象；新增时可空但必须有临时引用 |
| `before_ref` | 更新前对象或版本引用；新增时可空 |
| `payload` | 拟写入字段或状态差异 |
| `source_refs` | 支撑本操作的消息、来源或工具结果引用 |
| `confirmation_refs` | 支撑信息地位升级的 Chat 消息引用，可空 |
| `unresolved_refs` | 本操作仍保留的未决或冲突，可空 |
| `risk_level` | 治理层使用的风险等级 |
| `reason_codes` | 可枚举的形成原因 |

整个提案还必须带有 `package_id`、基础消息范围、`base_state_version`、`base_package_version` 和提案 Schema 版本。

模型负责提出语义内容，系统负责补齐确定性的版本、身份、顺序和幂等字段。模型不得自行伪造确认消息 ID、来源 ID 或当前版本号。

## 5. 提案策略

复杂输入不创建第二套运行链，只选择不同提案策略。

### 5.1 直接增量

适用于单一、清晰且来源明确的变化。只生成最小操作集合，不重新总结整份结构化包。

### 5.2 冲突保留

适用于来源相互冲突：

1. 分别保留冲突内容和来源。
2. 标记冲突字段或关系。
3. 形成待澄清或待决策候选。
4. 不选择“看起来更合理”的一方。

### 5.3 多候选拆分

适用于一句话同时包含多个可独立判断的方向：

- 能分别确认的候选拆成独立对象。
- 共享背景通过来源或关系连接，不复制成多个事实。
- 无法确定边界时保留为待澄清，不强行拆分。
- 已确认规则按“是否可以独立修改、替代或废止”决定约束卡颗粒度；忠实拆分确认内容本身不要求用户再次批准卡片数量。

### 5.4 类型化结果承接

待澄清被解决后，不修改原对象类型：

- 只补足事实或问题理解时，更新相关证据、问题和待澄清状态，不强制生成新卡。
- 形成稳定边界时，创建已生效约束并关联原待澄清。
- 完成真实取舍时，更新或创建已决定事项并关联原待澄清。
- 同时存在取舍过程与后续稳定边界时，可以形成关联的已决定事项与已生效约束，两者不得复制同一份正文。

### 5.5 交接草稿刷新

适用于用户请求交接或当前包已具备可读结构：

- 从同一结构化包的对象和状态确定性装配交接模块。
- 已确认约束、已完成决策、待确认决策和未决内容分槽表达。
- 可以创建或刷新草稿版本，但不得因此自动成为已确认交接。

“打开问题、收束结构、判断去向”可以作为模型内部组织提案的思考角度，但不是持久化阶段、独立 agent 或必须逐步输出的三次调用。

## 6. 控制顺序

收敛回合固定执行以下控制顺序：

1. 锁定基础消息和包版本。
2. 生成最小结构化提案。
3. 执行结构验证，拒绝非法字段和状态变化。
4. 执行来源验证，拒绝不存在或范围不匹配的引用。
5. 执行策略验证，检查冲突、未决和对象类型。
6. 执行风险分类和治理裁决。
7. 在提交前重新检查消息、状态和包版本。
8. 由统一提交器原子写入允许的操作。

结构输出错误可以在预算内修复。修复只能纠正格式、缺失字段和可确定的引用，不得补造事实、确认或来源。

## 7. 部分放行

一个提案可以同时包含低风险整理和高影响升级。治理应按操作裁决，而不是简单整包全过或全拒：

- 来源收录、冲突标记和候选整理通过时可以提交。
- 缺少确认依据的信息地位升级被移除或降级为候选。
- 操作之间存在原子依赖时，依赖组必须一起通过或一起拒绝。
- 最终提交只包含通过验证与治理的操作，并记录被降级或拒绝的原因。

如果仍有任何操作成功提交，业务结果为 `applied`。只有没有可提交变化且目标升级尚不具备条件时，才返回 `not_ready`。

## 8. Chat 与收敛回合分工

- Chat 负责把问题说清楚、提出建议、解释影响并承接用户确认或否定。
- 收敛回合负责把已形成的语义整理为结构化提案。
- Chat 不直接写包；收敛回合不追加第二条主 Assistant 回复。
- 确认不足时，收敛只保留允许显影的待决策等候选，或结束为 `not_ready`，由后续正常 Chat 继续引导。未确认的约束提议只留在 Chat，不写入约束卡。

用户说“确定，本周只做 CSV”时，只要内容、确定语气和作用范围已经清楚，该 User 消息本身可以作为直接确认依据，收敛可以形成已完成决策，不要求 Assistant 先复述再让用户重复确认。用户说“可以考虑 CSV”时，只能形成候选方向或待决策项。

## 9. 投影与打包边界

- 画布、Todo、里程碑和 Toast 只消费已提交状态，不属于提案事实源。
- 交接不是另起一份自由总结，而是同一包 Schema 在草稿、待确认、已确认或已过时状态下的使用方式。
- 投影失败不回滚事实提交，可以从当前包版本重建。

## 10. 设计禁令

- 不允许把产品体验旅程硬编码成主题阶段机。
- 不允许为复杂输入创建平行的复杂回合主链。
- 不允许重新生成整包来替代最小增量提案。
- 不允许用摘要掩盖来源断裂、冲突或未决。
- 不允许因用户要求交接而跳过同一套验证和治理。
- 不允许让卡片、Toast 或固定回执替代 Chat 中的产品判断确认。
