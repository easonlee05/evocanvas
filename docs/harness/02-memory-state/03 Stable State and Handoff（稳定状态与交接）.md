# Stable State and Handoff（稳定状态与交接）

> 当前成熟度层级：`L3 可指导实现的治理规格层`
> 编码门槛：`可作为 1.0 包版本治理状态、交接可用性、确认范围、过时判断和指针更新的实现输入`

## 1. 职责边界

本文档定义同一结构化包版本何时只是工作草稿，何时可以作为正式交接依据，以及底层变化后如何保留历史并判定过时。

结构化工作包与结构化交接物不采用两套 Schema。交接是同一包版本达到治理条件后的使用方式，不是重新自由生成一份总结。

## 2. 不可变正文与有效状态

包版本正文提交后不可修改。版本创建时记录 `initial_governance_status`：

```text
draft / pending_confirmation / confirmed
```

读取时，系统将版本正文与状态账本叠加，得到当前有效状态：

```text
draft / pending_confirmation / confirmed / outdated
```

- 确认、风险标注和过时通过追加事件表达。
- `outdated` 不回写旧版本正文。
- 导出视图可以显示当前有效状态，但导出本身不是新的事实版本。

## 3. 交接不等于全部解决

一个包版本可以在仍有未决时被确认。确认表示：

- 当前目标和边界表达准确。
- 已确认约束与已完成决策没有混入候选。
- 未解决问题和待确认决策已经被明确列出。
- 用户认可该版本可以按这些边界交给下一位人或下游 AI。

确认不表示所有问题已经解决，也不能把未决自动变成非阻塞。

## 4. 交接视图

交接视图从同一包版本确定性组织：

1. 当前目标与主题边界。
2. 输入背景与关键来源。
3. 已确认约束引用。
4. 已完成决策引用。
5. 仍未解决的问题引用。
6. 待确认决策引用。
7. 推荐后续动作及其对象、来源引用。
8. 当前里程碑依据（1.0 不实现，字段预留恒空）。

交接视图不得复制对象正文成为第二份可独立编辑内容。需要更新正文时，修改源对象并创建新包版本；视图随后重算。

## 5. 进入待确认的条件

包版本进入 `pending_confirmation` 前至少满足：

1. 包 Schema、对象和关系通过结构验证。
2. 交接视图所有对象和来源引用可解析。
3. 已确认约束、已完成决策、候选和未决已正确分槽。
4. 所有影响交接使用的冲突都已显性保留。
5. 不存在被标为 `invalid` 却仍作为稳定依据的对象。
6. 推荐后续动作能够回指对象、未决或来源。
7. 当前版本的 `content_checksum` 已固定。

待确认只表示“现在可以请用户确认这份交接边界”，不是后台运行等待态，也不创建确认队列。

## 6. 确认一个包版本

包版本进入 `confirmed` 必须有作用于该版本的 `ConfirmationRecord`，至少确认：

- `package_id` 与具体 `package_version`。
- 交接目标和使用范围。
- 用户认可的核心内容或模块。
- 仍存未决与风险。
- 确认依据：可来自「Assistant 提议后 User 明确确认」路径（`proposal_message_refs` 必填），或 User 主动给出的明确、完整且带范围的直接陈述（`proposal_message_refs` 可空）。含糊、保留、举例或范围不明的表达不构成有效确认。

正常 Chat 已经完成上述确认时，收敛回合可以在同一原子提交中创建版本、记录确认并推进 `latest_confirmed_version`，不再要求用户确认“是否生成交接物”。

如果待确认版本已经存在且正文没有变化，则执行纯治理提交：只记录确认、更新有效治理状态并推进 `latest_confirmed_version`，不创建内容相同的新版本。

如果确认只覆盖部分模块，只能确认对应对象或模块；整包继续保持 `draft` 或 `pending_confirmation`。泛化“可以”无法匹配具体版本和范围时，不得确认整包。

## 7. 两个版本指针

### 7.1 当前工作版本

`current_version` 指向 Chat 与收敛默认读取的最新工作版本。它可以是草稿、待确认或已确认。

### 7.2 最近可用确认版本

`latest_confirmed_version` 指向最近仍可安全交接的确认版本：

- 新草稿版本出现时保持不变。
- 新版本完成整包确认后推进。
- 当前指向版本过时时，重新选择仍有效的最近确认版本；没有则置空。
- 不能因为 `current_version` 更新就默认旧确认版本已经过时。

Chat 默认使用 `current_version` 继续工作；正式交接和下游调用默认使用 `latest_confirmed_version`。如果两者不同，界面必须清楚显示“当前工作草稿”和“最近可用交接版本”的差异。

## 8. 过时判断

### 8.1 必须过时

以下变化影响交接主判断时，确认版本进入 `outdated`：

- 已生效约束被替代、撤回或发现关键冲突。
- 已决定事项被重开、推翻或确认范围失效。
- 关键来源被修正、撤回或证明不可靠。
- 当前目标或主题边界发生实质变化。
- 未决从非阻塞升级为阻塞，导致原交接用途不再安全。

### 8.2 保持可用但加风险

只影响外围说明、非关键来源或不改变下游动作的变化，可以追加 `package_version_risk_annotated`，保留 `confirmed` 状态。风险标注必须说明影响范围和来源。

### 8.3 不构成过时

- 仅创建了一个更新的草稿版本。
- 画布排布、卡片位置或视觉样式变化。
- 不改变正文语义的格式修订。
- 投影或 Toast 失败。

## 9. 回流与回退

- 新证据使约束、决策或待澄清重新打开时，在当前包创建新版本，不修改旧确认版本。
- 交接视图发现上游对象状态错误时，回到源对象修正，再生成新版本。
- 回退到历史内容时，以历史版本为基础创建新的当前版本，保留 `derived_from_version`。
- 已过时版本可以查看和追溯，但不得被默认交给下游。

## 10. 下游使用规则

| 使用场景 | 默认版本 |
| --- | --- |
| 正常 Chat 与继续收敛 | `current_version` |
| 用户查看当前画布 | `current_version` 的投影 |
| 正式交接给同事 | `latest_confirmed_version` |
| 下游 AI 实现、评审或拆解 | `latest_confirmed_version` |
| 历史核对与回退 | 明确指定历史版本 |

若没有可用的 `latest_confirmed_version`，系统可以导出带醒目草稿标记的当前版本，但不能把它描述为正式交接或安全下游输入。

正式发布或外部写入仍需独立外部动作门禁，包版本已确认不自动授权副作用。

## 11. 设计禁令

- 不允许把交接写成聊天总结。
- 不允许复制对象正文形成可独立漂移的交接文档。
- 不允许把候选、待确认和未决写进稳定内容槽位。
- 不允许整包确认洗平仍存未决。
- 不允许修改旧版本正文来表达确认或过时。
- 不允许让画布完整度、文档可读性或模型置信度替代用户确认。

## 12. L3 验收场景

- 当前草稿版本和最近确认版本可以同时存在并分别读取。
- 包含显式未决的版本仍可被用户确认为准确交接。
- 部分确认不会把整包升为 `confirmed`。
- 新草稿版本不会自动使旧确认版本过时。
- 关键约束被替代后，依赖它的确认版本进入 `outdated`，正文保持不变。
- 外围说明变化只追加风险标注，不必强制整包过时。
- 交接视图中的任一条目都能回到同版本中的源对象与原始来源。
