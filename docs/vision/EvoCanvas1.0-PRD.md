## 2. 产品背景

现实中的产品经理工作，并不是从“打开文档开始写 PRD”开始的。

更常见的真实工作流是：

1. 从 leader、老板、售前、运营、研发、设计、客户、数据报表、会议、聊天、文档、截图、竞品和临时想法中接收零散输入。
2. 在多轮对齐中不断补充信息，试图弄清楚“这件事到底要解决什么问题”。
3. 在不同人提供的信息、约束、偏好和现实限制之间来回切换。
4. 一边盯细节，一边尽量不丢掉整体目标。
5. 最终把模糊问题转化为规则、方案、结论、原型和交付物。

这类工作天然有几个痛点：

1. 输入来源太碎，且很多是跨媒介、跨角色、跨时间出现的。
2. 会议纪要只能覆盖部分输入，不能替产品经理完成整体认知收敛。
3. 文档适合沉淀结果，不适合承载持续演化中的思考过程。
4. 自由白板虽然有空间感，但很容易变成无结构的逻辑堆积。
5. 聊天式 AI 虽然能回答问题，但无法稳定维护一张持续演化的工作面。

因此，EvoCanvas 1.0 的目标不是优化“写出来”，而是优化：

`想明白`

更准确地说，是帮助产品经理把脑子里的模糊想法、多源输入、反馈碎片、跨团队对齐过程，外化为一个持续演化、可回看、可推进的工作画布。

## 3. 产品目标

### 3.1 一句话定位

EvoCanvas 1.0 是一张持续演化的产品经理工作画布，用来把多源输入转化为结构化上下文、待澄清问题、业务规则、当前结论和推进动作。

### 3.2 核心用户问题

EvoCanvas 1.0 需要解决的不是“写 PRD 太累”，而是：

1. 需求一开始太模糊，难以理清。
2. 输入来源太散，缺少统一收束入口。
3. 一旦盯住某个细节，就容易丢掉整体目标。
4. 很难持续追踪哪些问题还没澄清。
5. 规则、术语、字段口径容易在推进中散掉。
6. 结论会变化，但变化过程缺乏结构化记录。
7. 会议、聊天、文档和截图之间缺少统一的工作界面。

### 3.3 业务目标

1. 支持产品经理导入和汇入多种输入，快速形成结构化产品工作画布。
2. 支持 AI 自动从输入中提炼证据、问题、待澄清项，并在画布中显影。
3. 支持产品经理围绕问题、规则、方案、结论和推进动作持续收敛工作内容。
4. 支持展示轻量里程碑提示，帮助识别当前推进位置。
5. 支持通过右侧 AI 助手持续推进画布演化，而不是仅生成静态文本。
6. 支持从画布收束出后续可继续推进的结构化产品上下文。

### 3.4 成功标准

1. 产品经理在导入任一核心输入后，可以看到结构化的画布初始化结果，并明确看到当前最重要的待澄清问题。
2. 产品经理可以快速看见哪些地方还没讲清楚、哪些信息彼此冲突、哪些事项必须人拍板，而不必自己从长文里翻找。
3. 产品经理可以围绕同一件事，在画布上同时看到输入、问题、约束、决策和交接准备状态，并区分哪些内容仍不稳定。
4. 一次关键讨论后，产品经理可以回看“这次到底推进了什么、消除了哪些不确定性、留下了哪些未决问题”，而不是只看到聊天记录。
5. 画布中的结构最终能够收束为后续可继续推进的结构化产品上下文，并可被其他 AI 在新上下文中复用。

### 3.5 1.0 首版验证命题

EvoCanvas 1.0 首版要验证的不是“能不能搭一套完整 PM 工作台”，而是以下更硬的命题：

1. 多源混杂输入是否可以被系统稳定收束为一组可推进的 `待澄清问题`、`约束` 和 `待决策项`。
2. AI 是否可以像一个合格的产品同事一样，优先暴露不确定性，而不是过早替用户脑补结论。
3. 经过一轮收敛后的结果，是否能够生成一份可交接的结构化产品上下文，供不同 AI 或不同会话继续推进。
4. 首版必须优先验证“需求失真是否降低”，而不是优先追求“对象类型是否齐全”或“界面模块是否完整”。

## 4. 核心规则与约束

1. EvoCanvas 1.0 的第一入口是 `输入编译`，不是 `新建 PRD`。
2. EvoCanvas 1.0 首版只验证“输入编译 -> 待澄清问题 -> 约束 / 待决策 -> 结构化交接物”这一最小闭环，不以搭建完整 PM 操作系统为目标。
3. 主画布是连续画布，不采用硬边框切割大区域。
4. 主画布宽度表达逻辑结构，不表达时间顺序。
5. 时间维度通过底部轻量里程碑条承载，用于提示当前推进位置，不通过横向无限扩张画布承载。
6. 工作台对象分为 `卡片`、`系统挂件` 和 `个人挂件预留` 三层；卡片是正式业务对象，挂件是辅助视图或个人工具。
7. 系统挂件用于投影当前状态、推进位置或操作辅助，不得取代源卡片成为独立事实源。
8. 个人挂件用于个人思考与操作便利，可自由移动、折叠和 pin，但默认不进入结构化交接物，且 1.0 不与卡片层打通。
9. AI 可以自动做低风险结构整理，但不得在高影响动作上绕过用户确认。
10. Active Todos 不是任务管理系统，而是当前活跃缺口投影视图。
11. Todo 不是独立事实源，所有 Todo 必须回指原始卡片。
12. 首版不要求完整结论体系，任何稳定判断优先以“约束”或“待决策结果”形式落地。
13. 当输入之间存在冲突、上下文不足或指代不清时，系统必须优先显性化冲突与缺口，而不是静默合并。
14. 任何被标记为 `已生效` 或 `已确认` 的信息，都必须有明确来源、确认方式或可追溯的用户裁决。
15. 首版不做多人实时协作。
16. 首版不做自由白板模式。

## 5. 用户角色

| 用户角色 | 角色说明 | 核心诉求 |
| --- | --- | --- |
| 产品经理 | 核心目标用户，负责接收需求、整理上下文、推进收敛 | 接住输入、理清问题、追踪缺口、沉淀规则、形成结论 |
| AI 助手 | 系统内协作对象，负责提炼、归纳、追问和显影 | 把自然语言和输入材料编译为结构化画布变化 |
| AI 协作体 | Codex、Claude Code、Antigravity 等在后续上下文中继续推进工作的 AI 协作对象 | 复用结构化上下文，继续参与澄清、约束沉淀、待决策收束和交接推进 |

### 5.1 首版使用边界

1. 首版只面向单人工作台。
2. 首版不涉及多个 AI 在同一画布内实时协作编辑。
3. 首版默认用户是产品经理，其他外部角色的信息通过输入材料进入画布，并由 AI 协作整理。

## 6. 产品范围

### 6.0 范围分层说明

本节将 EvoCanvas 拆分为：

1. `1.0 首版必须范围`：用于验证产品核心命题的最小闭环。
2. `后续版本规划范围`：方向明确，但不纳入 1.0 交付承诺。

如果某项能力不能直接提升“多源输入收敛为可交接上下文”的验证效率，则默认不进入 1.0。

### 6.1 1.0 首版必须范围

| 一级模块 | 二级模块 | 功能范围 |
| --- | --- | --- |
| 输入编译 | 输入接入 | 导入会议纪要、聊天摘录、用户反馈、数据说明、截图说明、竞品摘录、文档片段、临时想法 |
| 输入编译 | 输入编译 | 识别输入类型、提取事实、识别冲突、推断问题和缺口、生成初步结构化卡片 |
| 主画布 | 主要栏目 | 探索发现、焦点问题、待澄清项、规则约束、方案与决策、落地交接 |
| 主画布 | 阶段映射 | 前端当前采用 discovery / define / handoff 的轻量阶段映射，不展开为完整项目阶段系统 |
| 主画布 | 卡片体系 | 证据卡、问题卡、待澄清卡、约束卡、待决策 / 方案承接卡、交接物承接卡 |
| 主画布 | 卡片关系 | 来源于、澄清了、支持、阻塞、冲突于、产出为 |
| 主画布 | 卡片手动修订 | 卡片标题 / 摘要原地编辑、模块内排序、合法跨栏目迁移与轻确认 |
| AI 助手 | 对话显影 | 识别意图、定位对象、生成更新建议、应用到画布 |
| AI 助手 | 追问与确认 | 对模糊输入追问，对高影响动作请求确认，对冲突信息要求裁决 |
| 工作台挂件 | 系统挂件 | 项目时间轴与活跃缺口两类系统挂件，用于表达推进位置与当前活跃缺口投影视图，不作为独立事实源 |
| 工作台挂件 | 个人挂件预留 | 便签、停车区、时钟、专注计时器等个人挂件形态允许预留，但不纳入 1.0 首版必须验收项，且默认不进入结构化交接物 |
| 输出 | 结构化交接物 | 从当前画布收束出可供人或 AI 继续推进的结构化产品上下文 |

### 6.2 后续版本规划范围

后续版本不按“补功能清单”推进，而按产品能力升级路径推进。每一版都应回答一个更大的产品命题，避免在 1.0 未验证完成前过早堆叠复杂能力。

#### 2.0 路线：从“需求收敛工作台”升级到“方案收束工作台”

2.0 的目标不是简单把 1.0 中暂缓的对象补回来，而是在 `1.0 已经证明输入能够稳定收敛` 的前提下，继续回答：

`在问题、约束和待决策明确之后，系统能否帮助 PM 把当前主题继续收束成可执行方案。`

2.0 重点能力：

1. 引入方案层对象：方案卡、结论卡、推进项。
2. 让 `规划` 与 `推进` 两条阶段带从轻量承接升级为可深度使用。
3. 支持围绕多个候选方案进行比较、取舍和收束。
4. 支持从交接物继续生成结构化方案包，而不只是停留在上下文交接层。
5. 支持对“当前为什么这样做”形成更明确的决策链路记录。

2.0 不变原则：

1. 仍然坚持“先暴露不确定性，再形成方案”，不允许方案层压过问题澄清层。
2. 仍然不以多人协作为核心，不把复杂协作流提前引入。

#### 3.0 路线：从“单人 PM 工作台”升级到“多角色协作面”

3.0 的目标是让 EvoCanvas 不再只是 PM 的个人工作面，而是成为多角色围绕同一份问题、约束、方案和决策进行协作的产品协作面。

3.0 重点能力：

1. 多人实时协作与评论线程。
2. 角色化协作视图：PM、设计、研发、业务、评审参与方看到的重点不同。
3. 明确的决策和确认流：谁能确认约束，谁能确认方案，谁提供反馈。
4. 更强的评审闭环：围绕待决策 / 方案承接卡、结论卡、方案卡保留完整协作记录。
5. 更丰富的里程碑对比与进度变更追溯能力。

3.0 不变原则：

1. 协作建立在已结构化对象之上，而不是让多人同时编辑混乱输入。
2. 不为“所有人都能改”牺牲对象清晰度与事实边界。

#### 4.0 路线：从“产品协作面”升级到“交付编排面”

4.0 的目标是把 EvoCanvas 从“想明白、协同收束”继续推进到“让后续交付更可编排、更可追踪”。

4.0 重点能力：

1. 更复杂的关系网络与全局依赖分析。
2. 更完整的文档、规格、原型联动能力。
3. 更强的外部系统接入：项目管理平台、知识库、IM、需求系统等。
4. 更完整的推进状态面、交付链路和后续动作编排能力。
5. 从交接物、方案包继续派生出更正式的规格包、任务包、评审包。

4.0 不变原则：

1. 外部打通服务于“减少失真和提高交付闭环”，而不是为接入而接入。
2. 交付编排建立在前几版已经稳定的对象模型和协作协议之上。

#### 后续路线总原则

1. `1.0` 先证明“输入能被稳定收敛为可交接上下文”。
2. `2.0` 再证明“上下文能继续收束为可执行方案”。
3. `3.0` 再证明“多角色能围绕这些结构化对象协作”。
4. `4.0` 最后证明“协作结果能继续被编排到交付落地链路”。

### 6.3 首版不包含范围

1. 多人实时协作。
2. 完整项目管理甘特图。
3. 自由白板模式。
4. 复杂权限体系。
5. 高保真原型自动生成。
6. 完整文档编辑器。
7. 老板驾驶舱。
8. 复杂外部系统打通能力。
9. 完整方案卡、结论卡、推进项体系的深度运营。
10. 全局复杂关系图谱与自动化依赖推理。

## 7. 核心业务流程

## 7.1 多源输入编译流程

1. 产品经理进入 EvoCanvas 工作台。
2. 产品经理通过输入编译台导入一项或多项输入。
3. 系统识别输入类型。
4. AI 从输入中提取事实、问题、冲突和缺口。
5. 系统在画布中生成初步卡片，并显式标出当前存在的冲突信息或信息不足点。
6. Active Todos 根据卡片状态投影当前活跃缺口。
7. 产品经理开始在画布和右侧 AI 助手中进行收敛。

## 7.2 认知收敛流程

1. 产品经理查看画布上的证据卡、问题卡和待澄清卡。
2. 产品经理补充判断、追问或表达方向。
3. AI 优先判断当前输入是否应新增待澄清卡、约束卡或待决策 / 方案承接卡，而不是直接产出结论。
4. 当输入之间存在冲突、缺失关键前提或存在多种解释时，AI 必须先显性化冲突并追问，不得直接合并。
5. 高影响动作在写入前要求用户确认。
6. 画布结构持续变化，用户可以结合底部轻量里程碑条理解当前大致推进位置。

## 7.3 约束沉淀流程

1. 产品经理围绕术语、字段、状态、权限、边界和口径形成约束。
2. AI 将约束整理为约束卡，并保留对应来源和确认方式。
3. 与约束相关的待澄清卡被关闭、阻塞或转入待决策状态。
4. 已确认约束成为后续结构化交接物的组成部分。

## 7.4 待决策收束流程

1. 当某项信息不是“尚未澄清”，而是“必须由 PM 拍板”时，系统生成待决策 / 方案承接卡。
2. 该卡必须明确决策主题、备选解释或建议方案、影响范围和所需确认人。
3. 用户确认后，该卡进入已决定状态，其结果更新相关待澄清卡或约束卡。
4. 每一个关键节点的沉淀都可反映到轻量里程碑提示中。

## 7.5 结构化交接物流程

1. 当当前主题的主要待澄清项已收敛，关键约束已沉淀，必要决策已完成后，系统可生成结构化交接物。
2. 结构化交接物必须明确：当前目标、输入背景、已确认约束、仍未解决的问题、待确认决策和推荐后续动作。
3. 用户确认交接物后，可将其提供给其他同事或 AI，在新上下文中继续推进。
4. 若后续推进暴露新冲突或新缺口，应允许从交接物回流到待澄清或待决策状态。

## 8. 功能需求与原型设计要求

## 8.1 输入编译台

### 8.1.1 功能说明

输入编译台是 EvoCanvas 1.0 的统一入口能力，用于把不同来源、不同形态、不同成熟度的输入编译到同一张产品工作画布上。

输入编译台的目标不是简单上传文件，而是：

1. 识别输入类型。
2. 提取可用事实。
3. 推断问题与缺口。
4. 生成初步结构化卡片。
5. 将输入并入现有画布，而不是覆盖现有理解。

### 8.1.2 支持的输入类型

首版至少支持以下输入：

1. 会议纪要
2. 聊天摘录
3. 用户反馈列表
4. 数据结论说明
5. 竞品摘录
6. 截图与配套说明
7. 历史文档片段
8. 一段临时想法或方向描述

### 8.1.3 页面字段与组件要求

| 页面区域 | 字段名称 | 组件要求 | 说明 |
| --- | --- | --- | --- |
| 输入区 | 输入类型 | Select / 自动识别标签 | 支持手动指定或由系统自动识别 |
| 输入区 | 输入正文 | Textarea / 富文本承接区 | 支持长文本粘贴 |
| 输入区 | 附件说明 | Textarea | 用于补充截图、文件等的说明文字 |
| 输入区 | 导入按钮 | Button | 点击后进入编译流程 |
| 输入区 | 编译方式 | Segmented Control | 追加到当前画布 / 新建工作画布 |
| 状态区 | 编译状态 | Badge / 文本 | 待处理、处理中、已完成、失败 |

### 8.1.4 关键交互

1. 用户输入内容后，可直接点击导入。
2. 系统应允许用户选择“并入当前工作面”或“作为新工作面开始”。
3. 导入完成后，系统应给出本轮显影摘要。
4. 若输入内容过于模糊，AI 应先追问，不直接显影为高影响结论。

### 8.1.5 状态与异常展示

1. 输入为空时，不允许提交。
2. 输入过长时，应给出长度提示或分段处理提示。
3. 识别失败时，应提示用户补充输入类型或背景说明。
4. 编译失败时，应保留原输入内容并支持重试。

### 8.1.6 验收标准

1. 用户可成功导入至少 8 类首版支持输入。
2. 系统可在合理时间内完成编译，并生成初步卡片。
3. 输入被并入现有工作面时，不会覆盖已有卡片结构。

## 8.2 主画布

### 8.2.1 功能说明

主画布是 EvoCanvas 1.0 的核心工作面，用于承载输入编译结果、当前问题结构、待澄清缺口、约束沉淀、待决策事项、轻量方案承接、结构化交接物以及它们之间的轻量关系。

主画布承担的不是文档展示功能，而是产品经理的核心工作功能：

1. 看见当前有哪些输入正在影响这件事。
2. 看见当前对问题的理解到了哪一步。
3. 看见哪些地方还没有收敛。
4. 看见哪些约束已经形成。
5. 看见哪些事项仍待决策。
6. 看见当前是否已经具备对外继续推进的交接条件。

工作台中的对象分为三层：

1. `卡片`：正式业务对象，参与关系、状态、栏目归属和结构化交接物。
2. `系统挂件`：由系统投影出的辅助视图，如活跃缺口和项目时间轴，用于帮助用户看清当前状态与推进位置。
3. `个人挂件预留`：便签、停车区、时钟、专注计时器等个人辅助工具，用于承接个人工作习惯，不纳入 1.0 首版必须验收项。

三层对象的协作规则如下：

1. 卡片必须有明确栏目归属，是 AI 和用户共同维护的正式对象层。
2. 系统挂件可以漂移、折叠和 pin，但任何内容都必须回指卡片或里程碑语义，不能单独成为事实源。
3. 个人挂件默认不进入结构化交接物，也不应被 AI 直接视为已确认事实。
4. 个人挂件在 1.0 中停留在个人辅助层，不进入正式对象链路。

### 8.2.2 页面布局要求

主画布采用“连续画布 + 栏目簇”的布局，不采用大块线框切割页面。

页面结构要求如下：

1. 主画布位于工作台中央区域，占据页面主体宽度和高度。
2. 主画布默认展示当前最新状态下的所有活跃栏目与卡片。
3. 画布以栏目标题提示当前内容的主要结构，而不是强调复杂阶段切换。
4. 各栏目承载同类卡片，并通过关系与状态形成整体工作面。
5. 画布本体支持纵向滚动浏览，不应依赖横向无限扩张作为首版主要交互。
6. 当内容超出当前视口时，应优先通过纵向扩展承载，而不是迫使用户频繁横向拖拽。
7. 画布与右侧 AI 助手、右上 Active Todos、底部轻量里程碑条保持联动，但在视觉上应保持主工作面的独立性。
8. 底部工具栏应提供挂件统一入口，用于打开挂件面板并添加组件；入口层不承担挂件运行态管理。

### 8.2.3 当前栏目与阶段映射

主画布在当前前端主要按六个栏目组织内容，同时在底层维持轻量阶段映射。

前端当前主栏目为：

- 探索发现
- 焦点问题
- 待澄清项
- 规则约束
- 方案与决策
- 落地交接

其中，底层阶段映射当前采用：

- discovery
- define
- handoff

这些栏目表达主流程方向，但不意味着流程严格单向。系统必须允许回流、替代和重新打开。

各栏目当前承担的职责如下：

1. 探索发现：承接证据、来源、附件线索与原始输入投影。
2. 焦点问题：表达当前主题、问题定义与阶段性理解。
3. 待澄清项：显性化信息不足、术语冲突、边界未定与待补问事项。
4. 规则约束：沉淀已明确或待确认的边界、口径、规则与限制。
5. 方案与决策：承接需要拍板的事项，以及轻量方案比较或建议。
6. 落地交接：承接结构化交接内容及继续推进所需的最小上下文。

### 8.2.4 栏目定义与展示规则

栏目簇是当前前端中的语义聚类容器，不是死板分栏。

展示规则如下：

1. 每个栏目必须有清晰标题。
2. 栏目内部卡片应自动聚类，默认采用自上而下堆叠或小范围网格排列。
3. 栏目之间应通过留白形成视觉分组，而不是通过粗线框切割。
4. 栏目在当前状态下无内容时，应支持隐藏或轻量空状态展示，不应强制占满空间。
5. 同一张卡片应有一个主归属栏目，但允许被其他栏目引用。
6. 当前固定栏目集合应与前端一致：探索发现、焦点问题、待澄清项、规则约束、方案与决策、落地交接。

### 8.2.5 卡片排布与聚类规则

主画布中的卡片排布需要同时满足可读性和结构稳定性。

排布规则如下：

1. 卡片默认按栏目自动聚集。
2. 同类型卡片在同一栏目内应保持统一样式和近似尺寸节奏。
3. 新生成卡片默认插入所属栏目的可见区域，不应随机散落在画布空白区。
4. 用户拖动卡片时，应优先吸附到最近的合法栏目。
5. 首版不允许卡片脱离栏目长时间悬浮在无归属区域。
6. 当一个栏目中卡片数量较多时，应优先纵向展开，而不是自动拆成多个远距离分区。
7. 被 pin 的卡片应优先保持在用户当前可见区域或该栏目顶部。

### 8.2.6 关系线展示规则

关系线是辅助信息，不应压过卡片本身成为主视觉对象。

展示规则如下：

1. 默认只展示轻量关系提示，不展示全图复杂连线网络。
2. 用户选中卡片时，仅高亮该卡片的直接相关关系。
3. 未选中卡片的关系线应弱化展示或隐藏。
4. 关系线应避免穿越大量无关卡片，减少视觉污染。
5. 首版关系线主要用于帮助用户理解“来源于、澄清了、支持、阻塞、替代、产出为”等关键关系。

### 8.2.7 轻量里程碑提示对主画布的影响

当前前端中的底部时间组件为轻量里程碑条，主要用于提供推进位置感知，而不是切换一套严格的历史快照视图。

当前 1.0 的时间提示规则如下：

1. 里程碑条默认展示一个示意性的推进位置。
2. 它用于辅助用户理解“当前大致处于什么推进阶段”，不要求切换严格的历史版本视图。
3. Active Todos 与主画布仍以当前最新状态为准。
4. 时间提示不应改变真实底层数据。
5. 后续若演进为真实里程碑系统，再补充历史快照与状态切换语义。

### 8.2.8 关键交互

1. 用户可在栏目内浏览卡片。
2. 用户可点击任一卡片查看其完整内容或进入对应编辑态。
3. 用户可拖动卡片到其他合法栏目。
4. 用户选中卡片时，仅高亮直接相关关系。
5. 用户可从 Todo 面板点击回到主画布中的源卡。
6. 用户可从右侧 AI 对话中的变化摘要跳转到对应卡片。

### 8.2.9 空状态与异常展示

1. 当某个栏目为空时，应展示轻量空状态，而不是占满大面积说明文案。
2. 当当前状态下没有某类卡片时，不应强行展示占位噪音。
3. 当主画布首次初始化失败时，应保留输入编译结果和错误提示。
4. 当某张卡片的关系解析失败时，应优先保底展示卡片本体，不应导致整块栏目消失。
5. 当画布内容过少时，不应通过大面积留白掩盖信息不足，而应继续补齐结构说明、字段说明和栏目定义。

### 8.2.10 验收标准

1. 用户可以一眼识别当前主要栏目。
2. 同类卡片在视觉上保持一致，并按栏目自然聚类。
3. 画布不会因为关系线过多而失去可读性。
4. 轻量里程碑条不会干扰主画布理解。
5. 用户能够通过主画布快速定位当前问题、当前缺口和当前可对外交接的结构。

## 8.3 卡片体系

### 8.3.1 功能说明

EvoCanvas 1.0 的主对象不是文档章节，而是产品经理在真实工作中持续操作的中间对象。

卡片与挂件必须显式区分：

1. 卡片是正式业务对象，参与关系、状态流转和结构化交接物。
2. 系统挂件是系统生成的辅助视图，不取代卡片本身。
3. 个人挂件是工作台层工具，不默认进入正式对象层。

为避免首版过度设计，卡片体系分为：

#### 1.0 首版核心卡片

- 证据卡
- 问题卡
- 待澄清卡
- 约束卡
- 待决策 / 方案承接卡
- 交接物承接卡

#### 后续版本扩展卡片

- 方案卡
- 结论卡
- 推进项

### 8.3.2 通用卡片设计原则

卡片体系必须同时满足以下目标：

1. 支持用户在高密度信息场景下快速扫描。
2. 支持 AI 以稳定结构写入和更新内容。
3. 支持产品经理逐步把模糊认知收束成结构化对象。
4. 支持通过少量字段和状态表达当前推进位置。
5. 支持详情面板承载更完整内容，而不是把所有内容都挤在卡面上。

### 8.3.3 通用卡面字段

所有卡片在产品上统一展示这些基础信息：

- 标题
- 一句话摘要
- 当前状态
- 标签
- 更新时间
- 来源
- 关联项数量

通用展示规则如下：

1. 标题默认单行展示，超出部分省略。
2. 一句话摘要默认展示 2 行，超出部分折叠。
3. 状态必须以明确标签或标记展示，不允许只写进正文。
4. 来源以短标签或来源计数方式展示，不在卡面堆叠长来源文本。
5. 卡面默认不展示长段落正文。

### 8.3.4 卡片详情面板要求

用户点开任一卡片后，应能查看：

1. 完整标题
2. 完整摘要
3. 当前状态
4. 来源引用
5. 关联卡片
6. 历史变更摘要
7. 可执行操作

详情面板是卡片的完整信息承载层。卡面只承载“扫一眼就能判断”的信息，不承担长文阅读功能。

### 8.3.5 证据卡

#### 8.3.5.1 功能说明

证据卡用于承接会议纪要、聊天、截图、访谈、反馈、竞品资料和文档片段等输入来源。

它是事实输入的结构化投影，不代表正式结论。

#### 8.3.5.2 卡面字段与组件要求

| 字段名称 | 组件要求 | 说明 |
| --- | --- | --- |
| 标题 | 文本 | 证据来源标题或 AI 提炼标题 |
| 摘要 | 多行文本 | 证据的核心内容提炼 |
| 来源类型 | Tag | 会议纪要 / 聊天 / 截图 / 反馈 / 竞品 / 文档 |
| 引用数量 | Text / Badge | 当前被多少卡片引用 |
| 更新时间 | Text | 最近整理时间 |

#### 8.3.5.3 详情面板字段

1. 原始摘录
2. 来源对象
3. 输入时间
4. AI 提炼说明
5. 被引用关系

#### 8.3.5.4 关键交互

1. 用户可查看原始内容与提炼摘要。
2. 用户可手动修订证据摘要。
3. 用户可把证据卡绑定到问题卡、约束卡或待决策 / 方案承接卡。

#### 8.3.5.5 状态与异常展示

1. 证据原文缺失时，仍需保留摘要和来源标记。
2. 原文解析失败时，应展示“原始内容不可完整解析”提示。

#### 8.3.5.6 验收标准

1. 系统可正确展示证据来源类型。
2. 用户可查看原始证据与提炼摘要。
3. 证据卡可被其他卡片引用。

### 8.3.6 问题卡

#### 8.3.6.1 功能说明

问题卡用于表达当前对问题的理解，包括业务问题、用户对象、痛点和目标方向。

#### 8.3.6.2 卡面字段与组件要求

| 字段名称 | 组件要求 | 说明 |
| --- | --- | --- |
| 标题 | 文本 | 当前问题名称 |
| 摘要 | 多行文本 | 当前对问题的简述 |
| 成熟度 | Tag | 初步理解 / 待收敛 / 已收敛 |
| 关联待澄清数 | Badge | 与该问题相关的缺口数量 |
| 更新时间 | Text | 最近更新时间 |

#### 8.3.6.3 详情面板字段

1. 问题背景
2. 目标用户
3. 核心痛点
4. 当前业务目标
5. 关联证据
6. 关联待澄清
7. 关联规则和方案

#### 8.3.6.4 关键交互

1. 用户可编辑问题定义。
2. 用户可将证据卡归并到问题卡下。
3. 用户可从问题卡生成待澄清卡、约束卡或待决策 / 方案承接卡。

#### 8.3.6.5 状态与异常展示

1. 当问题定义过于模糊时，应提示用户继续收敛。
2. 当问题卡失去来源证据支撑时，应提示“缺少来源支撑”。

#### 8.3.6.6 验收标准

1. 用户可从问题卡理解当前问题核心。
2. 问题卡可关联证据、待澄清、规则和方案。

### 8.3.7 待澄清卡

#### 8.3.7.1 功能说明

待澄清卡用于暴露术语冲突、规则未定、边界不清、风险未决和必须补问的信息。

它是 Active Todos 的主来源，也是 EvoCanvas 1.0 首版最重要的显性对象。

#### 8.3.7.2 卡面字段与组件要求

| 字段名称 | 组件要求 | 说明 |
| --- | --- | --- |
| 标题 | 文本 | 待澄清问题名称 |
| 摘要 | 多行文本 | 为什么需要澄清 |
| 优先级 | Badge | 高 / 中 / 低 |
| 阻塞范围 | Tag | 约束 / 决策 / 交接 |
| 当前状态 | Tag | 待提出 / 待确认 / 已澄清 / 已阻塞 / 已关闭 |

#### 8.3.7.3 详情面板字段

1. 具体待确认问题
2. 建议追问对象
3. 阻塞说明
4. 关联问题
5. 被哪些约束或决策澄清

#### 8.3.7.4 关键交互

1. 用户可手动确认是否将其纳入当前活跃缺口。
2. 用户可在聊天中直接回答该问题。
3. 用户确认后可关闭、阻塞或转化为约束 / 待决策项。

#### 8.3.7.5 状态与异常展示

1. 已澄清问题不得继续展示为活跃缺口。
2. 被关闭的问题应保留历史，不应直接删除。
3. 当系统无法判断“该继续追问还是该进入待决策”时，应优先保持待澄清状态，而不是过早升级。

#### 8.3.7.6 验收标准

1. 待澄清卡能够清晰表达当前缺口。
2. 待澄清卡可被 Todo 面板正确投影。
3. 用户可将其关闭、阻塞或澄清。

### 8.3.8 冲突信息显性化要求

EvoCanvas 1.0 首版必须把冲突信息当作一等对象处理，即使首版不单独设计“冲突卡”，也必须满足以下规则：

1. 当两条证据、两条约束、或证据与当前判断之间发生明显冲突时，系统必须在相关卡片上显式标记“存在冲突”。
2. 冲突状态必须能够被用户看见、点击和追溯来源，不能仅作为 AI 内部推理状态存在。
3. 冲突被解决前，不得将对应信息默认为已生效约束或稳定交接内容。
4. 当冲突需要 PM 明确拍板时，系统应生成待决策 / 方案承接卡，而不是静默合并。

### 8.3.9 约束卡

#### 8.3.9.1 功能说明

约束卡用于沉淀术语、字段、状态、约束、权限、流程、数据口径等定义。它是 1.0 首版的核心对象，因为首版要验证的重点不是方案是否完整，而是边界是否被钉住。

#### 8.3.9.2 卡面字段与组件要求

| 字段名称 | 组件要求 | 说明 |
| --- | --- | --- |
| 标题 | 文本 | 约束标题 |
| 摘要 | 多行文本 | 当前约束的一句话说明 |
| 约束类型 | Tag | 术语 / 字段 / 状态 / 权限 / 计费 / 流程 / 边界 |
| 当前状态 | Tag | 草稿中 / 待确认 / 已生效 / 已替代 / 已归档 |
| 影响范围 | Text / Tag | 约束作用范围 |

#### 8.3.9.3 详情面板字段

1. 完整约束描述
2. 适用范围
3. 例外说明
4. 关联字段或数据口径
5. 来源证据
6. 确认人或确认方式
7. 是否存在冲突约束

#### 8.3.9.4 关键交互

1. 用户可修改约束文本。
2. 用户可确认约束生效。
3. 用户可将旧约束替代为新约束。
4. 用户可将互相冲突的约束标记为待决策输入。

#### 8.3.9.5 状态与异常展示

1. 草稿中的约束不得默认视为生效约束。
2. 已替代约束应保留历史，并显式展示“已替代”状态。
3. 发生冲突的约束不得同时参与“已生效”判断，必须显式标记冲突状态或进入待决策。

#### 8.3.9.6 验收标准

1. 用户可区分草稿约束与生效约束。
2. 约束卡可作为结构化交接物的支持依据。

### 8.3.10 待决策 / 方案承接卡

#### 8.3.10.1 功能说明

待决策 / 方案承接卡用于表达“不是信息不足，而是必须由 PM 明确拍板，或需要以轻量方案承接比较”的事项。

#### 8.3.10.2 卡面字段与组件要求

| 字段名称 | 组件要求 | 说明 |
| --- | --- | --- |
| 标题 | 文本 | 当前决策主题 |
| 摘要 | 多行文本 | 为什么需要拍板 |
| 决策类型 | Tag | 口径 / 方向 / 边界 / 优先级 / 例外 |
| 当前状态 | Tag | 待判断 / 待确认 / 已决定 / 已归档 |
| 影响范围 | Text / Tag | 受影响的约束、问题或交接物 |

#### 8.3.10.3 详情面板字段

1. 具体决策问题
2. 当前可选解释或方案
3. 决策影响范围
4. 关联待澄清或冲突信息
5. 决策结果引用

#### 8.3.10.4 关键交互

1. 用户可明确选择决策结果。
2. 用户可拒绝当前建议并保持待决策状态。
3. 用户确认后，相关约束和待澄清卡同步更新。

#### 8.3.10.5 状态与异常展示

1. 未完成决策的待决策 / 方案承接卡必须持续可见，不得被系统自动关闭。
2. 已决定结果需保留“如何决定”的可追溯记录。

#### 8.3.10.6 验收标准

1. 用户能区分“还没问清楚”和“必须拍板 / 需要比较承接”这两类对象。
2. 待决策 / 方案承接卡可正确回指相关待澄清、约束或冲突信息。

### 8.3.11 交接物承接卡

#### 8.3.11.1 功能说明

交接物承接卡用于承接当前主题的结构化产品上下文，是 EvoCanvas 1.0 对外继续推进的最小交接单元。

#### 8.3.11.2 卡面字段与组件要求

| 字段名称 | 组件要求 | 说明 |
| --- | --- | --- |
| 标题 | 文本 | 当前交接主题 |
| 摘要 | 多行文本 | 当前已收敛出的可执行上下文摘要 |
| 当前状态 | Tag | 草稿中 / 待确认 / 已确认 / 已过时 |
| 覆盖范围 | Text / Tag | 覆盖了哪些问题、约束和决策 |
| 未决数 | Badge | 当前仍未解决的缺口数量 |

#### 8.3.11.3 详情面板字段

1. 当前目标
2. 背景输入摘要
3. 已确认约束列表
4. 已完成决策列表
5. 仍未解决的问题
6. 推荐后续动作
7. 来源里程碑与关联卡片

#### 8.3.11.4 关键交互

1. 用户可生成交接物草稿。
2. 用户可确认交接物进入可使用状态。
3. 用户可从交接物回跳到原始约束、待澄清和待决策对象。

#### 8.3.11.5 状态与异常展示

1. 未确认的交接物不得被标记为可直接外发。
2. 若交接物依赖的约束或决策发生变化，应显式提示“交接物已过时”。

#### 8.3.11.6 验收标准

1. 交接物承接卡能汇总当前主题的核心背景、约束、决策和未决问题。
2. 交接物承接卡可作为新会话或新 AI 的继续输入使用。

### 8.3.12 后续版本扩展卡片

以下对象已确认有价值，但不纳入 1.0 首版必须实现：

- 方案卡
- 结论卡
- 推进项

后续版本可在 1.0 核心闭环验证通过后，再引入这些对象的完整生命周期。

### 8.3.13 卡片通用操作要求

用户应支持：

1. 编辑标题和摘要
2. 调整状态
3. pin / unpin
4. 合并重复卡片
5. 手动新增卡片
6. 移动卡片到其他栏目
7. 绑定证据或外部链接
8. 触发交接物生成或更新
9. 标记冲突或待裁决状态

这里的 `pin / unpin` 指卡片在当前可见区域或所在栏目顶部的优先保留，不等同于挂件在工作台上的悬浮钉住机制。

### 8.3.14 状态与异常展示

1. 当卡片缺少必要来源时，应给出来源缺失提示。
2. 当卡片正文过长时，卡面必须截断，详情面板完整展示。
3. 当同一输入被重复编译为多张卡片时，应支持合并。
4. 当卡片状态与其所在模块明显不匹配时，应允许系统建议迁移。
5. 当卡片存在冲突但未解决时，应显式提示，不得继续按“已生效”使用。

### 8.3.15 验收标准

1. 系统可正确展示 1.0 首版核心卡片。
2. 用户可在详情面板中查看完整内容。
3. 用户可完成核心轻量编辑操作。
4. 不同类型卡片在信息表达上有清晰区分。
5. 卡片可承接 AI 自动生成与用户手动修订两种来源。


## 8.4 卡片手动修订与迁移

### 8.4.1 功能说明

EvoCanvas 1.0 的卡片不是静态展示物，而是产品经理接管 AI 初稿、手动修正认知结构的最小操作对象。

首版需要支持一套克制但可用的卡片手动修订能力，使用户能够：

1. 直接修正 AI 生成的标题与摘要。
2. 在同一栏目内快速调整卡片顺序。
3. 在符合语义的前提下，把卡片从一个阶段或模块迁移到另一个合法归属。
4. 通过手动修订，把“尚未稳定的 AI 判断”收束为更可靠的结构化对象。

该模块的目标不是把 EvoCanvas 做成自由白板，也不是在 1.0 首版就建立完整协作审批流，而是验证：

`产品经理是否能快速接管并修正 AI 编译结果。`

### 8.4.2 设计原则

卡片手动修订模块必须遵循以下原则：

1. 优先保持浏览态清晰，不让编辑控件长期占满画布。
2. 编辑能力服务于结构化修订，而不是鼓励长文写作。
3. 拖拽代表对象归属变化或状态迁移，不代表自由摆放。
4. 同模块排序应足够顺滑，跨阶段迁移应足够谨慎。
5. 所有迁移都必须服从对象语义，不允许把画布退化为无边界白板。

### 8.4.3 首版范围

1. 支持卡片标题原地编辑。
2. 支持卡片摘要原地编辑。
3. 支持栏目内卡片排序。
4. 支持合法的跨栏目迁移。
5. 支持在跨阶段迁移时给出轻确认提示。

首版明确不包含：

1. 自由像素级摆放卡片。
2. 同一张卡片的多人同时编辑。
3. 拖拽后自动改写右侧 AI 对话历史。
4. 拖拽后自动改写结构化交接物正文。
5. 卡片级复杂审批流、评论流和权限流。

### 8.4.4 原地编辑规则

首版采用轻量原地编辑，不引入完整表单式详情编辑器作为主入口。

规则如下：

1. 用户可直接点击标题进入单行编辑态。
2. 标题编辑在失焦时自动保存。
3. 用户可直接点击摘要进入多行编辑态。
4. 摘要编辑通过 `Cmd/Ctrl + Enter` 保存，通过 `Esc` 取消。
5. 单击卡片默认仍优先执行“选中卡片”，应通过双击或明确点击可编辑区域进入编辑态。
6. 进入编辑态后，该卡片临时不可拖拽，避免文本选择与拖拽冲突。
7. 首版原地编辑只覆盖标题与摘要，不要求在卡面直接编辑标签、负责人、状态、关系和来源。

### 8.4.5 排序与拖拽规则

卡片移动在产品语义上分为两类：

1. 同栏目内排序
2. 跨栏目迁移

排序与拖拽规则如下：

1. 同栏目内排序时，用户拖动卡片后松手即生效。
2. 同栏目内排序只改变显示顺序，不改变卡片类型与阶段语义。
3. 跨栏目迁移时，目标容器必须是系统定义的合法落点。
4. 拖拽过程中，合法落点应高亮提示，非法区域应弱化或拒绝响应。
5. 卡片不得长时间停留在无归属的画布空白区。
6. 关系线在卡片落位后自动重算，不要求用户手工调整。

### 8.4.6 合法迁移路径

首版允许的跨阶段迁移不是任意移动，而是有限的状态升级路径。

系统至少应支持以下典型迁移：

1. 证据卡 -> 问题卡
2. 待澄清卡 -> 约束卡
3. 待澄清卡 -> 待决策 / 方案承接卡
4. 问题卡 -> 交接物承接卡引用输入
5. 已形成稳定结果的卡片 -> 推进阶段中的后续动作承接位

同时必须满足以下约束：

1. 不允许将任意卡片自由拖入无关栏目。
2. 不允许通过一次拖拽静默改变卡片的核心语义而不给出说明。
3. 当目标模块与当前状态明显冲突时，系统应拒绝落下并保持原位。

### 8.4.7 轻确认规则

为了兼顾效率与语义准确性，首版对不同移动动作采用不同确认策略：

1. 同栏目内排序不需要额外确认。
2. 跨阶段迁移在松手后必须给出轻确认提示。
3. 轻确认文案必须明确说明这次迁移将带来的语义变化，而不是只弹出泛化的“是否确认”。

示例：

- 这张卡将从“待澄清”转为“已确认约束”
- 这张卡将从“待澄清”转为“待决策事项”

用户取消后，卡片应恢复原位置与原状态。

### 8.4.8 状态与异常展示

1. 正在编辑的卡片不得进入拖拽态。
2. 正在拖拽的卡片不得同时进入编辑态。
3. 非法落点不应先落下再报错，而应直接拒绝。
4. 跨栏目确认被取消后，卡片应回到原栏目与原排序位置。
5. 当卡片信息不完整，不影响编辑入口显示，但应保留必要的缺失提示。

### 8.4.9 验收标准

1. 用户可直接在画布上修改标题与摘要，而不必先打开详情面板。
2. 同栏目内卡片排序可稳定生效，且不会改变卡片语义。
3. 合法跨阶段迁移可被正确识别，并在确认后更新归属。
4. 非法迁移路径会被拒绝，不会破坏画布结构。
5. 编辑与拖拽不会互相抢占，用户可清楚感知当前处于哪种操作模式。


## 8.5 卡片关系

### 8.5.1 功能说明

第一版只支持少量高价值关系，避免画布变得难以理解。

产品层统一采用中文关系词：

- 来源于
- 澄清了
- 支持
- 阻塞
- 冲突于
- 产出为

### 8.5.2 关系展示要求

1. 关系线默认轻展示。
2. 选中卡片时才重点显示其直接关系。
3. 不显示复杂全图蜘蛛网关系。

### 8.5.3 验收标准

1. 用户能清楚理解关系含义。
2. 关系不会压过卡片本身成为视觉主体。

## 8.6 右侧 AI 助手

### 8.6.1 功能说明

右侧 AI 助手不是普通聊天框，而是：

`把自然语言编译成画布变化的工作入口`

同时它也承担多源输入的统一接入口，以及当前工作面的持续收敛职责。

右侧 AI 助手的核心价值不是“能聊天”，而是：

1. 吸收输入。
2. 提炼结构。
3. 暴露缺口。
4. 发起追问。
5. 生成建议。
6. 驱动画布更新。

### 8.6.2 页面布局要求

右侧 AI 助手采用常驻侧栏布局，固定在主画布右侧。

布局要求如下：

1. 右侧侧栏应始终可见，不作为临时弹窗存在。
2. 顶部展示 AI 助手标题、当前工作上下文提示和关闭/折叠入口。
3. 中部展示消息流，承载用户输入、AI 回复、变化摘要和确认请求。
4. 底部展示输入区、附件入口和快捷操作入口。
5. AI 助手宽度应固定在可阅读、可操作的范围内，不随消息长度频繁抖动。

### 8.6.3 页面字段与组件要求

| 页面区域 | 字段名称 | 组件要求 | 说明 |
| --- | --- | --- | --- |
| 顶部区 | 助手标题 | Text | 展示当前助手身份 |
| 顶部区 | 当前上下文提示 | Text / Badge | 展示当前正在处理的主题或当前里程碑进度信息 |
| 消息流 | 用户消息 | Bubble | 展示用户输入 |
| 消息流 | AI 回复 | Bubble | 展示 AI 的解释、追问、建议 |
| 消息流 | 变化摘要 | Inline Summary Card | 展示本轮新增、更新、关闭、建议确认等变化 |
| 消息流 | 确认请求 | Confirmation Card | 用于承载高影响动作确认 |
| 输入区 | 输入框 | Textarea | 支持多行自然语言输入 |
| 输入区 | 附件入口 | Icon Button | 支持导入补充材料 |
| 输入区 | 发送按钮 | Button | 提交当前输入 |
| 快捷区 | 建议动作 | Chips / Button Group | 提供总结、检查一致性、生成问题等快捷动作 |

### 8.6.4 核心能力

AI 助手首版应具备以下能力：

1. 承接多源输入。
2. 识别用户当前意图。
3. 定位应该影响的卡片或模块。
4. 生成结构化更新建议。
5. 在符合规则时自动应用低风险更新。
6. 对高影响动作请求确认。
7. 对模糊输入主动追问。
8. 输出本轮变化摘要。
9. 支持用户从消息跳回对应画布对象。
10. 对冲突信息进行显性标记并升级为待决策。

### 8.6.5 输入模式

右侧 AI 助手首版至少支持以下输入模式：

1. 直接对话输入
2. 粘贴长文本
3. 粘贴聊天摘录
4. 粘贴会议纪要片段
5. 上传截图并补充说明
6. 引用当前画布中的卡片继续讨论

输入模式要求如下：

1. 用户可以在不离开当前工作面的情况下持续补充输入。
2. 用户在讨论某张卡片时，应支持把该卡片作为当前对话上下文。
3. 输入过长时，应提示系统正在分段理解，而不是直接静默失败。

### 8.6.6 七类基础动作

第一版只允许 AI 驱动以下七类基础动作：

1. 新增卡片
2. 更新卡片
3. 改变状态
4. 建立关系
5. 标记冲突
6. 关闭问题
7. 标记进度/更新里程碑

这些动作必须可被审计、可回执、可定位到具体对象。

### 8.6.7 对话显影流程

每轮对话按以下流程执行：

1. 识别意图
2. 定位对象
3. 判断是继续追问、显性化冲突、沉淀约束、生成待决策，还是生成交接物
4. 生成更新建议
5. 应用到画布
6. 输出变化摘要

其中“识别意图”不仅适用于聊天回复，也适用于长文本导入后的后续追问。

系统应能判断输入更像：

1. 事实来源
2. 当前问题
3. 待澄清点
4. 约束补充
5. 待决策事项
6. 交接物收束

### 8.6.8 信任分级

不是所有动作都应由 AI 自动写入。

#### 自动写入

适用于低风险事实整理：

- 证据卡
- 问题卡
- 待澄清卡
- 约束卡说明补充
- 弱关系

#### 建议确认后写入

适用于高影响动作：

- 新建待决策 / 方案承接卡
- 待澄清卡改为已澄清
- 约束卡改为已生效
- 生成交接物
- 触发里程碑推进

#### 只追问，不写入

适用于输入模糊、指代不清、前后冲突或存在多种解释的情况。

### 8.6.9 确认请求规则

当 AI 识别到高影响动作时，应以确认请求卡形式提示用户，而不是静默写入。

确认请求至少需要包含：

1. 本轮建议动作类型
2. 将影响哪些卡片
3. 建议结果摘要
4. 确认 / 取消入口

例如：

- 建议生成一张待决策 / 方案承接卡
- 建议关闭 2 个待澄清问题
- 建议将某条约束标记为已生效
- 建议生成一张结构化交接物
- 建议推进或更新当前里程碑进度

### 8.6.10 追问规则

当输入不清晰时，AI 应优先追问，而不是强行落图。

至少以下情况需要优先追问：

1. 指代不清
2. 前后冲突
3. 约束存在多种解释
4. 决策表达不完整
5. 输入更像情绪判断而非业务判断

追问应尽量具体，并指向当前缺少的信息，而不是泛泛地要求“补充更多背景”。

### 8.6.10A 协作协议

为了让 AI 更像“产品同事”而不是“会整理卡片的聊天框”，首版必须遵守以下协作协议：

1. 优先级顺序固定为：`先暴露不确定性 -> 再沉淀约束 -> 再形成待决策 -> 最后生成交接物`。
2. 当用户的一句话同时可以被理解为“约束”或“结论”时，默认先视为待确认约束，而不是直接视为稳定结论。
3. 当来源信息之间冲突时，AI 不得私下选择其一，必须显性标记冲突并要求用户裁决或补充背景。
4. 任何进入“已生效”或“已确认”状态的内容，都必须能追溯到具体来源、确认方式或用户裁决记录。
5. 交接物生成前，AI 必须显式说明当前仍未解决的关键缺口，不能伪装成“已经完整收敛”。

### 8.6.11 对话回执

AI 每次更新画布后，应给出本轮变化摘要，例如：

- 新增了 2 张待澄清卡
- 更新了 1 张约束卡
- 关闭了 1 个待澄清问题
- 标记了 1 组冲突信息
- 有 1 条待决策建议等待确认

变化摘要至少应包括：

1. 新增了什么
2. 更新了什么
3. 关闭了什么
4. 是否有待确认动作

### 8.6.12 关键交互

1. 用户可直接输入自然语言驱动画布更新。
2. 用户可引用当前卡片继续讨论。
3. 用户可在消息中确认或拒绝高影响动作。
4. 用户可点击变化摘要跳转到相关卡片。
5. 用户可通过快捷动作触发总结、检查一致性、生成问题等操作。

### 8.6.13 状态与异常展示

1. 当 AI 正在处理中时，应展示处理中状态，而不是让输入区无反馈。
2. 当 AI 无法理解用户输入时，应明确提示并给出继续操作建议。
3. 当某次更新动作失败时，应展示失败原因，并尽量保留已成功的部分动作。
4. 当高影响动作等待确认时，应在消息流中持续可见，直到用户处理。
5. 当某次消息只产生追问而未更新画布时，应明确说明“当前未对画布做变更”。

### 8.6.14 验收标准

1. AI 可对低风险动作自动显影。
2. AI 在高影响动作前可进行确认。
3. AI 在模糊输入时会优先追问，而不是强行落图。
4. 用户可从消息和变化摘要跳回相关卡片。
5. AI 助手在整个工作流中是持续性的工作入口，而不是一次性导入工具。
6. AI 在不同轮次中会优先遵守“先暴露不确定性，再推进已确认结构”的协作规则。

## 8.7 系统挂件：活跃缺口（Active Todos）

### 8.7.1 功能说明

`Active Todos` 是一个系统挂件，不是任务管理列表，也不是独立事实源。

它表达的是：

`当前还没有收敛、并且正在影响产品经理继续推进的认知缺口面板`

它的目标不是替代任务系统，而是帮助产品经理快速识别：

1. 当前最值得优先处理的问题是什么。
2. 哪些缺口正在阻塞方案继续收束。
3. 哪些动作已经清楚，但还没有被推进完成。

### 8.7.2 页面布局要求

Active Todos 采用右上角常驻悬浮挂件布局。

布局要求如下：

1. 挂件默认常驻可见，但支持折叠、pin / unpin 与画布内漂移。
2. 钉住状态下固定在工作台右上角；取消钉住后可作为漂移挂件自由移动。
3. 面板标题区展示当前 Todo 总数。
4. 面板主体区按条目列表展示当前活跃 Todo。
5. 条目数过多时，应支持滚动查看。
6. 面板不承担复杂编辑功能，重点在于快速浏览、定位和处理。

### 8.7.3 来源

第一版只从以下对象投影生成：

- 待澄清卡
- 待决策 / 方案承接卡
- 少量待确认约束卡

只有满足以下条件之一的对象才进入 Active Todos：

1. 阻塞后续推进
2. 需要 PM 明确拍板
3. 需要找别人确认
4. 已形成明确动作但还未完成

### 8.7.4 Todo 类型

产品上分为三类：

- 待澄清
- 待决策
- 待定义

类型含义如下：

#### 待澄清

表示当前还有问题没有讲清楚，需要继续问清。

#### 待定义

表示方向已经大致明确，但规则、字段、口径或范围还未落定。

#### 待决策

表示信息已收敛到需要 PM 拍板，但当前尚未做出最终判断。

### 8.7.5 页面字段与组件要求

| 字段名称 | 组件要求 | 说明 |
| --- | --- | --- |
| 标题 | 文本 | Todo 一句话标题 |
| 类型 | Badge | 待澄清 / 待定义 / 待决策 |
| 优先级 | Badge | 高 / 中 / 低 |
| 来源栏目 | 文本 | 来自哪个栏目 |
| 阻塞状态 | Icon + 文本 | 是否阻塞其他卡片推进 |
| 源卡引用 | Jump Link / Icon | 点击后跳回源卡 |

### 8.7.6 优先级规则

首版优先级分为：

- 高
- 中
- 低

优先级计算应至少参考以下因素：

1. 是否阻塞后续推进
2. 是否影响当前已确认约束或交接物
3. 是否影响当前主题能否对外继续推进
4. 是否被用户手动标记为重要

### 8.7.7 关键交互

1. 点击 Todo 后可定位到源卡。
2. 用户可在聊天中直接处理该 Todo。
3. Todo 完成后，应同步更新源卡状态。
4. 用户可快速识别当前哪些 Todo 属于“必须先处理”的内容。

### 8.7.8 状态与异常展示

1. 当没有活跃 Todo 时，应展示轻量空状态，例如“当前没有活跃缺口”。
2. 当源卡被删除、归档或状态异常时，Todo 应同步失效，不得悬空保留。
3. 当 Todo 与当前里程碑节点不一致时，应以当前里程碑进度投影视图为准。
4. 当同一缺口被重复投影时，应支持合并而不是重复展示。
5. 挂件的折叠、拖动和 pin 状态只影响展示方式，不应改变底层 Todo 投影结果。

### 8.7.9 验收标准

1. Todo 面板只展示活跃缺口。
2. 每条 Todo 均可定位回源卡。
3. Todo 不是独立事实源。
4. Todo 类型和优先级可帮助用户快速判断先处理什么。

## 8.8 系统挂件：项目时间轴

### 8.8.1 功能说明

当前前端中的项目时间轴是一个系统挂件，用于展示当前主题在推进感知上的大致位置。

它承载的是辅助性的推进提示，帮助产品经理理解“当前大致推进到哪里了”，而不是复杂的历史进度版本回放或甘特图式任务管理。

在术语上，项目时间轴延续“轻量里程碑条”的语义，但在工作台表达上统一归入系统挂件体系。

### 8.8.2 页面布局要求

项目时间轴默认以工作台左下角常驻挂件呈现；取消钉住后，可在画布中作为漂移挂件自由摆放。

布局要求如下：

1. 挂件在视觉上应清晰独立，以轻量横条和节点提示组成。
2. 挂件支持折叠、pin / unpin 与画布内漂移，不应与主画布拖拽产生冲突。
3. 组件上可展示示意性的阶段标签与节点（如：阶段定义、内测发布、MVP 上线）。
4. 可使用垂直指示线和提示标签标识“当前进度点”。
5. 它应强调“辅助定位”，不应被用户误解为完整项目排期视图。

### 8.8.3 里程碑定位

它用于查看：

1. 当前主题大致推进到了哪一个阶段。
2. 当前工作区距离下一个交付节点还差哪些关键缺口。

该组件不用于：

1. 复杂的历史认知版本回溯与回放。
2. 细粒度到人的开发工时排期与甘特图。
3. 替代外部专业的项目管理系统。

### 8.8.4 里程碑定义

当前前端中的里程碑条以演示性节点为主，用于表达工作区推进感，而不是精确项目计划：

1. 可包含阶段节点名称（如“内测发布”“MVP 上线”）。
2. 可辅助提醒当前阶段应重点收敛什么。
3. 可带有示意性时间段标注，但不要求严谨排期语义。

### 8.8.5 里程碑更新

当前 1.0 中，里程碑条以展示当前位置为主，不要求形成严格自动推进机制。

若后续保留该能力，可参考以下更新来源：

1. 当前主题完成关键澄清与约束沉淀。
2. 用户手动标记当前推进位置。
3. 结构化交接物达到可继续推进状态。

### 8.8.6 核心交互

1. 用户可查看当前里程碑节点与当前位置提示。
2. 用户可折叠、pin / unpin 或拖动该挂件，以适配当前工作习惯。
3. 前端可通过高亮节点或当前位置表达当前推进位置。
4. 首版不要求历史日志折叠、精确时间回放或完整项目计划编辑能力。
5. 用户可通过组件本体头部完成 pin、折叠、关闭和拖动等运行态操作。

### 8.8.7 验收标准

1. 项目时间轴视觉表现轻量、规整，不干扰主画布操作。
2. 用户可快速了解当前大致推进阶段及所面临的缺口。
3. 该组件不会被误解为完整项目管理视图。

### 8.8.8 个人挂件预留

除系统挂件外，EvoCanvas 1.0 为个人挂件保留正式产品定义，但不纳入首版必须验收项。

当前预留的个人挂件方向包括：

1. 便签
2. 停车区（Parking Lot）
3. 时钟
4. 专注计时器

个人挂件统一遵循以下规则：

1. 可自由移动、折叠、关闭和 pin。
2. 默认不参与卡片关系计算，也不自动写入结构化交接物。
3. 1.0 不要求个人挂件内容进入正式推进链路。
4. 个人挂件表达的是工作习惯和临时辅助，不表达稳定产品结论。
5. 个人挂件的添加入口统一放在底部工具栏，但添加后的运行态控制仍由组件本体负责。

### 8.8.9 挂件面板

#### 8.8.9.1 功能说明

挂件面板是底部工具栏触发的轻量添加面板。

它的职责只有一个：

`把挂件添加到当前画布`

它不是组件管理后台，也不是挂件运行态控制面板。

#### 8.8.9.2 页面结构要求

1. 挂件面板由底部工具栏中的挂件入口按钮触发。
2. 面板以轻量浮层形式出现在底部工具栏上方。
3. 面板不要求搜索框、Tab 分类或筛选器。
4. 面板主体直接展示当前可添加挂件列表。

#### 8.8.9.3 列表项字段与组件要求

每个挂件项至少展示：

| 字段名称 | 组件要求 | 说明 |
| --- | --- | --- |
| 图标 | Icon | 挂件识别图标 |
| 名称 | Text | 挂件名称 |
| 一句话说明 | Secondary Text | 说明该挂件解决什么问题 |
| 添加按钮 | Primary / Secondary Button | 将挂件加入当前画布 |

当前 1.0 面板中可出现的挂件项包括：

1. 项目时间轴
2. 活跃缺口
3. 便签
4. 停车区
5. 时钟
6. 专注计时器

#### 8.8.9.4 添加后的默认行为

1. 用户点击添加后，对应挂件应立即出现在当前画布中。
2. 系统挂件优先落到其默认锚点位置。
3. 个人挂件优先落到当前视口附近的非主焦点区域，避免遮挡核心卡片。
4. 新添加挂件可有轻量出现反馈，但不应打断当前工作流。

#### 8.8.9.5 不包含范围

挂件面板在 1.0 中不包含以下能力：

1. 搜索
2. Tab 分类
3. 状态标签，例如“已显示”“已钉住”“已隐藏”
4. pin / unpin
5. 折叠 / 关闭
6. 一键整理布局

这些能力若需要存在，应放在组件本体上，而不是放在挂件面板里。

#### 8.8.9.6 验收标准

1. 用户可通过底部工具栏进入挂件面板。
2. 用户可从面板中直接添加挂件。
3. 用户不会把挂件面板误解为运行态管理面板。

## 9. 数据结构与计算口径

### 9.1 卡片基础结构

每张卡片至少包含以下基础字段：

| 字段名称 | 说明 |
| --- | --- |
| 卡片 ID | 全局唯一标识 |
| 卡片类型 | evidence / problem / clarification / constraint / decision-or-option / handoff |
| 标题 | 当前卡片标题 |
| 摘要 | 卡片的一句话或短文本摘要 |
| 状态 | 当前状态 |
| 标签 | 辅助分类标签 |
| 主归属栏目 | 当前主要所在栏目 |
| 来源引用 | 指向输入来源或来源卡片 |
| 关系引用 | 指向关联卡片关系 |
| 里程碑标记 | 该卡在哪些里程碑节点中活跃 |
| 更新时间 | 最近更新时间 |

### 9.2 卡片类型字段口径

不同卡片在基础字段之外应具备类型化扩展字段。

#### 证据卡扩展字段

1. 来源类型
2. 原始摘录
3. 输入时间
4. 引用数量
5. 冲突标记

#### 问题卡扩展字段

1. 目标用户
2. 核心痛点
3. 当前业务目标
4. 关联待澄清数

#### 待澄清卡扩展字段

1. 优先级
2. 阻塞范围
3. 建议追问对象
4. 澄清结果引用

#### 约束卡扩展字段

1. 约束类型
2. 适用范围
3. 例外说明
4. 确认方式
5. 冲突标记

#### 待决策 / 方案承接卡扩展字段

1. 决策类型或方案类型
2. 备选解释或建议方案
3. 影响范围
4. 决策结果引用

#### 交接物承接内容扩展字段

1. 当前目标
2. 已确认约束列表
3. 已完成决策列表
4. 未解决问题列表
5. 推荐后续动作

### 9.3 关系结构口径

首版支持的关系类型包括：

1. 来源于
2. 澄清了
3. 支持
4. 阻塞
5. 冲突于
6. 产出为

每条关系至少记录：

1. 关系 ID
2. 起点卡片 ID
3. 终点卡片 ID
4. 关系类型
5. 创建时间
6. 是否当前有效

### 9.4 挂件基础口径

工作台挂件不是统一业务事实模型，但至少应具备以下展示与状态字段：

1. 挂件 ID
2. 挂件类型（系统挂件 / 个人挂件）
3. 挂件子类型（如活跃缺口、项目时间轴、便签）
4. 当前展示状态（钉住 / 漂移 / 折叠 / 关闭）
5. 默认锚点位置
6. 漂移坐标
7. 关联源对象引用
8. 最近更新时间

当前 1.0 首版必须落地的系统挂件包括：

1. 活跃缺口（Active Todos）
2. 项目时间轴

### 9.5 活跃缺口系统挂件计算口径

Active Todos 不是独立事实源，而是由当前活跃卡片投影生成。

只有满足以下条件之一的对象才进入 Active Todos：

1. 阻塞后续推进
2. 需要 PM 明确拍板
3. 需要找别人确认
4. 已形成明确动作但还未完成

投影来源仅限：

1. 待澄清卡
2. 待决策 / 方案承接卡
3. 少量待确认约束卡

### 9.6 Todo 优先级计算口径

Todo 优先级至少参考以下因素：

1. 是否阻塞后续推进
2. 是否影响当前已确认约束或交接物
3. 是否影响当前主题能否对外继续推进
4. 是否被用户手动标记为重要

首版优先级只分为：

- 高
- 中
- 低

### 9.7 项目时间轴数据口径

每个里程碑提示节点至少可关联：

1. 当前节点对应的推进目标
2. 当前阶段关注的核心卡片集合
3. 阻塞当前推进的活跃缺口列表
4. 当前已沉淀的规则与决策

### 9.8 项目时间轴更新口径

当前前端中的项目时间轴以当前位置提示为主，不要求严格的数据驱动推进。

若后续保留更新能力，可参考以下触发来源：

1. 当前主题建立了关键卡片结构
2. 阻塞性问题被关闭或澄清
3. 用户手动标记当前位置
4. 形成可继续推进的结构化交接物

以下情况不应单独推动里程碑提示变化：

1. 卡片的常规文字微调
2. 常规画布拖拽与排布整理
3. 纯视觉样式变更

### 9.9 AI 变更集口径

AI 不直接输出整张画布，而应输出结构化变更集。

首版允许的变更集类型包括：

1. 新增卡片
2. 更新卡片字段
3. 修改卡片状态
4. 新增关系
5. 标记冲突
6. 关闭问题
7. 标记当前进度/更新里程碑

### 9.10 结构化交接物口径

结构化交接物是 EvoCanvas 1.0 首版最重要的对外交付对象，不等价于 PRD，也不等价于完整 machine spec。

每份交接物至少必须包含：

1. 当前主题与目标
2. 背景输入摘要
3. 已确认约束
4. 已完成决策
5. 仍未解决的问题
6. 推荐后续动作
7. 关联当前里程碑和关键来源引用

结构化交接物必须满足：

1. 可被人类快速理解并继续推进
2. 可被新的 AI 会话作为继续输入使用
3. 若底层约束或决策变化，应可被识别为已过时

每条变更至少应包含：

1. 变更类型
2. 目标对象
3. 变更内容摘要
4. 是否需确认
5. 变更结果状态

## 10. 状态、权限与异常规则

### 10.1 通用状态

所有卡片共享五个顶层状态：

- 草稿中
- 待确认
- 生效中
- 已阻塞
- 已归档

通用状态解释如下：

#### 草稿中

表示该对象已被识别或创建，但当前仍处于形成过程，不应作为稳定依据参与后续判断。

#### 待确认

表示该对象已经具备足够信息，但仍需要产品经理明确确认。

#### 生效中

表示该对象当前有效，可作为后续方案、结论或推进的依据。

#### 已阻塞

表示该对象当前无法继续推进，通常依赖其他问题或结论先解决。

#### 已归档

表示该对象不再处于活跃工作流中，但应保留历史记录。

### 10.2 类型化状态

#### 证据卡

- 已收录
- 已引用
- 已归档

#### 问题卡

- 初步理解
- 待收敛
- 已收敛
- 已归档

#### 待澄清卡

- 待提出
- 待确认
- 已澄清
- 已阻塞
- 已关闭

#### 约束卡

- 草稿中
- 待确认
- 已生效
- 已替代
- 已归档

#### 待决策 / 方案承接卡

- 待判断
- 待确认
- 已决定
- 已归档

#### 交接物承接卡

- 草稿中
- 待确认
- 已确认
- 已过时

### 10.3 状态流转规则

#### 待澄清卡

可接受的主要流转包括：

1. 待提出 -> 待确认
2. 待确认 -> 已澄清
3. 待确认 -> 已阻塞
4. 待确认 -> 已关闭

#### 约束卡

可接受的主要流转包括：

1. 草稿中 -> 待确认
2. 待确认 -> 已生效
3. 已生效 -> 已替代

#### 待决策 / 方案承接卡

可接受的主要流转包括：

1. 待判断 -> 待确认
2. 待确认 -> 已决定
3. 已决定 -> 已归档

#### 交接物承接卡

可接受的主要流转包括：

1. 草稿中 -> 待确认
2. 待确认 -> 已确认
3. 已确认 -> 已过时

### 10.4 权限规则

1. 首版默认单人工作台，不区分多人编辑权限。
2. 当前用户拥有所有画布内操作权限。
3. AI 仅通过受控动作修改画布，不可绕过确认规则。
4. 高影响动作必须经过用户确认后才可生效。

### 10.5 AI 动作权限规则与确认提案

AI 可自动执行的动作包括：

1. 新增证据卡
2. 新增问题卡
3. 新增待澄清卡
4. 更新约束说明补充
5. 建立弱关系
6. 标记冲突

AI 不可直接自动生效的动作包括：

1. 新建待决策 / 方案承接内容
2. 将约束卡改为已生效
3. 关闭关键待澄清问题
4. 生成或刷新交接物承接结果
5. 调整高影响推进状态

对于这些高影响动作，当前前端应通过确认提案队列承载，用户批准 / 拒绝后再落盘。

### 10.6 异常规则

1. 输入编译失败时，原输入必须保留。
2. 高影响动作未确认时，不允许直接落图。
3. 里程碑进度更新失败时，不应影响当前画布状态。
4. 卡片关系解析失败时，应保底展示卡片本体。
5. AI 无法理解输入时，应优先追问，不得生成高影响结构。
6. Todo 投影异常时，应回退到源卡视角，而不是保留失效 Todo。

## 11. 验收标准汇总

### 11.1 输入与显影

1. 用户导入任一受支持输入后，系统可以在合理时间内初始化画布。
2. 初始化结果至少包含证据卡、问题卡和待澄清卡。
3. 初始化结果若存在冲突或缺失，应显式生成冲突标记或待澄清对象，而不是静默忽略。
4. 用户可在右侧对话中继续补充信息并驱动画布更新。

### 11.2 输入类型覆盖

系统首版至少支持以下输入被编译进同一工作面：

1. 会议纪要
2. 自然语言想法
3. 聊天摘录
4. 用户反馈列表
5. 数据结论说明
6. 文档片段

### 11.3 画布结构

1. 画布采用连续结构，不出现被硬边框切碎的主区域。
2. 当前主要栏目可被清晰识别。
3. 同类卡片在视觉和布局上保持聚类一致性。

### 11.4 活跃缺口挂件

1. Todo 面板只展示当前活跃缺口。
2. 每条 Todo 均可定位回源卡。
3. Todo 处理完成后，源卡状态同步更新。

### 11.5 结构化交接物

1. 当关键待澄清项已收敛、关键约束已确认、必要决策已完成时，系统可生成结构化交接物。
2. 交接物必须包含目标、背景、已确认约束、已完成决策、未决问题、轻量建议方案和推荐后续动作。
3. 当前前端默认将其作为只读派生结果展示。
4. 交接物可被不同会话或不同 AI 作为继续推进输入使用。

### 11.6 项目时间轴

1. 用户可查看项目时间轴提供的推进位置提示。
2. 前端可通过高亮节点或当前位置提示表达当前推进位置。
3. 该组件不会替代主画布结构，也不承担完整项目管理职责。

### 11.7 AI 协作

1. AI 可自动处理低风险结构化整理。
2. AI 在高影响动作前会给出确认建议。
3. AI 在输入不清晰时优先追问，而不是强行落图。
4. AI 在存在冲突时优先显性化冲突，而不是私下合并。
5. AI 在首版流程中优先产出待澄清、约束和待决策，而不是过早产出最终结论。

### 11.8 核心命题验证

1. 对同一主题，在不同会话中根据同一份结构化交接物继续推进时，核心约束和待决策识别结果应保持稳定，不因表达顺序变化而大幅漂移。
2. 与“纯聊天记录继续推进”相比，使用 EvoCanvas 结构化交接物继续推进时，需求漏点和歧义应显著减少。

## 12. 非功能性需求

1. 主画布应保持视觉克制，避免白板式视觉混乱。
2. 卡片密度要支持产品经理长时间浏览，不应被长文挤满。
3. 关键操作需要可回退，尤其是结论替代和问题关闭。
4. 轻量里程碑提示展示应快速、稳定，不造成明显页面阻塞。
5. AI 更新应尽量采用增量变更，避免整图重绘。

## 13. 术语表

| 术语 | 定义 |
| --- | --- |
| 输入编译台 | 把不同来源输入编译到同一张画布上的统一入口能力 |
| 栏目簇 | 主画布上的语义分组层，当前以前端六栏目结构为准 |
| 卡片 | 进入正式对象层、参与关系和结构化交接物的业务对象 |
| 系统挂件 | 由系统投影出的辅助视图，例如活跃缺口与项目时间轴 |
| 个人挂件 | 服务个人思考和操作便利的工作台工具，默认不进入正式对象层 |
| 证据卡 | 事实输入的结构化投影 |
| 待澄清卡 | 当前尚未收敛、需要追问或确认的问题卡 |
| Active Todos | 系统挂件之一，当前还没有收敛、并且正在影响推进的缺口投影视图 |
| 项目时间轴 | 系统挂件之一，用于表达当前主题推进位置的时间轴挂件 |
| 轻量里程碑条 | 项目时间轴在里程碑语义上的旧称，当前统一归入系统挂件体系 |
