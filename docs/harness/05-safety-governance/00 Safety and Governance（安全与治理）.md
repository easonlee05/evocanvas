# Safety and Governance（安全与治理）

> 当前成熟度层级：`L3 可指导实现的治理规格层`
> 编码门槛：`可作为 1.0 状态、权限、确认与异常规则的实现输入；具体接口仍需在后端模型中落字段`

## 1. 分组目的

本组同时放置安全（safety）和治理（governance），但二者不是同一概念。

- 安全（safety）回答：系统如何避免危险、越权、误导和过早收敛。
- 治理（governance）回答：系统如何决定什么内容可以生效、谁能确认、如何回退和追溯。

在 EvoCanvas 1.0 的 `Vibe Shaping` 语境里，最大的风险不是 AI 写得不够像文档，而是 AI 把尚未成形的感觉过早固化成结论，把冲突和缺口包装成“已经想清楚”。

因此，本组文档的核心职责是：让 AI 可以大胆帮助用户整理和推进，但不能绕过事实边界、确认规则和可追溯状态。

## 2. 安全与治理的分界

[Safety（安全）](./01%20Safety%EF%BC%88%E5%AE%89%E5%85%A8%EF%BC%89.md) 偏运行防护，关注“这一步会不会造成误导或越权”。它可以让动作停下来、降级为草稿、转为追问，或要求生成确认请求。

[Governance（治理）](./02%20Governance%EF%BC%88%E6%B2%BB%E7%90%86%EF%BC%89.md) 偏状态生效，关注“这个对象现在是否可以作为后续依据”。它决定候选内容能否进入待确认、生效中、已决定、已确认交接等状态。

简单说：

- 安全负责防止系统做错危险动作。
- 治理负责防止系统把未成立内容当成已成立事实。
- 高影响动作必须同时经过安全判断和治理确认。

## 3. 与产品主链的关系

EvoCanvas 1.0 的最小闭环是：

```md
输入编译 -> 待澄清问题 -> 约束 / 待决策 -> 结构化交接物
```

安全与治理贯穿这条闭环：

- 输入编译阶段：保留来源，不把解释混入证据。
- 待澄清阶段：把缺口显性化，不静默补全。
- 约束 / 待决策阶段：区分“边界已经成立”和“需要用户拍板”。
- 结构化交接阶段：显式带出已确认、未解决和待确认内容。

## 5. 两条底线

第一，AI 有建议权和整理权，但没有天然生效权。

第二，画布上看起来完整，不等于事实已经成立；只有来源、状态、确认方式和回执都能对上，内容才可以成为后续交接或下游 AI 的依据。
