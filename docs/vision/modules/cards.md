## 2. 模块定位

卡片模块是 EvoCanvas 1.0 的正式结构化状态投影层。

卡片不是文档章节，也不是纯视觉容器。前五类卡片投影产品经理与 AI 共同维护的结构化业务对象；交接物承接卡投影结构化包版本及其交接模块。

卡片的模块边界如下：

1. 业务卡片参与栏目归属、关系计算和类型化状态流转；交接物承接卡展示包版本的交接内容和治理状态。
2. 卡片是系统挂件的上游事实来源。
3. 卡片可以被 pin，但这里的 pin 指优先保留在当前可见区域或栏目顶部。
4. 卡片不承担时钟、便签、停车区、计时器等个人工作台挂件角色。

## 3. 模块目标

卡片模块要解决的是“多源输入如何被稳定收敛为可推进对象”，而不是“如何把内容堆成文档”。

模块目标包括：

1. 把不同来源输入沉淀为统一对象层，并通过结构化包版本组织交接视图。
2. 让用户快速区分事实、问题、缺口、约束、待决策和交接物。
3. 让 AI 能稳定生成和更新对象，而不是只输出长文本。
4. 让对象之间形成可追溯的推进链路。

---

## 4. 模块范围

### 4.1 1.0 首版核心卡片

1. 证据卡
2. 问题卡
3. 待澄清卡
4. 约束卡
5. 待决策 / 方案承接卡
6. 交接物承接卡

前五类卡片投影独立业务对象；交接物承接卡投影同一主题的结构化包版本与交接模块，不另存一份独立正文或状态。

### 4.2 后续版本扩展卡片

1. 方案卡
2. 结论卡
3. 推进项

### 4.3 不在本模块范围

1. 多人实时编辑同一卡片。
2. 把卡片当成自由白板元素任意漂浮。
3. 把个人挂件自动升级为卡片。
4. 把卡片直接等同于任务系统条目。

## 5. 通用卡片结构

### 5.1 功能说明

所有卡片都应共享统一基础结构，以保证：

1. 用户的扫描体验稳定。
2. AI 的写入格式稳定。
3. 不同卡片可以在同一工作面中协同存在。

### 5.2 通用卡面字段

| 字段名称 | 说明 |
| --- | --- |
| 卡片 ID | 全局唯一标识 |
| 卡片类型 | evidence / problem / clarification / constraint / decision-or-option / handoff |
| 标题 | 当前卡片标题 |
| 摘要 | 一句话或短文本摘要 |
| 状态 | 当前状态 |
| 标签 | 辅助分类标签 |
| 主归属栏目 | 当前主要所在栏目 |
| 来源引用 | 指向输入来源或来源卡片 |
| 关系引用 | 指向关联卡片 |
| 更新时间 | 最近更新时间 |

### 5.3 通用展示规则

1. 标题默认单行展示，超出省略。
2. 摘要默认展示 2 行，超出折叠。
3. 状态必须显式展示，不允许只埋在正文里。
4. 卡面不展示长段落正文，完整内容进入详情面板。

### 5.4 卡片详情面板要求

任一卡片点开后，应能查看：

1. 完整标题
2. 完整摘要
3. 当前状态
4. 来源引用
5. 关联卡片
6. 历史变更摘要
7. 可执行操作

## 6. 卡片类型要求

### 6.1 证据卡

#### 6.1.1 功能说明

证据卡用于承接会议纪要、聊天、截图、访谈、反馈、竞品资料和文档片段等输入来源。

它表达的是事实输入的结构化投影，不代表正式结论。

#### 6.1.2 页面字段与组件要求

| 字段名称 | 组件要求 | 说明 |
| --- | --- | --- |
| 标题 | 文本 | 证据来源标题或 AI 提炼标题 |
| 摘要 | 多行文本 | 证据核心内容提炼 |
| 来源类型 | Tag | 会议纪要 / 聊天 / 截图 / 反馈 / 竞品 / 文档 |
| 引用数量 | Badge | 被多少卡片引用 |
| 更新时间 | Text | 最近整理时间 |

#### 6.1.3 关键交互

1. 用户可查看原文与提炼摘要。
2. 用户可修订证据摘要。
3. 用户可把证据卡绑定到问题卡、约束卡或待决策卡。

#### 6.1.4 验收标准

1. 用户能看清证据来源类型。
2. 证据卡可作为其他卡片的来源支撑。

### 6.2 问题卡

#### 6.2.1 功能说明

问题卡用于表达当前对问题的理解，包括业务问题、用户对象、痛点和目标方向。

#### 6.2.2 页面字段与组件要求

| 字段名称 | 组件要求 | 说明 |
| --- | --- | --- |
| 标题 | 文本 | 当前问题名称 |
| 摘要 | 多行文本 | 当前问题简述 |
| 成熟度 | Tag | 初步理解 / 待收敛 / 已收敛 |
| 关联待澄清数 | Badge | 与问题相关的缺口数量 |
| 更新时间 | Text | 最近更新时间 |

#### 6.2.3 关键交互

1. 用户可编辑问题定义。
2. 用户可将证据卡归并到问题卡下。
3. 用户可从问题卡生成待澄清卡、约束卡或待决策卡。

#### 6.2.4 验收标准

1. 用户能从问题卡理解当前问题核心。
2. 问题卡可关联证据、待澄清、约束和待决策。

### 6.3 待澄清卡

#### 6.3.1 功能说明

待澄清卡用于暴露术语冲突、规则未定、边界不清、风险未决和必须补问的信息。

它是 Active Todos 的主来源，也是 1.0 首版最重要的显性对象。

#### 6.3.2 页面字段与组件要求

| 字段名称 | 组件要求 | 说明 |
| --- | --- | --- |
| 标题 | 文本 | 待澄清问题名称 |
| 摘要 | 多行文本 | 为什么需要澄清 |
| 优先级 | Badge | 高 / 中 / 低 |
| 阻塞范围 | Tag | 约束 / 决策 / 交接 |
| 当前状态 | Tag | 待提出 / 待确认 / 已澄清 / 已阻塞 / 已关闭 |

#### 6.3.3 关键交互

1. 用户可确认是否将其纳入当前活跃缺口。
2. 用户可在 AI 对话中直接回答该问题。
3. 用户确认后可关闭、阻塞或转化为约束 / 待决策项。

#### 6.3.4 验收标准

1. 待澄清卡可清晰表达当前缺口。
2. 待澄清卡可被活跃缺口挂件正确投影。

### 6.4 约束卡

#### 6.4.1 功能说明

约束卡用于沉淀术语、字段、状态、权限、流程和边界定义。

它是 1.0 首版最重要的稳定对象之一，因为首版要先验证“边界是否被钉住”。

#### 6.4.2 页面字段与组件要求

| 字段名称 | 组件要求 | 说明 |
| --- | --- | --- |
| 标题 | 文本 | 约束标题 |
| 摘要 | 多行文本 | 约束的一句话说明 |
| 约束类型 | Tag | 术语 / 字段 / 状态 / 权限 / 流程 / 边界 |
| 当前状态 | Tag | 草稿中 / 待确认 / 已生效 / 已替代 / 已归档 |
| 影响范围 | Text / Tag | 约束作用范围 |

#### 6.4.3 关键交互

1. 用户可修改约束文本。
2. 用户可确认约束生效。
3. 用户可将旧约束替代为新约束。
4. 用户可将冲突约束标记为待决策输入。

#### 6.4.4 验收标准

1. 用户可区分草稿约束和已生效约束。
2. 约束卡可作为结构化交接物的支持依据。

### 6.5 待决策 / 方案承接卡

#### 6.5.1 功能说明

待决策 / 方案承接卡用于表达“不是信息不足，而是必须明确拍板”的事项。

#### 6.5.2 页面字段与组件要求

| 字段名称 | 组件要求 | 说明 |
| --- | --- | --- |
| 标题 | 文本 | 当前决策主题 |
| 摘要 | 多行文本 | 为什么需要拍板 |
| 决策类型 | Tag | 口径 / 方向 / 边界 / 优先级 / 例外 |
| 当前状态 | Tag | 待判断 / 待确认 / 已决定 / 已归档 |
| 影响范围 | Text / Tag | 受影响对象 |

#### 6.5.3 关键交互

1. 用户可明确选择决策结果。
2. 用户可拒绝当前建议并保持待决策状态。
3. 用户确认后，相关约束和待澄清同步更新。

#### 6.5.4 验收标准

1. 用户能区分“还没问清楚”和“必须拍板”。
2. 待决策卡可回指待澄清、约束和冲突信息。

### 6.6 交接物承接卡

#### 6.6.1 功能说明

交接物承接卡用于承接当前主题的结构化产品上下文，是对外继续推进的最小交接单元。

卡面内容和状态由对应结构化包版本及状态账本确定性投影，不作为第六类可独立修改的业务对象。

#### 6.6.2 页面字段与组件要求

| 字段名称 | 组件要求 | 说明 |
| --- | --- | --- |
| 标题 | 文本 | 当前交接主题 |
| 摘要 | 多行文本 | 当前已收敛出的可执行上下文摘要 |
| 当前状态 | Tag | 草稿中 / 待确认 / 已确认 / 已过时 |
| 覆盖范围 | Text / Tag | 覆盖的问题、约束和决策 |
| 未决数 | Badge | 当前仍未解决的缺口数量 |

#### 6.6.3 关键交互

1. 系统可在收敛命中后生成或刷新交接草稿，用户也可显式请求生成。
2. 用户可确认交接物进入可使用状态。
3. 用户可从交接物回跳到原始约束、待澄清和待决策对象。

#### 6.6.4 验收标准

1. 交接物承接卡能汇总当前主题的核心背景、约束、决策和未决问题。
2. 交接物承接卡可作为新 AI 会话继续输入使用。

## 7. 卡片关系

### 7.1 功能说明

卡片关系用于帮助用户理解对象之间的支持、来源和阻塞链路。

### 7.2 首版支持的关系类型

1. 来源于
2. 澄清了
3. 支持
4. 阻塞
5. 冲突于
6. 产出为

### 7.3 展示原则

1. 关系线是辅助信息，不压过卡片本身。
2. 默认只展示轻量关系提示。
3. 选中卡片时，高亮其直接关系。

### 7.4 验收标准

1. 关系类型可被清晰区分。
2. 用户可从关系理解推进链路。

## 8. 卡片手动修订与迁移

### 8.1 功能说明

卡片不是静态展示物，而是产品经理接管 AI 初稿、修正认知结构的最小操作对象。

### 8.2 首版必须支持的操作

1. 编辑标题和摘要
2. 调整状态
3. pin / unpin
4. 合并重复卡片
5. 手动新增卡片
6. 移动卡片到其他栏目
7. 绑定证据或外部链接
8. 触发交接物生成或更新
9. 标记冲突或待裁决状态

### 8.3 迁移原则

1. 用户拖动卡片时，应优先吸附到最近合法栏目。
2. 首版不允许卡片脱离栏目长时间悬浮在无归属区域。
3. 高影响迁移可触发轻确认。

### 8.4 与挂件的边界

1. 卡片的 pin 不等同于挂件的悬浮钉住。
2. 卡片不能以自由漂移状态替代工作台挂件。
3. 个人挂件内容进入卡片层，必须通过显式转换动作。

## 9. 状态与异常规则

### 9.1 状态要求

卡片状态必须显式可见，并与类型约束一致。

首版主要状态流转要求如下：

1. 证据卡以整理与引用状态为主，不进入“已生效”语义。
2. 问题卡应支持从“初步理解”逐步收敛到“已收敛”。
3. 待澄清卡应支持“待提出 -> 待确认 -> 已澄清 / 已阻塞 / 已关闭”。
4. 约束卡应支持“草稿中 -> 待确认 -> 已生效 / 已替代 / 已归档”。
5. 待决策卡应支持“待判断 -> 待确认 -> 已决定 / 已归档”。
6. 交接物承接卡应显示对应包版本的“草稿中 -> 待确认 -> 已确认 / 已过时”，不得独立写入另一套状态。

### 9.2 异常要求

1. 缺少来源时，应给出来源缺失提示。
2. 存在冲突但未解决时，应显式标记。
3. 同一输入被重复编译为多张卡片时，应支持合并。
4. 卡片状态与所在栏目明显不匹配时，应允许系统建议迁移。

### 9.3 非功能要求

1. 高密度场景下仍可快速扫描。
2. 卡片详情与卡面职责清晰，不把所有内容都堆到卡面。
3. 不同类型卡片在视觉上有稳定区分。

## 10. 验收标准汇总

### 10.1 对象层成立

1. 首版核心卡片类型完整成立。
2. 用户能区分事实、问题、缺口、约束、待决策和交接物。

### 10.2 可持续推进

1. 卡片可由 AI 生成，也可由用户修订。
2. 卡片能形成来源、关系和状态链路。
3. 卡片能持续汇总到结构化交接物。

### 10.3 与挂件边界清晰

1. 系统挂件只投影卡片，不替代卡片。
2. 个人挂件不自动升级为卡片。
3. 卡片模块与挂件模块职责分离清晰。
