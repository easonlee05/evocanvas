# EvoCanvas Prompt Engineering（提示工程）

> 临时迁移说明：本组文档只用于当前 harness 重构期间抽取语义，后续可删除。未来阅读与维护以 `docs/harness/` 为准。

> 当前成熟度层级：`L2 对象与流程定义层`
> 使用方式：`作为与 harness 平行的横切工程面文档，不替代 harness 七层设计`

## 1. 文档目的

本文档只做一件事：

- 定义 EvoCanvas 1.0 中 `prompt engineering` 的职责边界、模块骨架与控制契约

本文档不做这些事：

- 不把 `prompt engineering` 写成 harness 第八层
- 不把 `prompt engineering` 冒充为产品主方法论
- 不把具体提示词文案提前写成实现终稿
- 不重复定义主阶段链、对象清单、升级门槛、验证规则或治理放行规则

因此，这是一份“语言接口编排设计文档”，不是“七层 harness 替代文档”。

## 2. 在 EvoCanvas 中它是什么

在 EvoCanvas 1.0 中，`prompt engineering` 不是“写几段好 prompt”，而是：

- 把 harness 已定义好的阶段目标、对象约束、验证要求与治理边界
- 稳定翻译成 `LLM` 可执行行为的语言接口工程

一句话说：

- `prompt engineering` 的职责，不是优化说法，而是约束行为

它与 harness 的关系不是上下级替代关系，而是：

- harness 定义系统必须具备哪些控制能力
- `prompt engineering` 负责把这些控制能力翻译成模型当前回合可执行的控制信号

因此，它与 `docs/harness/` 平行建档，但不与 harness 并列成“两套主骨架”。

## 3. 与 harness 的边界

从工程控制面看，EvoCanvas 当前建议做如下区分：

- `prompt engineering`：控制模型此步该如何被驱动与约束
- harness engineering：控制系统如何组织工具、状态、验证、治理与交接

这里的关系更接近“不同控制面”，而不是严格树状学术层级。

对 EvoCanvas 来说，当前最重要的是先把以下边界钉住：

- `prompt engineering` 不定义产品目标
- `prompt engineering` 不定义七层职责
- `prompt engineering` 不重写主阶段链与对象语义基线
- `prompt engineering` 不拥有最终验证权或治理放行权
- `prompt engineering` 不把模型内部推理过程直接当成交付对象

## 4. 核心设计目标

EvoCanvas 的 `prompt engineering` 首要目标不是“让回答更像专家”，而是：

- 让模型少越权
- 让模型少跳步
- 让模型少伪装确定性
- 让模型更稳定地产出结构化中间物

因此，它应优先服务以下目标：

- 阶段内动作正确
- 输出对象正确
- 风险边界显性化
- 回执与交接可继续推进

## 5. 模块级骨架

EvoCanvas 当前仍采用四模块口径：

1. 系统基座提示（system base prompt）
2. 阶段提示（stage prompt）
3. 对象提示（object prompt）
4. 回执 / 交接提示（receipt / handoff prompt）

但在结构上，应将它理解为：

- `3 个控制模块 + 1 个输出模块`

更具体地说：

- `系统基座提示 + 阶段提示` 构成主控骨架
- `对象提示` 作为对象压缩模块挂载在主控骨架之后
- `回执 / 交接提示` 作为输出模块挂载在结果整形末端

这里的“交接提示”不是另一套独立强主控，而是：

- 当阶段进入结构化交接时，回执输出向跨回合打包态的延长

## 6. 当前控制契约

### 6.1 系统基座提示

系统基座提示负责提供四类全局控制信号：

- 全局原则
- 全局禁止动作
- 强制披露义务
- 模块优先级规则

它是提示体系的“宪法层”。

当系统基座提示与其他模块冲突时，当前默认采用：

- 单向硬覆盖
- 强制进入标准冲突回执

### 6.2 阶段提示

阶段提示不是重新定义阶段链，而是把 harness 已定义好的阶段规则翻译成当前回合可执行的控制信号。

它当前最小应翻译出四类信息：

- 当前阶段目标
- 当前动作边界
- 当前主对象选择
- 最小回执要求

其中，“最小回执要求”当前只要求两件事：

- 必须披露哪些边界槽位
- 本轮建议去向是什么

### 6.3 对象提示

对象提示不是决定“这一轮该不该生成这个对象”，而是把已经被阶段提示选中的主对象压成正确语义形态。

它当前最小应翻译出三类信息：

- 对象类型
- 对象必备语义槽位
- 禁止越权声明

对象提示不得反向改写阶段判断，但可以在对象压不成立时发出降级提醒。

### 6.4 回执 / 交接提示

回执 / 交接提示是输出模块。

其中：

- 回执提示负责表达当前回合发生了什么，并做轻量整理
- 交接提示负责在结构化交接阶段，把回执输出延长为跨回合可继续推进的打包结果

它不负责：

- 补写上游未给出的事实
- 重做阶段判断
- 宣布验证通过
- 宣布治理放行

## 7. 一次运行里它们怎么协作

为了避免“四模块”停留在概念名词，当前可把一次典型运行理解为以下顺序：

1. `系统基座提示` 先声明全局不变边界。
2. `阶段提示` 再把当前回合收窄到某一阶段目标、动作边界和主对象选择。
3. `对象提示` 在被允许的前提下，把当前主对象压成正确语义形态。
4. `回执提示` 把本轮形成结果、未决边界和建议去向整理成可见输出。
5. 如果当前阶段已经进入结构化交接，`交接提示` 再把回执输出延长为跨回合打包结果。

如果运行中出现异常，当前默认按以下方式收口：

- 如果违反系统基座规则：直接硬覆盖，并切换到标准冲突 / 降级回执。
- 如果阶段目标与对象压缩发生张力：以阶段提示为准，但允许对象提示发出降级提醒。
- 如果对象压不成立：不得硬写成“已形成对象”，必须在回执中显式披露。

## 8. 从方法论到提示骨架的下钻方式

当前文档已经不再停留在“只有框架名字”的层面，但它仍然不是终稿提示词。

它更接近后续写 prompt 时要遵守的骨架约束：

- 先写这个模块拿到什么输入
- 再写这个模块必须产出什么控制信号
- 再写这个模块绝不能替代什么能力
- 最后才写这个模块的具体措辞

对 EvoCanvas 来说，后续真正写模块 prompt 时，建议统一遵守以下顺序：

1. 先写模块目标
2. 再写允许动作 / 禁止动作
3. 再写必须显式输出的槽位
4. 最后才写表达风格或语言偏好

这也是当前版本坚持“不先写终稿文案”的原因：

- 如果先写说法，后面往往会把控制边界写散
- 如果先写控制骨架，后面具体文案反而容易替换

## 9. 当前默认可见边界

EvoCanvas 当前不要求默认暴露完整内部推理。

真正应被显性化的，是以下边界：

- 未决问题
- 冲突边界
- 未确认前提
- 当前收敛置信度

如果对象提示触发“对象压不成立”的降级提醒，这一信息也必须作为回执必显槽位被带出。

## 10. 与 `思维链（CoT）` 的边界

`思维链（CoT）` 不是 EvoCanvas `prompt engineering` 的主对象。

它最多只是：

- 某些 prompt 在内部可能调用的一类推理展开策略

但在 EvoCanvas 1.0 中：

- 不默认要求对外暴露完整内部推理
- 不把 `思维链（CoT）` 单独当成治理依据
- 不把 `思维链（CoT）` 等同于透明性

## 11. 当前设计禁令

以下做法应被视为 `prompt engineering` 的设计禁令：

- 把 `prompt engineering` 写成 harness 第八层
- 在 `docs/prompt-engineering/` 中重写主阶段链、对象清单或升级门槛
- 用 prompt 偷偷替代验证与治理
- 让阶段提示越权覆盖系统基座规则
- 让对象提示直接决定对象生效
- 让回执提示补写上游没有给出的事实判断
- 把交接提示写成“自动宣布可正式交接”
- 把 `思维链（CoT）` 误当成对外主交付对象

## 12. 当前 L2 结论

截至当前版本，EvoCanvas 关于 `prompt engineering` 的主干结论如下：

- `prompt engineering` 与 `docs/harness/` 平行建档
- 它是横切工程面，不是 harness 第八层
- 它负责翻译既有规则，不负责重写系统规则
- 它当前采用“四模块口径，3 个控制模块 + 1 个输出模块”的骨架
- `系统基座提示` 提供全局覆盖边界
- `阶段提示` 负责当前回合主控
- `对象提示` 负责对象压缩与降级提醒
- `回执 / 交接提示` 负责结果整形与跨回合打包
- 其首要目标是约束行为，而不是美化答案
