# EvoCanvas Harness 宪法 v1

> 当前成熟度层级：`L2 对象与流程定义层`
> 编码门槛：`未达到 L3，不应直接作为稳定实现规格；可继续指导补齐治理规则`

## 1. 文档目的

本文档从系统视角定义 EvoCanvas 的 Harness Engineering 总体设计原则。

这里的 Harness 不等于 prompt，也不等于某个 agent runtime。它是包裹在模型外的控制系统，用于把一个概率型生成器约束成一个可推进产品工作的受控系统。

本文档不解释当前实现，而是指导未来设计。

## 2. EvoCanvas 的系统定义

EvoCanvas 是一个面向产品经理的对话驱动工作台。

它的首版目标不是写出一份漂亮 PRD，而是把多源混杂输入稳定收敛成以下四类结构化结果：

- 待澄清问题
- 约束与边界
- 待决策事项
- 结构化交接物

因此，EvoCanvas 的核心系统任务不是 `回答问题`，而是 `推动状态收敛`。

## 3. Harness 的一句话定义

在 EvoCanvas 中，Harness 是一套把 AI 提案转化为受控画布状态变化的控制系统。

这套控制系统必须保证：

- AI 先暴露不确定性，而不是抢先下结论
- 高影响动作不能绕过确认
- 所有稳定事实都必须可追溯
- 上下文切换必须结构化，而不是依赖超长聊天历史
- 输出必须能被人或下游 agent 继续推进

## 3.1 Harness 成熟度层级

为避免系统在治理规格尚未收稳时过早进入实现，EvoCanvas 当前将 harness 成熟度划分为四层：

- `L1 产品原则层`
  - 主要回答“产品想解决什么”“系统边界在哪里”
- `L2 对象与流程定义层`
  - 主要回答“有哪些核心对象”“最小流程怎样推进”
- `L3 可指导实现的治理规格层`
  - 主要回答“对象最小字段是什么”“什么能升级、什么要回退、什么必须拦截”
- `L4 可直接编码的运行时规格层`
  - 主要回答“结构模式（schema）怎么写”“状态枚举怎么定”“验证器怎么落”“日志与回执字段怎么记”

这四层不是为了做成熟度装饰，而是为了约束实现节奏。

当前系统级规则是：

- 只有达到 `L3` 的模块，才允许直接进入主实现编码
- 低于 `L3` 的模块，默认继续先补 harness 规则，而不是直接扩写主流程代码
- 不要求所有模块都达到 `L4` 才能开始开发；更实际的路径是让关键模块先达到 `L3`，再进入第一批实现

对后续 AI协作，统一增加以下约束：

- 每次改写 harness 文档后，都应重新判断受影响模块当前处于 `L1 / L2 / L3 / L4` 哪一层
- 如果层级发生变化，应同步更新相关文档中的层级判断或编码门槛说明
- 不得把尚未达到 `L3` 的模块误当成稳定实现规格

## 4. 第一性原则

### 4.1 产品原则优先于模型能力

模型再强，也不能推翻产品规则。

EvoCanvas 的产品规则是：

- 先暴露不确定性
- 再沉淀约束
- 再形成待决策
- 最后生成结构化交接物

任何违反这个顺序的行为，都应被视为系统偏航，而不是“模型自由发挥”。

### 4.2 对象优先于文本

系统的核心事实不应保存在长对话里，而应保存在结构化对象里。

对话只是输入通道，不是事实层。

进一步说，EvoCanvas 中应显式区分四个层次：

- 对话流：用户与 agent 的原始交互过程
- 结构化对象：系统从对话与材料中映射出的可治理工作对象
- 卡片：结构化对象在画布中的可视化回显或操作入口
- 交接包（handoff package）：将一批结构化对象按规则聚合后的阶段性交付物

因此：

- 卡片不是事实来源
- 交接物（handoff）不是原始事实来源
- 原始依据应来自输入内容、来源引用和可追溯判断链

### 4.3 建议权与生效权分离

AI 可以提出建议，但不能天然拥有事实生效权。

系统必须显式区分：

- 原始输入
- AI 提案（AI proposal）
- 用户确认结果
- 已发布交接物（published handoff）

### 4.4 可追溯优先于“看起来合理”

在 EvoCanvas 中，内容是否看起来像真的，不足以进入事实层。

只有满足来源、状态和治理条件的对象，才可以被视为稳定产物。

### 4.5 收敛流程优先于聊天流畅性

EvoCanvas 的设计中心不是“对话顺滑”，而是“收敛正确”。

必要时，系统应该中断、追问、挂起确认，而不是为了顺滑继续生成。

### 4.6 透明优先于虚假完整

当系统尚未充分澄清，但用户要求“直接给方案”时，EvoCanvas 的默认立场不是拒绝服务，也不是抢先脑补，而是透明优先。

这意味着：

- 系统可以生成可推进草稿
- 但必须显性披露未决问题、冲突边界、未确认前提和当前收敛置信度
- 系统不得把这种草稿伪装成稳定结论

## 5. 系统边界

EvoCanvas 1.0 只解决一个最小闭环：

`输入编译 -> 待澄清问题 -> 约束 / 待决策 -> 结构化交接物`

因此，1.0 不以以下目标为设计中心：

- 完整 PRD 自动生成
- 自由白板创作
- 多人实时协作
- 复杂项目管理系统
- 全自动方案裁决

## 6. 系统中的四层事实

### 6.1 原始输入（Raw Input）

原始输入层，保存会议纪要、聊天摘录、截图说明、反馈、数据快照说明等原始材料。

特点：

- 可引用
- 可追溯
- 不直接等于系统结论

### 6.2 结构化提案（Structured Proposal）

结构化提案层，保存 AI 从输入中抽取和提出的来源片段（source fragment）、解释对象（interpretation）、待澄清项（clarification）、约束候选（constraint candidate）、待决策候选（decision candidate）等建议对象。

特点：

- 可以进入画布
- 不自动等于已确认事实
- 允许被质疑、替换、驳回

### 6.3 已确认工作事实（Confirmed Working Truth）

确认后的工作事实层，保存已满足生效条件的约束、已裁决的待决策结果、已确认的重要边界。

特点：

- 可成为后续推理前提
- 必须可追溯
- 必须受治理层保护

### 6.4 已发布交接物（Published Handoff）

结构化交接层，面向后续人或 AI 的可继续推进上下文。

特点：

- 强调“已清楚什么”和“还没清楚什么”同时可见
- 不是把不确定性抹平，而是把不确定性显性化后带出去

## 6.5 结构化对象基线

EvoCanvas 1.0 当前建议至少维护以下底层结构化对象：

- 来源片段（source fragment）
- 解释对象（interpretation）
- 待澄清项（clarification）
- 约束（constraint）
- 待决策候选（decision candidate）
- 已确认决策（confirmed decision）
- 结构化交接包（handoff package）

其中：

- 来源片段是底层依据对象，不等于卡片文本
- 解释对象是可挑战的中间理解层，不等于正式结论
- 交接物（handoff）是聚合性交付物，不等于前面各对象本体

当前阶段不建议把偏好（preference）做成一级主对象，而应先作为解释对象或待决策对象中的轻量字段存在

## 6.6 收敛置信度

EvoCanvas 需要维护一个收敛置信度，用于判断系统当前是否适合继续压缩问题空间。

该置信度不应完全由 AI 自评，也不应完全由死规则决定，而应采用混合机制：

- 规则层负责给出底线判断
- AI 负责在有限范围内做局部微调

当规则层与 AI 判断冲突时，应采用分级否决机制：

- 低风险对象允许 AI 在有限范围内推动继续收敛
- 高风险对象由规则层保留最终否决权

当收敛置信度低于阈值时，系统默认进入保守模式：

- 增强风险提醒
- 不主动压缩为稳定结论
- 只有在用户再次明确要求推进时，才允许输出带风险标记的可推进草稿

## 7. 系统的最小状态推进逻辑

EvoCanvas 的主状态机不是聊天状态机，而是收敛状态机。

最小流程为：

1. 输入接入（Intake）：接住新输入
2. 输入编译（Compilation）：提取来源片段、解释对象、问题和缺口
3. 待澄清显影（Clarification）：显性化冲突、未知项和待澄清
4. 约束 / 决策收敛（Constraint / Decision Convergence）：沉淀约束，形成待裁决事项
5. 结构化交接（Handoff）：收束当前结果，生成结构化交接物

系统不要求所有问题都先被解决，才允许进入交接物（handoff）阶段。

系统要求的是：

- 已知与未知必须一起被结构化交接

## 7.1 当前已达成的系统级共识

截至当前版本，EvoCanvas 的系统级基线立场如下：

- 默认采取透明优先，而不是效率优先或绝对保守
- 在信息不完整时允许输出可推进草稿，但不得伪装成稳定结论
- 系统维护混合式收敛置信度，并在低置信度时自动转入保守模式
- 高风险对象的最终否决权由规则层保留
- 高风险判断不看“是否改动画布结构”，而看“是否改变事实边界与下游依据”

## 7.2 对象关系基线

当前版本，EvoCanvas 对主要对象关系的基线理解如下：

- 来源片段（source fragment）回答“原输入里说了什么”
- 解释对象（interpretation）回答“agent 当前理解成了什么”
- 待澄清项（clarification）回答“哪类缺口若不补齐，会影响后续推进”
- 约束（constraint）回答“哪些边界已经成立，当前不能越”
- 已确认决策（confirmed decision）回答“在可行空间中，已经正式选了哪一条”
- 交接包（handoff package）回答“当前已知、未定与风险如何被结构化带给下一位人或下一轮 agent”

这几类对象不是卡片类型清单，而是底层语义对象清单。卡片是否存在、如何展示，只是这些对象的界面映射问题。

## 7.3 来源片段与解释对象

从系统视角看：

- 来源片段（source fragment）负责保存不改变原意的底层依据
- 解释对象（interpretation）负责承接来源之上的可挑战中间理解

它们共同构成 EvoCanvas 在“原始输入”和“正式判断”之间的必要缓冲层。

更细的对象语义、允许动作与生效条件，统一以治理层为准：

- `docs/harness/G-governance/00 Governance（治理）.md`

## 7.4 待澄清项、约束与决策

从系统视角看：

- 待澄清项（clarification）负责承接会影响后续推进的信息缺口
- 约束（constraint）负责承接已经成立的事实性边界
- 已确认决策（confirmed decision）负责承接已经完成的正式选择

三者共同构成 EvoCanvas 在“不确定性暴露”之后的主要收敛骨架。

更细的升级条件、字段要求、稳定性与裁决边界，不在系统视图（system view）内展开，统一以治理层为准：

- `docs/harness/G-governance/00 Governance（治理）.md`

## 8. ETCLOVG 在 EvoCanvas 中的职责分工

### 8.1 G：治理（Governance）

定义什么能做、什么不能做、什么必须确认、什么才算事实生效。

### 8.2 V：验证（Verification）

定义系统如何证明自己没有乱做、漏做、跳步做。

### 8.3 L：生命周期与编排（Lifecycle & Orchestration）

定义收敛流程如何推进、何时暂停、何时升级、何时生成交接物。

### 8.4 C：上下文与记忆（Context & Memory）

定义模型在每一轮能看到什么、长期记住什么、何时复水、何时遗忘。

### 8.5 T：工具接口（Tool Interfaces）

定义外部输入与能力如何进入系统，以及工具结果如何被纳入证据链。

### 8.6 O：可观测性（Observability）

定义系统每一轮如何被解释、回放、诊断和追责。

### 8.7 E：执行环境（Execution Environment）

定义这些控制规则最终跑在什么受控环境内，并保证失败恢复和并发隔离。

## 9. 推荐的设计顺序

ETCLOVG 是完整视角，但不是实现顺序。

EvoCanvas 推荐按以下优先级设计：

1. G：先定义事实边界与确认边界
2. V：再定义验证与回执机制
3. L：再定义收敛流程和阶段切换
4. C：再定义上下文与记忆策略
5. T：再定义输入和工具协议
6. O：再定义追踪、回放与审计模型
7. E：最后选运行时承载方案

## 10. 受治理的发散-收敛-裁判模式

EvoCanvas 不应把每一轮都做成单代理直出。

对于低复杂度、低风险、低歧义输入，系统可以走简单编排：输入理解 -> 提案（proposal） -> 验证 -> 治理 -> 应用。

但对于以下复杂回合，系统应启用一种受治理的三角模式：

- 多源输入彼此冲突
- 用户输入范围大而模糊
- 同一主题存在多个候选方案分支
- 当前回合既可能新增待澄清项（clarification），也可能过早生成结论
- 即将生成交接物（handoff），但上游对象仍存在不稳定边界

这套模式的系统级含义只有一条：

- 对高复杂度回合，EvoCanvas 需要把“打开空间”“压缩空间”“判定边界”分离，而不是默认单代理直出

更细的角色职责、回合轮转和适用条件，不在系统视图（system view）内展开，统一以生命周期与编排层为准：

- `docs/harness/L-lifecycle-orchestration/`

### 10.6 系统级结论

EvoCanvas 不采用“直接生成结论”的单线式 agent 路径作为唯一默认范式。

对于高认知密度回合，更合适的机制是：

- 先发散
- 再收敛
- 再裁判
- 必要时回流再发散

其目标不是制造辩论效果，而是降低错误收敛的概率。

## 11. 交接物（Handoff）的系统定义

在 EvoCanvas 中，交接物（handoff）的本质不是总结文档，而是一个面向下一位人或下一轮 AI 的结构化上下文包。

它的核心职责不是宣布“问题已经定义完成”，而是以不失真的方式交代：

- 当前主题是什么
- 哪些内容已经稳定
- 哪些问题仍未解决
- 哪些边界不能越过
- 接下来应基于什么继续推进

因此，交接物（handoff）应满足以下立场：

- 身份上首先是结构化上下文包
- 表达上可以具有总结式可读性
- 但不得为了“像总结”而牺牲未决问题、冲突边界和来源链

一句话说：

- 交接物（handoff）先服务于“继续推进”，再服务于“快速读懂”

进一步说，交接物（handoff）的默认上游不应是原始对话流本身，也不应是用户原话的直接拼装，而应是已经过整理的结构化对象。

也就是说：

- 来源片段（source fragment）主要提供追溯依据
- 解释对象（interpretation）提供可挑战的中间理解
- 约束（constraint）/ 待决策候选（decision candidate）/ 已确认决策（confirmed decision）提供正式判断骨架
- 交接物（handoff）负责将这些对象按“可继续推进”的目标重新编排成交付结构

因此，交接物（handoff）的本体更接近“结构化对象交接包”，而不是“原话拼装包”或“聊天总结”。

## 11.1 交接物（Handoff）的三层内容结构

为了同时保证推进效率与真实性边界，交接物（handoff）应至少显式区分三类内容：

- 已确认内容
- 高置信但未确认内容
- 未决问题 / 待拍板事项

更细的分层条件、条目字段、共存规则与拆条规则，不在系统视图（system view）内展开，统一以治理层、编排层与验证层为准：

- `docs/harness/G-governance/00 Governance（治理）.md`
- `docs/harness/L-lifecycle-orchestration/`
- `docs/harness/V-verification/`

## 11.2 交接物（Handoff）的最小骨架

EvoCanvas 的交接物（handoff）最小骨架在系统层只保留一个要求：

- 必须同时交代当前目标、稳定内容、未决内容和边界内容

更细的包层字段、条目字段、对象映射、状态表达和复杂度控制，不在系统视图（system view）内展开，统一以治理层为主落点：

- `docs/harness/G-governance/00 Governance（治理）.md`

## 11.3 高置信但未确认内容的比例约束

从系统视角看，高置信但未确认内容可以进入交接物（handoff），但不得因此伪装成正式事实，且不得吞掉已确认内容与未决内容之间的边界。

更细的比例约束与草稿 / 正式（draft / formal）门禁，统一以治理层与验证层为准：

- `docs/harness/G-governance/00 Governance（治理）.md`
- `docs/harness/V-verification/`

## 11.4 交接物（Handoff）主体内容的计数规则

从系统视角看，交接物（handoff）的主体内容必须保持“单条只承载一个可继续推进的核心判断”。

更细的计数口径、拆条触发、主对象 / 非主对象治理和软上限规则，统一以治理层与编排层为准：

- `docs/harness/G-governance/00 Governance（治理）.md`
- `docs/harness/L-lifecycle-orchestration/`

## 11.5 交接物（Handoff）的复杂度控制原则

在 EvoCanvas 1.0 中，交接物（handoff）的首要目标是降低失真，而不是把命名、标题或展示规约做到过细。

这条原则保留在系统视图（system view）中，是因为它属于系统级取舍，而不是单一层的技术细则。

## 12. 关键待澄清项的系统定义

关键待澄清项（critical clarification）的系统意义是：

- 它不是普通不确定性，而是会真实改变后续收敛路径的对象
- 它的关闭属于高风险动作，不能被普通收敛直接带过

更细的判定方法与关闭门禁，统一以治理层为准：

- `docs/harness/G-governance/00 Governance（治理）.md`

## 13. Harness Engineer 的职责定义

在 EvoCanvas 中，Harness Engineer 不等于“调 prompt 的人”。

Harness Engineer 的职责是：

- 定义对象与状态机
- 定义治理规则与风险边界
- 定义上下文与来源协议
- 定义编排与中断条件
- 定义验证与回执机制
- 定义审计和可观测模型

其首要产物不是 prompt，而是：

- 规则
- 协议
- 状态机
- 验证器
- 审计模型

## 14. 系统级禁令

以下行为在 EvoCanvas 1.0 中应被视为系统级禁令：

- 在存在明显冲突时静默合并为稳定结论
- 在没有来源支撑时把内容写成已确认约束
- 在高风险状态变化上绕过确认
- 把交接物（handoff）当作“自动总结文档”而非结构化交接层
- 把聊天历史当作长期事实层
- 让工具输出直接越级成为最终结论
- 在低收敛置信度下把草稿伪装成稳定结论
- 把交接物（handoff）退化成“自动总结文档”
- 在未经过关键待澄清项判定前关闭高影响待澄清项（clarification）

## 15. 宪法级成功标准

如果这套 Harness 设计是正确的，那么 EvoCanvas 1.0 应具备以下表现：

- 用户能快速看见系统认为“不清楚”的地方，而不是只看到被包装后的答案
- 任何重要结论都能回指来源、确认过程和状态变化路径
- 系统能够在不强迫一次性做完所有判断的前提下，持续稳定推进
- 交接物（handoff）可以作为下一轮人机协作的可靠上下文入口
