EvoCanvas 不是 PRD 生成器、自由白板或完整项目管理系统。它是一款以 `Vibe Shaping（感觉塑形）` 为核心的对话驱动收敛工作台，用来把尚未成形的感觉与多源输入塑造成结构化问题、约束、决定与可交接上下文。

## 2. 产品背景

现实中的产品思考通常不是从“打开文档写 PRD”开始，而是从领导意见、客户反馈、会议、聊天、数据、截图、竞品和临时想法等碎片输入开始。

用户需要完成的实际工作包括：

1. 在跨媒介、跨角色、跨时间的输入中理解真正问题。
2. 区分事实、假设、偏好、约束和必须拍板的事项。
3. 在关注局部细节时保持整体目标不丢失。
4. 暴露尚未澄清、互相冲突或来源不足的信息。
5. 把逐渐成形的判断沉淀为可继续推进的结构。
6. 把当前结果交给下一位同事或下游 AI，而不重新解释全部聊天。
7. 在后续项目中复用历史规则和判断，同时避免把旧结论误当成当前事实。

会议纪要只能覆盖部分输入，文档更适合沉淀结果，自由白板容易堆积无结构内容，普通聊天式 AI 又难以持续维护稳定工作面。EvoCanvas 因此优先优化的不是“写出来”，而是：

`想明白，并把想明白的上下文可靠地交出去。`

## 3. 产品目标

### 3.1 一句话定位

EvoCanvas 1.0 是一个以 `Vibe Shaping` 为核心的对话驱动收敛工作台，帮助产品经理和其他产品思考密集型用户，把尚未成形的感觉与多源输入塑造成结构化问题、约束、决定与交接物。

### 3.2 Vibe Shaping 定义

`由 agent 引导，把用户尚未成形的感觉、直觉和零散表达，逐步塑造成可讨论、可追溯、可收敛的结构化思考。`

它允许用户从模糊开始。Pi 先接住、理解、命名和追问，再将稳定到可以治理的内容形成候选；只有满足来源、确认和提交门禁后，结构才显影到画布。

### 3.3 体验旅程与核心闭环

外层体验旅程：

`感觉接入 -> 对话塑形 -> 结构收敛 -> 画布显影 -> 结构化交接`

结构收敛的内层闭环：

`输入编译 -> 待澄清问题 -> 约束 / 待决策 -> 结构化交接物`

项目知识库位于主链两侧：它可以向输入环节提供带来源的历史知识，也可以接收用户显式发布的已确认交接物，但不能绕过结构收敛成为第二套事实源。

### 3.4 业务目标

1. 支持用户从一句感觉、一段聊天、一份纪要或一组碎片材料开始。
2. 支持 Pi 提炼来源事实、问题、冲突、缺口和候选结构。
3. 支持用户围绕问题、规则、方案、决定和推进动作持续收敛。
4. 支持稳定结构通过卡片、栏目、关系和系统挂件显影。
5. 支持从当前稳定结构形成可供人和下游 AI 使用的交接物。
6. 支持把主动添加的来源和已确认交接物编译为可追溯项目知识。
7. 优先验证需求失真是否下降，不以页面数量或文档长度作为成功标准。

### 3.5 首版验证命题

1. 模糊 vibe 能否被 Pi 接住、命名和追问，而不是被迫先结构化填写。
2. 多源混杂输入能否稳定收敛为待澄清、约束和待决策。
3. Pi 能否优先暴露不确定性，而不是过早脑补结论。
4. 画布能否只显影稳定结构，而不是把所有原始混沌摊开。
5. 结构化交接物能否减少下一轮实现、评审或任务拆解中的漏点与歧义。
6. 项目知识能否带着来源被复用，并在冲突或过时时显式提示。

## 4. 用户与使用边界

### 4.1 核心用户

| 用户 | 核心场景 | 核心诉求 |
| --- | --- | --- |
| 产品经理 | 接收需求、整理上下文、推进收敛和交接 | 接住输入、看清缺口、固定边界、形成交接 |
| 创业者 / 设计师 / 业务负责人 | 从模糊直觉收敛方向、体验原则和业务判断 | 把感觉塑形成可推进结构 |
| 下游 AI 工具 | 消费已经确认的交接物或面向 AI 的 PRD | 基于稳定上下文执行实现、评审或拆解 |

Pi 是产品内协作能力，不是拥有最终确认权的用户角色。

### 4.2 1.0 使用边界

1. 首版为单人工作台。
2. 不支持多人实时协作、角色化审批或多人共同编辑。
3. 产品经理是首要用户，但同一闭环可服务其他单人产品思考场景。
4. Codex、Claude Code、Antigravity 等下游工具只消费已收敛结果，不默认参与 EvoCanvas 内部澄清。
5. 外部系统接入、外发和不可逆副作用使用独立动作门禁。

## 5. 产品原则与硬约束

1. 第一入口是感觉接入，不是新建 PRD 或复杂模板选择。
2. 画布是稳定结构的显影层，不是原始混沌的第一承载层。
3. 系统可以自动形成草稿和候选，但信息地位升级不得绕过用户确认。
4. 当来源冲突、上下文不足或指代不清时，必须先显性化和追问。
5. 普通 Chat 不直接修改稳定结构化包。
6. 已生效或已确认内容必须能回指来源、确认方式或用户裁决。
7. Workspace Artifact Revision 是稳定结构的事实源；Canvas、挂件、Toast、摘要和图谱都是投影或提示。
8. 前五类卡片投影正式业务对象；交接物承接卡投影结构化包版本。
9. Active Todos 只投影活跃缺口，不是任务管理系统或独立事实源。
10. 项目时间轴只表达轻量推进位置，不是甘特图。
11. 个人挂件默认不进入正式对象层或交接物。
12. 知识库 Wiki 页面是可重建解释层，不直接成为当前约束、决定或交接事实。
13. 已确认交接物可以被显式发布到知识库，但确认交接不自动授权外部发布。
14. 不新增平行运行时、平行事实源或平行确认流。
15. 首版不做自由白板模式、完整项目管理系统或大而全企业知识库。

### 6.3 后续版本路线

#### 2.0：方案收束工作台

在 1.0 已证明输入可以稳定收敛的前提下：

1. 引入方案卡、结论卡和推进项。
2. 支持多个候选方案比较、取舍和收束。
3. 从交接物继续形成可执行方案包。
4. 强化“为什么这样决定”的决策链。

#### 3.0：多角色产品协作面

1. 多人实时协作与评论。
2. PM、设计、研发、业务和评审方的角色化视图。
3. 明确的约束、方案和决定确认权限。
4. 围绕结构化对象形成评审闭环。

#### 4.0：交付编排面

1. 更复杂的依赖与规格、原型、任务联动。
2. 项目管理平台、组织知识库、IM 和需求系统接入。
3. 从交接物派生规格包、任务包和评审包。
4. 更完整的推进状态和交付链路。

路线顺序不能倒置：先证明收敛，再扩展方案、协作和交付编排。

## 7. 产品架构与端到端流程

### 7.1 产品模块关系

```text
【输入与对话塑形】
  感觉 / 材料 / 知识引用
          ↓
  理解、命名、追问、候选、确认
          ↓ 受治理语义提交
【Workspace Artifact Revision】
          ↓
  ┌───────┼────────┐
  ↓       ↓        ↓
【卡片】 【主画布】 【挂件】
  └───────┼────────┘
          ↓
【结构化交接】 ──显式发布──> 【项目知识库】
          ↑                       │
          └────知识引用快照────────┘
```

### 7.2 端到端主流程

1. 用户输入一句感觉或导入材料。
2. 原输入先被保存，Pi 再理解、命名、拆解和追问。
3. 事实、冲突、问题、约束线索和待决策线索被分层表达。
4. 未确认候选保留在 Primary Pi Session。
5. 来源事实通过完整性检查后可收录；其他稳定语义在 Chat 中获得确认后提交。
6. 统一提交能力验证来源、身份、基础 Revision、作用范围和幂等性。
7. 提交成功后形成新的不可变 Revision。
8. Canvas、卡片关系和系统挂件从 Revision 增量重建或更新。
9. 当当前主题具备可读边界时，系统生成或刷新结构化交接草稿。
10. 用户确认交接内容和未决边界后形成已确认交接版本。
11. 已确认交接物可以被人或下游 AI 使用，也可由用户显式发布到项目知识库。
12. 后续知识通过带版本的只读引用快照重新进入新的工作区，并再次接受当前上下文的治理。

### 7.3 关键回流

1. 新来源暴露冲突：回到对话塑形和待澄清。
2. 待澄清转为必须拍板：进入待决策。
3. 约束或决定变化：相关交接物进入已过时。
4. 交接确认前发现关键缺口：回到待澄清或待决策。
5. 知识页陈旧、冲突或来源失效：作为来源风险进入当前对话，不直接修改 Revision。

## 8. 模块职责与联动合同

### 8.1 输入与对话塑形

- 负责：原始输入、Primary Pi Session、理解命名、追问、候选、Chat 确认和结构变化提议。
- 不负责：直接写 Canvas、自动发布知识、代替用户确认决定。
- 输出：来源引用、确认依据和受治理的最小语义操作。

详细要求见：[输入与对话塑形模块 PRD](./modules/input-and-dialogue.md)。

### 8.2 主画布

- 负责：current Revision 的可视化投影、栏目、局部关系、布局和聚焦。
- 不负责：保存业务正文、确认信息地位或把坐标变成业务关系。
- 输出：可浏览、可回源、可重建的工作面。

详细要求见：[主画布模块 PRD](./modules/canvas.md)。

### 8.3 卡片

- 负责：正式对象的类型化卡片投影、字段、状态、关系、手动修订和迁移。
- 不负责：个人挂件、自由白板元素和独立任务对象。
- 输出：问题、约束、决定和交接等稳定结构的可操作投影。

详细要求见：[卡片模块 PRD](./modules/cards.md)。

### 8.4 挂件

- 负责：活跃缺口、项目时间轴和个人工作辅助。
- 不负责：成为独立事实源或完整任务 / 排期系统。
- 输出：回指正式对象或用户个人状态的辅助视图。

详细要求见：[挂件模块 PRD](./modules/widgets.md)。

### 8.5 项目知识库

- 负责：项目来源版本、LLM Wiki 编译页、查询、来源回看、健康检查和知识引用快照。
- 不负责：直接决定当前约束、修改 Workspace Artifact 或充当组织级知识平台。
- 输出：带页面版本、来源版本、检索时间和健康状态的知识引用。

详细要求见：[项目知识库模块 PRD](./modules/knowledge-base.md)。

### 8.6 结构化交接

- 负责：交接内容装配、确认、版本、过时、AI PRD 派生和显式知识发布。
- 不负责：独立于 Workspace Artifact 维护第二正文或自动执行外发。
- 输出：已确认、可追溯、可继续推进的上下文版本。

详细要求见：[结构化交接模块 PRD](./modules/handoff.md)。

## 9. 核心对象与事实权威

### 9.1 权威层次

| 层级 | 主要内容 | 权威说明 |
| --- | --- | --- |
| 原始来源 | 用户输入、导入材料、工具读取结果、知识来源版本 | 说明“来源里说了什么”，不得被投影静默改写 |
| Primary Pi Session | 对话、候选、工具运行和技术过程 | 是过程真相；未确认候选不等于稳定产品事实 |
| Workspace Artifact Revision | 正式对象、关系、确认引用和交接版本 | 稳定结构的唯一事实源 |
| Canvas / Handoff / 系统挂件 | 卡片、栏目、交接视图和活跃缺口 | 从 Revision 派生，可重建，不独立写事实 |
| 项目知识库 Wiki | 基于来源编译的概念、实体、规则和模板页 | 可复用解释层；进入工作区时重新成为来源输入 |
| UI 状态 | 坐标、缩放、选中、折叠、Toast、搜索排序 | 纯展示或个性化状态 |

### 9.2 正式对象

1. 证据。
2. 问题。
3. 待澄清。
4. 约束。
5. 待决策 / 方案承接。
6. 结构化工作包及交接版本。

对象字段、类型化状态和关系详见 [卡片模块](./modules/cards.md)；交接内容与版本详见 [结构化交接模块](./modules/handoff.md)。

### 9.3 单一提交边界

1. Pi 和用户直接语义编辑共用受治理提交能力。
2. 提交器只接受类型化最小操作，不接受整包自由覆写。
3. 提交前验证主体、来源、基础 Revision、确认范围、内容哈希和幂等键。
4. 同一次稳定化产生原子有效的 Revision，不按每条消息或每张投影卡片创建版本。
5. Canvas、Handoff 和知识编译运行都不能绕过 Product Kernel 写入稳定结构。

## 10. 状态、确认、权限与异常

### 10.1 状态原则

1. 每类业务对象只维护一套可写的类型化状态。
2. “来源依据、形成中、未解决、稳定可用、历史保留”等通用分组由对象类型和状态派生，不独立写入。
3. 结构或来源验证结果独立表达为未验证、通过、警告或不通过，不替代对象状态。
4. 交接物承接卡读取包版本状态，不形成第二套交接状态。
5. Wiki 页面健康状态、图谱关系和搜索分数属于知识投影，不修改 Workspace Artifact。

### 10.2 确认边界

无需产品语义确认即可自动形成：

1. Primary Pi Session 中的草稿与候选。
2. 经过完整性检查的原始来源事实。
3. current Revision 可确定性计算的索引、哈希和投影元数据。

必须在 Chat 中固定含义和范围后才能稳定化：

1. 正式问题和待澄清项。
2. 约束。
3. 方案、待决策和决定。
4. 对象与关系的语义更新、解决、撤回或替代。
5. 交接内容、范围和风险接受。

Chat 已经形成有效确认时，不建立独立确认队列，也不重复要求批准“是否生成卡片”。

### 10.3 权限边界

1. 首版当前用户拥有本工作区的产品编辑权限。
2. Pi 只能通过受治理工具读取和提出变化。
3. Pi 默认只读访问项目知识；知识写入和发布由知识库服务独立检查。
4. 正式外发、知识发布和其他不可逆动作需要显式用户动作。
5. 下游 AI 默认只消费交接物，不反向修改当前工作区。

### 10.4 通用异常原则

1. 原始输入或来源解析失败时保留原文。
2. 稳定状态读取失败时可以继续普通对话，但必须阻止稳定写入。
3. 缺少确认依据时只保留候选，不显影。
4. 版本冲突时读取最新 Revision，并重新确认受影响范围。
5. 投影失败不回滚或复制稳定事实；应从 Revision 重建。
6. 运行结果未知时不声称成功，也不自动重复提交。
7. LLM Wiki 不可用时，主工作区稳定内容和交接读取仍可工作。

模块具体状态机和异常文案由对应模块 PRD 维护。

## 11. 总体验收标准

### 11.1 感觉接入与对话塑形

1. 用户可从一句模糊感觉开始，无需先填写完整需求。
2. Pi 首先给出可纠正的理解和关键追问，而不是直接输出完整方案。
3. 多源冲突、歧义和来源不足被显式呈现。
4. 未确认候选只存在于 Session，不提前显影。

### 11.2 稳定结构与画布

1. 经确认提交后，正式对象在正确栏目增量显影。
2. 用户可查看来源、关系、状态和变化摘要。
3. Canvas、关系线和系统挂件可从 current Revision 重建。
4. 布局变化不会改变对象事实或状态。

### 11.3 结构化交接

1. 交接物包含目标、背景、约束、决定、未决、后续动作和来源。
2. 未决不会被伪装成已确认结论。
3. 用户确认内容和未决边界后，交接版本才可作为正式依据。
4. 底层关键事实变化后，旧交接能够被识别为已过时。
5. 已确认交接可派生面向 AI 的 PRD，并标记源版本。

### 11.4 项目知识复用

1. 用户能够从来源编译并浏览带来源的 Wiki 页面。
2. 搜索、问答和图谱结果可以回看页面与原始来源版本。
3. 知识加入工作区时生成只读引用快照，不直接成为当前事实。
4. 冲突、陈旧、孤立和来源缺失被显式提示。
5. 只有用户选择的来源或已确认交接物可以被发布到知识库。

### 11.5 核心命题验证

1. 使用同一已确认交接物进入实现、评审或任务拆解时，核心约束和决定不应因表达顺序变化而大幅漂移。
2. 与直接交付聊天记录相比，使用 EvoCanvas 交接物时需求漏点和歧义应显著减少。
3. 从知识库复用历史判断时，用户能够辨认其来源、版本、健康状态和当前适用性。

## 12. 非功能性需求

1. **可读性**：主画布视觉克制，卡片密度适合长时间浏览。
2. **可恢复**：Revision、Session 和关键确认持久化；投影和索引可重建。
3. **一致性**：提交使用版本检查和原子持久化，不能出现半提交稳定状态。
4. **可追溯**：稳定对象、交接版本和知识引用可回到来源与确认依据。
5. **可降级**：Pi、关系投影、挂件或知识服务局部失败时，不破坏已确认稳定状态。
6. **项目隔离**：工作区、知识空间和来源不得跨租户或项目泄漏。
7. **增量体验**：AI 和 Canvas 更新优先使用增量变化，避免整图重绘。
8. **可回退**：关键语义变更通过替代、归档或新 Revision 表达，不覆盖历史版本。
9. **兼容性**：优先支持桌面端现代浏览器，移动端不作为 1.0 核心工作面。
10. **诚实状态**：运行、编译、投影或发布的部分成功、失败和结果未知必须可见。

## 13. 术语表

| 术语 | 定义 |
| --- | --- |
| 感觉接入 | 用户用一句感觉、关键词或其他未成形输入启动工作的入口 |
| Vibe Shaping | Pi 引导用户把感觉和碎片逐步塑造成可讨论、可追溯结构的过程 |
| 对话塑形 | 理解、命名、拆解和追问，使模糊表达逐步成形 |
| 结构收敛 | 把输入治理为待澄清、约束、待决策和交接物的核心闭环 |
| Workspace Artifact Revision | 保存正式对象、关系、确认和交接版本的不可变稳定结构版本 |
| 画布显影 | 将 current Revision 中的稳定对象投影为卡片、栏目、关系和缺口 |
| 卡片 | 正式业务对象或交接包版本在 Canvas 上的可操作投影 |
| 系统挂件 | 从正式对象或确定性计算结果派生的辅助视图 |
| 个人挂件 | 服务个人思考和操作便利、默认不进入正式对象层的工具 |
| Active Todos | 由待澄清和待决策等活跃缺口派生的系统挂件 |
| 结构化交接物 | 当前稳定结构面向下一位人或下游 AI 的治理视图 |
| 面向 AI 的 PRD | 从已确认交接版本派生、供下游 AI 实现或评审使用的需求输入 |
| 项目知识库 | 当前项目范围内沉淀来源、编译 Wiki 并提供可追溯知识引用的模块 |
| LLM Wiki | 将原始来源编译成结构化、互相链接的 Markdown Wiki 的模式与参考实现 |
| 知识引用快照 | 知识加入工作区时对页面版本、来源版本、检索时间和健康状态形成的只读记录 |
| 投影 | 可从权威数据重建的 Canvas、挂件、交接视图、索引或图谱表现 |
