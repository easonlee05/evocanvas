# Gate Adjudication（门禁裁决）

> 当前成熟度层级：`L3 可指导实现的治理规格层`
> 编码门槛：`可作为 1.0 信息地位升级检查、Chat 确认范围匹配和外部动作分流的实现输入`

## 1. 职责边界

门禁裁决回答：一次提案中的哪些操作需要确认依据，以及现有 Chat 记录是否足以支持本次信息地位变化。

本层只定义门禁如何挂到编排主链：

- 风险等级和对象政策由安全与治理层定义。
- 消息引用真实性由来源验证负责。
- 状态流转合法性由结构验证负责。
- 门禁只匹配“拟升级内容”与“用户实际确认范围”。

## 2. 三类动作边界

### 2.1 结构整理

可以在验证通过后自动提交：

- 新增相关证据片段、实际问题、Chat 后仍影响推进的待澄清和冲突标记。
- 新增或更新待决策候选。
- 创建或刷新达到可评审条件的交接草稿。
- 建立弱关系、拆分混合对象或合并重复候选。

这些动作改变工作结构，但不宣布内容已经成立，因此不要求用户确认“是否生成卡片”。

### 2.2 信息地位升级

必须有 Chat 中明确且带范围的确认依据：

- 新增、实质修改或替代约束。
- 待决策进入已决定。
- 待澄清进入已澄清，或关键待澄清被关闭（「关键」判定标准见 [Object Governance §4](../05-safety-governance/05%20Object%20Governance%EF%BC%88%E5%AF%B9%E8%B1%A1%E6%B2%BB%E7%90%86%EF%BC%89.md)）。
- 交接版本进入已确认并可作为下游依据。
- 未确认内容被提升为可供下游依赖的前提。
- 其他会改变事实边界的语义状态变化。

### 2.3 外部不可逆动作

正式发布、向外部系统写入、触发真实执行或其他不可逆副作用，使用独立的外部动作门禁。该门禁可以复用 Chat 说明，但不能因为结构化包已经确认就默认放行外部操作。

普通包版本更新不进入外部审批队列。

## 3. 门禁挂载点

信息地位门禁在提案完成结构、来源和策略验证后，原子提交前执行：

```text
结构化提案
-> 结构 / 来源 / 策略验证
-> 风险分类
-> 信息地位门禁
-> 治理裁决
-> 版本复检
-> 原子提交
-> 外部动作门禁（仅当提案涉及外部不可逆副作用时，独立执行）
```

门禁按提案操作逐项判断，执行二元：结构整理在验证通过后自动提交，信息地位升级必须有确认依据。低风险整理与高影响升级可以出现在同一提案中，但必须支持部分放行和原子依赖组。

风险分级（见 Facts and Risk §2）决定留痕强度和显影提示级别，不决定门禁分支——门禁执行只有"自动"和"需确认"两条路径。

## 4. 确认依据最小结构

每个需要确认的信息地位升级，至少携带：

| 字段 | 含义 |
| --- | --- |
| `confirmation_path` | Assistant 提议后确认，或 User 直接明确陈述 |
| `proposal_message_refs` | Assistant 提出判断、范围和影响的消息引用；直接陈述路径可空 |
| `user_confirmation_refs` | User 直接陈述、确认、否定或修正的消息引用 |
| `confirmed_claims` | 被确认的具体判断或状态变化 |
| `scope_refs` | 适用对象、字段、版本或时间范围 |
| `remaining_unresolved_refs` | 没有随本次确认一起解决的未决 |
| `confirmation_kind` | 明确确认、部分确认、否定、撤回或修正 |

这些字段由系统基于真实消息确定性装配或验证。模型可以提出候选映射，但不能伪造消息引用或扩大确认范围。

## 5. 范围匹配规则

| Chat 表达 | 门禁结果 | 结构化处理 |
| --- | --- | --- |
| 明确确认具体判断和范围 | 放行对应升级 | 只升级匹配对象和字段 |
| User 主动给出明确、完整且带范围的产品判断 | 放行对应升级 | 记录直接确认路径，不要求重复确认 |
| 只确认部分内容 | 部分放行 | 其余保持候选、待确认或未决 |
| “可以考虑”“大概这样”等试探表达 | 不放行升级 | 可以保留候选 |
| 明确否定 | 拒绝原升级 | 保留否定记录，必要时撤回候选 |
| 带修正确认 | 只放行修正后的内容 | 原建议不得按旧内容生效 |
| 确认后又被撤回或新消息推翻 | 判定失效或过期 | 不提交旧升级，进入最新水位重判 |
| 只有界面点击或泛化“可以”，无法确定所指 | 不放行升级 | 后续正常 Chat 澄清范围 |

确认匹配以语义和作用范围为准，不能只依赖最近一条消息的字面关键词。

若新确认内容与已有约束冲突，门禁还必须检查替代意图：明确表示修改、废止或替换旧约束，或当前上下文唯一指向该修改时，才允许建立替代关系。仅仅出现得更晚，不足以覆盖旧约束；替代意图未成立时，旧约束保持原生效状态，冲突必须显性保留并等待澄清或决策。

## 6. 同回合直接生效

如果 Chat 已经包含完整提议与确认，或 User 已直接给出明确、完整且带范围的产品判断，收敛回合可以在一次原子提交中：

1. 创建相应结构化对象。
2. 记录候选到稳定地位的有序变化。
3. 写入确认依据和仍存未决。
4. 提交最终已生效、已决定或已确认状态。

这不叫绕过待确认，而是待确认条件已经在 Chat 中满足。系统不需要先创建一版待确认对象，再要求用户重复确认一次。

## 7. 确认不足时的处理

门禁不负责发送追问，也不创建后台确认任务：

- 若待决策等候选本身可合法提交，则降级为候选或待确认状态，并随本次提案提交；未确认的约束提议不得降级写入约束卡。
- 若没有任何可提交变化，则收敛以 `not_ready` 正常结束。
- 后续 Chat 根据当前工作面继续引导，新的用户消息再次经过判断器。

画布卡片、Toast 和固定变化回执都不能代替 Chat 确认。

## 8. 设计禁令

- 不允许把“创建对象”和“对象已成立”视为同一风险。
- 不允许为新建待决策候选或交接草稿强制增加一次操作确认。
- 不允许把礼貌性短句脱离提议范围解释为确认。
- 不允许整包确认洗平包内仍存未决。
- 不允许用普通结构化确认替代外部不可逆动作批准。
- 不允许建立长期占用运行权的确认队列或 `awaiting_confirmation` 状态。
