# Failure and Recovery（失败与恢复）

> 方法成熟度：`L3 可指导实现的治理规格层`
> 目标实现归属：`Pi 技术恢复 + EvoCanvas 业务一致性恢复`
> 当前实现状态：`原生失败恢复合同已接入，端到端证据待补齐`
> 实现说明：运行失败、稳定提交失败、投影失败和外部副作用失败分别处理，不能用统一“重试”掩盖效果边界。

## 1. 控制目标

任何失败都必须回答：失败发生在哪一层、权威状态是否已改变、是否可安全重试，以及用户下一步能做什么。

## 2. 故障分类

| 层 | 权威判断 | 默认恢复 |
| --- | --- | --- |
| Pi 模型 / Session | Pi 技术 Trace 和 Session | 原 Session 重试或恢复 |
| 只读工具 | Tool Result | 修复来源后重读 |
| 工作包提交 | 幂等查询和 current Revision | 查询后重试或重做差异 |
| Canvas 投影 | Revision 与投影检查点 | 从 Revision 重建 |
| 外部副作用 | 外部回执和幂等查询 | 先核对，确认安全后重试 |

## 3. 原子性边界

- 一个 `workspace.commit` 要么完整创建并发布新 Revision，要么完全不可见。
- Revision 创建、current 指针更新和确定性依赖传播属于同一原子边界。
- Canvas 投影与 Revision 提交不在同一事务；投影失败不回滚业务状态。
- 外部副作用与工作包提交不得伪装成一个跨系统原子事务；使用 Outbox / Saga 明确中间状态。

## 4. 结果未知

连接中断、超时或进程崩溃时：

1. 使用幂等键或外部效果 ID 查询权威结果。
2. 已成功：补记 Tool Result 或恢复关联，不重放动作。
3. 已失败：按可重试性处理。
4. 仍未知：保持 `unknown`，阻止同一不可逆动作自动重试，并提示人工核对。

恢复器只读取工具注册时固定的 `replay: safe | never`：

- `safe`：先按幂等键和请求哈希查询；确认未执行或重复无新增效果后才自动重放。
- `never`：无论 Turn 是否可恢复都不自动重放；`unknown` 只能通过外部回执、人工核对或专用查询工具收敛。
- 未声明、版本不匹配或策略读取失败一律按 `never` 处理。

## 5. Outbox 与投影恢复

提交成功后产生的投影或通知事件使用可重放 Outbox，至少包含 `event_id`、`revision_id`、目标消费者、尝试次数和状态。消费者按 `event_id` 幂等；投影始终从指定 Revision 计算，不从上次 Canvas 状态增量猜测。

## 6. 版本冲突恢复

收到 `stale_revision` 后：

1. 读取 latest Revision。
2. 计算原基础版本到 latest 的差异。
3. 判断待提交操作是否仍可无歧义应用。
4. 任何语义范围或确认内容变化都重新展示给用户。
5. 使用新的 `base_revision_id` 和新的幂等键提交。

不得自动把旧操作覆盖到新版本。

## 7. 用户可见反馈

反馈至少说明：哪一步失败、工作包或外部状态是否可能已变化、当前保留了什么、下一安全动作。不得仅显示“出错了，请重试”。

## 8. 原因码

```text
runtime.*       # 模型、Session、取消、恢复
context.*       # 工作快照和来源读取
instruction.*   # 指令与 Skill
workspace.*     # Revision、状态、确认、幂等
projection.*    # Canvas 与其他派生视图
external.*      # 外部副作用
```

原因码稳定、可聚合；人类消息可以演进，但不能作为机器分支条件。

## 9. 验收场景

1. 提交响应丢失后按幂等键发现已成功，只展示一次 Revision。
2. 外部发送状态未知时系统禁止自动重发，并清楚提示人工核对。
3. Canvas 消费者停机后恢复，可按 Outbox 重放到最新 Revision。
4. 版本冲突涉及确认对象时，系统不会自动合并并沿用旧确认。
5. Pi 回复失败但提交已成功时，重新进入 Workspace 能看到稳定变更和可追溯 Tool Result。
6. 恢复器缺失工具版本或 replay 策略时按 `never` 停止，不用默认重试猜测。
