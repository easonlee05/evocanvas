# B 端产品操作手册编写格式与规范

本文档定义了 B 端平台产品操作手册的标准结构、排版与内容规范，用于指导各项功能模块操作手册的标准编写作业。

## 1. 内容结构标准

根据模块包含功能点的复杂程度，操作手册分为"单操作场景"和"多操作场景"两类结构，请根据实际业务复杂度进行选择。

**【强制要求】**：
- 带有"（可为空）"的节点如果无实际内容，请直接整段删除，严禁在文档中保留空标题。
- 绝对禁止在文档中出现"实际功能名称1"等占位词，必须替换为真实的业务功能名称。
- 在描述前提条件（尤其是权限）时，**一律表述为"当前操作账号需具备对应的操作权限"**，绝不允许写死具体的角色名称（如"超级管理员"、"租户管理员"、"系统管理员"等）。

### 结构一：单操作场景（适用于单核心功能模块）

```markdown
# [模块名称]操作手册
## 业务场景（描述业务背景：解决什么问题，满足什么需求）
## 操作场景（功能描述：这个功能具体能做什么）
### 注意事项（可为空，包含高危/重要提示）
### 前提条件（可为空，例如：当前操作账号需具备对应的操作权限、依赖资源已就绪等）
### 操作步骤
### 后续操作（可为空）
## 相关文档（可为空）
```

### 结构二：多操作场景（适用于包含多个子功能的复杂模块）

当一个模块包含多个子功能（如：新建、配置、监控、扩容、删除）时，各个子功能模块的章节**必须进行合理排序**。
**章节排序原则**：
1. **基于生命周期逻辑**：优先按照业务自然流转的顺位进行排序（即：从无到有的创建/接入 -> 状态配置 -> 日常使用与监控 -> 资源变更与扩容 -> 销毁与删除）。
2. **基于重要与高频程度**：如果没有强生命周期关联，则按照操作的重要程度和发生频率排序（核心常用功能在前，低频运维功能在后）。

```markdown
# [模块名称]操作手册
## 业务场景（描述业务背景：解决什么问题，满足什么需求）
## 操作场景（功能描述：该模块包含哪些子功能，多个子功能使用表格列出概览）

## [子功能 1，例如：创建XXX]
### 注意事项（可为空，包含高危/重要提示）
### 前提条件（可为空）
### 操作步骤
### 后续操作（可为空）

## [子功能 2，例如：XXX监控与维护]
### 注意事项（可为空，包含高危/重要提示）
### 前提条件（可为空）
### 操作步骤
### 后续操作（可为空）

## 相关文档（可为空）
```

## 2. 排版与说明规范（红线要求）

1. **截图权威性（最高准则）**：所有页面名称、字段标签、按钮文字、校验提示及统计维度，必须严格以提供的截图内容为准。若截图与文字材料冲突，以截图为最高优先级。
2. **颗粒度极其详细**：不遗漏任何一个可见字段。每一个输入框、下拉单选或展示字段，必须解释其【业务含义】、【约束条件】，对于输入项需给出合理的【取值样例】。
2. **输入、展示与动作彻底分离（核心红线）**：
   - **输入参数表**：**仅限**真实的输入填写项（如文本框、下拉框、数值配置）。参数表固定为两列：`| 参数 | 说明 |`。
   - **展示字段表**：对于详情页、列表页等纯只读展示的数据字段，必须使用两列表格：`| 展示字段 | 字段说明 |`。
   - **操作动作**：模式切换、开关（打开/关闭）、勾选复选框、点击按钮等影响操作流的动作，**绝对禁止**放入任何表格中，必须在操作步骤中以文字单独、清晰地描述。
3. **参数/字段解释的专业性**：解释需详细说明其背后的业务目的。**必须保持 B 端技术文档的专业与严谨**，严禁使用任何口语化、拟人化的比喻，必须统一使用标准的 IT 及业务架构术语。
4. **界面元素加粗规范**：**仅**对具体的界面交互实体（如页面名称、按钮名称、页签、特定操作选项）使用 `**粗体**` 进行高亮（例如：点击 **确认** 按钮）。**严禁**使用 `【】` 括号包裹按钮名称；严禁对解释性长句、段落或提示标题滥用粗体。
5. **提示信息规范**：遇到高危操作（如删除）、重要提示等，**严禁**使用 Markdown 的 `>` 引用块语法。必须统一归纳并使用 `### 注意事项` 作为标准标题，放置在对应功能的操作步骤或前提条件之前。
6. **长文档拆分原则**：如果当前模块包含的操作场景过多（例如超过 5-6 个功能点，且逻辑差异较大），必须主动根据业务边界将其拆分为多份独立的操作手册。
7. **排版防错**：单一步骤下的单一说明直接用连贯的一句话陈述，不使用无序列表；多并列选项才使用无序列表。Markdown 表格内换行请严格使用 `<br>` 标签。
