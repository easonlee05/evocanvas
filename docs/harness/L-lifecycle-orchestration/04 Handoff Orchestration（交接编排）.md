# 交接编排（Handoff Orchestration）

> 当前成熟度层级：`L3 可指导实现的治理规格层`
> 编码门槛：`已达到 L3，可直接指导第一批交接编排与草稿 / 正式边界实现`

本文件展开 L 层中的交接编排基线，集中保存交接物的位置、条目组织原则、草稿 / 正式边界与下游保护口径。

## 这一层回答什么问题

交接编排回答：

- handoff 在 L 层中处于什么位置
- handoff 应从哪些上游对象收束而来
- handoff 的内部结构如何保持已知与未知并存
- 什么时候只能输出草稿，不能输出正式交接物

## handoff 的基本位置

交接物（handoff）不是聊天总结，也不是原话拼装包。

它是面向下一位人或下一轮 AI 的结构化上下文包，先服务于继续推进，再服务于快速读懂。

L 层当前明确以下原则：

- handoff 来源于当前结构化对象，而不是重新自由生成
- handoff 同时包含已知与未知，不得掩盖未解决待澄清项
- handoff 不得绕过确认把草稿（draft）冒充正式版（formal）

## handoff 的主要上游对象

交接物（handoff）的默认编排单位不是原话，也不是聊天回合，而是已经形成的结构化对象。

条目应优先承接：

- 解释对象（interpretation）
- 约束（constraint）
- 待决策候选（decision candidate）
- 已确认决策（confirmed decision）

来源片段（source fragment）默认作为这些条目的追溯依据存在，而不是直接成为 handoff 的主要写作单位。

## handoff 的三层内容结构

handoff 在编排上应显式区分三层内容：

- 已确认内容
- 高置信但未确认内容
- 未决问题 / 待拍板事项

当待拍板事项已经成为当前推进主轴时，handoff 应将其从普通未决问题中抬升为独立槽位。

## 草稿 / 正式边界

关于 handoff 的内部稳定性，当前先保留以下基线：

- 高置信但未确认内容默认不应超过主体内容的三分之一
- 若超过该阈值，handoff 只能保持 draft 状态
- handoff 主体内容按结构化条目数计数
- 每条主体内容只承载一个核心判断

## 单主对象编排原则

handoff 条目默认采用：

`单主对象编排`

也就是：

- 每条条目必须有唯一主对象
- 主对象优先由下游作用决定
- 状态稳定性用于校正主对象选择
- 对象类型只作为最后兜底裁决

非主对象只用于支撑主对象继续推进，默认承担：

- 依据
- 边界
- 风险
- 未决

其中：

- 依据可以细分为当前依据与追溯指针
- 例外默认作为边界的特殊子类处理
- 未决可以附带风险说明，但两者治理上仍应分开

## 拆条规则

handoff 条目的拆分规则应显式区分硬条件与软条件：

- 若出现第二主判断或独立下游动作，必须拆条
- 若只是条目过载、状态过杂、阅读负担过高，则强烈建议拆条

为避免把次要命名问题过度制度化，L 层当前只要求：

- 条目主句能表达主判断
- 条目主句能表达下游方向

除此之外，不要求在 1.0 阶段引入更细的命名算法。

## 条目字段与包层字段的最小治理集

在条目字段层，L 层当前建议采用最小可推进集：

- 主判断
- 状态层级
- draft 标记（可选）
- 下游方向
- 依据摘要 + 追溯指针
- 未决 / 风险提示

在包层字段上，L 层建议保持轻治理外壳：

- 当前目标
- 整体状态
- 适用范围 / 主题边界
- 条目列表
- 整体未决提醒

其中，整体状态建议采用轻量双轴：

- 交接形态：草稿 / 正式（draft / formal）
- 收敛成熟度：进行中 / 可交接 / 已发布

## handoff 与状态账本的关系

交接物（handoff）不复制整份状态账本，而是条件吸收最小可继续推进状态上下文。

当前基线是：

- 默认只吸收阶段结论
- 只有当前推进卡住时，才补阻塞原因和下一步方向

这里所说的“下一步方向”默认不展开成执行清单，而只保留下一阶段或一条轻动作提示。

当阶段结论尚未被最新判定覆盖时，handoff 默认保留旧阶段结论，同时补一条“最新判定未生效”的轻提示。

只有当这条未生效更新已经影响下游主要动作时，才将其升为独立槽位。

## 进入交接阶段后的首个推进检查点

进入结构化交接阶段后，首个推进检查点默认不先看包装是否完整，而先看交接分层是否已经成立。

当前顺序是：

- 先看已确认内容、高置信未确认内容、未决问题是否已经能够分开
- 再看条目主对象是否已经可选
- 再看包层最小结构是否可成立

如果三层状态暂时还分不开，默认先停留在交接阶段的首个推进检查点，并优先在交接阶段内整理分层。

只有当这类混写已经说明上游阶段结论本身不成立时，才从交接阶段显式回流。

## 交接阶段的主链次序

当首个推进检查点通过后，交接阶段默认不先组包，而先进入条目编排。

当前主链次序是：

1. 先做条目编排
2. 再由条目结果反推包层组装

条目编排的第一个默认动作是先选主对象，再围绕主对象决定是否分条，以及如何承接已确认 / 高置信未确认 / 未决分层。

只有当条目编排失败已经反证上游阶段结论不成立时，才触发显式回流。

## 包层组装主骨架

包层组装拿到条目结果后，默认不先定整体状态或主题边界，而先判断这些条目是否已经足以支撑整包成立。

这里所说的“足以支撑整包成立”，当前至少要求：

- 已经形成能承接整包主轴的主条目
- 三层分层已经成立
- 没有会污染整包的关键冲突或关键未决

当条目足以支撑整包成立后，整体状态默认先定收敛成熟度，再据此约束草稿 / 正式形态。

## 主题边界与整体未决汇总

包层主题边界默认不从全部条目机械并集反推，而是先从主条目反推，再用其他条目做边界校正。

整体未决提醒默认也不直接收所有条目未决，而是先收会影响整包使用的未决，再用主条目未决与跨条目未决做补强。

## 映射与编排规范

交接物（handoff）条目采用对象编排，不采用机械对象镜像。

每条条目必须存在且只存在一个主对象，其余对象只能作为非主对象附着其上。

主对象判定默认采用以下顺序：

1. 下游作用优先
2. 状态稳定性校正
3. 对象类型兜底

## 已确认决策进入交接物的门槛

一个刚形成的已确认决策（confirmed decision）进入结构化交接包（handoff package）的“已确认内容”时，默认不要求机械地先等一轮，但必须先检查：

- 这次确认本身是否足够明确
- 影响范围是否已经清楚
- 是否仍存在会污染这次确认含义的关键未决或关键冲突

## 共存、复用与拆条规范

已确认内容与高置信未确认内容允许条件共存，但未确认部分只能作为边界补充、风险说明或小范围保留项。

一旦未确认部分会触发独立下游动作，就必须拆条，不能因为它只是“补充说明”而继续挂在同一条里。

## 标题、字段与复杂度控制

对于条目标题、命名或展示主句，L 层只保留最小要求：

- 能表达主判断
- 能表达下游方向

同样地，交接物（handoff）条目字段只保留最小要求，不鼓励在 1.0 阶段提前扩成重结构：

- 主判断必须存在
- 状态层级必须清楚
- 下游方向必须可见
- 依据必须至少能回答“为什么当前可以这样交接”
- 未决与风险必须至少以轻量方式显性化
