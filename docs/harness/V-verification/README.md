# V 层宪法：验证（Verification）

> 当前成熟度层级：`L2 对象与流程定义层`
> 编码门槛：`未达到 L3，不应直接作为稳定实现规格；需继续把治理规则压成可执行校验项`

## 1. 这一层回答什么问题

V 层回答：

- 系统如何证明自己没有乱来
- 哪些输出算通过，哪些输出必须被拦住
- 如何防止“看起来像对的”混进事实层

V 层是 EvoCanvas 从“会生成”走向“可交付”的关键层。

## 2. EvoCanvas 的验证立场

在 EvoCanvas 中，验证的对象不是“文风好不好”，而是：

- 对象是否结构正确
- 流程是否符合产品原则
- 结论是否有来源
- 高风险动作是否经过治理

验证也必须清楚区分：

- 对话流
- 结构化对象
- 卡片回显
- 交接物（handoff）

其中，卡片只是界面映射，不是事实来源；handoff 是聚合性交付物，不是原始依据。

## 3. V 层设计原则

### 3.1 生成与验证必须分离

提出提案（proposal）的组件，不能是唯一的裁判者。

### 3.2 验证先于生效

重要对象在进入已确认事实（confirmed truth）之前，必须先经过验证。

### 3.3 验证以确定性规则为基础

不是所有验证都要靠另一个模型。

首先应用确定性规则检查：

- 结构模式（schema）
- 状态迁移
- 来源完整性
- 策略约束

### 3.4 用户确认是验证的一部分，但不是全部

用户确认对高风险动作很重要，但系统不能把所有验证责任都甩给用户。

## 4. 四类验证

### 4.1 结构验证

检查输出对象是否满足基本结构规则。

包括：

- 类型是否合法
- 必填字段是否齐全
- 引用是否存在
- 状态转换是否允许

### 4.2 来源验证

检查关键对象是否具备足够来源支撑。

包括：

- 是否存在来源引用（source refs）
- 是否存在证据链（evidence chain）
- 是否存在未处理冲突
- 是否能解释为什么进入当前状态

对于来源片段（source fragment）与解释对象（interpretation），还应额外验证：

- 来源片段是否只是标准化摘录，而非语义重写
- 解释对象是否能回指一个或多个明确来源片段
- 解释对象是否只承载一个核心判断
- 低置信解释是否被误当成正式结论

### 4.3 流程验证

检查系统是否违反 EvoCanvas 的产品推进原则。

包括：

- 是否在明显缺口存在时跳过待澄清阶段（clarification）
- 是否在无确认时固化高风险结论
- 是否把交接物（handoff）当作自由生成总结

### 4.4 独立评估

对高价值输出进行额外检查。

可采用：

- 规则引擎
- 独立评估者（evaluator）
- 用户确认

对 EvoCanvas 1.0，推荐从“规则引擎 + 用户确认”起步。

## 5. 必须被验证的关键对象

以下对象必须进入强验证范围：

- 已确认约束（confirmed constraint）
- 已确认决策（confirmed decision）
- 已解决待澄清项（resolved clarification）
- 正式交接物（formal handoff）
- 对外引用的快照（snapshot）

## 6. 交接物（Handoff）验证规则

交接物（handoff）是 1.0 的核心交付物，因此需要单独规则。

交接草稿（draft handoff）至少应验证：

- 是否明确当前主题
- 是否包含开放问题（open questions）
- 是否包含约束（constraints）
- 是否包含决策（decisions）或待决策候选说明
- 是否能回指上游结构化对象
- 是否对已确认内容、高置信但未确认内容、未决问题 / 待拍板事项做出清晰分层

正式交接物（formal handoff）在此基础上还应验证：

- 是否经过确认流程
- 是否不存在关键未披露冲突
- 是否没有把未确认内容伪装成已确认事实
- 是否不存在高置信但未确认内容占比超限的情况

handoff 的补充验证规则包括：

- 主体内容是否按结构化条目数计数
- 每条主体内容是否只承载一个核心判断
- 是否存在把多个不同下游动作的判断混写进同一条的情况

## 7. 待澄清项（Clarification）验证规则

待澄清项（clarification）不能只是“多问几个问题”，而要验证：

- 问题是否指向真实缺口
- 是否与已有证据（evidence）或冲突（conflict）有关联
- 是否能推动后续约束 / 决策（constraint / decision）
- 是否说明了为什么要问
- 是否说明了不回答会阻塞或污染什么

对于低置信解释（low-confidence interpretation），验证还应检查：

- 是否真的影响后续约束、决策或交接包质量
- 若不影响推进，是否被错误升级为澄清

## 8. 失败策略

验证失败时，系统不应继续硬生成，而应明确进入以下之一：

- 降级为提案（proposal）
- 回退为待澄清项（clarification）
- 请求补充信息
- 中断等待确认

## 9. 对抗式编排的验证规则

当 EvoCanvas 启用发散者-收敛者-裁判者模式时，验证层必须额外回答两个问题：

- 发散是不是过度了
- 收敛是不是过早了

### 9.1 发散过度的判断标准

以下情况应被视为发散质量不足或发散过度：

- 提出的问题与当前主题无关
- 重复提出等价待澄清项（clarification）
- 无来源支撑地制造新冲突
- 打开大量低价值分支，妨碍推进

验证动作应包括：

- 去重
- 相关性检查
- 来源链检查
- 推进价值排序

### 9.2 收敛过早的判断标准

以下情况应被视为错误收敛：

- 在明显缺口存在时形成稳定约束
- 把冲突压缩成模糊中间说法
- 在没有足够证据（evidence）时形成待决策候选（decision candidate）
- 在未解决待澄清项（unresolved clarification）过多时直接生成看似完整的交接物（handoff）
- 把解释对象（interpretation）直接越级写成已确认决策（confirmed decision）
- 把偏好（preference）误写成约束（constraint）

验证动作应包括：

- 待澄清完整性检查（clarification completeness check）
- 冲突保留检查（conflict preservation check）
- 证据充分性检查（evidence sufficiency check）
- 交接物完整性检查（handoff completeness check）

### 9.3 裁判结果也需要被验证

裁判者不是天然正确。

裁判结果仍应接受以下检查：

- 是否引用了明确的验证规则
- 是否解释了为什么放行或驳回
- 是否错误放过了高风险动作
- 是否无故压制了高价值 clarification

### 9.4 复杂回合的最小验证闭环

对于三角编排，建议最小闭环为：

1. 验证发散结果的相关性和来源性
2. 验证收敛结果的结构性和非跳步性
3. 验证裁判结果的规则依据
4. 验证最终提案（proposal）是否满足进入治理流的最低条件

## 10. 设计禁令

- 不允许把“模型说得像”当作验证通过
- 不允许让生成模块自己判定自己已足够正确
- 不允许在来源断裂时生成 confirmed truth
- 不允许把用户确认当成系统唯一验证器
- 不允许把发散者和收敛者之间的争论本身当作验证完成
- 不允许让裁判者在无规则依据时拍脑袋决定结果

## 11. 1.0 最小落地要求

EvoCanvas 1.0 的 V 层至少应具备：

- 结构模式校验（schema validation）
- 状态迁移校验（validation）
- 来源链校验（validation）
- 流程规则校验（validation）
- 高风险动作的用户确认校验（validation）
- 交接物（handoff）的专门校验（validation）
- 发散过度与收敛过早的附加校验（validation）

此外，至少应补充以下对象级校验：

- source fragment（来源片段）的标准化摘录校验
- interpretation（解释对象）的单核心判断校验
- clarification（待澄清项）的“问题 / 原因 / 后果”完整性校验
- constraint（约束）的“内容 / 依据 / 影响范围”完整性校验
- decision candidate（待决策候选）的“选项 / 推荐 / 影响”完整性校验
