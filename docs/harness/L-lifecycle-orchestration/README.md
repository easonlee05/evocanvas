# L 层宪法：生命周期与编排（Lifecycle & Orchestration）

> 当前成熟度层级：`L3 可指导实现的治理规格层`
> 编码门槛：`已达到 L3，可直接指导第一批主流程实现；后续仍应继续向 L4 收紧`

## 1. 这一层回答什么问题

L 层回答：

- EvoCanvas 如何推进一张画布
- 一轮输入进入后应该先做什么、后做什么
- 什么情况下可以继续推进，什么情况下必须中断

L 层的核心不是多 agent 花样，而是产品收敛顺序。

## 2. EvoCanvas 的生命周期定义

EvoCanvas 的主生命周期不是“用户说一句，AI 回一句”，而是：

- 从混乱输入
- 到显性问题
- 到约束与待决策
- 到结构化交接

因此，L 层本质上是 `收敛编排层`。

## 3. L 层设计原则

### 3.1 先暴露不确定性，再推动结论

这是 EvoCanvas 的最高编排原则。

### 3.2 编排围绕阶段，不围绕话术

用户说话可以自由，但系统推进必须受阶段约束。

### 3.3 高影响动作应中断式推进

当系统即将做出会改变事实边界的动作时，必须允许暂停并等待确认，而不是一气呵成。

### 3.4 交接物（handoff）是阶段产物，不是聊天附赠品

交接物（handoff）必须建立在已有对象基础上收束生成，不能作为一句 prompt 的直接副产物。

进一步说，画布中的卡片只是结构化对象的界面映射，不是事实来源本身。L 层编排应围绕结构化对象流转，而不是围绕卡片外观流转。

### 3.5 低置信度时先保护真实性，再允许带风险推进

当系统收敛置信度不足时，L 层的默认动作不是继续压缩，而是增强透明披露。

此时系统可以：

- 输出可推进草稿
- 显示未决问题、冲突边界和风险提醒

但系统不应：

- 直接把中间态包装成稳定结论
- 默认关闭关键待澄清项

只有在用户再次明确要求推进时，系统才允许继续进行带风险收敛。

## 4. EvoCanvas 1.0 的五段主流程

### 4.1 输入接入（Intake）

目标：

- 接住新输入
- 确定输入主题和范围
- 识别输入类型

允许产物：

- 来源对象（source）
- 接入回执（intake receipt）
- 范围提示（scope hint）

### 4.2 输入编译（Compilation）

目标：

- 从多源输入中提取来源片段、解释对象、问题、冲突、术语和潜在边界

允许产物：

- 来源片段（source fragment）
- 解释对象（interpretation）
- 问题框定（problem framing）
- 待澄清候选（clarification candidate）

### 4.3 待澄清显影（Clarification）

目标：

- 显性化未知项、冲突项、歧义点和缺失前提

允许产物：

- 待澄清队列（clarification queue）
- 冲突标记（conflict marker）
- 问题包（question bundle）

澄清（clarification）的编排逻辑应遵守：

- 不是所有低置信解释都升级为澄清
- 只有会影响后续约束、待决策或交接包质量的信息缺口，才升级为澄清
- 澄清既可以针对事实缺口，也可以针对意图缺口

### 4.4 约束 / 决策收敛（Constraint / Decision Convergence）

目标：

- 把足够稳定的内容沉淀成约束
- 把必须人拍板的部分转成待决策

允许产物：

- 约束候选（constraint candidate）
- 待决策候选（decision candidate）
- 方案对比（option comparison）

这一阶段默认建立在以下链路之上：

- 来源片段（source fragment）
- 解释对象（interpretation）
- 待澄清项（clarification）
- 约束 / 待决策 / 已确认决策

也就是说，约束与决策不应直接从原始聊天文本越级生成，而应经过可追溯的理解层和必要的缺口治理。

### 4.5 结构化交接（Handoff）

目标：

- 把当前已知与未知一起打包成交接物

允许产物：

- 交接草稿（draft handoff）
- 正式交接候选（formal handoff candidate）
- 快照触发（snapshot trigger）

handoff 在编排上应显式区分三层内容：

- 已确认内容
- 高置信但未确认内容
- 未决问题 / 待拍板事项

## 5. 阶段切换条件

### 5.1 从输入接入（Intake）到输入编译（Compilation）

当输入已被接住并归入明确主题后，才进入输入编译（Compilation）阶段。

### 5.2 从输入编译（Compilation）到待澄清显影（Clarification）

只要存在以下任一情况，就必须进入 clarification（待澄清阶段）：

- 输入之间冲突
- 关键概念指代不清
- 缺少关键范围
- 风险边界不明

### 5.3 从待澄清显影（Clarification）到约束 / 决策收敛

只有当部分问题足够清楚，系统才允许将其升级为：

- 约束候选（constraint candidate）
- 待决策候选（decision candidate）

若某个澄清被回答，默认应先回流更新解释对象（interpretation），再判断是否已经足以形成约束或待决策。

### 5.4 从约束 / 决策收敛到结构化交接（Handoff）

交接物（handoff）不要求所有问题解决完，但要求当前结构已足够清楚，可以被继续推进。

handoff 必须同时包含：

- 当前已确认或较稳定内容
- 仍未解决的问题和边界

handoff 的目标不是“写出一份像成品的总结”，而是“生成一个能让下游继续推进且不失真的结构化上下文包”。

当待拍板事项已经成为当前推进主轴时，handoff 应将其从普通未决问题中抬升为独立槽位。

## 6. 中断点设计

L 层必须定义中断点，而不是默认一路自动执行。

建议至少设置以下中断点：

- 输入含明显冲突时
- 试图生成高风险对象时
- 试图关闭关键待澄清项（clarification）时
- 试图发布正式交接物（formal handoff）时

## 7. 角色分工原则

角色不是为了“多 agent 炫技”，而是为了把流程职责拆清楚。

建议角色职责如下：

- Input Compiler（输入编译者）：负责接住和编译新输入
- Interpreter（解释整理者）：负责形成可挑战的解释对象
- Clarifier（澄清者）：负责识别未知、冲突和缺口
- Constraint Steward（约束整理者）：负责沉淀候选约束
- Decision Steward（决策整理者）：负责形成候选待决策项
- Handoff Builder（交接构建者）：负责收束结构化交接物

所有角色都只拥有建议权，不天然拥有事实生效权。

其中，Interpreter（解释整理者）的职责尤其关键，因为它承接来源片段与正式判断之间的中间理解层，直接决定系统是否具备“可挑战、可纠偏”的收敛路径。

## 8. 复杂回合的三角编排

对于低复杂度回合，EvoCanvas 可以使用简单单轮编排。

但对于以下情况，建议启用“发散者-收敛者-裁判者”三角编排：

- 输入信息明显冲突
- 同时存在多个候选方案方向
- 当前主题边界模糊，无法直接形成稳定对象
- 准备生成交接物（handoff），但待澄清项（clarification）仍较多
- 系统判断当前回合存在过早收敛风险

### 8.1 三个角色的编排职责

#### 发散者

目标：

- 尽可能发现关键未知项、风险点和分叉路径

允许输出：

- 待澄清候选（clarification candidates）
- 冲突候选（conflict candidates）
- 方案分支（option branches）
- 缺失前提（missing assumptions）

不允许：

- 关闭问题
- 直接形成已确认事实（confirmed truth）

#### 收敛者

目标：

- 把发散结果压回结构化对象，并形成最小可推进结构

允许输出：

- 来源片段（source fragment）
- 解释对象（interpretation）
- 待澄清项（clarification）
- 约束候选（constraint candidate）
- 待决策候选（decision candidate）
- 交接草稿片段（handoff draft fragments）

不允许：

- 隐去关键冲突
- 越过确认直接固化高风险对象

#### 裁判者

目标：

- 检查当前回合是否应继续发散、允许收敛，还是必须中断

允许输出：

- 允许进入提案流（approve for proposal）
- 以低价值发散驳回（reject as low-value divergence）
- 打回补更多证据（send back for more evidence）
- 要求用户确认（require user confirmation）

不允许：

- 偷偷替任一角色补写事实内容

### 8.2 建议的单轮循环

复杂回合建议按以下顺序执行：

1. 发散者读取输入、现有对象和未决问题
2. 发散者提出冲突、缺口和候选分支
3. 收敛者把可保留结果映射为结构化提案（proposal）
4. 裁判者检查：
   - 发散是否有价值
   - 收敛是否过早
   - 来源是否足够
   - 是否触发高风险门禁
5. 若通过，则进入治理 / 验证 / 确认流
6. 若不通过，则回退为待澄清（clarification）、补证据或继续发散

### 8.3 循环次数约束

这套编排不应无限循环。

建议约束：

- 单回合最多 1 次主发散 + 1 次主收敛 + 1 次裁判
- 若裁判判定仍不足，则回退到下一轮用户交互或下一轮系统推进

原因是：

- EvoCanvas 的目标是稳定推进，不是内部无限辩论

### 8.4 启用条件与退出条件

启用条件：

- 当前回合复杂度高
- 当前主题存在明显未决冲突
- 直接收敛有较高失真风险

退出条件：

- 已形成足够清晰的待澄清项 / 约束候选 / 待决策候选（clarification / constraint / decision candidate）
- 裁判者判定继续发散收益下降
- 已触发用户确认或人工裁决点

### 8.5 回退策略

若三角编排未通过，系统应回退到以下之一：

- 待澄清队列（clarification queue）扩充
- 证据（evidence）补充请求
- 方案探索（option exploration）延迟
- 交接物（handoff）暂缓生成
- 用户裁决请求

这类回退应被视为正确的收敛保护，而不是失败。

## 9. 交接物（Handoff）的编排规则

交接物（handoff）生成必须满足以下原则：

- 来源于当前结构化对象，而不是重新自由生成
- 同时包含已知与未知
- 不得掩盖未解决待澄清项（unresolved clarification）
- 不得绕过确认把草稿（draft）冒充正式版（formal）

交接物（handoff）的默认编排单位不是原话，也不是聊天回合，而是已经形成的结构化对象。也就是说，交接物（handoff）条目应优先承接：

- 解释对象（interpretation）
- 约束（constraint）
- 待决策（decision candidate）
- 已确认决策（confirmed decision）

来源片段（source fragment）默认作为这些条目的追溯依据存在，而不是直接成为 handoff 的主要写作单位。

关于 handoff 的内部结构，还应满足：

- 高置信但未确认内容默认不应超过主体内容的三分之一
- 若超过该阈值，handoff 只能保持 draft 状态
- handoff 主体内容按结构化条目数计数
- 每条主体内容只承载一个核心判断

进一步说，handoff 条目默认采用“单主对象编排”，而不是自由聚合：

- 每条条目必须有唯一主对象
- 主对象优先由下游作用决定
- 状态稳定性用于校正主对象选择
- 对象类型只作为最后兜底裁决

非主对象只用于支撑主对象继续推进，默认承担：

- 依据
- 边界
- 风险
- 未决

其中：

- 依据可以细分为当前依据与追溯指针
- 例外默认作为边界的特殊子类处理
- 未决可以附带风险说明，但两者治理上仍应分开

拆条规则也应显式区分硬条件与软条件：

- 若出现第二主判断或独立下游动作，必须拆条
- 若只是条目过载、状态过杂、阅读负担过高，则强烈建议拆条

为避免把次要命名问题过度制度化，L 层只要求：

- 条目主句能表达主判断
- 条目主句能表达下游方向

除此之外，不要求在 1.0 阶段引入更细的命名算法。

在条目字段层，L 层建议采用最小可推进集，而不是完整穷举集：

- 主判断
- 状态层级
- draft 标记（可选）
- 下游方向
- 依据摘要 + 追溯指针
- 未决 / 风险提示（默认同槽，必要时再拆开）

在包层字段上，L 层建议保持轻治理外壳，而不是重审计外壳：

- 当前目标
- 整体状态
- 适用范围 / 主题边界
- 条目列表
- 整体未决提醒

其中，整体状态建议采用轻量双轴：

- 交接形态：草稿 / 正式（draft / formal）
- 收敛成熟度：进行中 / 可交接 / 已发布

对于复杂回合，交接物（handoff）的上游建议优先来自三角编排的收敛结果，而不是直接自由生成。

## 10. 设计禁令

- 不允许在存在明显缺口时直接输出稳定结论
- 不允许把交接物（handoff）当作任何阶段都能随手生成的总结
- 不允许把大量未确认内容堆叠后仍包装成正式交接物（formal handoff）
- 不允许在单条交接物（handoff）内容中混写多个可独立成立的判断
- 不允许让高影响动作一路自动推进到底
- 不允许用“对话顺畅”替代“状态正确”

## 11. 1.0 最小落地要求

EvoCanvas 1.0 的 L 层至少要做到：

- 明确的五段主流程
- clarification 优先于结论固化
- 高风险动作可中断等待确认
- 交接物（handoff）依赖已有对象结构生成
- 每轮推进都能映射到清晰的阶段语义
- 复杂回合可选启用三角编排，而不是永远单线直出
