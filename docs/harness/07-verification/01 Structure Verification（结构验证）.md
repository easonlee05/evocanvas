# Structure Verification（结构验证）

> 当前成熟度层级：`L3 可指导实现的治理规格层`

## 1. 这一层回答什么问题

结构验证回答：这个对象、关系或动作载荷在形式上能不能成立。

它不判断内容真假，也不决定对象是否生效。它只先守住承载面：对象类型、必填字段、引用、状态、关系与动作参数是否足够完整。

## 2. 正式对象层的最小结构要求

所有进入正式对象层的卡片至少需要：

- 对象 ID。
- 对象类型。
- 标题或摘要。
- 当前状态。
- 当前栏目或主题归属。
- 最小来源锚点，或明确的来源缺失提示。
- 创建方式：AI 自动生成、用户手动创建、导入或编辑。

如果这些最小字段不成立，对象不应继续进入待确认、已生效、已决定或已确认状态。

## 3. 按对象类型检查

### 3.1 证据卡

至少需要：来源类型、来源摘要、与当前主题的关联。

### 3.2 问题卡

至少需要：问题表达、问题所指向的主题、关联输入或来源缺失提示。

### 3.3 待澄清卡

至少需要：具体待确认问题、为什么需要澄清、阻塞范围、当前状态。

### 3.4 约束卡

至少需要：约束内容、约束类型、当前状态、确认方式或来源依据、冲突标记位。

### 3.5 待决策 / 方案承接卡

至少需要：决策主题、候选解释或建议方案、影响范围、关联待澄清或冲突信息、当前状态。

### 3.6 交接物承接卡

至少需要：

- 当前交接主题
- 背景输入摘要
- 已确认约束
- 已完成决策
- 未解决问题
- 待确认决策
- 推荐后续动作
- 关键来源引用
- 当前状态

## 4. 关系结构检查

卡片关系至少需要：

- 起点对象。
- 终点对象。
- 关系类型。
- 创建方式。

首版关系类型包括：来源于、澄清了、支持、阻塞、冲突于、产出为。

如果关系未能成功建立：

- 不得连带隐藏已经成立的卡片本体。
- 不得伪造关系填补空洞。
- 应允许工作面保留对象，但显式暴露关系缺失。

## 5. 状态结构检查

结构验证必须阻止非法状态跳跃。

例如：

- 待澄清卡不能绕过待确认语义，直接被写成已关闭或已澄清。
- 约束卡不能从草稿中直接进入已生效，必须先经过待确认。
- 待决策 / 方案承接卡不能从待判断直接进入已决定，必须先经过待确认。
- 交接物承接卡不能从草稿中直接进入已确认。

结构验证只判断状态流转是否合法；是否真的允许生效，仍由治理层决定。

## 6. 动作结构检查

验证对象不只有卡片，也包括准备执行的动作。

以下动作在结构上必须可表达：

### 6.1 轻确认动作

跨栏目或跨阶段迁移的轻确认至少需要：

- 当前对象是谁。
- 原栏目与目标栏目。
- 这次迁移会带来的语义变化。
- 确认 / 取消入口。

### 6.2 确认请求动作

高影响动作的确认请求至少需要：

- 准备执行什么。
- 为什么这属于高影响动作。
- 会影响哪些对象、状态或交接结果。
- 用户可确认或取消。

### 6.3 变化摘要条目

如果系统声称“已新增 / 已更新 / 已关闭 / 建议确认”，对应条目至少要能回指实际对象或动作，不得只给抽象描述。

## 7. 工作面一致性检查

结构验证还需要检查用户看见的工作面是否站得住：

- 变化摘要里提到的对象，画布上应能找到。
- Active Todos 里显示的缺口，至少要回指一个待澄清、约束、待决策或交接相关对象。
- 里程碑状态变化不能脱离底层对象状态独立漂移。
- 被标记为已过时的交接物，必须存在触发它过时的依赖变化。
