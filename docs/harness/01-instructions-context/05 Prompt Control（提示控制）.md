# Prompt Control（提示控制）

> 当前成熟度层级：`L2 对象与流程定义层`

## 1. 这一层回答什么问题

本文档定义 EvoCanvas 如何把指令组织成模型当前回合可执行的语言控制面。

这里的提示控制，不是“写一段更聪明的 prompt”，而是把 harness 已经定义好的产品原则、阶段目标、对象边界、验证要求和治理约束，翻译成模型本轮必须遵守的行动边界。

它服务的是 EvoCanvas 1.0 的 `Vibe Shaping`：

```md
感觉接入 -> 对话塑形 -> 结构收敛 -> 画布显影 -> 结构化交接
```

因此，提示控制的目标不是让 AI 更快给答案，而是让 AI 在正确阶段做正确动作，并把不确定性、冲突、待确认动作和对象地位表达清楚。

## 2. 它和指令、上下文的关系

提示控制属于 `01-instructions-context/`，因为它同时依赖两件事：

- 指令：规定模型应该怎样行动、怎样克制、怎样排序。
- 上下文：规定模型当前基于什么工作面行动。

提示控制不独立定义产品目标，也不独立定义对象模型。它只负责把已有规则转成当前回合可执行的语言约束。

可以理解为：

```md
产品规则 + 当前上下文 -> 当前回合语言控制面
```

## 3. 核心职责

EvoCanvas 的提示控制至少承担六类职责：

1. 固定 AI 的协作姿态：像产品同事一样先理解、命名、拆解和追问。
2. 缩窄本轮动作空间：明确当前是在理解 vibe、追问、显影、沉淀约束、形成待决策，还是收束交接。
3. 压住对象地位：防止解释对象、待澄清、约束草稿、待决策和交接物互相冒充。
4. 外显风险边界：把未决问题、冲突、未确认前提和当前收敛置信度带出来。
5. 约束写入动作：低风险整理可以建议或自动应用，高影响动作必须确认。
6. 形成可继续推进的回执：让用户和下一轮 AI 都知道本轮推进了什么、还悬着什么。

## 4. 全局基座控制

全局基座控制是所有回合都必须遵守的语言边界。

它至少包含：

- 透明优先，不抢先下结论。
- 冲突不得静默合并。
- 信息不足时可以给出可推进草稿，但必须显式披露边界。
- 草稿不得伪装成稳定结论。
- 高影响内容不得自行宣布生效。
- 任何进入“已确认”或“已生效”的内容，都必须能追溯到来源、确认方式或用户裁决。

当全局基座控制与当前阶段目标发生冲突时，全局基座优先。

例如：

- 当前阶段想继续收束，但来源冲突尚未解释，系统应先显性化冲突。
- 用户要求“直接定下来”，但该结论缺少来源或确认，系统只能给带风险边界的草稿。
- 回执看起来可以写得更完整，但未决问题仍存在，系统必须把未决问题保留下来。

## 5. 阶段控制

阶段控制负责把当前回合绑定到一个明确推进目标，而不是让 AI 每次都用同一种回答方式工作。

EvoCanvas 1.0 的阶段控制至少要覆盖：

| 阶段 | 本轮允许做什么 | 本轮不应做什么 |
| --- | --- | --- |
| 感觉接入 | 接住原始表达，识别它更像 vague vibe、事实材料、问题表达、方案想法、约束线索还是待决策线索 | 要求用户先写完整需求 |
| 对话塑形 | 复述理解、命名、拆解、提出具体追问 | 直接生成完整方案或大量画布对象 |
| 结构收敛 | 提取事实、问题、冲突、缺口，生成待澄清、约束候选或待决策候选 | 把候选内容直接写成稳定结论 |
| 画布显影 | 在语义边界、来源线索和栏目归属足够清楚时显影为卡片、关系和缺口投影 | 把不稳定内容强行落成正式对象 |
| 结构化交接 | 打包已知、未知、已决和未决，形成可继续推进的产品上下文 | 抹平未决问题或宣布自动可外发 |

阶段控制每轮至少应明确：

1. 当前阶段目标是什么。
2. 当前允许哪些动作。
3. 当前禁止哪些越级动作。
4. 当前主对象是什么。
5. 本轮回执至少要披露什么。
6. 本轮建议去向是什么。

## 6. 对象地位控制

对象地位控制负责防止模型把“看起来合理的文字”误写成“已经成立的事实”。

EvoCanvas 1.0 至少要压住以下对象地位：

- 来源片段：只能表达原始输入里说了什么，不能替系统下结论。
- 解释对象：表达当前理解，但必须保持可挑战。
- 待澄清项：表达缺口或冲突，不能写成已解决答案。
- 约束草稿：表达可能成立的边界，不能写成已生效约束。
- 待决策候选：表达需要 PM 拍板的事项，不能写成已决定结果。
- 已确认决策：必须有确认记录或用户裁决，不能由模型自行宣布。
- 结构化交接物：打包当前状态，必须保留未决边界，不能伪装成完整最终 PRD。

对象提示真正要控制的不是字段数量，而是对象地位。

常见偏航包括：

- 把解释对象写成结论。
- 把待澄清项写成建议答案。
- 把待决策候选写成默认已决定。
- 把交接物写成没有风险边界的最终交付。

## 7. 右侧 AI 助手的提示控制

右侧 AI 助手是提示控制最主要的运行入口。

它不是普通聊天框，而是把自然语言编译成画布变化的工作入口。

因此，每轮提示控制都应帮助 AI 助手稳定完成：

1. 识别意图。
2. 定位对象。
3. 判断是追问、显性化冲突、沉淀约束、生成待决策，还是生成交接物。
4. 生成更新建议。
5. 根据风险等级应用、挂起或请求确认。
6. 输出变化摘要。

当用户引用某张卡片继续讨论时，提示控制应显式要求模型围绕这张卡片的对象地位、来源关系、待澄清项、约束和待决策来回应，而不是泛泛回到整个项目历史。

## 8. 自动写入与确认边界

提示控制必须区分三类动作。

### 8.1 可以低风险自动整理

适用于：

- 证据卡补充
- 问题卡草稿
- 待澄清卡
- 约束说明补充
- 弱关系建议
- 变化摘要

即使自动整理，也必须保留来源和回执。

### 8.2 必须建议确认后写入

适用于：

- 新建待决策 / 方案承接卡
- 待澄清卡改为已澄清
- 约束卡改为已生效
- 生成结构化交接物
- 推进或更新当前里程碑

这类动作要进入确认请求，而不是被模型静默写入。

### 8.3 只追问，不写入

适用于：

- 指代不清
- 前后冲突
- 来源不足
- 约束存在多种解释
- 决策表达不完整
- 输入更像情绪判断而非业务判断

此时提示控制应让 AI 先输出具体追问，而不是强行落图。

## 9. 回执与交接表达

回执不是简单总结，也不是装饰性结尾。

它是用户理解本轮推进、系统进入下一轮上下文装配的重要压缩层。

每轮回执至少要表达：

1. 本轮新增了什么。
2. 本轮更新了什么。
3. 本轮关闭了什么。
4. 哪些内容仍未确认。
5. 是否存在冲突、缺口或降级提醒。
6. 下一步建议去向是什么。

当进入结构化交接时，交接表达应至少带出：

- 当前主题
- 输入背景
- 已确认约束
- 已完成决策
- 仍未解决的问题
- 待确认决策
- 推荐后续动作

交接表达不能补写上游没有给出的事实，也不能宣布验证通过或治理放行。

## 10. 与思维链的边界

思维链（CoT）不是 EvoCanvas 的主交付对象。

EvoCanvas 需要对用户显性化的是：

- 未决问题
- 冲突边界
- 未确认前提
- 当前收敛置信度
- 对象是否降级
- 哪些动作需要确认

系统不默认对外暴露完整内部推理过程，也不把内部推理过程当成治理依据。

透明性来自边界可见、来源可追溯、状态可解释，而不是来自暴露完整推理文本。

## 11. 设计禁令

以下做法应被视为提示控制失效：

1. 用一段 prompt 替代验证或治理。
2. 让阶段目标覆盖全局风险边界。
3. 让对象控制直接宣布对象生效。
4. 让回执补写上游没有给出的事实。
5. 把未确认草稿整理得像稳定结论。
6. 把结构化交接物写成完整传统 PRD。
7. 把内部推理过程当成对外交付物。
8. 为了回答顺滑而省略待澄清、冲突或待确认动作。

## 12. 最小落地口径

当后续进入实现或模板设计时，每个可执行提示至少要回答：

1. 当前回合属于哪个产品阶段。
2. 当前阶段允许哪些动作。
3. 当前阶段禁止哪些越级动作。
4. 当前主对象是什么。
5. 当前对象不能冒充什么地位。
6. 当前必须披露哪些边界。
7. 当前是否允许写入，还是必须确认或追问。
8. 当前回执应如何压缩本轮变化。

如果这八项没有回答清楚，就不应把提示文本当成稳定实现规格。
