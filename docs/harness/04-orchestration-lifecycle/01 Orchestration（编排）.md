# Orchestration（编排）

> 方法成熟度：`L3 可指导实现的治理规格层`
> 目标实现归属：`Pi Agent Core 原生 Tool Loop`
> 当前实现状态：`原生编排已接入，推进顺序待验证`
> 实现说明：本文描述推进顺序和不变量，不定义 Supervisor、阶段路由器或独立编排组件。

## 1. 控制目标

让同一个 Pi 根据当前上下文选择下一步，同时确保任何路径都不能绕过来源、确认、版本和副作用边界。

## 2. Pi 可选择的下一步

Pi 在一个正常 Tool Loop 中可自主选择：

- 直接回答或解释；
- 追问缺失信息；
- 读取对象、历史或来源；
- 应用适合的 Skill；
- 比较候选方案；
- 展示一个待确认的稳定变更；
- 在确认充分后调用语义提交工具；
- 在明确授权后调用外部副作用工具。

EvoCanvas 不输出 `stage`、`next_action`、置信阈值或触发提示来替 Pi 作语义选择。

## 3. 强制顺序不变量

1. 精确引用前先读取对应对象或来源。
2. 发现冲突时先显性化，不静默选择一方。
3. Pi 推断要稳定化前先展示含义、范围、依据和影响。
4. 用户确认后才可提交对应语义操作。
5. 提交成功后才可让 Canvas 显影。
6. 外部不可逆动作在工作包确认之外另取行动授权。

这些是不变量，不是要求每个任务机械经过的阶段。

## 4. 用户反馈处理

- 补充信息：继续当前 Session，必要时更新候选。
- 否定候选：候选留在历史，不产生稳定撤回动作。
- 修改范围：重新展示受影响内容并取得新确认。
- 直接编辑：提交新 Revision，下一轮 Pi 自然读取。
- 中断或转题：Pi 保留 Session 历史；未确认候选不进入工作包。

## 5. 并发与去重

编排不维护产品侧租约。Pi Main Lane 的技术并发由 Pi 管理；稳定状态并发由 `base_revision_id` 和幂等键管理；投影和通知由 Outbox 事件 ID 去重。

## 6. 失败与恢复

| 失败 | 恢复 |
| --- | --- |
| Skill 不可用 | 允许普通对话，禁止声称已应用该方法 |
| 读取失败 | 明示缺口，可继续无关分析，不提交依赖该来源的结论 |
| 确认不清晰 | 留在 Session 继续澄清 |
| 版本冲突 | 读取差异，重做受影响确认 |
| 提交成功但回复失败 | 以 Revision 为准，恢复后解释已发生变更 |
| 投影失败 | 从 Revision 重建，不重新运行语义收敛 |

## 7. 观测要求

使用 Pi Trace 记录模型、Skill、工具和技术终态；使用提交元数据记录确认、操作、Revision 和依赖影响。不得为“编排过程”复制一套产品运行日志。

## 8. 验收场景

1. 简单事实问答可直接结束，不被迫创建对象。
2. 模糊需求可多轮追问，直到用户确认前均无稳定写入。
3. 用户明确确认后，同一 Pi 直接提交，无调度器或第二模型裁决。
4. 直接编辑产生 Revision 后，不创建编排任务唤起 Pi。
5. 任何路径调用外部工具前都能证明存在匹配授权。
