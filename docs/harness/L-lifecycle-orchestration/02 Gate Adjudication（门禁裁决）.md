# 门禁裁决（Gate Adjudication）

> 当前成熟度层级：`L3 可指导实现的治理规格层`
> 编码门槛：`已达到 L3，可直接指导第一批高影响动作拦截实现`

本文件展开 L 层中的门禁裁决主干，集中保存高影响动作定义、双层挂载口径、最强触发条件、确认请求最小内容与确认后的默认顺序。

## 这一层回答什么问题

门禁裁决回答：

- 哪些动作不能只靠阶段内重判
- 什么情况下必须停下来要求用户确认
- 确认请求至少要包含什么
- 用户确认后，L 层默认先做什么

门禁裁决器的定位不是主调度中心，而是 `高影响动作的例外升级器`。

## 默认升级规则

L 层当前默认规则是：

- 检查点未通过时，先停留当前阶段并重判
- 只有高影响动作才从重判升级到门禁裁决

也就是说，门禁裁决器不参与所有日常推进，只处理真正会改变事实边界或下游依赖关系的动作。

## 门禁的主链挂载方式

L 层当前对门禁裁决器采用：

`事件触发为主 + 正式交接前固定门禁位`

也就是说：

- 门禁裁决器不是阶段推进器之外的第二主链
- 日常推进默认仍由阶段推进器和阶段内检查点承接
- 只有少数高影响动作按事件触发切出到门禁裁决
- `正式交接物（formal handoff）` 进入前，额外保留一个固定门禁位

当前不再增加第二个固定门禁位。

原因是：

- 需要把正式交接这个最容易污染下游的节点单独钉牢
- 同时避免把 L 层写成到处设卡的审批流
- 保持“轻量主状态机 + 稀疏高影响拦截”的主干形态

## 高影响动作定义

当前高影响动作先按两种挂载方式区分：

1. `固定门禁位`
2. `事件触发门禁`

其中：

- `正式交接物（formal handoff）` 只走固定门禁位
- `改变事实边界` 是最强事件触发条件
- `关闭关键未决` 采用条件触发，不默认一关闭就升门禁

其中，`改变事实边界` 是最强门禁触发条件。

## 改变事实边界的最强判定依据

改变事实边界的最强判定依据当前先固定为：

`状态变化`

也就是只要某个对象或判断从：

- 未确认
- 可挑战
- 候选态

进入：

- 已确认
- 已生效
- 可作为下游事实使用

就应视为触发了事实边界变化。

对象升级或下游可用性变化可以作为辅助判断，但当前不应压过状态变化这个硬触发口径。

## 关闭关键未决的条件触发口径

`关闭关键未决`

默认不是普遍审批动作，而是条件触发动作。

当前基线是：

- 只有当关闭关键未决会改写事实边界时，才升级为事件触发门禁
- 或者当它会改变交接主表达时，才升级为事件触发门禁
- 不满足上述条件时，默认留在阶段内重判，不直接切门禁

这里的 `交接主表达` 当前只限于三类：

- 主结论
- 主边界
- 主风险

不把普通摘要措辞变化一并抬升为门禁触发条件。

其中，`主风险` 当前只限于三类：

- 核心阻断风险
- 高概率失真风险
- 关键未决污染风险

这里的 `高概率失真风险` 也先收窄为以下后果型口径：

- 会让下游采取错误动作
- 会让下游错误引用边界或前提
- 会让下游把未决问题误读为稳定前提

也就是说，L 层不把一般的信息不充分直接等同于门禁风险。

## 门禁触发后的默认第一动作

当门禁裁决器接到“事实边界将发生状态变化”的信号后，默认第一动作是：

`要求用户确认`

原因是：

- 事实边界变化是 EvoCanvas 1.0 中最不应由系统自行滑过的动作
- 用户确认是最小可解释、最小越权风险的第一保护动作

`补充依据`、`回退待澄清` 可以作为后续动作，但不取代“先确认”这个第一动作。

## 确认请求的最小必要内容

当门禁裁决器触发要求用户确认时，确认请求最少必须包含：

- 拟生效内容
- 依据摘要
- 仍存未决

这样确认请求既不会轻飘到只剩“要不要确认”，也不会膨胀成整包上下文转储。

它的目标是让用户清楚知道：

- 要拍板什么
- 当前凭什么推进
- 还有哪些地方其实还没收稳

## 用户确认后的默认顺序

用户确认之后，L 层默认先：

`更新状态账本`

也就是先把“候选态 -> 已确认态”的事实变化落稳，再决定：

- 是否恢复阶段推进
- 是否触发对象升级
- 是否允许进入交接编排

这与“状态变化是事实边界最强判定依据”的主线保持一致。
