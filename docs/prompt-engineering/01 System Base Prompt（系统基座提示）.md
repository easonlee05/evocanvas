# System Base Prompt（系统基座提示）

## 1. 定位

系统基座提示是 EvoCanvas `prompt engineering` 的全局不变规则载体。

它回答的不是：

- 当前这一步怎么做

而是：

- 无论当前在哪一步，模型都必须服从哪些统一边界

## 2. 最小翻译契约

系统基座提示当前最小应翻译四类全局控制信号：

- 全局原则
- 全局禁止动作
- 强制披露义务
- 模块优先级规则

其中，全局原则至少包括：

- 透明优先，不抢先下结论
- 冲突不得静默合并
- 信息不足时允许给出可推进草稿，但必须显式披露边界
- 草稿不得伪装成稳定结论
- 高风险内容不得自行宣布生效

## 3. 输入面

系统基座提示虽然是全局不变模块，但它仍然有自己的输入面。

它当前应默认读取的，不是某一轮的具体业务内容，而是以下四类上位信息：

- 产品级收敛原则
- 全局风险禁令
- 全局披露义务
- 模块优先级规则

因此，它的内容应该尽量稳定，不应随着阶段切换频繁改写。

## 4. 输出面

系统基座提示不产出业务对象，它产出的是约束性语言信号。

这些信号至少应能稳定影响下游三件事：

- 阻止模型跳步或越权
- 阻止模型把不稳定内容包装成稳定事实
- 强制模型在输出中保留最低风险披露

如果后续写成模板，系统基座提示至少要包含以下段落：

```text
你当前始终必须遵守的规则是什么
你绝不能做的动作是什么
当信息不足或冲突存在时，你必须如何披露
当你与下游模块发生冲突时，应按什么优先级处理
```

## 5. 覆盖规则

系统基座提示当前默认拥有最高优先级。

当它与阶段提示、对象提示、回执 / 交接提示发生冲突时，默认采用：

- 单向硬覆盖
- 强制进入标准冲突回执

这意味着：

- 下游模块不得局部申请绕过
- 下游模块不得把冲突静默吞掉
- 冲突结果必须被外显，而不是只停留在内部拦截

当前最典型的覆盖场景包括：

- 阶段提示允许继续推进，但系统基座提示认为仍存在不可静默合并的冲突
- 对象提示试图把高置信草稿压成稳定对象
- 回执提示试图把未确认内容整理成像结论的表述

这些情况下，系统基座提示都应直接打断下游常规推进口径。

## 6. 常见失控点

如果系统基座提示写得太弱，最容易出现以下失控：

- 每个阶段都各写一套自己的“透明原则”，最后口径漂移
- 模型在压力下优先给答案，而不是优先暴露未决边界
- 回执看起来很完整，但悄悄把草稿和事实写混

因此，系统基座提示最怕的不是“太强”，而是“像价值观说明，但没有运行时约束力”。

## 7. 它不负责什么

- 不负责声明当前阶段
- 不负责替代对象定义
- 不负责替代验证回执
- 不负责最终治理放行
- 不负责重写 harness 已定义的对象与阶段规则

## 8. 与其他模块的关系

- 它为阶段提示提供总边界
- 它为对象提示提供统一表达纪律
- 它为回执 / 交接提示提供最低披露要求
- 它对其他三类模块拥有最终覆盖优先级

因此，系统基座提示可以被看作整个提示体系的“宪法层”。
