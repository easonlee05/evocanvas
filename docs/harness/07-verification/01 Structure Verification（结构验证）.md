# Structure Verification（结构验证）

> 当前成熟度层级：`L3 可指导实现的治理规格层`

## 1. 这一层回答什么问题

结构验证回答：这个对象、关系或动作载荷在形式上能不能成立。

它不判断内容真假，也不决定对象是否生效。它只先守住承载面：对象类型、必填字段、引用、状态、关系与动作参数是否足够完整。

## 2. 正式对象层的最小结构要求

所有进入正式对象层的卡片至少需要：

- 对象 ID。
- 对象类型。
- 标题或摘要。
- 当前类型化状态；交接物承接卡则提供对应包版本与有效治理状态引用。
- 独立验证状态。
- 当前栏目或主题归属。
- 最小来源锚点，或明确的来源缺失提示。
- 创建方式：AI 自动生成、用户手动创建、导入或编辑。

如果这些最小字段不成立，对象不应继续进入待确认、已生效、已决定或已确认状态。

## 3. 按对象类型检查

### 3.1 证据卡

至少需要：原始摘录、来源定位、结构化摘要，以及与当前主题的关联。

### 3.2 问题卡

至少需要：一个明确的实际问题、关联输入或来源缺失提示；不得把多个无关问题塞入同一张卡。

### 3.3 待澄清卡

至少需要：具体待确认问题、为什么在 Chat 后仍未解决、影响范围和当前状态。

### 3.4 约束卡

至少需要：约束内容、约束类型、适用范围、Chat 确认依据、来源依据和冲突标记位。缺少有效确认时不得创建约束卡。

### 3.5 待决策 / 方案承接卡

至少需要：决策主题、当前轻量选项、主要取舍、AI 推荐、影响范围、关联待澄清或冲突信息、当前状态。

### 3.6 交接物承接卡

至少需要：

- 当前交接主题
- 背景输入摘要
- 已确认约束
- 已完成决策
- 未解决问题
- 待确认决策
- 推荐后续动作
- 关键来源引用
- 当前状态

## 4. 关系结构检查

卡片关系至少需要：

- 起点对象。
- 终点对象。
- 关系类型。
- 创建方式。

首版关系类型包括：来源于、澄清了、支持、阻塞、冲突于、产出为。

如果关系未能成功建立：

- 不得连带隐藏已经成立的卡片本体。
- 不得伪造关系填补空洞。
- 应允许工作面保留对象，但显式暴露关系缺失。

## 5. 状态结构检查

结构验证必须阻止非法状态跳跃。

检查时以对象类型对应的类型化状态为唯一业务状态。通用治理分组只能由“对象类型 + 类型化状态”按版本化规则派生，不接受调用方直接写入；结构验证自身的通过、警告或不通过结果写入独立验证状态，不改变对象生命周期。

例如：

- 待澄清卡进入已关闭或已澄清时必须存在对应确认与作用范围。
- 约束卡创建、实质修改或替代时必须具备明确内容、适用范围和 Chat 确认依据，不存在可显影的约束候选态。
- 待决策 / 方案承接卡进入已决定时必须具备明确决策主题、结果和确认依据。
- 交接物承接卡所投影的包版本进入已确认时，必须具备完整交接结构和确认依据。

如果 Chat 已经完整满足确认条件，同一原子提交可以同时记录对象创建和信息地位升级，不要求先持久化一个仅用于等待确认的中间包版本。结构验证仍须检查有序状态变化能否在状态账本中完整表达。

结构验证只判断状态流转是否合法；是否真的允许生效，仍由治理层决定。

## 6. 动作结构检查

验证对象不只有卡片，也包括准备执行的动作。

以下动作在结构上必须可表达：

### 6.1 轻确认动作

跨栏目或其他语义迁移的轻确认至少需要：

- 当前对象是谁。
- 原栏目与目标栏目。
- 这次迁移会带来的语义变化。
- Chat 中确认 / 取消的可追溯记录。

### 6.2 Chat 确认依据

高影响信息地位升级至少需要：

- 准备执行什么。
- 为什么这会改变事实边界或下游可用性。
- 会影响哪些对象、状态或交接结果。
- 被确认的具体判断和作用范围。
- Assistant 提议与 User 确认、否定或修正的可追溯消息引用。
- 确认后仍然存在的未决。

### 6.3 显影提示条目

如果系统通过 Toast 或其他显影提示说明“已新增 / 已更新 / 已关闭”，对应提示至少要能回指实际对象或动作，不得只给抽象描述。确认仍在正常 Chat 中完成，不由显影提示承担。

## 7. 工作面一致性检查

结构验证还需要检查用户看见的工作面是否站得住：

- 显影提示提到的对象，画布上应能找到。
- Active Todos 里显示的缺口，至少要回指一个待澄清、约束、待决策或交接相关对象。
- 里程碑状态变化不能脱离底层对象状态独立漂移。
- 被标记为已过时的交接物，必须存在触发它过时的依赖变化。
