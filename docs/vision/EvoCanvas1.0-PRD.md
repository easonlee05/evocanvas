## 2. 产品背景

现实中的产品经理工作，并不是从“打开文档开始写 PRD”开始的。

更常见的真实工作流是：

1. 从 leader、老板、售前、运营、研发、设计、客户、数据报表、会议、聊天、文档、截图、竞品和临时想法中接收零散输入。
2. 在多轮对齐中不断补充信息，试图弄清楚“这件事到底要解决什么问题”。
3. 在不同人提供的信息、约束、偏好和现实限制之间来回切换。
4. 一边盯细节，一边尽量不丢掉整体目标。
5. 最终把模糊问题转化为规则、方案、结论、原型和交付物。

这类工作天然有几个痛点：

1. 输入来源太碎，且很多是跨媒介、跨角色、跨时间出现的。
2. 会议纪要只能覆盖部分输入，不能替产品经理完成整体认知收敛。
3. 文档适合沉淀结果，不适合承载持续演化中的思考过程。
4. 自由白板虽然有空间感，但很容易变成无结构的逻辑堆积。
5. 聊天式 AI 虽然能回答问题，但无法稳定维护一张持续演化的工作面。

因此，EvoCanvas 1.0 的目标不是优化“写出来”，而是优化：

`想明白`

更准确地说，是帮助产品经理把脑子里的模糊想法、多源输入、反馈碎片、跨团队对齐过程，外化为一个持续演化、可回看、可推进的工作画布。

## 3. 产品目标

### 3.1 一句话定位

EvoCanvas 1.0 是一张持续演化的产品经理工作画布，用来把多源输入转化为结构化上下文、待澄清问题、业务规则、当前结论和推进动作。

### 3.2 核心用户问题

EvoCanvas 1.0 需要解决的不是“写 PRD 太累”，而是：

1. 需求一开始太模糊，难以理清。
2. 输入来源太散，缺少统一收束入口。
3. 一旦盯住某个细节，就容易丢掉整体目标。
4. 很难持续追踪哪些问题还没澄清。
5. 规则、术语、字段口径容易在推进中散掉。
6. 结论会变化，但变化过程缺乏结构化记录。
7. 会议、聊天、文档和截图之间缺少统一的工作界面。

### 3.3 业务目标

1. 支持产品经理导入和汇入多种输入，快速形成结构化产品工作画布。
2. 支持 AI 自动从输入中提炼证据、问题、待澄清项，并在画布中显影。
3. 支持产品经理围绕问题、规则、方案、结论和推进动作持续收敛工作内容。
4. 支持展示项目里程碑与进度条，直观了解当前在生命周期中的推进节点。
5. 支持通过右侧 AI 助手持续推进画布演化，而不是仅生成静态文本。
6. 支持从画布收束出后续可继续推进的结构化产品上下文。

### 3.4 成功标准

1. 产品经理在导入任一核心输入后，可以看到结构化的画布初始化结果，并明确看到当前最重要的待澄清问题。
2. 产品经理可以快速看见哪些地方还没讲清楚、哪些信息彼此冲突、哪些事项必须人拍板，而不必自己从长文里翻找。
3. 产品经理可以围绕同一件事，在画布上同时看到输入、问题、约束、决策和交接准备状态，并区分哪些内容仍不稳定。
4. 一次关键讨论后，产品经理可以回看“这次到底推进了什么、消除了哪些不确定性、留下了哪些未决问题”，而不是只看到聊天记录。
5. 画布中的结构最终能够收束为后续可继续推进的结构化产品上下文，并可被其他同事或 AI 在新上下文中复用。

### 3.5 1.0 首版验证命题

EvoCanvas 1.0 首版要验证的不是“能不能搭一套完整 PM 工作台”，而是以下更硬的命题：

1. 多源混杂输入是否可以被系统稳定收束为一组可推进的 `待澄清问题`、`约束` 和 `待决策项`。
2. AI 是否可以像一个合格的产品同事一样，优先暴露不确定性，而不是过早替用户脑补结论。
3. 经过一轮收敛后的结果，是否能够生成一份可交接的结构化产品上下文，供不同 AI 或不同会话继续推进。
4. 首版必须优先验证“需求失真是否降低”，而不是优先追求“对象类型是否齐全”或“界面模块是否完整”。

## 4. 核心规则与约束

1. EvoCanvas 1.0 的第一入口是 `输入编译`，不是 `新建 PRD`。
2. EvoCanvas 1.0 首版只验证“输入编译 -> 待澄清问题 -> 约束 / 待决策 -> 结构化交接物”这一最小闭环，不以搭建完整 PM 操作系统为目标。
3. 主画布是连续画布，不采用硬边框切割大区域。
4. 主画布宽度表达逻辑结构，不表达时间顺序。
5. 时间维度通过底部里程碑进度条承载，清晰标注各个关键交付节点，不通过横向无限扩张画布承载。
6. AI 可以自动做低风险结构整理，但不得在高影响动作上绕过用户确认。
7. Active Todos 不是任务管理系统，而是当前活跃缺口投影视图。
8. Todo 不是独立事实源，所有 Todo 必须回指原始卡片。
9. 首版不要求完整结论卡体系，任何稳定判断优先以“约束”或“待决策结果”形式落地。
10. 当输入之间存在冲突、上下文不足或指代不清时，系统必须优先显性化冲突与缺口，而不是静默合并。
11. 任何被标记为 `已生效` 或 `已确认` 的信息，都必须有明确来源、确认方式或可追溯的用户裁决。
12. 首版不做多人实时协作。
13. 首版不做自由白板模式。

## 5. 用户角色

| 用户角色 | 角色说明 | 核心诉求 |
| --- | --- | --- |
| 产品经理 | 核心目标用户，负责接收需求、整理上下文、推进收敛 | 接住输入、理清问题、追踪缺口、沉淀规则、形成结论 |
| AI 助手 | 系统内协作对象，负责提炼、归纳、追问和显影 | 把自然语言和输入材料编译为结构化画布变化 |
| 评审参与方 | leader、研发、设计、运营、业务等，被 PM 在过程中引用和对齐 | 通过问题、约束、决策和交接上下文参与收敛，不直接作为首版系统内用户 |

### 5.1 首版使用边界

1. 首版只面向单人工作台。
2. 评审参与方暂不直接在系统中多人编辑。
3. 首版默认用户是产品经理，其他角色的信息通过输入材料和 AI 整理进入画布。

## 6. 产品范围

### 6.0 范围分层说明

本节将 EvoCanvas 拆分为：

1. `1.0 首版必须范围`：用于验证产品核心命题的最小闭环。
2. `后续版本规划范围`：方向明确，但不纳入 1.0 交付承诺。

如果某项能力不能直接提升“多源输入收敛为可交接上下文”的验证效率，则默认不进入 1.0。

### 6.1 1.0 首版必须范围

| 一级模块 | 二级模块 | 功能范围 |
| --- | --- | --- |
| 输入编译 | 输入接入 | 导入会议纪要、聊天摘录、用户反馈、数据说明、截图说明、竞品摘录、文档片段、临时想法 |
| 输入编译 | 输入编译 | 识别输入类型、提取事实、识别冲突、推断问题和缺口、生成初步结构化卡片 |
| 主画布 | 阶段带 | 首版只要求 `发现` 与 `定义` 两条阶段带完整成立；`规划` 与 `推进` 只保留最小展示能力 |
| 主画布 | 模块簇 | 证据池、问题定义、待澄清、规则与约束、待决策、结构化交接物 |
| 主画布 | 卡片体系 | 证据卡、问题卡、待澄清卡、约束卡、待决策卡、交接物卡 |
| 主画布 | 卡片关系 | 来源于、澄清了、支持、阻塞、冲突于、产出为 |
| 主画布 | 卡片手动修订 | 卡片标题 / 摘要原地编辑、模块内排序、合法跨阶段迁移与轻确认 |
| AI 助手 | 对话显影 | 识别意图、定位对象、生成更新建议、应用到画布 |
| AI 助手 | 追问与确认 | 对模糊输入追问，对高影响动作请求确认，对冲突信息要求裁决 |
| Todo | Active Todos | 投影当前待澄清、待定义、待决策的活跃缺口 |
| 时间轴 | 里程碑进度条 | 展示项目生命周期与里程碑阶段，支持查看与标记当前进度 |
| 输出 | 结构化交接物 | 从当前画布收束出可供人或 AI 继续推进的结构化产品上下文 |

### 6.2 后续版本规划范围

后续版本不按“补功能清单”推进，而按产品能力升级路径推进。每一版都应回答一个更大的产品命题，避免在 1.0 未验证完成前过早堆叠复杂能力。

#### 2.0 路线：从“需求收敛工作台”升级到“方案收束工作台”

2.0 的目标不是简单把 1.0 中暂缓的对象补回来，而是在 `1.0 已经证明输入能够稳定收敛` 的前提下，继续回答：

`在问题、约束和待决策明确之后，系统能否帮助 PM 把当前主题继续收束成可执行方案。`

2.0 重点能力：

1. 引入方案层对象：方案卡、结论卡、推进项。
2. 让 `规划` 与 `推进` 两条阶段带从轻量承接升级为可深度使用。
3. 支持围绕多个候选方案进行比较、取舍和收束。
4. 支持从交接物继续生成结构化方案包，而不只是停留在上下文交接层。
5. 支持对“当前为什么这样做”形成更明确的决策链路记录。

2.0 不变原则：

1. 仍然坚持“先暴露不确定性，再形成方案”，不允许方案层压过问题澄清层。
2. 仍然不以多人协作为核心，不把复杂协作流提前引入。

#### 3.0 路线：从“单人 PM 工作台”升级到“多角色协作面”

3.0 的目标是让 EvoCanvas 不再只是 PM 的个人工作面，而是成为多角色围绕同一份问题、约束、方案和决策进行协作的产品协作面。

3.0 重点能力：

1. 多人实时协作与评论线程。
2. 角色化协作视图：PM、设计、研发、业务、评审参与方看到的重点不同。
3. 明确的决策和确认流：谁能确认约束，谁能确认方案，谁提供反馈。
4. 更强的评审闭环：围绕待决策卡、结论卡、方案卡保留完整协作记录。
5. 更丰富的里程碑对比与进度变更追溯能力。

3.0 不变原则：

1. 协作建立在已结构化对象之上，而不是让多人同时编辑混乱输入。
2. 不为“所有人都能改”牺牲对象清晰度与事实边界。

#### 4.0 路线：从“产品协作面”升级到“交付编排面”

4.0 的目标是把 EvoCanvas 从“想明白、协同收束”继续推进到“让后续交付更可编排、更可追踪”。

4.0 重点能力：

1. 更复杂的关系网络与全局依赖分析。
2. 更完整的文档、规格、原型联动能力。
3. 更强的外部系统接入：项目管理平台、知识库、IM、需求系统等。
4. 更完整的推进状态面、交付链路和后续动作编排能力。
5. 从交接物、方案包继续派生出更正式的规格包、任务包、评审包。

4.0 不变原则：

1. 外部打通服务于“减少失真和提高交付闭环”，而不是为接入而接入。
2. 交付编排建立在前几版已经稳定的对象模型和协作协议之上。

#### 后续路线总原则

1. `1.0` 先证明“输入能被稳定收敛为可交接上下文”。
2. `2.0` 再证明“上下文能继续收束为可执行方案”。
3. `3.0` 再证明“多角色能围绕这些结构化对象协作”。
4. `4.0` 最后证明“协作结果能继续被编排到交付落地链路”。

### 6.3 首版不包含范围

1. 多人实时协作。
2. 完整项目管理甘特图。
3. 自由白板模式。
4. 复杂权限体系。
5. 高保真原型自动生成。
6. 完整文档编辑器。
7. 老板驾驶舱。
8. 复杂外部系统打通能力。
9. 完整方案卡、结论卡、推进项体系的深度运营。
10. 全局复杂关系图谱与自动化依赖推理。

## 7. 核心业务流程

## 7.1 多源输入编译流程

1. 产品经理进入 EvoCanvas 工作台。
2. 产品经理通过输入编译台导入一项或多项输入。
3. 系统识别输入类型。
4. AI 从输入中提取事实、问题、冲突和缺口。
5. 系统在画布中生成初步卡片，并显式标出当前存在的冲突信息或信息不足点。
6. Active Todos 根据卡片状态投影当前活跃缺口。
7. 产品经理开始在画布和右侧 AI 助手中进行收敛。

## 7.2 认知收敛流程

1. 产品经理查看画布上的证据卡、问题卡和待澄清卡。
2. 产品经理补充判断、追问或表达方向。
3. AI 优先判断当前输入是否应新增待澄清卡、约束卡或待决策卡，而不是直接产出结论。
4. 当输入之间存在冲突、缺失关键前提或存在多种解释时，AI 必须先显性化冲突并追问，不得直接合并。
5. 高影响动作在写入前要求用户确认。
6. 画布结构持续变化，用户可以直观对照当前里程碑对应的进度条状态。

## 7.3 约束沉淀流程

1. 产品经理围绕术语、字段、状态、权限、边界和口径形成约束。
2. AI 将约束整理为约束卡，并保留对应来源和确认方式。
3. 与约束相关的待澄清卡被关闭、阻塞或转入待决策状态。
4. 已确认约束成为后续结构化交接物的组成部分。

## 7.4 待决策收束流程

1. 当某项信息不是“尚未澄清”，而是“必须由 PM 拍板”时，系统生成待决策卡。
2. 待决策卡必须明确决策主题、备选解释、影响范围和所需确认人。
3. 用户确认后，待决策卡进入已决定状态，其结果更新相关待澄清卡或约束卡。
4. 每一个关键节点的沉淀均对应到进度条的特定里程碑。

## 7.5 结构化交接物流程

1. 当当前主题的主要待澄清项已收敛，关键约束已沉淀，必要决策已完成后，系统可生成结构化交接物。
2. 结构化交接物必须明确：当前目标、输入背景、已确认约束、仍未解决的问题、待确认决策和推荐后续动作。
3. 用户确认交接物后，可将其提供给其他同事或 AI，在新上下文中继续推进。
4. 若后续推进暴露新冲突或新缺口，应允许从交接物回流到待澄清或待决策状态。

## 8. 功能需求与原型设计要求

## 8.1 输入编译台

### 8.1.1 功能说明

输入编译台是 EvoCanvas 1.0 的统一入口能力，用于把不同来源、不同形态、不同成熟度的输入编译到同一张产品工作画布上。

输入编译台的目标不是简单上传文件，而是：

1. 识别输入类型。
2. 提取可用事实。
3. 推断问题与缺口。
4. 生成初步结构化卡片。
5. 将输入并入现有画布，而不是覆盖现有理解。

### 8.1.2 支持的输入类型

首版至少支持以下输入：

1. 会议纪要
2. 聊天摘录
3. 用户反馈列表
4. 数据结论说明
5. 竞品摘录
6. 截图与配套说明
7. 历史文档片段
8. 一段临时想法或方向描述

### 8.1.3 页面字段与组件要求

| 页面区域 | 字段名称 | 组件要求 | 说明 |
| --- | --- | --- | --- |
| 输入区 | 输入类型 | Select / 自动识别标签 | 支持手动指定或由系统自动识别 |
| 输入区 | 输入正文 | Textarea / 富文本承接区 | 支持长文本粘贴 |
| 输入区 | 附件说明 | Textarea | 用于补充截图、文件等的说明文字 |
| 输入区 | 导入按钮 | Button | 点击后进入编译流程 |
| 输入区 | 编译方式 | Segmented Control | 追加到当前画布 / 新建工作画布 |
| 状态区 | 编译状态 | Badge / 文本 | 待处理、处理中、已完成、失败 |

### 8.1.4 关键交互

1. 用户输入内容后，可直接点击导入。
2. 系统应允许用户选择“并入当前工作面”或“作为新工作面开始”。
3. 导入完成后，系统应给出本轮显影摘要。
4. 若输入内容过于模糊，AI 应先追问，不直接显影为高影响结论。

### 8.1.5 状态与异常展示

1. 输入为空时，不允许提交。
2. 输入过长时，应给出长度提示或分段处理提示。
3. 识别失败时，应提示用户补充输入类型或背景说明。
4. 编译失败时，应保留原输入内容并支持重试。

### 8.1.6 验收标准

1. 用户可成功导入至少 8 类首版支持输入。
2. 系统可在合理时间内完成编译，并生成初步卡片。
3. 输入被并入现有工作面时，不会覆盖已有卡片结构。

## 8.2 主画布

### 8.2.1 功能说明

主画布是 EvoCanvas 1.0 的唯一主工作面，用于承载输入编译结果、当前问题结构、待澄清缺口、约束沉淀、待决策事项、结构化交接物以及它们之间的轻量关系。

主画布承担的不是文档展示功能，而是产品经理的核心工作功能：

1. 看见当前有哪些输入正在影响这件事。
2. 看见当前对问题的理解到了哪一步。
3. 看见哪些地方还没有收敛。
4. 看见哪些约束已经形成。
5. 看见哪些事项仍待决策。
6. 看见当前是否已经具备对外继续推进的交接条件。

### 8.2.2 页面布局要求

主画布采用“连续画布 + 阶段带 + 模块簇”的布局，不采用大块线框切割页面。

页面结构要求如下：

1. 主画布位于工作台中央区域，占据页面主体宽度和高度。
2. 主画布默认展示当前里程碑或最新进度下的所有活跃模块簇和卡片。
3. 画布顶部展示阶段带标题，用于提示当前内容的主要工作阶段。
4. 阶段带下方展示对应模块簇，每个模块簇承载同类卡片。
5. 画布本体支持纵向滚动浏览，不应依赖横向无限扩张作为首版主要交互。
6. 当内容超出当前视口时，应优先通过纵向扩展承载，而不是迫使用户频繁横向拖拽。
7. 画布与右侧 AI 助手、右上 Active Todos、底部时间轴保持联动，但在视觉上应保持主工作面的独立性。

### 8.2.3 阶段带定义

主画布按产品经理的工作流组织为四条阶段带，但 1.0 首版只要求前两条阶段带完整可用：

- 发现
- 定义
- 规划
- 推进

这四条阶段带表达主流程方向，但不意味着流程严格单向。系统必须允许回流、替代和重新打开。

#### 发现

作用：

1. 承接输入来源。
2. 展示当前需求和信息是从哪里来的。
3. 帮助 PM 看见输入的原始面貌，而不是直接被结果覆盖。

该阶段带下的模块簇包括：

- 用户反馈
- 会议输入
- 市场 / 竞品
- 证据池

#### 定义

作用：

1. 对输入进行问题理解。
2. 暴露当前尚未收敛的问题和缺口。
3. 沉淀约束、术语、字段和交接轮廓。

该阶段带下的模块簇包括：

- 问题定义
- 待澄清
- 规则与约束
- 待决策

#### 规划

作用：

1. 形成当前可对外继续推进的交接内容。
2. 收束关键决策和里程碑状态。
3. 把模糊思考推进到可判断、可交接的层面。

该阶段带在 1.0 首版只保留轻量承接能力，主要用于承接结构化交接物和必要里程碑进度条，不要求完整建立复杂任务管理系统。

#### 推进

作用：

1. 承接已经形成的交接动作。
2. 组织后续动作说明和关键输出引用。
3. 让画布从“想明白”自然过渡到“继续推进下去”。

该阶段带在 1.0 首版不作为深度运营区，只保留最小的交接物落点与后续动作说明。

### 8.2.4 模块簇定义与展示规则

模块簇是阶段带下的语义聚类容器，不是死板分栏。

展示规则如下：

1. 每个模块簇必须有清晰标题。
2. 模块簇内部卡片应自动聚类，默认采用自上而下堆叠或小范围网格排列。
3. 模块簇之间应通过留白形成视觉分组，而不是通过粗线框切割。
4. 模块簇在当前里程碑下无内容时，应支持隐藏或轻量空状态展示，不应强制占满空间。
5. 同一张卡片应有一个主归属模块簇，但允许被其他模块引用。
6. 模块簇应支持后续扩展，但首版只展示当前定义的固定模块集合。

### 8.2.5 卡片排布与聚类规则

主画布中的卡片排布需要同时满足可读性和结构稳定性。

排布规则如下：

1. 卡片默认按模块簇自动聚集。
2. 同类型卡片在同一模块簇内应保持统一样式和近似尺寸节奏。
3. 新生成卡片默认插入所属模块簇的可见区域，不应随机散落在画布空白区。
4. 用户拖动卡片时，应优先吸附到最近的合法模块簇。
5. 首版不允许卡片脱离模块簇长时间悬浮在无归属区域。
6. 当一个模块簇中卡片数量较多时，应优先纵向展开，而不是自动拆成多个远距离分区。
7. 被 pin 的卡片应优先保持在用户当前可见区域或该模块簇顶部。

### 8.2.6 关系线展示规则

关系线是辅助信息，不应压过卡片本身成为主视觉对象。

展示规则如下：

1. 默认只展示轻量关系提示，不展示全图复杂连线网络。
2. 用户选中卡片时，仅高亮该卡片的直接相关关系。
3. 未选中卡片的关系线应弱化展示或隐藏。
4. 关系线应避免穿越大量无关卡片，减少视觉污染。
5. 首版关系线主要用于帮助用户理解“来源于、澄清了、支持、阻塞、替代、产出为”等关键关系。

### 8.2.7 里程碑进度对主画布的影响

当用户选择或切换底部时间轴的不同里程碑节点时，主画布应展示对应里程碑阶段的认知结构与卡片状态。

里程碑影响规则如下：

1. 画布展示的卡片集合与所处里程碑阶段绑定，只高亮展示当前阶段的核心内容。
2. 卡片状态反映对应里程碑时期的进展（如：内测发布前应解决所有高优待澄清）。
3. Active Todos 同步反映当前里程碑下的剩余活跃缺口。
4. 当前已完成或已替代的卡片可以标记并在对应里程碑视图中做归档处理。
5. 用户可以点击返回“最新当前进度”以查看当前的全局大盘。
6. 里程碑变化不应改变真实底层数据，只改变查看视图。
7. 返回“最新当前进度”后，应恢复最新全局大盘视图。

### 8.2.8 关键交互

1. 用户可在模块簇内浏览卡片。
2. 用户可点击任一卡片进入详情面板。
3. 用户可拖动卡片到其他合法模块簇。
4. 用户选中卡片时，仅高亮直接相关关系。
5. 用户切换当前所选里程碑时，主画布应平滑切换到对应状态。
6. 用户可从 Todo 面板点击回到主画布中的源卡。
7. 用户可从右侧 AI 对话中的变化摘要跳转到对应卡片。

### 8.2.9 空状态与异常展示

1. 当某个模块簇为空时，应展示轻量空状态，而不是占满大面积说明文案。
2. 当当前里程碑阶段没有某类卡片时，不应强行展示占位噪音。
3. 当主画布首次初始化失败时，应保留输入编译结果和错误提示。
4. 当某张卡片的关系解析失败时，应优先保底展示卡片本体，不应导致整块模块簇消失。
5. 当画布内容过少时，不应通过大面积留白掩盖信息不足，而应继续补齐结构说明、字段说明和模块定义。

### 8.2.10 验收标准

1. 用户可以一眼识别四条阶段带和当前主要模块簇。
2. 同类卡片在视觉上保持一致，并按模块簇自然聚类。
3. 画布不会因为关系线过多而失去可读性。
4. 进度条切换后，主画布可正确反映当时里程碑阶段对应的状态。
5. 用户能够通过主画布快速定位当前问题、当前缺口和当前可对外交接的结构。

## 8.3 卡片体系

### 8.3.1 功能说明

EvoCanvas 1.0 的主对象不是文档章节，而是产品经理在真实工作中持续操作的中间对象。

为避免首版过度设计，卡片体系分为：

#### 1.0 首版核心卡片

- 证据卡
- 问题卡
- 待澄清卡
- 约束卡
- 待决策卡
- 交接物卡

#### 后续版本扩展卡片

- 方案卡
- 结论卡
- 推进项

### 8.3.2 通用卡片设计原则

卡片体系必须同时满足以下目标：

1. 支持用户在高密度信息场景下快速扫描。
2. 支持 AI 以稳定结构写入和更新内容。
3. 支持产品经理逐步把模糊认知收束成结构化对象。
4. 支持通过少量字段和状态表达当前推进位置。
5. 支持详情面板承载更完整内容，而不是把所有内容都挤在卡面上。

### 8.3.3 通用卡面字段

所有卡片在产品上统一展示这些基础信息：

- 标题
- 一句话摘要
- 当前状态
- 标签
- 更新时间
- 来源
- 关联项数量

通用展示规则如下：

1. 标题默认单行展示，超出部分省略。
2. 一句话摘要默认展示 2 行，超出部分折叠。
3. 状态必须以明确标签或标记展示，不允许只写进正文。
4. 来源以短标签或来源计数方式展示，不在卡面堆叠长来源文本。
5. 卡面默认不展示长段落正文。

### 8.3.4 卡片详情面板要求

用户点开任一卡片后，应能查看：

1. 完整标题
2. 完整摘要
3. 当前状态
4. 来源引用
5. 关联卡片
6. 历史变更摘要
7. 可执行操作

详情面板是卡片的完整信息承载层。卡面只承载“扫一眼就能判断”的信息，不承担长文阅读功能。

### 8.3.5 证据卡

#### 8.3.5.1 功能说明

证据卡用于承接会议纪要、聊天、截图、访谈、反馈、竞品资料和文档片段等输入来源。

它是事实输入的结构化投影，不代表正式结论。

#### 8.3.5.2 卡面字段与组件要求

| 字段名称 | 组件要求 | 说明 |
| --- | --- | --- |
| 标题 | 文本 | 证据来源标题或 AI 提炼标题 |
| 摘要 | 多行文本 | 证据的核心内容提炼 |
| 来源类型 | Tag | 会议纪要 / 聊天 / 截图 / 反馈 / 竞品 / 文档 |
| 引用数量 | Text / Badge | 当前被多少卡片引用 |
| 更新时间 | Text | 最近整理时间 |

#### 8.3.5.3 详情面板字段

1. 原始摘录
2. 来源对象
3. 输入时间
4. AI 提炼说明
5. 被引用关系

#### 8.3.5.4 关键交互

1. 用户可查看原始内容与提炼摘要。
2. 用户可手动修订证据摘要。
3. 用户可把证据卡绑定到问题卡、约束卡或待决策卡。

#### 8.3.5.5 状态与异常展示

1. 证据原文缺失时，仍需保留摘要和来源标记。
2. 原文解析失败时，应展示“原始内容不可完整解析”提示。

#### 8.3.5.6 验收标准

1. 系统可正确展示证据来源类型。
2. 用户可查看原始证据与提炼摘要。
3. 证据卡可被其他卡片引用。

### 8.3.6 问题卡

#### 8.3.6.1 功能说明

问题卡用于表达当前对问题的理解，包括业务问题、用户对象、痛点和目标方向。

#### 8.3.6.2 卡面字段与组件要求

| 字段名称 | 组件要求 | 说明 |
| --- | --- | --- |
| 标题 | 文本 | 当前问题名称 |
| 摘要 | 多行文本 | 当前对问题的简述 |
| 成熟度 | Tag | 初步理解 / 待收敛 / 已收敛 |
| 关联待澄清数 | Badge | 与该问题相关的缺口数量 |
| 更新时间 | Text | 最近更新时间 |

#### 8.3.6.3 详情面板字段

1. 问题背景
2. 目标用户
3. 核心痛点
4. 当前业务目标
5. 关联证据
6. 关联待澄清
7. 关联规则和方案

#### 8.3.6.4 关键交互

1. 用户可编辑问题定义。
2. 用户可将证据卡归并到问题卡下。
3. 用户可从问题卡生成待澄清卡、约束卡或待决策卡。

#### 8.3.6.5 状态与异常展示

1. 当问题定义过于模糊时，应提示用户继续收敛。
2. 当问题卡失去来源证据支撑时，应提示“缺少来源支撑”。

#### 8.3.6.6 验收标准

1. 用户可从问题卡理解当前问题核心。
2. 问题卡可关联证据、待澄清、规则和方案。

### 8.3.7 待澄清卡

#### 8.3.7.1 功能说明

待澄清卡用于暴露术语冲突、规则未定、边界不清、风险未决和必须补问的信息。

它是 Active Todos 的主来源，也是 EvoCanvas 1.0 首版最重要的显性对象。

#### 8.3.7.2 卡面字段与组件要求

| 字段名称 | 组件要求 | 说明 |
| --- | --- | --- |
| 标题 | 文本 | 待澄清问题名称 |
| 摘要 | 多行文本 | 为什么需要澄清 |
| 优先级 | Badge | 高 / 中 / 低 |
| 阻塞范围 | Tag | 约束 / 决策 / 交接 |
| 当前状态 | Tag | 待提出 / 待确认 / 已澄清 / 已阻塞 / 已关闭 |

#### 8.3.7.3 详情面板字段

1. 具体待确认问题
2. 建议追问对象
3. 阻塞说明
4. 关联问题
5. 被哪些约束或决策澄清

#### 8.3.7.4 关键交互

1. 用户可手动确认是否将其纳入当前活跃缺口。
2. 用户可在聊天中直接回答该问题。
3. 用户确认后可关闭、阻塞或转化为约束 / 待决策项。

#### 8.3.7.5 状态与异常展示

1. 已澄清问题不得继续展示为活跃缺口。
2. 被关闭的问题应保留历史，不应直接删除。
3. 当系统无法判断“该继续追问还是该进入待决策”时，应优先保持待澄清状态，而不是过早升级。

#### 8.3.7.6 验收标准

1. 待澄清卡能够清晰表达当前缺口。
2. 待澄清卡可被 Todo 面板正确投影。
3. 用户可将其关闭、阻塞或澄清。

### 8.3.8 冲突信息显性化要求

EvoCanvas 1.0 首版必须把冲突信息当作一等对象处理，即使首版不单独设计“冲突卡”，也必须满足以下规则：

1. 当两条证据、两条约束、或证据与当前判断之间发生明显冲突时，系统必须在相关卡片上显式标记“存在冲突”。
2. 冲突状态必须能够被用户看见、点击和追溯来源，不能仅作为 AI 内部推理状态存在。
3. 冲突被解决前，不得将对应信息默认为已生效约束或稳定交接内容。
4. 当冲突需要 PM 明确拍板时，系统应生成待决策卡，而不是静默合并。

### 8.3.9 约束卡

#### 8.3.9.1 功能说明

约束卡用于沉淀术语、字段、状态、约束、权限、流程、数据口径等定义。它是 1.0 首版的核心对象，因为首版要验证的重点不是方案是否完整，而是边界是否被钉住。

#### 8.3.9.2 卡面字段与组件要求

| 字段名称 | 组件要求 | 说明 |
| --- | --- | --- |
| 标题 | 文本 | 约束标题 |
| 摘要 | 多行文本 | 当前约束的一句话说明 |
| 约束类型 | Tag | 术语 / 字段 / 状态 / 权限 / 计费 / 流程 / 边界 |
| 当前状态 | Tag | 草稿中 / 待确认 / 已生效 / 已替代 / 已归档 |
| 影响范围 | Text / Tag | 约束作用范围 |

#### 8.3.9.3 详情面板字段

1. 完整约束描述
2. 适用范围
3. 例外说明
4. 关联字段或数据口径
5. 来源证据
6. 确认人或确认方式
7. 是否存在冲突约束

#### 8.3.9.4 关键交互

1. 用户可修改约束文本。
2. 用户可确认约束生效。
3. 用户可将旧约束替代为新约束。
4. 用户可将互相冲突的约束标记为待决策输入。

#### 8.3.9.5 状态与异常展示

1. 草稿中的约束不得默认视为生效约束。
2. 已替代约束应保留历史，并显式展示“已替代”状态。
3. 发生冲突的约束不得同时参与“已生效”判断，必须显式标记冲突状态或进入待决策。

#### 8.3.9.6 验收标准

1. 用户可区分草稿约束与生效约束。
2. 约束卡可作为结构化交接物的支持依据。

### 8.3.10 待决策卡

#### 8.3.10.1 功能说明

待决策卡用于表达“不是信息不足，而是必须由 PM 明确拍板”的事项。

#### 8.3.10.2 卡面字段与组件要求

| 字段名称 | 组件要求 | 说明 |
| --- | --- | --- |
| 标题 | 文本 | 当前决策主题 |
| 摘要 | 多行文本 | 为什么需要拍板 |
| 决策类型 | Tag | 口径 / 方向 / 边界 / 优先级 / 例外 |
| 当前状态 | Tag | 待判断 / 待确认 / 已决定 / 已归档 |
| 影响范围 | Text / Tag | 受影响的约束、问题或交接物 |

#### 8.3.10.3 详情面板字段

1. 具体决策问题
2. 当前可选解释或方案
3. 决策影响范围
4. 关联待澄清或冲突信息
5. 决策结果引用

#### 8.3.10.4 关键交互

1. 用户可明确选择决策结果。
2. 用户可拒绝当前建议并保持待决策状态。
3. 用户确认后，相关约束和待澄清卡同步更新。

#### 8.3.10.5 状态与异常展示

1. 未完成决策的待决策卡必须持续可见，不得被系统自动关闭。
2. 已决定决策需保留“如何决定”的可追溯记录。

#### 8.3.10.6 验收标准

1. 用户能区分“还没问清楚”和“必须拍板”这两类对象。
2. 待决策卡可正确回指相关待澄清、约束或冲突信息。

### 8.3.11 交接物卡

#### 8.3.11.1 功能说明

交接物卡用于承接当前主题的结构化产品上下文，是 EvoCanvas 1.0 对外继续推进的最小交接单元。

#### 8.3.11.2 卡面字段与组件要求

| 字段名称 | 组件要求 | 说明 |
| --- | --- | --- |
| 标题 | 文本 | 当前交接主题 |
| 摘要 | 多行文本 | 当前已收敛出的可执行上下文摘要 |
| 当前状态 | Tag | 草稿中 / 待确认 / 已确认 / 已过时 |
| 覆盖范围 | Text / Tag | 覆盖了哪些问题、约束和决策 |
| 未决数 | Badge | 当前仍未解决的缺口数量 |

#### 8.3.11.3 详情面板字段

1. 当前目标
2. 背景输入摘要
3. 已确认约束列表
4. 已完成决策列表
5. 仍未解决的问题
6. 推荐后续动作
7. 来源里程碑与关联卡片

#### 8.3.11.4 关键交互

1. 用户可生成交接物草稿。
2. 用户可确认交接物进入可使用状态。
3. 用户可从交接物回跳到原始约束、待澄清和待决策对象。

#### 8.3.11.5 状态与异常展示

1. 未确认的交接物不得被标记为可直接外发。
2. 若交接物依赖的约束或决策发生变化，应显式提示“交接物已过时”。

#### 8.3.11.6 验收标准

1. 交接物卡能汇总当前主题的核心背景、约束、决策和未决问题。
2. 交接物卡可作为新会话或新 AI 的继续输入使用。

### 8.3.12 后续版本扩展卡片

以下对象已确认有价值，但不纳入 1.0 首版必须实现：

- 方案卡
- 结论卡
- 推进项

后续版本可在 1.0 核心闭环验证通过后，再引入这些对象的完整生命周期。

### 8.3.13 卡片通用操作要求

用户应支持：

1. 编辑标题和摘要
2. 调整状态
3. pin / unpin
4. 合并重复卡片
5. 手动新增卡片
6. 移动卡片到其他模块簇
7. 绑定证据或外部链接
8. 触发交接物生成或更新
9. 标记冲突或待裁决状态

### 8.3.14 状态与异常展示

1. 当卡片缺少必要来源时，应给出来源缺失提示。
2. 当卡片正文过长时，卡面必须截断，详情面板完整展示。
3. 当同一输入被重复编译为多张卡片时，应支持合并。
4. 当卡片状态与其所在模块明显不匹配时，应允许系统建议迁移。
5. 当卡片存在冲突但未解决时，应显式提示，不得继续按“已生效”使用。

### 8.3.15 验收标准

1. 系统可正确展示 1.0 首版核心卡片。
2. 用户可在详情面板中查看完整内容。
3. 用户可完成核心轻量编辑操作。
4. 不同类型卡片在信息表达上有清晰区分。
5. 卡片可承接 AI 自动生成与用户手动修订两种来源。


## 8.4 卡片手动修订与迁移

### 8.4.1 功能说明

EvoCanvas 1.0 的卡片不是静态展示物，而是产品经理接管 AI 初稿、手动修正认知结构的最小操作对象。

首版需要支持一套克制但可用的卡片手动修订能力，使用户能够：

1. 直接修正 AI 生成的标题与摘要。
2. 在同一模块簇内快速调整卡片顺序。
3. 在符合语义的前提下，把卡片从一个阶段或模块迁移到另一个合法归属。
4. 通过手动修订，把“尚未稳定的 AI 判断”收束为更可靠的结构化对象。

该模块的目标不是把 EvoCanvas 做成自由白板，也不是在 1.0 首版就建立完整协作审批流，而是验证：

`产品经理是否能快速接管并修正 AI 编译结果。`

### 8.4.2 设计原则

卡片手动修订模块必须遵循以下原则：

1. 优先保持浏览态清晰，不让编辑控件长期占满画布。
2. 编辑能力服务于结构化修订，而不是鼓励长文写作。
3. 拖拽代表对象归属变化或状态迁移，不代表自由摆放。
4. 同模块排序应足够顺滑，跨阶段迁移应足够谨慎。
5. 所有迁移都必须服从对象语义，不允许把画布退化为无边界白板。

### 8.4.3 首版范围

1. 支持卡片标题原地编辑。
2. 支持卡片摘要原地编辑。
3. 支持模块簇内卡片排序。
4. 支持合法的跨模块簇与跨阶段迁移。
5. 支持在跨阶段迁移时给出轻确认提示。

首版明确不包含：

1. 自由像素级摆放卡片。
2. 同一张卡片的多人同时编辑。
3. 拖拽后自动改写右侧 AI 对话历史。
4. 拖拽后自动改写结构化交接物正文。
5. 卡片级复杂审批流、评论流和权限流。

### 8.4.4 原地编辑规则

首版采用轻量原地编辑，不引入完整表单式详情编辑器作为主入口。

规则如下：

1. 用户可直接点击标题进入单行编辑态。
2. 标题编辑在失焦时自动保存。
3. 用户可直接点击摘要进入多行编辑态。
4. 摘要编辑通过 `Cmd/Ctrl + Enter` 保存，通过 `Esc` 取消。
5. 单击卡片默认仍优先执行“选中卡片”，应通过双击或明确点击可编辑区域进入编辑态。
6. 进入编辑态后，该卡片临时不可拖拽，避免文本选择与拖拽冲突。
7. 首版原地编辑只覆盖标题与摘要，不要求在卡面直接编辑标签、负责人、状态、关系和来源。

### 8.4.5 排序与拖拽规则

卡片移动在产品语义上分为两类：

1. 同模块簇内排序
2. 跨模块簇或跨阶段迁移

排序与拖拽规则如下：

1. 同模块簇内排序时，用户拖动卡片后松手即生效。
2. 同模块簇内排序只改变显示顺序，不改变卡片类型与阶段语义。
3. 跨模块簇迁移时，目标容器必须是系统定义的合法落点。
4. 拖拽过程中，合法落点应高亮提示，非法区域应弱化或拒绝响应。
5. 卡片不得长时间停留在无归属的画布空白区。
6. 关系线在卡片落位后自动重算，不要求用户手工调整。

### 8.4.6 合法迁移路径

首版允许的跨阶段迁移不是任意移动，而是有限的状态升级路径。

系统至少应支持以下典型迁移：

1. 证据卡 -> 问题卡
2. 待澄清卡 -> 约束卡
3. 待澄清卡 -> 待决策卡
4. 问题卡 -> 交接物卡引用输入
5. 已形成稳定结果的卡片 -> 推进阶段中的后续动作承接位

同时必须满足以下约束：

1. 不允许将任意卡片自由拖入无关模块簇。
2. 不允许通过一次拖拽静默改变卡片的核心语义而不给出说明。
3. 当目标模块与当前状态明显冲突时，系统应拒绝落下并保持原位。

### 8.4.7 轻确认规则

为了兼顾效率与语义准确性，首版对不同移动动作采用不同确认策略：

1. 同模块簇内排序不需要额外确认。
2. 跨阶段迁移在松手后必须给出轻确认提示。
3. 轻确认文案必须明确说明这次迁移将带来的语义变化，而不是只弹出泛化的“是否确认”。

示例：

- 这张卡将从“待澄清”转为“已确认约束”
- 这张卡将从“待澄清”转为“待决策事项”

用户取消后，卡片应恢复原位置与原状态。

### 8.4.8 状态与异常展示

1. 正在编辑的卡片不得进入拖拽态。
2. 正在拖拽的卡片不得同时进入编辑态。
3. 非法落点不应先落下再报错，而应直接拒绝。
4. 跨阶段确认被取消后，卡片应回到原模块簇与原排序位置。
5. 当卡片信息不完整，不影响编辑入口显示，但应保留必要的缺失提示。

### 8.4.9 验收标准

1. 用户可直接在画布上修改标题与摘要，而不必先打开详情面板。
2. 同模块簇内卡片排序可稳定生效，且不会改变卡片语义。
3. 合法跨阶段迁移可被正确识别，并在确认后更新归属。
4. 非法迁移路径会被拒绝，不会破坏画布结构。
5. 编辑与拖拽不会互相抢占，用户可清楚感知当前处于哪种操作模式。


## 8.5 卡片关系

### 8.5.1 功能说明

第一版只支持少量高价值关系，避免画布变得难以理解。

产品层统一采用中文关系词：

- 来源于
- 澄清了
- 支持
- 阻塞
- 冲突于
- 产出为

### 8.5.2 关系展示要求

1. 关系线默认轻展示。
2. 选中卡片时才重点显示其直接关系。
3. 不显示复杂全图蜘蛛网关系。

### 8.5.3 验收标准

1. 用户能清楚理解关系含义。
2. 关系不会压过卡片本身成为视觉主体。

## 8.6 右侧 AI 助手

### 8.6.1 功能说明

右侧 AI 助手不是普通聊天框，而是：

`把自然语言编译成画布变化的工作入口`

同时它也承担多源输入的统一接入口，以及当前工作面的持续收敛职责。

右侧 AI 助手的核心价值不是“能聊天”，而是：

1. 吸收输入。
2. 提炼结构。
3. 暴露缺口。
4. 发起追问。
5. 生成建议。
6. 驱动画布更新。

### 8.6.2 页面布局要求

右侧 AI 助手采用常驻侧栏布局，固定在主画布右侧。

布局要求如下：

1. 右侧侧栏应始终可见，不作为临时弹窗存在。
2. 顶部展示 AI 助手标题、当前工作上下文提示和关闭/折叠入口。
3. 中部展示消息流，承载用户输入、AI 回复、变化摘要和确认请求。
4. 底部展示输入区、附件入口和快捷操作入口。
5. AI 助手宽度应固定在可阅读、可操作的范围内，不随消息长度频繁抖动。

### 8.6.3 页面字段与组件要求

| 页面区域 | 字段名称 | 组件要求 | 说明 |
| --- | --- | --- | --- |
| 顶部区 | 助手标题 | Text | 展示当前助手身份 |
| 顶部区 | 当前上下文提示 | Text / Badge | 展示当前正在处理的主题或当前里程碑进度信息 |
| 消息流 | 用户消息 | Bubble | 展示用户输入 |
| 消息流 | AI 回复 | Bubble | 展示 AI 的解释、追问、建议 |
| 消息流 | 变化摘要 | Inline Summary Card | 展示本轮新增、更新、关闭、建议确认等变化 |
| 消息流 | 确认请求 | Confirmation Card | 用于承载高影响动作确认 |
| 输入区 | 输入框 | Textarea | 支持多行自然语言输入 |
| 输入区 | 附件入口 | Icon Button | 支持导入补充材料 |
| 输入区 | 发送按钮 | Button | 提交当前输入 |
| 快捷区 | 建议动作 | Chips / Button Group | 提供总结、检查一致性、生成问题等快捷动作 |

### 8.6.4 核心能力

AI 助手首版应具备以下能力：

1. 承接多源输入。
2. 识别用户当前意图。
3. 定位应该影响的卡片或模块。
4. 生成结构化更新建议。
5. 在符合规则时自动应用低风险更新。
6. 对高影响动作请求确认。
7. 对模糊输入主动追问。
8. 输出本轮变化摘要。
9. 支持用户从消息跳回对应画布对象。
10. 对冲突信息进行显性标记并升级为待决策。

### 8.6.5 输入模式

右侧 AI 助手首版至少支持以下输入模式：

1. 直接对话输入
2. 粘贴长文本
3. 粘贴聊天摘录
4. 粘贴会议纪要片段
5. 上传截图并补充说明
6. 引用当前画布中的卡片继续讨论

输入模式要求如下：

1. 用户可以在不离开当前工作面的情况下持续补充输入。
2. 用户在讨论某张卡片时，应支持把该卡片作为当前对话上下文。
3. 输入过长时，应提示系统正在分段理解，而不是直接静默失败。

### 8.6.6 七类基础动作

第一版只允许 AI 驱动以下七类基础动作：

1. 新增卡片
2. 更新卡片
3. 改变状态
4. 建立关系
5. 标记冲突
6. 关闭问题
7. 标记进度/更新里程碑

这些动作必须可被审计、可回执、可定位到具体对象。

### 8.6.7 对话显影流程

每轮对话按以下流程执行：

1. 识别意图
2. 定位对象
3. 判断是继续追问、显性化冲突、沉淀约束、生成待决策，还是生成交接物
4. 生成更新建议
5. 应用到画布
6. 输出变化摘要

其中“识别意图”不仅适用于聊天回复，也适用于长文本导入后的后续追问。

系统应能判断输入更像：

1. 事实来源
2. 当前问题
3. 待澄清点
4. 约束补充
5. 待决策事项
6. 交接物收束

### 8.6.8 信任分级

不是所有动作都应由 AI 自动写入。

#### 自动写入

适用于低风险事实整理：

- 证据卡
- 问题卡
- 待澄清卡
- 约束卡说明补充
- 弱关系

#### 建议确认后写入

适用于高影响动作：

- 新建待决策卡
- 待澄清卡改为已澄清
- 约束卡改为已生效
- 生成交接物
- 触发里程碑推进

#### 只追问，不写入

适用于输入模糊、指代不清、前后冲突或存在多种解释的情况。

### 8.6.9 确认请求规则

当 AI 识别到高影响动作时，应以确认请求卡形式提示用户，而不是静默写入。

确认请求至少需要包含：

1. 本轮建议动作类型
2. 将影响哪些卡片
3. 建议结果摘要
4. 确认 / 取消入口

例如：

- 建议生成一张待决策卡
- 建议关闭 2 个待澄清问题
- 建议将某条约束标记为已生效
- 建议生成一张结构化交接物
- 建议推进或更新当前里程碑进度

### 8.6.10 追问规则

当输入不清晰时，AI 应优先追问，而不是强行落图。

至少以下情况需要优先追问：

1. 指代不清
2. 前后冲突
3. 约束存在多种解释
4. 决策表达不完整
5. 输入更像情绪判断而非业务判断

追问应尽量具体，并指向当前缺少的信息，而不是泛泛地要求“补充更多背景”。

### 8.6.10A 协作协议

为了让 AI 更像“产品同事”而不是“会整理卡片的聊天框”，首版必须遵守以下协作协议：

1. 优先级顺序固定为：`先暴露不确定性 -> 再沉淀约束 -> 再形成待决策 -> 最后生成交接物`。
2. 当用户的一句话同时可以被理解为“约束”或“结论”时，默认先视为待确认约束，而不是直接视为稳定结论。
3. 当来源信息之间冲突时，AI 不得私下选择其一，必须显性标记冲突并要求用户裁决或补充背景。
4. 任何进入“已生效”或“已确认”状态的内容，都必须能追溯到具体来源、确认方式或用户裁决记录。
5. 交接物生成前，AI 必须显式说明当前仍未解决的关键缺口，不能伪装成“已经完整收敛”。

### 8.6.11 对话回执

AI 每次更新画布后，应给出本轮变化摘要，例如：

- 新增了 2 张待澄清卡
- 更新了 1 张约束卡
- 关闭了 1 个待澄清问题
- 标记了 1 组冲突信息
- 有 1 条待决策建议等待确认

变化摘要至少应包括：

1. 新增了什么
2. 更新了什么
3. 关闭了什么
4. 是否有待确认动作

### 8.6.12 关键交互

1. 用户可直接输入自然语言驱动画布更新。
2. 用户可引用当前卡片继续讨论。
3. 用户可在消息中确认或拒绝高影响动作。
4. 用户可点击变化摘要跳转到相关卡片。
5. 用户可通过快捷动作触发总结、检查一致性、生成问题等操作。

### 8.6.13 状态与异常展示

1. 当 AI 正在处理中时，应展示处理中状态，而不是让输入区无反馈。
2. 当 AI 无法理解用户输入时，应明确提示并给出继续操作建议。
3. 当某次更新动作失败时，应展示失败原因，并尽量保留已成功的部分动作。
4. 当高影响动作等待确认时，应在消息流中持续可见，直到用户处理。
5. 当某次消息只产生追问而未更新画布时，应明确说明“当前未对画布做变更”。

### 8.6.14 验收标准

1. AI 可对低风险动作自动显影。
2. AI 在高影响动作前可进行确认。
3. AI 在模糊输入时会优先追问，而不是强行落图。
4. 用户可从消息和变化摘要跳回相关卡片。
5. AI 助手在整个工作流中是持续性的工作入口，而不是一次性导入工具。
6. AI 在不同轮次中会优先遵守“先暴露不确定性，再推进已确认结构”的协作规则。

## 8.7 Active Todos

### 8.7.1 功能说明

`Active Todos` 不是任务管理列表，而是：

`当前还没有收敛、并且正在影响产品经理继续推进的认知缺口面板`

它的目标不是替代任务系统，而是帮助产品经理快速识别：

1. 当前最值得优先处理的问题是什么。
2. 哪些缺口正在阻塞方案继续收束。
3. 哪些动作已经清楚，但还没有被推进完成。

### 8.7.2 页面布局要求

Active Todos 采用右上角常驻悬浮面板布局。

布局要求如下：

1. 面板默认常驻可见，不依赖用户每次手动展开。
2. 面板标题区展示当前 Todo 总数。
3. 面板主体区按条目列表展示当前活跃 Todo。
4. 条目数过多时，应支持滚动查看。
5. 面板不承担复杂编辑功能，重点在于快速浏览、定位和处理。

### 8.7.3 来源

第一版只从以下对象投影生成：

- 待澄清卡
- 待决策卡
- 少量待确认约束卡

只有满足以下条件之一的对象才进入 Active Todos：

1. 阻塞后续推进
2. 需要 PM 明确拍板
3. 需要找别人确认
4. 已形成明确动作但还未完成

### 8.7.4 Todo 类型

产品上分为三类：

- 待澄清
- 待决策
- 待定义

类型含义如下：

#### 待澄清

表示当前还有问题没有讲清楚，需要继续问清。

#### 待定义

表示方向已经大致明确，但规则、字段、口径或范围还未落定。

#### 待决策

表示信息已收敛到需要 PM 拍板，但当前尚未做出最终判断。

### 8.7.5 页面字段与组件要求

| 字段名称 | 组件要求 | 说明 |
| --- | --- | --- |
| 标题 | 文本 | Todo 一句话标题 |
| 类型 | Badge | 待澄清 / 待定义 / 待决策 |
| 优先级 | Badge | 高 / 中 / 低 |
| 来源模块 | 文本 | 来自哪个模块簇 |
| 阻塞状态 | Icon + 文本 | 是否阻塞其他卡片推进 |
| 源卡引用 | Jump Link / Icon | 点击后跳回源卡 |

### 8.7.6 优先级规则

首版优先级分为：

- 高
- 中
- 低

优先级计算应至少参考以下因素：

1. 是否阻塞后续推进
2. 是否影响当前已确认约束或交接物
3. 是否影响当前主题能否对外继续推进
4. 是否被用户手动标记为重要

### 8.7.7 关键交互

1. 点击 Todo 后可定位到源卡。
2. 用户可在聊天中直接处理该 Todo。
3. Todo 完成后，应同步更新源卡状态。
4. 用户可快速识别当前哪些 Todo 属于“必须先处理”的内容。

### 8.7.8 状态与异常展示

1. 当没有活跃 Todo 时，应展示轻量空状态，例如“当前没有活跃缺口”。
2. 当源卡被删除、归档或状态异常时，Todo 应同步失效，不得悬空保留。
3. 当 Todo 与当前里程碑节点不一致时，应以当前里程碑进度投影视图为准。
4. 当同一缺口被重复投影时，应支持合并而不是重复展示。

### 8.7.9 验收标准

1. Todo 面板只展示活跃缺口。
2. 每条 Todo 均可定位回源卡。
3. Todo 不是独立事实源。
4. Todo 类型和优先级可帮助用户快速判断先处理什么。

## 8.8 时间轴与里程碑进度条

### 8.8.1 功能说明

底部时间轴是一个横向项目里程碑进度条，用于展示项目的整体交付阶段、核心里程碑节点及当前所处进展位置。

它承载的是项目进度的可视化轻量推进，帮助产品经理清晰把握生命周期，而不是复杂的历史进度版本回放或复杂的甘特图任务管理。

### 8.8.2 页面布局要求

进度条位于主画布底部，横向铺开，作为工作台常驻的进度指示区。

布局要求如下：

1. 时间轴在视觉上应清晰独立，以灰色胶囊横条和节点气泡组成。
2. 进度条上依次展示各个核心里程碑阶段与节点（如：阶段定义、内测发布、MVP 上线）。
3. 使用明确的垂直指示线和指示标签标识“当前日期”或“当前进度点”（例如：当前日期 5月18日）。
4. 核心里程碑应具备当前所处状态的可视化高亮（如已完成、进行中、待开始）。

### 8.8.3 里程碑定位

它用于查看：

1. 当前项目整体推进到了哪一个关键阶段。
2. 距离下一个交付里程碑（如内测发布、MVP 上线）还有多远，以及对应的待处理任务缺口。

时间轴不用于：

1. 复杂的历史认知版本回溯与回放。
2. 细粒度到人的开发工时排期与甘特图。
3. 替代外部专业的项目管理系统。

### 8.8.4 里程碑定义

里程碑代表项目在生命周期中的核心阶段与交付状态：

1. 包含核心的交付节点名称（如“内测发布”、“MVP上线”、“公测”）。
2. 指导各阶段下的卡片收敛深度（例如：内测发布前，应澄清所有阻塞性问题）。
3. 具有计划交付的时间段标注。

### 8.8.5 里程碑更新

里程碑进度的推进可以由以下方式影响：

1. 关联问题的澄清和约束生效比例达到阶段要求，里程碑自动推进。
2. 产品经理手动点击或标记特定里程碑为完成状态。
3. 日期自然流转越过特定指标线。

### 8.8.6 核心交互

1. 用户可以点击里程碑节点，查看该里程碑关联的目标与核心卡片集。
2. 指示器支持拖拽以调整当前进度，或双击指示器回到真实时间。
3. 可折叠或展开下方的里程碑详细日志。

### 8.8.7 验收标准

1. 里程碑进度条视觉表现轻量、规整，不干扰主画布操作。
2. 指示线能精确指向当前日期或指定进度位置。
3. 用户可快速了解当前项目阶段及所面临的缺口。

## 9. 数据结构与计算口径

### 9.1 卡片基础结构

每张卡片至少包含以下基础字段：

| 字段名称 | 说明 |
| --- | --- |
| 卡片 ID | 全局唯一标识 |
| 卡片类型 | 证据卡 / 问题卡 / 待澄清卡 / 约束卡 / 待决策卡 / 交接物卡 |
| 标题 | 当前卡片标题 |
| 摘要 | 卡片的一句话或短文本摘要 |
| 状态 | 当前状态 |
| 标签 | 辅助分类标签 |
| 主归属模块簇 | 当前主要所在模块簇 |
| 来源引用 | 指向输入来源或来源卡片 |
| 关系引用 | 指向关联卡片关系 |
| 里程碑标记 | 该卡在哪些里程碑节点中活跃 |
| 更新时间 | 最近更新时间 |

### 9.2 卡片类型字段口径

不同卡片在基础字段之外应具备类型化扩展字段。

#### 证据卡扩展字段

1. 来源类型
2. 原始摘录
3. 输入时间
4. 引用数量
5. 冲突标记

#### 问题卡扩展字段

1. 目标用户
2. 核心痛点
3. 当前业务目标
4. 关联待澄清数

#### 待澄清卡扩展字段

1. 优先级
2. 阻塞范围
3. 建议追问对象
4. 澄清结果引用

#### 约束卡扩展字段

1. 约束类型
2. 适用范围
3. 例外说明
4. 确认方式
5. 冲突标记

#### 待决策卡扩展字段

1. 决策类型
2. 备选解释
3. 影响范围
4. 决策结果引用

#### 交接物卡扩展字段

1. 当前目标
2. 已确认约束列表
3. 已完成决策列表
4. 未解决问题列表
5. 推荐后续动作

### 9.3 关系结构口径

首版支持的关系类型包括：

1. 来源于
2. 澄清了
3. 支持
4. 阻塞
5. 冲突于
6. 产出为

每条关系至少记录：

1. 关系 ID
2. 起点卡片 ID
3. 终点卡片 ID
4. 关系类型
5. 创建时间
6. 是否当前有效

### 9.4 Active Todos 计算口径

Active Todos 不是独立事实源，而是由当前活跃卡片投影生成。

只有满足以下条件之一的对象才进入 Active Todos：

1. 阻塞后续推进
2. 需要 PM 明确拍板
3. 需要找别人确认
4. 已形成明确动作但还未完成

投影来源仅限：

1. 待澄清卡
2. 待决策卡
3. 少量待确认约束卡

### 9.5 Todo 优先级计算口径

Todo 优先级至少参考以下因素：

1. 是否阻塞后续推进
2. 是否影响当前已确认约束或交接物
3. 是否影响当前主题能否对外继续推进
4. 是否被用户手动标记为重要

首版优先级只分为：

- 高
- 中
- 低

### 9.6 里程碑阶段数据口径

每个里程碑节点至少关联并记录：

1. 当前里程碑的目标与对应核心卡片集合
2. 当前阶段的卡片状态
3. 阻塞当前交付的活跃缺口列表
4. 完成当前交付所沉淀的规则与决策

### 9.7 进度条更新触发口径

进度条的里程碑状态可以在发生重要推进事件时触发更新。

应当更新进度条进展的事件包括：

1. 画布建立了针对特定里程碑的关键卡片定义
2. 与该里程碑绑定的全部阻塞性问题被关闭或澄清
3. 用户手动推进或将进度指示线拖拽至最新里程碑
4. 产生了该里程碑对应的结构化交接物

不触发进度推进的情况包括：

1. 卡片的常规文字微调
2. 节点的常规画布拖拽与排布整理
3. 纯视觉颜色的变更

### 9.8 AI 变更集口径

AI 不直接输出整张画布，而应输出结构化变更集。

首版允许的变更集类型包括：

1. 新增卡片
2. 更新卡片字段
3. 修改卡片状态
4. 新增关系
5. 标记冲突
6. 关闭问题
7. 标记当前进度/更新里程碑

### 9.9 结构化交接物口径

结构化交接物是 EvoCanvas 1.0 首版最重要的对外交付对象，不等价于 PRD，也不等价于完整 machine spec。

每份交接物至少必须包含：

1. 当前主题与目标
2. 背景输入摘要
3. 已确认约束
4. 已完成决策
5. 仍未解决的问题
6. 推荐后续动作
7. 关联当前里程碑和关键来源引用

结构化交接物必须满足：

1. 可被人类快速理解并继续推进
2. 可被新的 AI 会话作为继续输入使用
3. 若底层约束或决策变化，应可被识别为已过时

每条变更至少应包含：

1. 变更类型
2. 目标对象
3. 变更内容摘要
4. 是否需确认
5. 变更结果状态

## 10. 状态、权限与异常规则

### 10.1 通用状态

所有卡片共享五个顶层状态：

- 草稿中
- 待确认
- 生效中
- 已阻塞
- 已归档

通用状态解释如下：

#### 草稿中

表示该对象已被识别或创建，但当前仍处于形成过程，不应作为稳定依据参与后续判断。

#### 待确认

表示该对象已经具备足够信息，但仍需要产品经理明确确认。

#### 生效中

表示该对象当前有效，可作为后续方案、结论或推进的依据。

#### 已阻塞

表示该对象当前无法继续推进，通常依赖其他问题或结论先解决。

#### 已归档

表示该对象不再处于活跃工作流中，但应保留历史记录。

### 10.2 类型化状态

#### 证据卡

- 已收录
- 已引用
- 已归档

#### 问题卡

- 初步理解
- 待收敛
- 已收敛
- 已归档

#### 待澄清卡

- 待提出
- 待确认
- 已澄清
- 已阻塞
- 已关闭

#### 约束卡

- 草稿中
- 待确认
- 已生效
- 已替代
- 已归档

#### 待决策卡

- 待判断
- 待确认
- 已决定
- 已归档

#### 交接物卡

- 草稿中
- 待确认
- 已确认
- 已过时

### 10.3 状态流转规则

#### 待澄清卡

可接受的主要流转包括：

1. 待提出 -> 待确认
2. 待确认 -> 已澄清
3. 待确认 -> 已阻塞
4. 待确认 -> 已关闭

#### 约束卡

可接受的主要流转包括：

1. 草稿中 -> 待确认
2. 待确认 -> 已生效
3. 已生效 -> 已替代

#### 待决策卡

可接受的主要流转包括：

1. 待判断 -> 待确认
2. 待确认 -> 已决定
3. 已决定 -> 已归档

#### 交接物卡

可接受的主要流转包括：

1. 草稿中 -> 待确认
2. 待确认 -> 已确认
3. 已确认 -> 已过时

### 10.4 权限规则

1. 首版默认单人工作台，不区分多人编辑权限。
2. 当前用户拥有所有画布内操作权限。
3. AI 仅通过受控动作修改画布，不可绕过确认规则。
4. 高影响动作必须经过用户确认后才可生效。

### 10.5 AI 动作权限规则

AI 可自动执行的动作包括：

1. 新增证据卡
2. 新增问题卡
3. 新增待澄清卡
4. 更新约束说明补充
5. 建立弱关系
6. 标记冲突

AI 不可直接自动生效的动作包括：

1. 新建待决策卡
2. 将约束卡改为已生效
3. 关闭关键待澄清问题
4. 生成交接物
5. 触发进度更新

### 10.6 异常规则

1. 输入编译失败时，原输入必须保留。
2. 高影响动作未确认时，不允许直接落图。
3. 里程碑进度更新失败时，不应影响当前画布状态。
4. 卡片关系解析失败时，应保底展示卡片本体。
5. AI 无法理解输入时，应优先追问，不得生成高影响结构。
6. Todo 投影异常时，应回退到源卡视角，而不是保留失效 Todo。

## 11. 验收标准汇总

### 11.1 输入与显影

1. 用户导入任一受支持输入后，系统可以在合理时间内初始化画布。
2. 初始化结果至少包含证据卡、问题卡和待澄清卡。
3. 初始化结果若存在冲突或缺失，应显式生成冲突标记或待澄清对象，而不是静默忽略。
4. 用户可在右侧对话中继续补充信息并驱动画布更新。

### 11.2 输入类型覆盖

系统首版至少支持以下输入被编译进同一工作面：

1. 会议纪要
2. 自然语言想法
3. 聊天摘录
4. 用户反馈列表
5. 数据结论说明
6. 文档片段

### 11.3 画布结构

1. 画布采用连续结构，不出现被硬边框切碎的主区域。
2. 阶段带和模块簇可被清晰识别。
3. 同类卡片在视觉和布局上保持聚类一致性。

### 11.4 Todo

1. Todo 面板只展示当前活跃缺口。
2. 每条 Todo 均可定位回源卡。
3. Todo 处理完成后，源卡状态同步更新。

### 11.5 结构化交接物

1. 当关键待澄清项已收敛、关键约束已确认、必要决策已完成时，系统可生成结构化交接物。
2. 交接物必须包含目标、背景、已确认约束、已完成决策、未决问题和推荐后续动作。
3. 交接物可被不同会话或不同 AI 作为继续推进输入使用。

### 11.6 时间轴

1. 用户可拖动或点击时间轴进度条查看对应里程碑阶段。
2. 系统可在交付目标达成时自动推进里程碑。
3. 用户可直观识别当前进度与目标里程碑的差值。

### 11.7 AI 协作

1. AI 可自动处理低风险结构化整理。
2. AI 在高影响动作前会给出确认建议。
3. AI 在输入不清晰时优先追问，而不是强行落图。
4. AI 在存在冲突时优先显性化冲突，而不是私下合并。
5. AI 在首版流程中优先产出待澄清、约束和待决策，而不是过早产出最终结论。

### 11.8 核心命题验证

1. 对同一主题，在不同会话中根据同一份结构化交接物继续推进时，核心约束和待决策识别结果应保持稳定，不因表达顺序变化而大幅漂移。
2. 与“纯聊天记录继续推进”相比，使用 EvoCanvas 结构化交接物继续推进时，需求漏点和歧义应显著减少。

## 12. 非功能性需求

1. 主画布应保持视觉克制，避免白板式视觉混乱。
2. 卡片密度要支持产品经理长时间浏览，不应被长文挤满。
3. 关键操作需要可回退，尤其是结论替代和问题关闭。
4. 里程碑切换应快速、稳定，不造成明显页面阻塞。
5. AI 更新应尽量采用增量变更，避免整图重绘。

## 13. 术语表

| 术语 | 定义 |
| --- | --- |
| 输入编译台 | 把不同来源输入编译到同一张画布上的统一入口能力 |
| 阶段带 | 主画布上的流程性分组层，用于表达发现、定义、规划、推进 |
| 模块簇 | 阶段带下的语义聚类容器 |
| 证据卡 | 事实输入的结构化投影 |
| 待澄清卡 | 当前尚未收敛、需要追问或确认的问题卡 |
| Active Todos | 当前还没有收敛、并且正在影响推进的缺口投影视图 |
| 里程碑进度条 | 展示交付生命周期与里程碑阶段的进度指示 |
