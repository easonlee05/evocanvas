# Maturity Levels（成熟度层级）

> 方法成熟度：`L3 可指导实现的治理规格层`
> 目标实现归属：`Harness 文档治理`
> 当前实现状态：`已应用`
> 实现说明：成熟度评价规格完整度，不评价代码完成度；每篇文档另记录当前实现状态。

## 1. 控制目标

阻止方向性说明被误当作可编码规则，也阻止仅因现有代码存在就把目标规格宣称为完成。

## 2. 四级定义

| 级别 | 能回答 | 不能声称 |
| --- | --- | --- |
| L1 产品原则层 | 为什么需要、守住什么价值 | 对象、流程或接口已明确 |
| L2 对象与流程定义层 | 有哪些对象、责任和主流程 | 边界情况和生效规则可直接实现 |
| L3 可指导实现的治理规格层 | 权威输入输出、权限确认、状态、失败恢复和验收 | 字段已达到最终代码级冻结 |
| L4 可直接编码的运行时规格层 | 精确 Schema、API、算法、时序和兼容规则 | 实现已完成或生产已验证 |

## 3. L3 七项门槛

一篇规范性 Harness 文档升为 L3 前必须明确：

1. 控制目标；
2. 实现归属；
3. 权威输入输出；
4. 权限与确认边界；
5. 状态推进、回退和过时；
6. 失败与恢复；
7. 验收场景。

内容可以引用同组权威子规格，但实现者不能被迫自行发明产品规则。

## 4. 当前实现状态

使用以下独立状态：

- `未开始`
- `合同已定，代码待迁移`
- `部分接入`
- `已验证`
- `1.0 延后`

L3 + 代码待迁移是合法组合；L4 也不自动等于已验证。

## 5. 组合文档判断

主文档成熟度取其完成职责所需规格的最低成熟度。参考、历史或决策记录应明确其规范性；历史参考不因内容详细而成为当前 L3。

## 6. 升降级规则

- 新证据推翻权威边界或主状态机：相关文档退回 L2 并重新收敛。
- 仅发现字段名或实现细节待调整：保持 L3，进入 L4 设计。
- 代码与 L3 冲突：代码标记迁移缺口，不能反向降低目标合同。
- 验收场景不可执行或关键失败无处理：不能保持 L3。

## 7. 验收场景

1. 文档只写“需要用户确认”但没定义确认范围时，评为 L2。
2. 文档已定义治理合同但代码未接入时，评为 L3 + 代码待迁移。
3. 有 API Schema 但缺失权限和恢复规则时，不能因技术详细而评为 L4。
4. 参考模型不进入当前成熟度汇总。
5. 全量审计可从每篇文档找到七项门槛或明确权威引用。
