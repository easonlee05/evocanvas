# Governance（治理）

> 当前成熟度层级：`L3 可指导实现的治理规格层`
> 编码门槛：`可作为 1.0 对象状态、Chat 确认依据、交接物门禁和异常回退的实现输入`

## 1. 这一层回答什么问题

治理回答：AI 从混杂输入中提出理解、问题、约束、决策和交接内容之后，系统如何判断这些内容能否生效、能否被下游依赖、什么时候必须回退或等待用户裁决。

EvoCanvas 1.0 的治理目标不是让 AI 少说话，而是让每一次收敛都有清楚边界：

- 这只是候选，还是已经可以作为依据。
- 这是信息缺口，还是需要用户拍板。
- 这是草稿交接，还是已确认交接。
- 这次变化有没有来源、确认方式和回执。

## 2. 基本立场

治理层保留四条基本立场：

1. AI 有建议权，没有天然生效权。
2. 对话流不是事实层，结构化包中的对象与信息地位才是可治理状态。
3. 画布卡片只是对象投影，来源和确认记录必须回到结构化包与原始消息。
4. 结构化交接物不是万能总结，它只能打包当前已经被治理过的工作状态。

当输入存在冲突、歧义或上下文缺失时，治理层要求系统先显性化冲突和缺口，不得静默合并。

## 3. 治理对象

EvoCanvas 1.0 的主治理对象是结构化包中的业务对象；画布以卡片形式显影这些对象：

- 证据卡：原始材料中与当前主题相关、值得引用的证据片段，不代表正式结论。
- 问题卡：需要解决的实际问题，一个问题对应一张卡。
- 待澄清卡：Chat 后仍未解决、并会影响后续判断的信息缺口。
- 约束卡：已经在 Chat 中确认的术语、字段、状态、权限、流程和边界等规则。
- 待决策 / 方案承接卡：必须由用户拍板，并保留轻量选项、取舍和推荐的事项。
- 交接物承接卡：达到可阅读、可评审条件的当前结构化交接视图入口。

来源片段、解释对象和候选提案可以作为后端内部结构，但对 1.0 主文档而言，它们服务于上述卡片，不替代卡片成为产品对象。

## 4. 治理检查点

治理层至少在以下时刻介入：

- 收敛部件准备新增或更新结构化对象时。
- 对象准备从草稿中进入待确认时。
- 对象准备进入已生效、已决定或已确认状态时。
- 关键待澄清准备关闭时。
- 结构化交接草稿准备生成或刷新，以及交接版本准备确认时。
- 新输入可能推翻旧约束、旧决策或旧交接物时。

每次检查至少回答：

1. 是否有来源或确认依据。
2. 是否存在冲突、缺口或未确认前提。
3. 当前对象类型是否正确。
4. 当前动作只是候选整理，还是信息地位升级。
5. 若属于信息地位升级，是否已有匹配范围的用户确认。
6. 结果是否需要写入状态账本。

## 5. 治理不负责什么

治理不负责决定界面如何展示，也不负责把内容写得更像文档。

治理只负责事实边界和状态生效：什么可以继续作为依据，什么必须停在草稿、待确认、待澄清或待决策。
