# Orchestration and Lifecycle（编排与生命周期）

> 当前成熟度层级：`L3 可指导实现的治理规格层`
> 编码门槛：`可作为 1.0 收敛调度、运行记录生命周期、信息地位升级和回流规则的实现输入`

## 1. 分组目的

本组定义 EvoCanvas 如何在不打断正常 Chat 的前提下，把已经聊清楚的增量推进为可验证、可治理、可追溯的结构化状态。

- [Orchestration（编排）](./01%20Orchestration%EF%BC%88%E7%BC%96%E6%8E%92%EF%BC%89.md) 回答：什么时候值得启动收敛，运行单元如何接续。
- [Lifecycle（生命周期）](./02%20Lifecycle%EF%BC%88%E7%94%9F%E5%91%BD%E5%91%A8%E6%9C%9F%EF%BC%89.md) 回答：Chat、判断、收敛、包版本和对象状态如何结束、过时与替代。

二者共同服务 `Vibe Shaping` 与交付物产出，但不把它们做成两套运行机制，也不把产品体验旅程固化为主题阶段状态机。

## 2. L3 主链

```text
持久化 User 消息或来源
-> 完成正常 Chat
-> 创建或合并收敛判断
-> 跳过 / 继续积累 / 触发
-> 按包串行执行收敛
-> 形成结构化提案
-> 结构、来源和策略验证
-> 信息地位与风险治理
-> 原子提交正文版本或包版本治理变化
-> 画布、Todo、里程碑与 Toast 投影
```

输入编译、显式整理请求、Chat 中的明确确认和语义编辑都进入同一判断与收敛主链。它们可以成为强触发信号，但不能绕过验证、治理或版本检查。

[Convergence Operations（收敛操作）](./03%20Convergence%20Operations%EF%BC%88%E6%94%B6%E6%95%9B%E6%93%8D%E4%BD%9C%EF%BC%89.md) 定义提案中允许出现的结构化操作，以及冲突、多候选和交接草稿如何在同一引擎内处理。

## 3. 职责边界

| 能力 | 负责什么 | 不负责什么 |
| --- | --- | --- |
| Chat | 理解、追问、比较、建议和承接用户确认 | 直接修改结构化包 |
| 后置判断 | 判断是否存在值得结构化的增量 | 生成对象或改变事实状态 |
| 编排 | 合并触发、调度收敛、连接验证与治理 | 判断内容真假或代替用户拍板 |
| 收敛回合 | 形成受控结构化提案 | 绕过统一提交器写入事实 |
| 生命周期 | 约束运行记录、包版本和对象状态演化 | 把产品旅程变成主题阶段机 |
| 治理 | 决定信息地位能否升级或降级 | 决定前台怎么展示 |
| 投影 | 显影已经提交的当前状态 | 成为事实源或确认入口 |

编排只调度，不拥有事实生效权；生命周期只描述合法演化，不重新定义运行时记录。

## 4. 确认边界

EvoCanvas 确认的是产品判断和信息地位，不是“是否允许系统生成一张卡”。

- 相关证据片段、实际问题、Chat 后仍影响推进的待澄清、待决策候选和达到可评审条件的交接草稿，在来源与结构通过验证后可以自动写入。
- 新增、实质修改或替代约束，以及决策变为已决定、关键待澄清关闭、交接版本变为已确认，必须能回指 Chat 中明确且带范围的确认依据。
- 正式外发、外部写入或其他不可逆副作用使用独立的外部动作门禁，不与普通结构化包更新混在一起。

[Gate Adjudication（门禁裁决）](./04%20Gate%20Adjudication%EF%BC%88%E9%97%A8%E7%A6%81%E8%A3%81%E5%86%B3%EF%BC%89.md) 只定义编排如何挂载这些门禁，不重复定义治理层的风险政策。

## 5. 核心不变量

1. Chat 不因后台收敛而拒绝接收新消息。
2. 每条原始 `user / assistant / tool` 消息独立保存，不被判断水位或结构化包替代。
3. 同一 `(workspace_id, package_id)` 同时最多一个可写收敛回合。
4. 每次收敛使用明确的消息范围、基础状态版本和基础包版本。
5. 新消息或语义写入使旧提案过期时，旧回合停止且不自动重放。
6. 没有正文变化时不创建新包版本；只有确认、过时或风险标注时可以执行纯治理提交；没有任何事实或治理提交时不产生画布变化提示。
7. Chat 已有有效确认时不得重复确认；确认不清时只能保持候选或未决。
8. 画布、Active Todos、里程碑和 Toast 都是提交后投影，不参与事实裁决。
