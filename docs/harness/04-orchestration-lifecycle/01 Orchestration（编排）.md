# Orchestration（编排）

> 当前成熟度层级：`L3 可指导实现的治理规格层`
> 编码门槛：`可作为 1.0 触发归并、收敛调度、结果路由和过期处理的实现输入`

## 1. 职责边界

编排回答两个问题：

1. 当前增量是否值得启动一次结构化收敛。
2. 命中后如何连接现有运行时、验证、治理、提交与投影能力。

编排不接管正常 Chat，也不自己生成事实。它复用运行时层定义的 `ChatTurn`、`ConvergenceJudgement`、`ConvergenceRun` 和 `CommitAttempt`，不新增平行的阶段任务或确认任务。

## 2. 触发来源

所有入口统一形成或合并一条收敛判断请求：

| 触发来源 | 默认信号 | 说明 |
| --- | --- | --- |
| Chat 完成 | 按内容判断 | 普通入口；逻辑上每轮检查，允许规则直接跳过 |
| 来源导入完成 | 强 | 原文先持久化，再判断可结构化范围 |
| 用户明确要求整理、更新或交接 | 强 | 只缩短触发判断，不绕过验证和治理 |
| Chat 中出现明确确认或否定 | 强 | 可能支持信息地位升级、撤回或替代 |
| 用户执行语义编辑 | 强 | 已先形成新状态版本，后续判断派生影响和过时关系 |
| 恢复器请求重判 | 按最新状态判断 | 只针对最新水位，不重放旧提案 |

判断记录通过 `signal_level`、`decision` 和 `reason_codes` 表达结果。建议至少支持以下原因码：

```text
no_semantic_delta
weak_semantic_delta
source_imported
explicit_organize
candidate_identified
conflict_identified
confirmation_detected
semantic_edit
handoff_requested
stale_recheck
```

原因码用于调度、诊断和评测，不是业务事实，也不注入结构化包。

## 3. 判断决策

判断只允许三种结果：

| 决策 | 使用条件 | 后续动作 |
| --- | --- | --- |
| `skip` | 没有新的业务语义或结构变化 | 结束判断，不创建收敛回合 |
| `defer` | 有弱增量，但尚不足以形成可靠结构变化 | 推进待重新判断水位，继续累积 |
| `trigger` | 已出现可结构化缺口、冲突、候选、确认、导入材料或明确整理要求 | 进入短合并窗口并尝试创建收敛回合 |

判断器不得：

- 生成、更新或关闭业务对象。
- 把礼貌性的“可以”“继续”脱离上下文解释为确认。
- 因用户明确要求整理而跳过来源、结构、策略或版本检查。
- 用一段模型总结替换待处理的原始消息范围。

## 4. 合并与调度规则

当判断结果为 `trigger` 时：

1. 先进入可配置的短合并窗口，吸收紧邻的连续消息。
2. 以 `(workspace_id, package_id)` 检查是否已有可写收敛回合。
3. 没有活跃回合时，使用最新水位创建一个收敛回合。
4. 已有活跃回合时，不再创建第二个写回合，只扩展唯一的待重新判断水位。
5. 活跃回合终止后，只对最新水位执行一次新判断。

精确时间窗口、弱信号累积阈值和小模型置信阈值属于可配置评测参数，不写死为产品规则。每次实际使用的参数版本必须进入 trace，保证可回放。

## 5. 收敛输入边界

调度器创建收敛回合时，至少钉住：

| 输入 | 对应运行时字段或引用 |
| --- | --- |
| 工作范围 | `workspace_id / conversation_id / package_id` |
| 原始消息范围 | `input_from_seq / input_through_seq` |
| 基础事实版本 | `base_state_version / base_package_version` |
| 触发依据 | `judgement_id` 或显式触发来源 |
| 当前结构化工作面 | 基础包版本引用 |
| 必要来源与工具原文 | 消息或来源引用，按需复水 |

调度输入不包含“当前产品阶段”。`Vibe Shaping`、需求澄清和交付物产出由当前任务目标、消息内容与结构化包状态共同体现，不需要另设 Stage Instruction。

## 6. 收敛执行顺序

一次收敛回合按固定控制顺序连接能力：

```text
装配工作面
-> 形成结构化提案
-> 结构验证
-> 来源验证
-> 策略验证
-> 风险分类与治理
-> 版本复检
-> 提交或正常结束
```

复杂输入仍走这条主链。冲突保留、多候选拆分和交接草稿生成只是提案策略，不创建“复杂回合”子状态机，也不要求模型依次执行一套可见阶段。

验证失败后的结构修复可以在同一回合内按预算重试；事实冲突、确认不足、治理拒绝和版本过期不得靠模型自循环绕过。

## 7. 结果路由

收敛的技术状态与业务结果分开。编排只按业务结果执行后续路由：

| 业务结果 | 编排动作 |
| --- | --- |
| `applied` | 发布提交事件，由画布、Todo、里程碑和 Toast 投影消费 |
| `no_change` | 正常结束，不创建包版本，不产生变化提示 |
| `not_ready` | 没有可提交候选变化，且目标信息地位尚不具备升级条件；正常结束并留给后续 Chat |
| `rejected_by_governance` | 正常结束并留 trace，不追加第二条 Assistant 消息 |
| 技术 `stale` | 停止写入；根据最新水位重新判断，不重放旧提案 |
| 技术 `failed` | 按运行时恢复规则处理，不伪造成功结果 |

如果候选、缺口或冲突已经形成合法变化并成功提交，业务结果应为 `applied`，即使其中某项地位升级被降级。`not_ready` 不等于运行挂起；若 Chat 中确认不足，后续正常 Chat 继续引导，后台不存在等待用户回复的确认队列。

## 8. 两类前台入口

### 8.1 输入编译

1. 先保存原始材料和来源元数据。
2. 创建强信号判断记录，明确本次来源范围。
3. 收敛回合提取证据、问题、冲突、缺口和候选对象。
4. 结构化结果按正确信息地位提交；不能确定的内容保持候选或未决。
5. 需要用户判断的语义问题由后续 Chat 承接，不由画布卡片发起审批。

### 8.2 右侧 AI 助手

1. 正常完成主 Assistant 回复。
2. 回复内完成必要追问、比较和产品判断确认。
3. 回复完成后创建或合并判断请求。
4. 命中后由独立收敛回合写入结构化包。
5. 提交后画布异步显影，不追加固定变化回执。

用户的新输入始终优先进入消息历史。后台收敛不得让 Chat 返回“当前工作区忙”。

## 9. 编排不负责什么

- 不决定用户最终的产品判断。
- 不定义对象字段和风险等级的业务政策。
- 不把产品体验旅程写成主题阶段状态机。
- 不让卡片、Toast 或固定回执承担确认职责。
- 不直接修改结构化包、状态账本或画布。
