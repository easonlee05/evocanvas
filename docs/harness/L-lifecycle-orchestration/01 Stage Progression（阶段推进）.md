# 阶段推进（Stage Progression）

> 当前成熟度层级：`L3 可指导实现的治理规格层`
> 编码门槛：`已达到 L3，可直接指导第一批阶段编排实现`

本文件展开 L 层主文档中的阶段推进主干，集中说明五段主流程、阶段推进器、检查点、停留规则与重判闭环。

## 这一层回答什么问题

阶段推进回答：

- 当前在哪个阶段
- 下一步允许往哪走
- 当前是否具备升级条件
- 若不具备升级条件，默认应如何继续推进

阶段推进器是 L 层的主调度中心。

## 五段主流程

### 输入接入（Intake）

目标：

- 接住新输入
- 确定输入主题和范围
- 识别输入类型

允许产物：

- 来源对象（source）
- 接入回执（intake receipt）
- 范围提示（scope hint）

### 输入编译（Compilation）

目标：

- 从多源输入中提取来源片段、解释对象、问题、冲突、术语和潜在边界

允许产物：

- 来源片段（source fragment）
- 解释对象（interpretation）
- 问题框定（problem framing）
- 待澄清候选（clarification candidate）

### 待澄清显影（Clarification）

目标：

- 显性化未知项、冲突项、歧义点和缺失前提

允许产物：

- 待澄清队列（clarification queue）
- 冲突标记（conflict marker）
- 问题包（question bundle）

澄清（clarification）的升级基线：

- 不是所有低置信解释都升级为澄清
- 只有会影响后续约束、待决策或交接质量的信息缺口，才升级为澄清
- 澄清既可以针对事实缺口，也可以针对意图缺口

### 约束 / 决策收敛（Constraint / Decision Convergence）

目标：

- 把足够稳定的内容沉淀成约束
- 把必须人拍板的部分转成待决策

允许产物：

- 约束候选（constraint candidate）
- 待决策候选（decision candidate）
- 方案对比（option comparison）

这一阶段默认建立在以下链路之上：

- 来源片段（source fragment）
- 解释对象（interpretation）
- 待澄清项（clarification）
- 约束 / 待决策 / 已确认决策

### 结构化交接（Handoff）

目标：

- 把当前已知与未知一起打包成交接物

允许产物：

- 交接草稿（draft handoff）
- 正式交接候选（formal handoff candidate）
- 快照触发（snapshot trigger）

## 阶段切换条件

### 从输入接入到输入编译

当输入已被接住并归入明确主题后，才进入输入编译（compilation）阶段。

### 从输入编译到待澄清显影

只要存在以下任一情况，就必须进入待澄清（clarification）阶段：

- 输入之间冲突
- 关键概念指代不清
- 缺少关键范围
- 风险边界不明

### 从待澄清显影到约束 / 决策收敛

只有当部分问题足够清楚，系统才允许将其升级为：

- 约束候选（constraint candidate）
- 待决策候选（decision candidate）

某个澄清被回答后，默认应先回流更新解释对象（interpretation），再判断是否已经足以形成约束或待决策。

### 待澄清回答后的默认路径

待澄清项（clarification）被回答后，默认不直接越级进入正式事实层，而应先回流更新解释对象（interpretation）。

只有在以下条件同时满足时，才允许有限直升（limited promotion）：

- 回答内容基本单义
- 当前冲突较低
- 风险较低
- 不会改变多个下游依据

这里所说的“单义”，默认采用更严格口径：

- 语义上基本只有一种合理解释
- 指向唯一主下游对象
- 不会顺带重写已有边界，也不会引出新的核心歧义

有限直升的上限默认是：

- 约束（constraint）
- 待决策候选（decision candidate）

它不允许直接形成已确认决策（confirmed decision）。

![待澄清项回答后的路径](./assets/03-clarification-answer-path.png)

这里所说的“不会改变多个下游依据”，默认采用“依据扇出”口径：

- 重点不是表面上改动了几个对象
- 而是这条回答会不会成为多个核心判断的共同新前提
- 即使表面上只更新一个对象，只要这个对象会反过来重写多条核心判断的依据链，也应视为“改变多个下游依据”

这里所说的“低风险回答”，默认不按内容类型粗略判定，而按是否改变事实边界与下游依据来判定。

也就是说：

- 内容类型只能作为辅助参考
- 真正关键的是，这条回答是否会改变事实边界
- 或是否会重写下游判断所依赖的依据链

只要满足其一，就不应被视为低风险回答。

如果某个回答本身不改变事实边界，但会明显改变推荐倾向，则默认采用条件看待：

- 若只是局部排序微调，且不改变正式边界，仍可视为低风险
- 但只要它会实质改变待决策候选（decision candidate）的推荐方向，就不再视为低风险

如果某个回答同时具备“消解旧冲突”与“引入新边界”两种效果，则默认采用分段处理：

- “消解旧冲突”可以计为收敛收益
- “引入新边界”必须单独评估是否改写事实边界与下游依据
- 系统不应只看净效果来粗略判定风险，也不应因为存在收敛收益，就自动放松对新边界的治理要求

如果只是把模糊说法压成更精确表达，只有在不改变事实边界与下游依据时，才可视为低风险精化。

如果某个解释对象（interpretation）从低置信变成高置信，但仍未形成正式边界，可以条件参与下游推进；一旦足以触发高风险对象生效，仍需补治理或确认动作。

如果一个回答同时影响多个解释对象（interpretation），只有在它们共享同一语义核且不会分叉出不同下游路径时，才允许条件并行更新。

如果旧待澄清项（clarification）可以关闭，但又自然暴露出下一层新的待澄清项，允许条件闭环；若新项其实说明旧项并未真正解决，则旧项不应关闭。

如果一个回答只解决了旧待澄清项的一部分，应优先判断旧项是否本来混入了多个缺口。若是，则拆分处理；若不是，则不关闭，只更新进度或置信状态。

### 从约束 / 决策收敛到结构化交接

交接物（handoff）不要求所有问题解决完，但要求当前结构已足够清楚，可以被继续推进。

handoff 必须同时包含：

- 当前已确认或较稳定内容
- 仍未解决的问题和边界

当待拍板事项已经成为当前推进主轴时，handoff 应将其从普通未决问题中抬升为独立槽位。

## 推进单位

阶段推进器的直接推进单位当前固定为：

`阶段节点 + 阶段内检查点`

这意味着：

- 阶段节点负责表达当前大段语义
- 阶段内检查点负责决定当前是否允许升级

L 层不采用“只看对象成熟度就自动换阶段”的主干模型。对象成熟度可以作为检查点判据，但不取代阶段主线。

## 检查点的首要职责

阶段内检查点的首要职责是：

`判断当前内容是否具备升级到下一阶段的条件`

风险暴露、用户确认、回退决策都不是并列主职责，而是“是否可升级”的判定依据。

## 检查点的综合判定顺序

检查点对“是否可升级”的判断采用综合判定，但主次顺序固定为：

1. 先看不确定性处理状态
2. 再看信息充分性
3. 最后看对象完备度

这样做的原因是：

- 若关键冲突、歧义、缺口未被处理，对象再齐也不应直接升级
- 信息不足时，系统可以先显性化未决，而不是用对象完整度掩盖缺口
- 对象完备度只作为后位条件，不应压过透明优先原则

## 未通过时的默认闭环

当检查点判定“暂不可升级”时，阶段推进器的默认动作是：

1. 停留当前阶段
2. 优先补充不确定性显影
3. 补充一轮后，回到当前检查点重新判定

这条默认闭环不直接回退上一阶段，也不默认立刻升级门禁。它先保护当前阶段内的收敛真实性。

### 为什么默认停留当前阶段

默认停留的原因是：

- 避免因为局部不满足条件就频繁回退抖动
- 避免把所有问题都交给门禁裁决器，导致主干失焦
- 保留在原语境里继续显影冲突、歧义、缺口和未确认前提

### 为什么优先补不确定性显影

停留当前阶段后，默认优先推动的不是补结论，也不是先补对象，而是：

`补充不确定性显影`

也就是继续把：

- 冲突
- 歧义
- 缺口
- 未确认前提

显出来，再决定是否补信息、补对象或继续推进。

## 高概率失真风险的默认处理

当阶段推进器识别到 `高概率失真风险` 时，L 层默认不直接把它等同于门禁。

当前主线是：

- 默认先停留当前检查点
- 先补充风险显影，而不是先补结论
- 显式说明风险来源、受影响边界、未确认前提
- 补充一轮后，回到当前检查点重判

只有当该风险已经：

- 改写事实边界
- 或改变交接主表达

时，才升级为事件触发门禁。

也就是说，L 层默认对这类风险采用：

`先阶段内透明收敛，再按污染程度决定是否升级门禁`

而不是“识别到高风险就一律审批”。

## 从停留升级到相邻前序回流

识别到高概率失真风险后，默认先停留当前检查点。

只有满足以下任一条件时，才允许升级为 `相邻前序回流`：

- 当前风险已经说明上游解释基础需要重写
- 当前阶段缺少关键输入，无法在本阶段继续收敛

这意味着：

- 如果问题仍可在当前阶段通过补显影消化，默认不回流
- 如果风险已经反证上游解释对象（interpretation）不成立，就不应硬留在原阶段
- 如果当前只是缺少关键输入，但问题框定仍成立，也应回到最接近补输入的前序语义位

## 相邻前序回流的默认目标

当触发这类回流时，默认不机械退一步，而是：

`按风险来源回流`

当前基线是：

- 如果是解释基础被改写，默认回流到 `输入编译（compilation）`
- 如果是关键输入缺失、但问题框定仍成立，默认回流到 `待澄清显影（clarification）`

因此，回流的首要目标不是流程退格，而是回到最能修复风险来源的上游语义位。

## 回流后的重返原检查点条件

按风险来源回流后，默认不允许“修一下就悄悄跳回”。

只有同时满足以下条件，才允许重回原先阶段的检查点：

- 已完成本次回流针对的最小修复
- 已完成风险重述
- 已在状态账本中留下回流原因与修复结果

其中，`风险重述` 最少要包含：

- 风险变化
- 修复动作
- 受影响边界
- 仍存未决
- 当前结论

这样做的目标是：

- 让原检查点重判有明确新依据
- 防止“局部修复”被误写成“整体收稳”
- 保证回流闭环对阶段推进器、状态账本和门禁裁决器都可解释

## 回流修复后的仍存未决落位

回流修复后，如果仍有未决，L 层默认采用：

`分级落位`

当前规则是：

- 如果仍存未决会继续影响当前阶段升级，回到 `待澄清显影（clarification）`
- 如果它已知但暂不阻断当前重判，则作为当前阶段尾项显式保留

也就是说，仍存未决不会一律重新抬升，也不会一律降成尾项提醒，而是继续服从“是否影响当前升级”的主干判断。

## 与门禁裁决的边界

阶段推进器负责日常推进与阶段内重判。

但当出现高影响动作时，默认不再只靠阶段内重判，而应升级到门禁裁决器处理。高影响动作的定义与处理规则见 [02 Gate Adjudication（门禁裁决）.md](</Users/apple/Desktop/evocanvas/docs/harness/L-lifecycle-orchestration/02 Gate Adjudication（门禁裁决）.md>)。
