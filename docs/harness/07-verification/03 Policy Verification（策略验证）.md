# Policy Verification（策略验证）

> 当前成熟度层级：`L3 可指导实现的治理规格层`

## 1. 这一层回答什么问题

策略验证回答：这次收敛有没有违背 EvoCanvas 1.0 的产品方法。

它防止的不是字段缺失，而是“结果看起来挺完整，路径却已经偏了”。

核心顺序固定为：

```md
先暴露不确定性 -> 再沉淀约束 -> 再形成待决策 -> 最后生成交接物
```

## 2. 不确定性显性化检查

以下情况应判为策略风险：

- 输入模糊、指代不清或前后冲突时，没有先追问或显性化冲突。
- 关键缺口存在，但系统直接往后沉淀结论。
- 本该暴露为待澄清的问题，被包装成一句平滑结论。
- 已经收敛的问题仍持续占据活跃缺口，制造假噪音。
- 同一轮 Chat 已经回答的问题仍被生成为待澄清卡。
- 不影响后续判断的普通疑问被大量显影，导致画布退化为聊天问题记录。
- 待澄清卡通过修改对象类型直接变成约束卡或待决策卡，导致原缺口身份与历史丢失。
- 已澄清或已关闭的待澄清卡仍停留在 Active Todos 或主画布默认视图，继续制造当前缺口假象。

策略验证在这里不是要求“问得越多越好”，而是要求系统只把真正影响推进的未知显性化。

## 3. 约束沉淀检查

以下情况应判为策略风险：

- 把一句偏好、猜测或局部理解直接写成已生效约束。
- 未经 Chat 明确确认，就把约束提议写入或显影为约束卡。
- 约束缺少确认方式，却被当成后续判断前提。
- 冲突约束没有显性标记，却继续参与交接收束。
- 新约束静默覆盖旧约束，没有替代关系、已替代状态或历史痕迹。
- 仅因新陈述出现得更晚，就自动判定旧约束已被替代。
- 把多条可独立确认、修改、替代或撤销的规则塞进同一张约束卡，导致局部治理只能整体重写。
- 核心含义、适用范围、阈值、例外、优先级或下游行为已改变，却仍在原对象上覆盖正文。
- 只凭用户确认，就把法律、平台政策、技术硬限制或数据结论等外部事实标记为已验证。

## 4. 待决策形成检查

以下情况应判为策略风险：

- 明明需要人拍板，却被系统写成既定结论。
- 待决策卡缺少决策主题、轻量选项、主要取舍、推荐或影响范围。
- 用户尚未确认，就把待判断内容写成已决定。
- 决策结果没有回写相关待澄清、约束或交接上下文。
- 一次确认同时形成决策结果和稳定规则边界时，只保留其中一种语义，导致“为何这样选”或“此后遵守什么”丢失。
- 已决定的卡退出 Active Todos 时也从主画布默认视图消失，使稳定决策结构不可见。

## 5. 交接收束检查

以下情况应判为策略风险：

- 关键待澄清仍未收敛，却生成看似可直接使用的交接物。
- 交接物没有明确未解决问题、待确认决策或推荐后续动作。
- 交接物把未确认约束伪装成已确认约束。
- 交接物被展开成传统完整 PRD，而不是当前主题的结构化产品上下文。
- 底层约束或决策已经变化，交接物却没有进入已过时或待刷新状态。

## 6. 高影响信息地位升级检查

以下信息地位升级属于策略上必须严查的变化：

- 将约束写成已生效。
- 将待判断内容写成已决定。
- 关闭关键待澄清。
- 将交接版本写成已确认或可供下游依赖。
- 通过跨栏目迁移改变对象语义。

如果这些动作绕过 Chat 中明确、带范围的确认依据或必要显性化步骤，策略验证必须失败。

清晰、完整且范围明确的用户直接陈述本身可以构成确认，不得为了形式完整而强迫用户先接受 Assistant 复述再重复确认。含糊、保留、举例、引用他人观点或范围不明的表达仍须继续澄清。

## 7. 工作台体验一致性检查

策略验证还要防止“产品体验已经偏离 1.0 要验证的命题”。

以下情况属于策略风险：

- 系统开始追求把内容写成一份漂亮大文档，而不是帮助用户看见缺口、约束、决策和交接状态。
- 工作面堆积大量低价值对象，掩盖真正影响推进的问题。
- 个人挂件或非正式内容被混入正式交接判断。
- 画布投影把允许显影的候选对象和已确认内容展示得没有区别，使用户无法看见哪些地方仍不稳定；未确认的约束提议不属于允许显影的候选对象，只保留在 Chat。

## 8. 策略验证失败后的默认方向

- 应先回到更保守的收敛位。
- 应先显性化冲突、缺口或待确认点。
- 应阻止把高影响结果伪装成已完成。
- 应让用户看到为什么这次没有继续推进，而不是只在内部静默失败。
