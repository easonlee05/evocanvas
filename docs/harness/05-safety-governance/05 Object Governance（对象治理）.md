# Object Governance（对象治理）

> 当前成熟度层级：`L3 可指导实现的治理规格层`
> 编码门槛：`可作为 1.0 卡片状态、AI 动作权限和 Chat 确认依据的实现输入`

## 1. 对象治理总原则

对象治理回答：每类卡片能承载什么、什么时候可以自动生成、什么时候必须等待确认、什么时候要回退或过时。

EvoCanvas 1.0 的对象不是文档段落，而是可追溯、可状态化、可交接的工作对象。

通用原则：

- 对象必须有类型，不能只是一段自由文本。
- 对象必须有且只有一套权威的类型化业务状态，不能只靠文案暗示是否成立。
- 高影响状态变化必须经过确认。
- 对象进入交接物前必须保留来源、未决和适用边界。

上下文筛选、治理门禁、交接和界面可以使用由“对象类型 + 类型化状态”确定性派生的通用治理分组，但不得把它作为第二套可写状态。结构、来源和策略验证结果使用独立验证状态表达，也不得混入对象生命周期。

## 2. 证据卡

证据卡承接会议纪要、聊天、截图、访谈、反馈、竞品资料和文档中的相关证据片段。完整原始材料独立保存，不直接等同于一张证据卡。

治理边界：

- 证据卡是事实输入的结构化投影，不代表正式结论。
- AI 可以自动新增与当前主题相关、值得引用的证据片段，但不得把全部材料机械切片铺满画布。
- 证据卡必须保留原始摘录、来源定位和结构化摘要；摘要可修订，但不得覆盖原始摘录。
- 证据原文缺失时，仍需保留摘要和来源标记，并提示来源不完整。
- 证据卡可以支持问题卡、约束卡或待决策卡，但不能直接替代它们。

类型化状态：已收录、已引用、已归档。

## 3. 问题卡

问题卡承接需要被解决的实际问题。一个问题对应一张卡，不强制设置主问题卡统领其他问题。

治理边界：

- 问题卡可以由 AI 自动生成。
- 不是每个疑问句都生成问题卡；纯信息缺口进入待澄清卡，需要选择方向的事项进入待决策卡。
- 相同或高度重叠的问题通过合并、聚类和归档控制数量，不通过拒绝建卡隐藏问题。
- 问题卡失去来源证据支撑时，应提示缺少来源支撑。
- 问题卡可以关联证据、待澄清、规则和方案。
- 问题卡本身不等于待决策结果，也不等于交接结论。

类型化状态：初步理解、待收敛、已收敛、已归档。

## 4. 待澄清卡

待澄清卡用于暴露术语冲突、规则未定、边界不清、风险未决和必须补问的信息。

治理边界：

- 待澄清的发现、追问和回答以 Chat 为主；同一轮已经回答清楚的问题不生成活跃待澄清卡。
- 只有 Chat 结束后仍未解决、并会影响问题、约束、决策或交接的缺口，才自动生成待澄清卡；不要求用户再次确认“是否建卡”。
- 待澄清卡是 Active Todos 的主要来源，但 Todo 不是独立事实源。
- 已澄清问题不得继续展示为活跃缺口。
- 当系统无法判断“继续追问”还是“进入待决策”时，应优先保持待澄清状态。
- 关闭关键待澄清问题属于高影响信息地位变化，必须确认。

类型化状态：待提出、待确认、已澄清、已阻塞、已关闭。

## 5. 约束卡

约束卡用于沉淀术语、字段、状态、权限、流程、计费、边界和数据口径等规则。

治理边界：

- AI 先在 Chat 中提出约束理解；用户确认、修正或否定后，收敛部件才可以写入并显影约束卡。
- 未确认的约束提议保留在 Chat；若本质上仍是信息缺口或方向选择，分别进入待澄清卡或待决策卡。
- 新增、实质修改或替代约束都必须回指 Chat 中明确且带范围的确认记录。
- 互相冲突的约束不得同时参与“已生效”判断，必须显性标记冲突或进入待决策。
- 约束被新事实替代时，旧约束应进入已替代或已归档，不直接删除。

类型化状态：已生效、已替代、已归档。

## 6. 待决策 / 方案承接卡

待决策 / 方案承接卡用于表达“不是信息不足，而是必须由用户拍板，或需要轻量方案承接比较”的事项。

治理边界：

- AI 可以在结构与来源通过验证后新增待决策 / 方案承接候选，不要求用户确认“是否生成卡片”。
- 该卡必须明确决策主题、当前轻量选项、主要取舍、影响范围和 AI 推荐；选项不是封闭答案集，用户可以提出新方向。
- 待决策卡不展开完整方案设计，完整方案卡仍属于后续版本能力。
- 进入已决定状态必须有 Chat 中明确且带范围的用户确认；确认后相关约束和待澄清卡需要同步更新。
- 未完成决策的卡必须持续可见，不得被系统自动关闭。
- 决策结果应回指相关待澄清、约束或冲突信息。

类型化状态：待判断、待确认、已决定、已归档。

## 7. 交接物承接卡

交接物承接卡承接当前主题的结构化产品上下文，是 1.0 对外继续推进的最小交接单元。

治理边界：

- 只有当前目标、背景、已确认约束、已完成决策和未决边界已经能够组织成可阅读、可评审内容时，才生成或刷新交接草稿并显影交接物承接卡。
- 交接草稿可以保留未解决问题和待确认决策，但必须显式展示；不要求所有问题先解决，也不要求用户确认“是否生成交接卡”。
- 交接版本进入已确认或可供下游依赖的状态必须有 Chat 中明确且带范围的用户确认。
- 未确认的交接物不得被标记为可直接外发。
- 若底层约束或决策发生变化，应显式提示交接物已过时。
- 用户必须能从交接物回跳到原始约束、待澄清和待决策对象。
- 交接物可以作为新会话或下游 AI 的继续输入，但不能遮蔽未解决问题。
- 卡面只展示标题、摘要、状态和未决数量等概览，完整内容仍来自同一结构化包版本。

显示状态：草稿中、待确认、已确认、已过时。该状态直接投影同一结构化包版本的有效治理状态，不是交接物承接卡自身可独立写入的第二套状态。

## 8. 关系治理

卡片关系用于帮助用户理解“来源于、澄清了、支持、阻塞、替代、产出为”等关键关系。

治理规则：

- 关系解析失败时，应保底展示卡片本体。
- 关系不能替代对象状态。
- 关系不能把未确认对象变成已生效对象。
- 交接物引用关系时，应优先引用已生效约束、已完成决策和仍未解决的问题。
