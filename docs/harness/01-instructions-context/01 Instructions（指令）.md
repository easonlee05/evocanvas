# Instructions（指令）

> 当前成熟度层级：`L2 对象与流程定义层`

## 1. 这一层回答什么问题

指令层定义模型应该怎样理解用户、怎样保持产品人格、怎样处理不确定性，以及怎样向用户表达。

它不负责定义 Agent 当前处于哪个阶段，也不负责决定何时生成结构化包、更新画布或执行治理动作。

## 2. 三类指令面

EvoCanvas 主对话只区分三类指令来源。

### 2.1 System Prompt

System Prompt 承载跨任务、跨会话稳定生效的规则：

1. 身份与协作关系。
2. 核心人格价值观及其行为定义。
3. 通用认知与协作原则。
4. 正常对话需要的领域语义区分。
5. 表达纪律与高频反模式。
6. 稳定的工具可信性原则。
7. 指令冲突、例外与升级边界。

System Prompt 不包含：

- 当前阶段与下一阶段。
- Supervisor 路由和内部角色计划。
- 卡片、Mutation、结构化包版本等内部实现细节。
- 当前对象、业务材料或画布快照。
- 动态工具清单与动态权限。
- 固定回执模板。

### 2.2 Runtime Developer Instructions

Runtime Developer Instructions 承载当前运行环境中模型必须遵守的动态治理信息：

- 当前权限和操作边界。
- 当前真正可用的工具、Skills 或能力。
- 工具使用规则和失败处理要求。
- 必要时的最小操作要求。

同一 Runtime Developer Message 还可以包含独立标记的结构化包数据分区。这个分区承载当前已版本化、受治理的工作状态，不是指令，也不能把包内候选内容提升为高优先级要求。

Runtime Developer Message 不应成为 Agent 内部状态转储，也不应直接塞入画布快照、未治理的业务材料全文或每轮临时生成的自由文本摘要。

### 2.3 User Prompt

User Prompt 是用户本轮的原始表达。

- 原样透传。
- 不追加角色说明。
- 不追加内部阶段。
- 不拼接结构化上下文。
- 不追加 JSON 格式要求。

运行时注入的数据应放在 Runtime Developer Message 的独立数据分区或其他独立输入项中，不能改写用户原话。

## 3. System Prompt 的人格锚点

EvoCanvas 主对话采用三个稳定人格价值观。

### 3.1 透明

显式表达不确定性、冲突、假设和信息来源，不通过流畅措辞掩盖信息缺口。

### 3.2 严谨

区分事实与推断、已确认与暂定、约束与待决策。稳定判断应能说明依据，无法确认时应明确边界。

### 3.3 共创

主动帮助用户推进理解，但不伪造共识、不替用户拥有最终判断，也不因保持克制而退化成只会追问的被动助手。

“结构化”和“克制”属于工作规则，不作为人格价值观单独承载。

## 4. 主对话需要理解的领域语义

System Prompt 只写入正常协作所需的稳定语义区分：

- 事实与推断。
- 已确认与暂定。
- 约束与待决策。
- 冲突与信息缺口。

System Prompt 不解释画布、卡片、结构化包、阶段节点或内部对象状态。主对话模型需要理解用户表达的地位，但不需要理解 EvoCanvas 的内部存储实现。

## 5. 指令优先级

模型可见指令的优先级为：

1. System Prompt：稳定且不可被下层静默覆盖。
2. Runtime Developer Instructions：在系统边界内补充当前环境规则。
3. User Prompt：表达用户本轮目标、偏好与补充信息。

低层指令可以具体化高层规则，但不能把暂定内容提升为确认事实，也不能要求模型伪造来源、工具结果或稳定结论。

## 6. 规则强度

规则措辞采用分级语言：

- `必须 / 不得`：产品不变量和可信性边界。
- `应当 / 优先`：默认行为和高频偏好。
- `可以 / 仅在……时`：条件性行为和例外。

不应把所有规则都写成同等强度的硬命令。真正不可违反的规则必须少而清楚。

## 7. 工具指令分工

System Prompt 只规定稳定原则，例如：

- 需要外部事实时先验证，不得凭空声称已经读取或执行。
- 工具失败或证据不足时明确说明，不伪造结果。
- 高风险操作服从权限和确认边界。

当前工具名称、参数、权限与使用方式由 Runtime Developer Instructions 和 Tool Schema 提供。

## 8. 规则写法

System Prompt 采用模块化、规则指令型写法：

1. 每个区块只承担一种规则职责。
2. 价值观后面必须跟随可观察的行为描述。
3. 高频边界可以使用短反例和替代表达。
4. 硬规则应说明适用条件或例外，避免绝对化误伤正常对话。
5. 不使用多组完整 Few-shot 对话塑造主对话行为。

例如，不只写“保持透明”，而应说明：

```text
当信息存在多种合理解释时，明确指出分歧和当前假设；不要选择一个更顺滑的版本并把它写成已确认事实。
```

## 9. 暂不冻结事项

以下内容尚未形成稳定结论：

- System Prompt 的最终字数或 Token 预算。
- 中文规则与英文强度词的最终混排方式。
- 各模块最终排序和具体措辞。
- 哪些反例经过评测后值得保留。

这些问题应在 System Prompt 初稿和评测样本形成后再决定。
