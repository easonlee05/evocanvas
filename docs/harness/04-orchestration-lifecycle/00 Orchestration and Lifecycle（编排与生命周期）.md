# Orchestration and Lifecycle（编排与生命周期）

> 当前成熟度层级：`L2 对象与流程定义层`
> 编码门槛：`未达到 L3，不应直接作为稳定实现规格；需继续补齐阶段状态、确认请求与回流规则`

## 1. 分组目的

本组同时放置“编排”和“生命周期”，但二者不是同一概念。

- 编排（orchestration）回答：当前这一轮该如何调度，先做什么，后做什么。
- 生命周期（lifecycle）回答：一个主题、回合或对象如何从模糊、候选、确认走到交接或归档。

在 EvoCanvas 1.0 中，这一组文档服务的是 `Vibe Shaping` 的推进骨架：

```md
感觉接入 -> 对话塑形 -> 结构收敛 -> 画布显影 -> 结构化交接
```

它不是为了把业务流程硬编码成单向流水线，而是为了让 AI 在每一轮都知道：

- 当前应该接住感觉、继续追问、显性化缺口，还是收束结构。
- 当前对象能否显影到画布。
- 当前动作是低风险整理，还是需要用户确认。
- 当前结果能否进入结构化交接物。

## 2. 边界声明

编排与生命周期不负责事实生效权。

- 编排决定本轮怎么推进。
- 生命周期决定对象和阶段如何演化。
- 状态账本记录推进结果。
- 验证判断结构和来源是否过关。
- 治理决定高影响动作能否生效。

因此，编排可以建议继续推进，但不能绕过确认把候选内容写成稳定事实。

## 3. 这一组的核心结论

EvoCanvas 的推进骨架不是“用户一句、AI 一答”的聊天循环，而是“受控收敛循环”。

默认顺序是：

```md
识别输入 -> 装配上下文 -> 判断阶段目标 -> 生成对象提案 -> 验证和风险分级 -> 应用 / 挂起 / 追问 -> 回执
```

这条循环必须服务 PRD 中的产品原则：

1. 模糊时先接住和命名，不急于生成方案。
2. 不确定时先追问和显性化冲突。
3. 足够清楚时才沉淀约束或待决策。
4. 结构稳定到可承载时才显影到画布。
5. 交接物必须带出已知、未知、已决和未决。

## 4. 这一组当前收稳的骨架

当前主骨架先收成三条：

1. 推进单位不是“聊了一轮”这么粗，而是 `阶段节点 + 阶段内检查点`。
2. 高影响动作不走第二主流程，而采用 `事件触发门禁 + 结构化交接前固定门禁位`。
3. 推进结果必须回写到状态账本，再影响 Active Todos、里程碑提示和交接物状态。

这三条让编排与生命周期既能服务右侧 AI 助手的持续推进，也能服务画布上的卡片迁移、轻确认和交接回流。
