# Technical Baseline（技术落地总览）

## 1. 文档定位

这组文档不是新的产品真相源，也不是要替代 `docs/harness/`。

它的职责只有一个：

- 把已经收敛到 `L3` 的 harness 规则，翻译成当前仓库里可以直接指导代码修改的技术口径。

因此，这里的优先级关系固定为：

1. `docs/vision/EvoCanvas1.0-PRD.md`：定义产品边界与 1.0 最小闭环
2. `docs/harness/`：定义 `L / G / V` 的运行规则、治理边界与验证原则
3. `docs/technical-specs/`：定义这些规则在当前代码中的承接方式、改造切口与接口约束

如果三者冲突，默认按上面的顺序回看，而不是让技术文档反过来改写产品事实。

## 2. 为什么现在要补这层

当前仓库已经满足“可以开始第一批实现”的门槛：

- `docs/harness/README.md` 已明确 `G 层、L 层、V 层已达到可直接指导第一批实现的 L3`
- 现有代码里也已经有可承接主闭环的 EvoCanvas 主路径：
  - 后端：`app/canvas/`
  - 前端：`frontend/src/pages/Workspace/`
  - API：`app/api/server.py`

但 harness 仍然更偏“运行原则与治理规格”，还没有完全沉淀成当前仓库可直接复用的：

- 运行时状态字段
- 前后端接口契约
- 验证回执结构
- 交接物对象的最小字段集

所以现在最合适的做法不是等一整套“大而全技术设计”，而是先补一层轻量技术规格，支撑第一批代码实践。

## 3. 当前实现判断

当前代码并不是一张白纸，而是已经存在一条可复用的 EvoCanvas 主线：

- `app/canvas/service.py`
  - 已负责工作区读取、回合开始、提案构建、确认流、交接刷新、快照生成
- `app/canvas/governance.py`
  - 已负责把提案分成自动应用或待确认
- `app/canvas/domain/`
  - 已提供工作区、卡片、变更提案、交接物等基础领域对象
- `frontend/src/pages/Workspace/`
  - 已承接主画布、卡片移动、关系连线、交接刷新、确认弹层等工作台交互

也就是说，当前最应该做的不是重写底座，而是把旧实现里“已经能承接 EvoCanvas 1.0”的部分收紧为正式口径。

## 4. 本目录的边界

本目录只处理以下问题：

- `L层（生命周期与编排）` 如何映射到当前回合状态、阶段推进和交接刷新
- `G层（治理）` 如何映射到提案风险分级、确认队列和正式生效边界
- `V层（验证）` 如何映射到验证挂载点、验证回执和默认分流
- 前端工作台如何作为投影层消费这些运行时结果，而不是自己发明事实

本目录不处理以下问题：

- 不重新定义 PRD
- 不重新设计完整 UI
- 不把 `C / T / O / E` 四层提前写成稳定规格
- 不把未来 2.0 / 3.0 的能力偷渡进 1.0

修改代码时，默认按下面的判断执行：

- 如果只是补 `app/canvas/` 里的状态字段、验证回执、确认流、交接物结构，可以直接改代码
- 如果改动会新增稳定 schema、持久化结构或跨端接口，先回看本目录对应文档再落代码
- 如果需求已经触到 `C / T / O / E` 的稳定规格，先补 harness，不要假装本目录已经给出最终答案

## 6. 首批实现原则

首批实现统一遵守以下原则：

- 复用 `app/canvas/` 现有底座，不做“看起来全新”的重写
- 前端继续保留 `discovery / define / handoff` 的轻量展示带，但不要把它误当成完整运行时状态机
- 高影响动作继续走确认流，不允许因为前端交互顺手就直接生效
- 交接物继续视为“从现有对象收束出的聚合层”，不是自由总结文本
- 任何新增字段、注释、Docstring，都必须使用 EvoCanvas 1.0 语义，不再回退到旧 `EvoLoop / PRD 生成器 / 任务大厅` 口径
