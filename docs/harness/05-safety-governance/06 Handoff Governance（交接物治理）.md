# Handoff Governance（交接物治理）

> 当前成熟度层级：`L3 可指导实现的治理规格层`

## 1. 这一层回答什么问题

交接物治理回答：当前画布什么时候可以收束为结构化交接物，交接物里哪些内容可以被下游依赖，哪些必须以未决或待确认形式保留。

EvoCanvas 1.0 的结构化交接物可以给同事阅读，也可以进一步派生为面向 AI 的 PRD，但它不等于传统完整 PRD，也不等于完整项目规格。

## 2. 可评审完整度

> **层次说明：** 本节定义交接物达到**可正式评审、可确认外发**的完整度要求（8 模块）。交接草稿的**显影门槛**（5 项核心能组织好即可显影）见 [Object Governance §7](./05%20Object%20Governance%EF%BC%88%E5%AF%B9%E8%B1%A1%E6%B2%BB%E7%90%86%EF%BC%89.md)。

每份结构化交接物至少包含以下 8 个模块，且只有这些模块均已能被有意义地填充时，才达到可正式评审、可确认外发条件：

1. 当前目标。
2. 输入背景。
3. 已确认约束。
4. 已完成决策。
5. 未解决问题。
6. 待确认决策。
7. 推荐后续动作。
8. 关键来源引用。（里程碑投影 1.0 不实现，`milestone_ref` 预留为空，见 State Ledger §8。）

未解决问题和待确认决策可以作为明确模块保留，不要求全部解决；只有空壳或无法解释边界时不得提前显影。

## 3. 进入交接前的检查

生成或刷新交接草稿前，系统至少检查：

- 关键待澄清项是否已收敛，或已显式保留为未解决问题。
- 关键约束是否已经确认；尚未确认的约束提议只能作为未决说明保留，不能进入已确认约束列表。
- 必要决策是否已完成，或明确列为待确认决策。
- 冲突是否已显性展示。
- 交接物引用的对象是否仍然有效。
- 交接物是否说明当前仍不能确定什么。

交接物的可读性不能凌驾于真实性之上。

## 4. 状态治理

交接物承接卡所引用的包版本有效治理状态是：

```md
草稿中 -> 待确认 -> 已确认 -> 已过时
```

治理规则：

- 草稿中：可以由 AI 生成，但只能作为工作草稿。
- 待确认：已经具备基本结构，需要用户确认。
- 已确认：可以作为后续沟通或下游 AI 输入的依据。
- 已过时：底层约束、决策或关键来源变化后，不再安全可用。

交接物承接卡只显示这套状态，不独立写入状态。生成或刷新草稿不要求额外操作确认；只有包版本从草稿或待确认进入已确认，并获得正式交接可用性时，才检查 Chat 确认依据。

## 5. 过时判断

以下情况应触发过时判断：

- 已确认约束被替代。
- 已完成决策被撤回或重开。
- 新输入暴露关键冲突。
- 原本未解决的问题变成阻塞性交接风险。
- 当前主题目标发生变化。

过时不等于删除。系统应保留旧交接物，标记其不再适合作为当前依据，并引导用户刷新或重新确认。

**执行主体与流程：**

过时标记为系统自动执行的降级动作，不走高影响信息地位升级的门禁，不需要用户确认。但系统必须：
1. 在 Chat 中发出低打扰提示："当前交接版本已过时，底层约束 / 决策已变化，建议刷新。"
2. 在账本追加 `package_version_marked_outdated` 事件，保留触发原因和来源引用。

**过时后的两条路径：**

| 用户动作 | 结果 |
| --- | --- |
| 刷新交接物（基于最新对象创建新版本） | 新版本从草稿开始，重新走确认流程 |
| 在 Chat 中明确声明"继续使用此版本" | 追加 `package_version_risk_annotated`，保持 `confirmed` 但加风险标注（见 Stable State §8.2） |

系统不得自动撤回过时标记；过时版本在用户主动操作前不恢复为可用。

## 6. 禁令

交接物治理明确禁止：

- 把聊天总结包装成结构化交接物。
- 把未确认约束混入已确认约束列表。
- 把待确认决策写成已完成决策。
- 为了让文档显得完整而隐藏关键未决。
- 在用户未确认前把交接物标记为可外发或可交给下游 AI 执行。
