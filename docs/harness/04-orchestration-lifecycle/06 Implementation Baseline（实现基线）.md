# Implementation Baseline（实现基线）

> 当前成熟度层级：`L2 对象与流程定义层`
> 编码门槛：`未达到 L3，不应直接作为稳定实现规格；本文件只汇总当前可继续收紧的实现基线`

## 1. 设计禁令

编排与生命周期当前至少保留以下禁令：

- 不允许在存在明显缺口时直接输出稳定结论。
- 不允许把结构化交接物当作任何阶段都能随手生成的总结。
- 不允许把大量未确认内容堆叠后包装成可外发交接物。
- 不允许让高影响动作一路自动推进到底。
- 不允许用“对话顺畅”替代“状态正确”。
- 不允许把 Active Todos、里程碑提示或个人挂件当作独立事实源。

## 2. 1.0 最小落地要求

EvoCanvas 1.0 的编排与生命周期至少要做到：

1. 明确五段产品旅程：感觉接入、对话塑形、结构收敛、画布显影、结构化交接。
2. 每轮都有明确阶段目标。
3. 每轮能区分自动应用、挂起确认、只追问和拒绝。
4. 高影响动作必须进入确认请求。
5. 状态账本记录确认和仍存未决。
6. 交接物来源于已有结构化对象，而不是自由总结。
7. 交接物必须显式保留未决问题和待确认决策。
8. 复杂回合可以打开问题、收束结构、裁决去向，但不能替代主阶段骨架。

## 3. 最小实现字段提醒

如果后续把这一组落到后端模型，当前至少应预留：

- 当前阶段字段。
- 当前检查点字段。
- 本轮结果类型：自动应用 / 挂起确认 / 只追问 / 失败。
- 触发的高影响动作类型。
- 待确认动作标识。
- 回流原因或停留原因。

这些字段不要求一步到位做成复杂状态机，但足以支撑 1.0 的阶段推进、轻确认和交接回流。

## 4. 当前可继续收紧的问题

后续进入 L3 前，需要继续补齐：

- 阶段字段和状态枚举。
- 各阶段检查点的最小通过条件。
- 确认请求的数据结构。
- 回流事件和状态账本的记录字段。
- 复杂回合的触发阈值。
- 交接物进入待确认和已确认的验证规则。

## 5. 跨层提醒

如果后续其他层与本组发生冲突，优先检查：

- 是不是把编排的“下一步怎么走”误写成验证的“是否过关”。
- 是不是把门禁的“是否需要确认”误写成治理的“是否已经生效”。
- 是不是把生命周期的“状态演化”误写成界面的“卡片展示”。
- 是不是把结构化交接物误写成完整 PRD 生成。
