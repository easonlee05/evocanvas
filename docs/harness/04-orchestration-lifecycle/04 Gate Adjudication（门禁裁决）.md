# Gate Adjudication（门禁裁决）

> 当前成熟度层级：`L2 对象与流程定义层`
> 编码门槛：`未达到 L3，不应直接作为稳定实现规格；需继续补齐确认请求字段、风险等级和放行规则`

## 1. 这一层回答什么问题

门禁裁决回答：

- 哪些动作不能自动写入。
- 什么情况下必须停下来要求用户确认。
- 确认请求至少要包含什么。
- 用户确认后，系统先更新什么。

门禁不是审批流产品，也不是到处设卡。它只处理会改变事实边界或下游依赖的高影响动作。

## 2. 门禁挂载方式

当前门禁采用：

`事件触发为主 + 结构化交接前固定门禁位`

也就是说：

- 日常推进默认仍由阶段检查点承接。
- 只有少数高影响动作才从普通推进切出到门禁。
- 结构化交接物进入待确认前，额外保留一个固定门禁位。

这样既能把高影响动作钉牢，又不把 1.0 做成复杂审批流。

## 3. 高影响动作

EvoCanvas 1.0 中，高影响动作至少包括：

- 新建待决策 / 方案承接内容。
- 将约束卡改为已生效。
- 关闭关键待澄清问题。
- 生成或刷新交接物承接结果。
- 推进或更新当前里程碑进度。
- 把未确认内容作为下游前提使用。

- 把待澄清、约束或待决策卡通过跨栏目迁移直接改变语义状态。

这些动作必须进入确认请求，而不是由 AI 静默写入。

## 4. 最强触发条件

只要对象从以下状态：

- 草稿中
- 待确认
- 可挑战
- 候选态

进入以下状态：

- 已确认
- 已生效
- 已决定
- 可作为下游前提

就应视为事实边界变化，必须触发门禁。

## 5. 关闭关键未决

关闭关键待澄清项不一定每次都触发门禁。

只有当关闭会产生以下影响时，才必须确认：

- 改变事实边界。
- 改变交接物主表达。
- 影响下游实现、评审或任务拆解。
- 让 Active Todos 中的核心缺口消失。

普通非阻塞提醒的关闭，可以在状态账本中记录，不必升级为门禁。

## 6. 确认请求最小内容

确认请求至少包含：

1. 建议动作类型。
2. 拟生效内容。
3. 建议结果摘要。
4. 将影响哪些卡片或对象。
5. 依据摘要。
6. 仍存未决。
7. 确认 / 取消入口。

确认请求的目标是让用户知道：

- 要拍板什么。
- 当前凭什么推进。
- 还有哪些东西其实没有一起解决。

如果这次门禁来自跨栏目迁移，确认文案还必须明确说明语义变化，而不是只弹出泛化“是否确认”。

## 7. 用户确认后的默认顺序

用户确认后，系统默认先更新状态账本。

然后再决定：

- 是否恢复阶段推进。
- 是否更新源卡状态。
- 是否同步 Active Todos。
- 是否刷新交接物。
- 是否更新里程碑提示。

确认不会自动洗平其他未决问题。

## 8. 门禁不负责什么

门禁不负责：

- 生成新事实。
- 替代验证器检查结构和来源。
- 替代用户作出产品判断。
- 替代状态账本记录确认结果。

门禁只决定当前高影响动作是否可以继续。
