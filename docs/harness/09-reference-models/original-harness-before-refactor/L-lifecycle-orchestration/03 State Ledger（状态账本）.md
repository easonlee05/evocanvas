# 状态账本（State Ledger）

> 当前成熟度层级：`L3 可指导实现的治理规格层`
> 编码门槛：`已达到 L3，可直接指导第一批阶段状态与回看实现`

本文件展开 L 层中的状态账本基线，集中保存最小记录范围、确认记录、关键未决与非阻塞提醒的记录口径。

## 这一层回答什么问题

状态账本回答：

- L 层最少要记住哪些推进状态
- 为什么这次能过、没过、停留或触发门禁
- 局部确认之后，哪些未决仍然保留
- 哪些残留问题继续阻塞升级，哪些只作为提醒

状态账本不是重审计系统，但必须提供最小可解释性。

## 最小记录范围

状态账本在 L 层的最小记录范围是：

- 阶段状态
- 判定结果
- 关键判定原因

这意味着它不只是记“现在在哪个阶段”，还要轻量记住：

- 这次检查点是否通过
- 为什么没通过
- 为什么停留
- 为什么触发门禁

## 关键判定原因的默认粒度

关键判定原因默认记录到：

- 原因类别
- 对应对象
- 简短说明

这样可以解释推进判断与门禁判断，但不会膨胀成完整过程复盘。

关键判定原因当前首要服务对象是：

- 阶段推进器

但它也可以被门禁裁决器和用户复用。主归属仍放在推进治理主干上，而不是单纯的解释面板。

## 确认记录的最小内容

状态账本在记录一次确认时，最少必须保留：

- 新状态
- 确认来源
- 确认时仍存未决

这样确认不会把世界“洗平”。

系统既知道：

- 什么已经被确认或获准继续引用
- 是谁或什么确认了它
- 当时还有哪些问题没有被一并解决

## 仍存未决的默认处理

状态账本记下“仍存未决”之后，这些未决默认采用：

`分级落位`

也就是说，局部确认只改变被确认对象的状态，不自动把其他未决一律洗平成尾项，也不自动全部重新抬升。

当前基线是：

- 如果仍存未决继续影响当前阶段升级，应回到对应阶段语义位继续承接，默认优先回到 `待澄清显影（clarification）`
- 如果仍存未决已知但暂不阻断当前重判，则继续保留在当前阶段语境中，作为显式尾项

### 继续作为阻塞条件的关键未决

若某个仍存未决属于以下任一类，则继续作为升级阻塞条件：

- 影响事实成立的未决
- 影响下游推进的未决
- 影响范围边界的未决

这三类共同构成当前 L 层中的 `关键未决`。

回流修复之后，如果这些关键未决仍然成立，状态账本应继续把它们记为升级阻塞条件，而不是因为“已经修过一次”自动降格。

### 非关键未决的默认降级

不属于上述三类关键未决的内容，默认降为：

`非阻塞提醒`

它们仍应保留、仍应可见，但默认不再阻塞阶段升级。

## 非阻塞提醒的双挂靠

非阻塞提醒采用：

`双挂靠`

也就是：

- 平时主要挂在对应对象上
- 状态账本保留摘要

这样既能保证提醒不脱离语义上下文，也不会在阶段推进时完全看不见。

## 非阻塞提醒摘要的首要作用

状态账本中的非阻塞提醒摘要，首要作用是：

`提示当前阶段仍有尾项`

它首先服务阶段治理，提醒系统和用户：

- 这轮可以继续推进
- 但还有残留问题没有消失

它不是一个新的后处理系统，也不应抢交接编排器的职责。

## 待复核对象的继续推进

当已确认决策（confirmed decision）或约束（constraint）进入待复核状态后，L 层负责决定它在推进链中如何被继续使用。

默认规则是：

- 如果复核触及核心边界、核心依据或下游主要动作，阶段推进器不得继续把它当作完全稳定前提使用
- 如果复核只触及外围说明、适用范围微调或局部影响，可以带复核保留继续推进
- 如果用户明确要求“先按原结论继续推进”，系统可以继续推进，但必须显式标记为“带复核保留的继续使用”
- 带复核保留的继续使用不能重新伪装成完全稳定的已确认决策（confirmed decision）

状态账本在这里的职责不是重新裁决事实是否有效，而是记录：

- 当前对象进入待复核的原因
- 它在推进链中是否仍可被条件引用
- 条件引用时保留了哪些风险或未决
